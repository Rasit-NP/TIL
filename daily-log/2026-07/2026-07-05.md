## HTTP 헤더 필드 문법
- 헤더 필드란 HTTP 메시지에서 request line 다음에 오는 메타데이터 줄을 가리킴
    - 요청 대상의 부가 정보를 키-값 쌍으로 전달하는 줄
    - 호스트, 콘텐츠 형식, 인증 정보 등이 여기에 담김
- RFC 7230 §3.2가 정의하는 헤더 필드 문법은 아래와 같음
```
header-field = field-name ":" OWS field-value OWS
```
- field-name이란 헤더의 이름을 가리키는 토큰
    - 콜론 왼쪽에 오는 식별자임
    - `Host`, `Content-Length`, `User-Agent`가 이에 해당함
- field-value란 그 헤더가 전달하는 값을 가리킴
    - 콜론 오른쪽에서 OWS를 제거한 실제 내용

### OWS의 정의
- OWS란 optional whitespace의 약자로, 있어도 되고 없어도 되는 공백을 가리킴
- 구성 문자는 SP와 HTAB 두 가지뿐임
    - SP란 space의 약자로, 공백 문자 0x20을 가리킴
    - HTAB란 horizontal tab의 약자로, 수평 탭 문자 0x09를 가리킴
- field-value 앞뒤에 올 수 있으며 의미에 영향을 주지 않음
    - 따라서 파싱 시 제거 대상

### field-name과 콜론 사이 공백 금지
- field-name과 콜론 사이에는 공백이 허용되지 않음 (RFC 7230 §3.2.4)
- `Host : localhost`처럼 이름과 콜론 사이에 공백을 넣는 형태는 문법 위반
    - 정상 입력만 처리하는 범위에서는 이 형태가 들어오지 않는다고 가정함
    - 명백한 malformed 입력에 대한 엄격 검증은 이후 검증 단계의 몫으로 미룸

### field-name 소문자 정규화
- field-name은 대소문자를 구별하지 않음(case-insensitive)
    - `Content-Length`와 `content-length`와 `CONTENT-LENGTH`는 모두 같은 헤더를 가리킴
- 정규화란 서로 다른 표현을 하나의 표준 형태로 통일하는 처리를 가리킴
- 저장 시점에 field-name을 ASCII 소문자로 정규화함
    - 조회할 때마다 대소문자를 맞추는 부담을 없애기 위함
    - 소문자를 표준 형태로 삼아 통일함

### 정규화 누락 시 조회 실패
- 정규화를 누락하면 `Content-Length`와 `content-length`가 서로 다른 키로 저장됨
- 이후 소문자 키로 값을 조회할 때 원본 대소문자와 어긋나 조회가 실패함
- 저장 시점에 소문자로 통일하면 조회 측이 항상 소문자 키만 쓰면 되므로 안정적임

## std::tolower 부호 확장 함정
- ASCII 소문자 변환에 `std::tolower`를 사용할 때 인자 타입에서 미정의 동작이 발생할 수 있음
    - 미정의 동작(UB)이란 undefined behavior의 약자로, 표준이 결과를 규정하지 않아 무엇이든 일어날 수 있는 상태를 가리킴
- `std::tolower(int)`는 인자가 `unsigned char`로 표현 가능한 값이나 `EOF`일 것을 요구함
    - EOF란 end of file의 약자로, 입력 끝을 나타내는 음수 상수를 가리킴

### char 부호 확장의 원인
- `char`가 부호 있는 타입인 플랫폼에서 0x80 이상의 바이트는 음수로 해석됨
    - 비 ASCII 바이트나 UTF-8 바이트가 헤더에 섞이면 `char` 값이 음수가 됨
- 음수를 `std::tolower`에 그대로 넘기면 `unsigned char` 범위도 `EOF`도 아니므로 UB에 진입함
- `static_cast<unsigned char>`로 먼저 승격한 뒤 넘겨 음수 진입을 차단함

```cpp
// char을 그대로 넘기면 음수 값에서 → unsigned char로 캐스팅 필수
std::string to_lower(std::string s){
    for (char& c : s){
        c = static_cast<char>(
            std::tolower(static_cast<unsigned char>(c))
        );
    }
    return s;
}
```
> std::tolower에 char를 직접 넘기지 않음
>
> 반드시 static_cast<unsigned char>로 감싸 음수 진입을 차단

## OWS 트리밍
- 트리밍이란 문자 앞뒤에서 특정 문자를 제거하는 처리를 가리킴
- `field-value` 앞뒤의 OWS를 제거해야 순수한 값만 저장됨
- 트리밍을 누락하면 `Host: localhost`에서 콜론 뒤 공백이 값에 포함되어 앞 공백이 붙은 값으로 저장됨
    - 이후 값 비교나 조회가 앞 공백 때문에 어긋남
```cpp
// field-value 앞뒤의 SP/HTAB를 제거해 순수 값만 남김
std::string trim_ows(const std::string& s){
    const char* ws = " \t";
    size_t begin = s.find_first_not_of(ws);
    if (begin == std::string::npos) return "";  // 전부 공백이면 빈 값
    size_t end = s.find_last_not_of(ws);
    return s.substr(begin, end - begin + 1);
}
```
- 트리밍 대상은 SP와 HTAB 두 문자뿐임
    - CR과 LF는 줄 구분자이므로 이 단계 이전에 이미 분리되어 있음

## HttpRequest 헤더 컨테이너
- 파싱된 헤더를 담은 컨테이너를 `HttpRequest`에 추가함
- 컨테이너로 `std::unordered_map<std::string, std::string>`을 선택
    - 키를 정규화한 소문자 field-name으로 저장함
    - 값을 트리밍된 field-value로 저장

```cpp
// include/http/HttpRequest.h
# include <string>
# include <unordered_map>

class HttpRequest{
public:
    std::string method;
    std::string path;
    std::string version;

    // 소문자 정규화된 field-name → 트리밍된 field-value
    std::unordered_map<std::string, std::string> headers;

    // isValid()는 request line 3 필드만 검증하며 헤더는 건드리지 않는다
    bool isValid() const{
        return !method.empty() && !path.empty() && !version.empty();
    }
};
```

### isValid의 검증 범위
- `isValid()`는 request line의 세 필드만 검증하는 상태를 유지함
- `Host` 필수 여부 같은 조건을 여기에 넣고 싶어질 수 있음
    - 그러나 그것은 파싱 성공 판정이 아니라 요청의 의미적 유효성 판정
    - 의미 검증이란 문법상 파싱은 됐으나 규약상 요구되는 값이 갖춰졌는지 판정하는 처리를 가리킴
- 파싱 성공과 의미 검증을 섞으면 두 관심사가 뒤엉키므로 분리함
    - HTTP/1.1의 `Host` 필수 검증은 응답 생성 단계로 미룸

## 헤더 상태 전이
- 파서는 진행 위치를 상태(State)로 표현하는 상태 머신 구조를 사용함
    - 상태란 파서가 지금 메시지의 어느 부분을 읽고 있는지를 나타내는 값
- request line 파싱이 끝난 지점에서 완료 상태로 가는 대신 헤더 상태로 전이시킴

### request line 종료 지점 변경
- request line 파싱이 성공하면 완료로 끝내지 않고 헤더 상태(`State::Headers`)로 전이시킴
    - request line만으로는 아직 메시지가 끝나지 않았으므로 성공을 반환하지 않음
    - 헤더 파싱이 남아있으므로 이어서 `parseHeaders` 호출로 흐름이 넘어감

```cpp
// src/http/HttpRequestParser.cpp
// request line 성공 시: 완료가 아니라 Headers 상태로 전이
Result HttpRequestParser::parseRequestLine(const char* data,
                                           size_t size,
                                           size_t& offset){
    // ... method/path/version 파싱 후 ...

    state_ = State::Headers;                    // 완료 상태 대신 헤더 상태로
    return parseHeaders(data, size, offset);    // 남은 바이트를 헤더 파서로
}
```

### parse의 상태 분기
- 최상위 `parse()`는 현재 상태에 따라 해당 상태 함수로 분기함
- 여기에 헤더 상태 분기를 추가함
    - 남은 바이트의 시작 위치를 오프셋으로 넘김
    - 단일 완결 버퍼 가정이므로 request line CRLF 다음 오프셋부터가 헤더 시작임
    - 오프셋을 참조로 전달해 각 파싱 함수가 소비 위치를 이어받게 함

```cpp
// src/http/HttpRequestParser.cpp
Result HttpRequestParser::parse(const char* data, size_t size){
    size_t offset = 0;
    switch (state_){
        case State::RequestLine:
            return parseRequestLine(data, size, offset);
        case State::Headers:
            return parseHeaders(data, size, offset);
        case State::Done:
            return Result::Ok;
    }
    return Result::Error;
}
```
```cpp
// include/http/HttpRequestParser.h
class HttpRequestParser{
public:
    Result parse(const char* data, size_t size);

private:
    Result parseRequestLine(const char* data, size_t size, size_t& offset);
    Result parseHeaders(const char* data, size_t size, size_t& offset);

    enum class State { RequestLine, Headers, Done };
    State state_ = State::RequestLine;
    HttpRequest request_;
};
```

## 헤더 섹션 종료 조건
- 헤더 섹션이란 request line 이후부터 빈 줄 직전까지의 모든 헤더 줄의 묶음을 가리킴
- 종료 신호는 빈 줄, 곧 아무 문자 없이 CRLF만 있는 줄
- 실제 바이트열에서는 마지막 헤더의 CRLF에 이어 빈 줄의 CRLF가 붙어 연속 CRLF가 됨
    - 앞의 CRLF는 마지막 헤더 줄의 끝
    - 뒤의 CRLF가 빈 줄, 곧 헤더 섹션 종료 신호

```
GET /path HTTP/1.1\r\n      ← request line 끝
Host: localhost:8080\r\n    ← 헤더 1
User-Agent: curl/8.0\r\n    ← 헤더 2
\r\n                        ← 빈 줄, 헤더 섹션 종료
```
- CRLF로 줄을 잘랐을 때 그 줄이 빈 문자열이면 종료 신호로 판정함
    - 종료 신호를 만나면 완료 상태로 전이하고 성공을 반환함

## parseHeaders 구현
- `key: value` 형태의 각 줄을 CRLF 단위로 반복 파싱함
- 각 줄에서 첫 번째 콜론을 기준으로 field-name과 field-value를 나눔
- field-name은 소문자 정규화, field-value는 OWS 트리밍 후 컨테이너에 저장함
- 빈 줄을 만나면 완료 상태로 전이함
```cpp
// src/http/HttpRequestParser.cpp
Result HttpRequestParser::parseHeaders(const char* data,
                                       size_t size,
                                       size_t& offset){
    while (offset < size){
        // 1. CRLF로 한 줄 경계 찾기
        size_t line_end = find_crlf(data, size, offset);    // \r\n 위치
        if (line_end == npos) return Result::Incomplete;    // 줄이 안 끝남

        std::string line(data + offset, line_end - offset);
        offset = line_end + 2;      // \r\n 두 바이트 건너뜀

        // 2. 빈 줄이면 헤더 섹션 종료
        if (line.empty()){
            state_ = State::Done;
            return Result::Ok;
        }

        // 3. 첫 번째 콜론만 구분자로 사용
        size_t colon = line.find(':');
        if (colon == std::string::npos){
            // 콜론 없는 줄은 malformed → 엄격 검증은 이후 단계
            // 정상 입력만 처리하는 범위이므로 무시하고 넘어감
            continue;
        }

        std::string name  = line.substr(0, colon);
        std::string value = line.substr(colon + 1);     // 콜론 뒤 전체

        // 4. 정규화와 트리밍 후 저장
        request_.headers[to_lower(name)] = trim_ows(value);
    }

    return Result::Incomplete;      // 종료 빈 줄을 못 만나고 버퍼가 끝남
}
```
### 첫 콜론만 구분자로 사용
- field-value 안에 콜론이 다시 등장할 수 있음
    - `Host: localhost:8080`은 값 부분에 포트 구분용 콜론을 포함함
- `find(':')`로 첫 번째 콜론 위치만 찾아 그 지점에서 한 번 나눔
    - 첫 콜론 왼쪽 전체가 field-name임
    - 첫 콜론 오른쪽 전체가 field-value임
    - 값을 다시 콜론으로 자르면 포트 번호가 잘려 나가므로 재분할하지 않음

> 첫 번째 콜론만 name/value 구분자로 사용
>
> 값 안의 콜론(localhost:8080)은 그대로 값에 남김

### field-name 내 공백 처리
- `Foo Bar: v`처럼 field-name 안에 공백이 있는 줄은 RFC상 잘못된 헤더임
- 다만 엄격 검증으로 400 응답을 유발하는 처리는 이후 단계의 몫
    - 정상 입력만 처리하는 범위이므로 이 형태를 별도로 거르지 않음
    - 명백한 malformed 검증은 이후 단계로 미룬다고 주석에 남김

## unordered_map 저장 한계
- `std::unordered_map`은 두 가지 성질 때문에 일부 헤더를 정확히 표현하지 못함

### 순서 비보존
- `unordered_map`은 삽입 순서를 보존하지 않는 해시 기반 연관 컨테이너
- 헤더의 원래 등장 순서가 필요할 때 이 컨테이너로는 복원할 수 없음
    - 다만 조회 목적에서는 순서가 대개 무의미하므로 이 범위에서는 문제되지 않음

### 중복 키 덮어쓰기
- 같은 field-name이 여러 번 전송될 수 있음
    - `Set-Cookie`는 쿠키마다 별도 줄로 여러 번 보내는 대표적 헤더임
- 대입 연산 `map[key] = value`는 기존 키를 덮어쓰므로 마지막 값만 남고 앞의 값들이 손실됨
- 덮어쓰기 허용으로 단순화하되 한계를 주석으로 명시함
    - 다중 값 헤더의 정식 처리는 이후 단계로 미룸

```cpp
// 주의: unordered_map은 같은 키를 덮어씀
// Set-Cookie 같은 다중 값 헤더는 마지막 값만 남음
// 다중 값 정식 처리는 이후 재검토 대상
request_.headers[to_lower(name)] = trim_ows(value);
```

## obs-fold 폐기
- obs-fold란 obsolete line folding의 약자로, 긴 헤더 값을 여러 줄로 접어 쓰던 구식 문법을 가리킴
    - 헤더 값 다음 줄을 공백이나 탭으로 시작해 이어붙이던 방식
- RFC 7230 §3.2.4는 이 문법을 폐기함
    - 여러 줄 접기가 파싱 복잡도를 키우고 요청 스머글링 같은 보안 문제를 유발했기 때문
    - 요청 스머글링이란 파서마다 경계를 다르게 해석하는 틈을 노려 요청을 몰래 끼워 넣는 공격을 가리킴
- 이 범위에서는 obs-fold를 파싱하지 않고 존재만 인지함
    - 정상 입력은 한 헤더가 한 줄에 담긴다고 가정함

## 검증
- 단일 완결 버퍼 입력 하나로 request line 3필드와 헤더 2개가 정확히 추출되는지 확인함
```cpp
// 단일 버퍼 한 방 입력 → request line + 헤더 2개 추출 검증
const char* raw = 
    "GET /path HTTP/1.1\r\n"
    "Host: localhost:8080\r\n"
    "User-Agent: curl/8.0\r\n"
    "\r\n";

HttpRequestParser parser;
Result r = parser.parse(raw, std::strlen(raw));

assert(r == Result::Ok);
assert(req.method  == "GET");
assert(req.path    == "/path");
assert(req.version == "HTTP/1.1");

// 소문자 키로 조회가 성공해야 함
assert(req.headers.at("host")       == "localhost:8080");
assert(req.headers.at("user-agent") == "curl/8.0");
```
- `host` 조회 성공은 소문자 정규화가 동작함을 확인함
- `localhost:8080` 보존은 첫 콜론만 구분자로 썼음을 확인함
- `curl/8.0`에 앞 공백이 없음은 OWS 트리밍이 동작함을 확인함

    │
    ├── 상태 전이
    │     ├── request line 끝 → State::Headers
    │     └── 빈 줄(연속 CRLF) → State::Done

    └── 저장 한계
