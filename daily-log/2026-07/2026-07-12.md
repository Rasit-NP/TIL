## 400 Bad Request의 정의
- 400 Bad Request란 서버가 클라이언트의 요청을 문법상 이해할 수 없을 때 반환하는 HTTP 상태 코드
    - 4로 시작하는 상태 코드는 클라이언트 측 오류를 나타냄
    - 그중 400은 문법 자체가 규약을 위반해 서버가 요청을 해석조차 할 수 없는 경우를 가리킴
- 정의 근거는 RFC 7230 §3.5와 §3.1.1임
    - §3.1.1은 request-line의 문법을 규정하고, 이를 위반한 요청은 서버가 거부해야 함을 명시함
    - §3.5는 메시지 파싱 시 견고성(robustness)과 보안 사이에서 서버가 취해야 할 태도를 규정함

### 문법 오류와 의미 오류의 경계
- 문법 오류란 바이트 배열 자체가 정해진 grammar를 따르지 않는 경우를 가리킴
    - 토큰 개수가 맞지 않거나, 버전 문자열 형식이 어긋나거나, 헤더에 콜론이 없는 경우임
    - 이 단계에서 다루는 대상
- 의미 오류란 문법상 파싱은 되지만 규약이 요구하는 값이 갖춰지지 않은 경우를 가리킴
    - HTTP/1.1에서 `Host` 헤더가 없는 요청이 대표적임
    - 이 단계에서는 다루지 않으며 응답 생성 단계로 미룸
- 파서의 책임은 문법 판정까지이며, 의미 판정은 상위 계층의 몫

## 에러 상태 단일화
- 에러 상태(`State::Error`)란 파서가 문법 위반을 확정한 뒤 머무는 종착 상태를 가리킴
- 이 단계에서는 오류 원인을 세분하지 않고 단일한 `Error` 상태로만 표현함
    - 400 Bad Request, 431 Request Header Fields Too Large, 505 HTTP Version Not Supported는 모두 서로 다른 상태 코드임
    - 그러나 파서 내부에서 이들을 구분하는 상태를 나누는 것은 이 단계에서 과설계임
- 상태 코드 매핑은 이후 단계로 미루고, 파서는 오류 발생 사실만 `Error` 하나로 표현함

### 오류 세분화를 미루는 이유
- 파서의 관심사는 입력이 문법에 맞는지의 이진 판정
- 어떤 상태 코드로 응답할지는 파싱이 끝난 뒤 결정해도 되는 별개의 관심사
- 두 관심사를 파서 안에서 섞으면 파서가 응답 정책까지 떠안게 되어 책임이 비대해짐

## absorbing state
### absorbing state의 정의
- absorbing state란 한 번 진입하면 어떤 입력에도 다른 상태로 빠져나가지 못하는 상태를 가리킴
    - 흡수 상태라고도 부르며, 상태 머신 이론에서 최종적으로 고정되는 상태를 의미함
    - 명명 의도는 이후의 모든 입력을 그 상태가 흡수해 상태 전이가 일어나지 않게 한다는 데 있음
- 파서의 `Error` 상태는 absorbing state여야 함
    - 문법 위반이 한 번 확정되면, 그 뒤에 어떤 유효한 바이트가 들어와도 요청 전체가 오염되었기 때문
    - 오류 이후에 도착한 바이트로 파싱을 재개하면 손상된 요청을 정상 요청처럼 취급하는 위험이 생김

### error latch의 정의
- latch란 한 번 설정되면 명시적으로 해제하기 전까지 값을 유지하는 저장 요소를 가리킴
    - 전자 회로의 래치 소자에서 온 용어로, 입력이 사라져도 상태를 붙잡아 두는 성질을 나타냄
- error latch란 오류 상태를 한 번 걸어두면 이후 호출에서 그 상태가 풀리지 않도록 붙잡는 장치를 가리킴
- 파서에서 error latch는 `state_`가 `State::Error`가 되면 이후 `parse()` 호출이 즉시 `Error`를 반환하도록 구현됨

## 진입 가드
### 진입 가드의 정의
- 진입 가드(guard clause)란 함수 본문 최상단에서 특정 조건을 먼저 검사해 조건에 맞으면 즉시 반환하는 코드 블록을 가리킴
    - 방어 절이라고도 부르며, 본격적인 로직 진입 전에 부적절한 경우를 걸러내는 목적을 가짐
- error latch를 구현하는 위치로 진입 가드를 사용함
    - `parse()`가 호출될 때마다 가장 먼저 `state_ == State::Error`인지 확인함
    - 이미 에러 상태이면 어떤 파싱도 시도하지 않고 즉시 `Result::Error`를 반환

### switch case 대신 진입 가드를 쓰는 이유
- 에러 상태 처리를 상태 분기 switch의 한 case로 넣을 수도 있음
- 그러나 상태 머신이 `while(true)` 루프로 상태 전이를 반복하는 구조에서는 case 방식이 재진입 위험을 만듦
    - 재진입이란 오류 상태에서 빠져나오지 못한 채 루프가 같은 상태를 반복 처리하려 시도하는 상황
    - case 안에서 상태를 바꾸지 않고 반환하면, 다음 루프 반복이 다시 같은 case로 들어와 무한 반복에 빠질 수 있음
- 진입 가드는 루프에 진입하기 전에 오류를 걸러내므로, 재진입 경로 자체가 생기지 않음
- 이 때문에 latch를 switch case가 아니라 진입 가드 한 곳으로 통일함

### 진입 가드와 상한 검증의 순서
- `parse()` 진입 시 두 종류의 선행 검증이 존재함
    - 하나는 error latch 검사
    - 다른 하나는 버퍼 크기가 상한을 넘었는지 검사하는 상한 초과 검증
- 이 둘의 순서는 error latch가 먼저, 상한 검증이 나중

```cpp
// src/http/HttpRequestParser.cpp
HttpRequestParser::Result
HttpRequestParser::parse(const char* data, size_t size){
    buffer_.append(data, size);         // 도착한 바이트 누적

    // 1. error latch: 이미 오류면 즉시 반환 (가장 먼저)
    if (state_ == State::Error){
        return Result::Error;
    }

    // 2. 상한 초과 검증: latch 뒤에 위치
    if (buffer_.size() > kMaxRequestSize){
        state_ = State::Error;
        return Result::Error;
    }

    // 3. 상태 분기
    while (true){
        // ... 상태별 파싱 ...
    }
}
```
- 순서를 이렇게 두는 이유는 이미 오류로 확정된 요청에는 추가 검증을 수행할 필요가 없기 때문임
    - error latch가 먼저 걸리면 그 뒤 검증 비용을 아낌
    - 상한 검증이 `state_`를 `Error`로 설정하는 경로와 latch 검사가 순서상 충돌하지 않게 됨
- `buffer_.append`는 두 검증보다 앞에 두어, 어떤 경로로 반환하든 도착한 바이트가 버퍼에 반영된 상태를 유지함

## request-line grammar 위반 검증
- request-line grammar란 요청 첫 줄이 따라야 하는 문법 규칙을 가리킴
    - 문법은 `method SP request-target SP HTTP-version CRLF` 형태임
- 이 문법을 위반하는 두 경우를 `Error`로 확정함
    - 토큰 개수가 세 개와 일치하지 않는 경우
    - 토큰 중 하나가 빈 문자열인 경우

### 토큰 개수 불일치
- 세 토큰은 두 개의 SP로 분리됨
- SP가 하나뿐이면 토큰이 둘밖에 나오지 않아 문법 위반
- SP가 세 개 이상이면 토큰이 넷 이상 생기거나 빈 토큰이 끼어들어 문법 위반
    - `GET  /index.html HTTP/1.1`처럼 공백이 연달아 오면 사이에 빈 토큰이 생김

### 빈 토큰 검증
- SP 위치는 맞더라도 SP 사이 문자열이 비어 있을 수 있음
    - method, path, version 중 하나라도 빈 문자열이면 문법상 유효하지 않음
- partial-accept란 일부 형식 위반을 걸러내지 못하고 정상으로 받아들이는 결함을 가리킴
    - 토큰 개수만 검사하고 빈 토큰을 검사하지 않으면 partial-accept가 발생함
    - 개수 검사와 빈 토큰 검사를 함께 수행해 이 결함을 제거함
```cpp
// request-line을 SP로 분리한 뒤 검증
// method/path/version 세 토큰이 모두 채워져야 통과
if (request_.method.empty() ||
    request_.path.empty() ||
    request_.version.empty()){
    state_ = State::Error;
    return Result::Error;
}
```

## HTTP-version 형식 검증
### HTTP-version grammar
- HTTP-version이란 요청이 따르는 프로토콜 버전을 나타내는 토큰을 가리킴
- RFC 7230이 정의하는 문법은 아래와 같음
```
HTTP-version = "HTTP/" DIGIT "." DIGIT
```
- 구성 요소의 정의는 아래와 같음
    - `"HTTP/"`는 다섯 글자 리터럴 접두사
    - DIGIT은 숫자 한 글자(`0`부터 `9`)를 가리킴
    - `"."`는 major 버전과 minor 버전을 가르는 점 하나
- 즉 정확히 `HTTP/` 뒤에 숫자 한 개, 점 하나, 숫자 한 개가 순서대로 와야 함

### 완전 일치 비교의 함정
- 버전 검증을 `version == "HTTP/1.1"` 형태의 완전 일치로 구현하는 방식은 잘못됨
    - `HTTP/1.0`은 유효한 요청임에도 이 비교에서 탈락함
    - `HTTP/1.1`만 통과시키면 정상적인 1.0 요청을 파괴함
- 검증 대상은 특정 버전 값이 아니라 grammar 형식임
    - 값의 범위 판정(지원하는 버전인지 여부)은 이 단계가 아니라 이후 단계의 몫
    - 형식만 문자 단위로 검사해 문법 적합성만 판정함

### 문자 단위 형식 검증
- 검증 절차는 문자열을 위치별로 하나씩 대조하는 방식임
    - 길이가 8인지 확인함
    - 앞 다섯 글자가 `HTTP/`인지 확인함
    - 여섯 번째 글자가 숫자인지 확인함
    - 일곱 번째 글자가 `.`인지 확인함
    - 여덟 번째 글자가 숫자인지 확인함

```cpp
// HTTP-version = "HTTP/" DIGIT "." DIGIT
// 형식만 검사하며 버전 값 범위는 판정하지 않음
static bool is_valid_version(const std::string& v){
    if (v.size() != 8) return false;
    if (v.compare(0, 5, "HTTP/") != 0) return false;
    // isdigit에 signed char를 넘기면 UB이므로 unsigned char로 캐스팅
    if (!std::isdigit(static_cast<unsigned char>(v[5]))) return false;
    if (v[6] != '.') return false;
    if (!std::isdigit(static_cast<unsigned char>(v[7]))) return false;
    return true;
}
```

## field-name 불법 입력 검증
- field-name이란 헤더 줄에서 콜론 왼쪽에 오는 헤더 이름 토큰을 가리킴
    - 헤더 문법은 `field-name ":" OWS field-value OWS` 형태임
- 이 단계에서 거부하는 불법 입력은 콜론이 없는 헤더 줄임

### 콜론 없는 헤더 줄
- 헤더 줄은 반드시 콜론으로 name과 value를 구분해야 함
- 콜론이 없는 줄은 name과 value의 경계를 확정할 수 없으므로 문법 위반
    - `Host localhost`처럼 콜론이 빠진 줄이 이에 해당함
- 콜론 탐색이 실패하면 `Error`로 확정함

```cpp
// 헤더 줄에서 첫 콜론 위치를 찾음
size_t colon = line.find(':');
if (colon == std::string::npos){
    state_ = State::Error;
    return Result::Error;
}
```

### CTL과 공백
- CTL이란 control character의 약자로, 제어 문자(0x00부터 0x1F, 그리고 0x7F)를 가리킴
- 엄밀한 field-name 검증은 name 내부에 공백이나 CTL이 섞였는지까지 확인해야 함
    - `Foo Bar: v`처럼 name에 공백이 있는 줄은 RFC상 위반임
- 이 단계에서는 콜론 유무만 확정하고, name 내부 문자 검증은 범위 밖으로 둠
    - 각 검증 분기당 최소 한 개의 테스트만 두는 이 단계의 범위와 맞추기 위함임

## bare LF 거부
### bare LF의 정의
- bare LF란 앞에 CRLF 규칙을 어기고 `\r` 없이 `\n`만 홀로 온 경우를 가리킴
    - 명명 의도는 짝이 되는 CR이 벗겨진(bare) LF라는 데 있음

### strict 거부를 택하는 이유
- 일부 구현은 bare LF를 CRLF와 동일하게 받아들이는 관용적(lenient) 처리를 함
- 이 파서는 bare LF를 문법 위반으로 확정하는 strict 거부를 택함
    - 파서마다 bare LF를 다르게 해석하면 요청 스머글링의 틈이 생김
    - 요청 스머글링이란 앞단 프록시와 뒷단 서버가 메시지 경계를 다르게 해석하는 차이를 노려 요청을 몰래 끼워 넣는 공격을 가리킴
    - 줄 종결 해석을 CRLF 하나로 엄격히 고정하면 이 해석 차이가 사라짐

### find_crlf만으로 탐지되지 않는 이유
- 줄 종결자 탐색 함수 `find_crlf`는 `\r\n` 시퀀스만 탐지하며 이 단계에서 그대로 유지함
- bare LF 입력은 `\r\n`을 포함하지 않으므로 `find_crlf`가 종결자를 찾지 못하고 `npos`를 반환함
- `npos`는 곧 "CRLF 없음"으로 해석되어 `Incomplete`로 이어짐
    - bare LF만 담긴 입력이 `Incomplete`로 새면, 파서는 CRLF를 기다리며 영원히 완결되지 않는 hang 상태에 빠짐
- 따라서 `find_crlf`가 `npos`를 반환한 뒤, 잔여 구간에 bare LF가 있는지 별도로 스캔해 `Error`로 확정해야 함

### 별도 스캔 구현
- 별도 스캔이란 `find_crlf`의 CRLF 탐색과 독립적으로, 잔여 바이트에 홀로 선 `\n`이 있는지 확인하는 처리를 가리킴
- 스캔 지점은 `find_crlf`가 `npos`를 반환한 직후임
    - CRLF가 발견되었다면 정상 줄이 하나 이상 있으므로 이 스캔에 진입하지 않음
    - CRLF가 없을 때만 진입해, 미완결(`Incomplete`)인지 bare LF 위반(`Error`)인지를 가름

```cpp
// find_crlf가 npos를 반환한 잔여 구간에서 bare LF를 탐지
// \n을 만났는데 바로 앞이 \r가 아니면 bare LF → Error
Result HttpRequestParser::parseRequestLine(){
    size_t crlf = find_crlf(buffer_, offset_);
    if (crlf == std::string::npos){
        // CRLF가 없을 때: bare LF 여부를 별도로 스캔
        for (size_t i = offset_; i<buffer_.size(); ++i){
            if (buffer_[i] == '\n'){
                // 맨 앞이거나 앞 바이트가 \r이 아니면 bare LF
                if (i == offset_ || buffer_[i-1] != '\r'){
                    state_ = State::Error;
                    return Result::Error;
                }
            }
        }
        return Result::Incomplete;  // bare LF 없음 → 진짜 미완결
    }

    // ... CRLF 발견 시 정상 파싱 경로 ...
    offset_ = crlf + 2;
    return Result::Ok;
}
```
- 이 스캔이 `Incomplete`와 `Error`를 가르는 핵심
    - bare LF가 있으면 hang 대신 즉시 `Error`로 종결됨
    - bare LF가 없으면 진짜로 데이터가 부족한 상태이므로 `Incomplete`로 다음 청크를 기다림

## 검증
### 각 분기당 최소 테스트
- 이 단계의 테스트는 각 에러 분기당 최소 한 개만 둠
    - 표 기반 parameterized 테스트로의 확장은 이후 단계의 몫
    - parameterized 테스트란 입력과 기대값의 표를 두고 한 테스트 본문을 여러 입력에 반복 적용하는 기법을 가리킴

```cpp
// version 형식 오류 → Error
{
    HttpRequestParser p;
    const char* raw = "GET / FOO\r\n\r\n";
    assert(p.parse(raw, std::strlen(raw)) == Result::Error);
}

// 콜론 없는 헤더 → Error
{
    HttpRequestParser p;
    const char* raw = "GET / HTTP/1.1\r\nHost localhost\r\n\r\n";
    assert(p.parse(raw, std::strlen(raw)) == Result::Error);
}

// bare LF 입력 → Incomplete로 새지 않고 Error
{
    HttpRequestParser p;
    const char* raw = "GET / HTTP/1.1\n";   // CRLF 아닌 bare LF
    Result r = p.parse(raw, std::strlen(raw));
    assert(r == Result::Error);             // Incomplete면 실패
}
```

### error latch 유지 검증
- error latch 검증이란 오류를 유발한 뒤 유효한 요청을 다시 넣어도 상태가 `Error`에 고정되는지 확인하는 테스트임
- 절차는 먼저 잘못된 입력으로 `Error`를 만든 뒤, 같은 파서 객체에 정상 요청을 재급식하는 것
    - latch가 걸려 있으면 정상 요청을 넣어도 여전히 `Error`가 반환됨
    - latch가 없으면 정상 요청이 파싱되어 `Ok`가 반환되며, 이는 absorbing state 성질이 깨졌음을 뜻함

```cpp
// error latch: 에러 유발 후 유효 요청을 재급식해도 Error 유지
{
    HttpRequestParser p;

    // 1. bare LF로 Error 확정
    const char* bad = "GET / HTTP/1.1\n";
    assert(p.parse(bad, std::strlen(bad)) == Result::Error);

    // 2. 완전히 유효한 요청을 이어서 급식
    const char* good = "GET / HTTP/1.1\r\n\r\n";
    assert(p.parse(good, std::strlen(good)) == Result::Error);
}
```
- 이 테스트가 통과하면 `Error` 상태가 absorbing state로 동작함이 확인됨
    - 오류 확정 이후의 어떤 입력도 상태를 되돌리지 못함

## 정리
```
HTTP 요청 파서 에러 처리
    │
    ├── 오류 판정 정책
    │     ├── 문법 오류만 판정 (의미 오류 제외)
    │     └── Error 단일 상태 (상태 코드 매핑 제외)
    │
    ├── absorbing state
    │     ├── error latch = 진입 가드
    │     └── latch → 상한 검증 순서
    │
    ├── 문법 검증 분기
    │     ├── request-line 토큰 개수·빈 토큰
    │     ├── HTTP-version 형식 (문자 단위)
    │     └── field-name 콜론 유무
    │
    └── bare LF 거부
          ├── find_crlf는 CRLF만 탐지 → npos
          ├── 별도 스캔으로 hang 차단
          └── Incomplete vs Error 판정
```
