## value-parameterized test의 정의
- value-parameterized test란 하나의 테스트 본문을 여러 입력값에 대해 반복 실행하는 GoogleTest 기능
    - value는 테스트에 주입되는 입력값을 가리킴
    - parameterized는 그 입력값을 외부에서 파라미터로 공급받는다는 뜻
- 동일한 검증 로직을 입력만 바꿔 반복할 때, 각 입력마다 별도 `TEST`를 손으로 작성하는 중복을 제거함
- 하나의 본문에서 N개의 파라미터를 공급하면 N개의 독립 테스트 인스턴스로 확장됨
    - 각 인스턴스는 개별적으로 성공/실패가 집계됨
    - 하나가 실패해도 나머지는 계속 실행됨

### table-driven test와의 관계
- table-driven test란 입력과 기대값의 조합을 표 형태의 데이터로 나열하고, 그 표를 순회하며 동일 로직으로 검증하는 설계 방식을 가리킴
    - table은 테스트 케이스를 행으로 담은 데이터 묶음을 가리킴
    - driven은 그 데이터가 테스트 실행을 구동한다는 뜻
- value-parameterized test는 GoogleTest가 제공하는 table-driven test의 실행 장치에 해당함
- 케이스를 데이터로 분리하면 새 케이스 추가가 표에 행 하나를 더하는 작업으로 축소됨
    - 검증 로직 자체는 손대지 않음

## TestWithParam 픽스처
- `testing::TestWithParam<T>`란 파라미터 타입 `T`를 받는 파라미터화 전용 픽스처 기반 클래스를 가리킴
    - `testing::Test`를 상속하면서 파라미터 접근 인터페이스를 추가한 형태
- 픽스처(fixture)란 여러 테스트가 공유하는 공통 준비 환경을 담는 클래스를 가리킴
- 파라미터화 테스트를 작성하려면 이 클래스를 상속한 픽스처를 먼저 정의함
```cpp
// size_t는 이 픽스처가 받을 파라미터 타입
class ParserTest : public testing::TestWithParam<size_t>{
protected:
    HttpRequestParser parser_;      // 각 인스턴스마다 새로 생성됨
};
```
- 각 파라미터 인스턴스마다 픽스처가 새로 생성됨
    - 인스턴스 간 상태가 공유되지 않아 격리가 보장됨

## GetParam 접근
- `GetParam()`이란 현재 실행 중인 인스턴스에 공급된 파라미터 값을 반환하는 픽스처 멤버 함수를 가리킴
- 테스트 본문에서 이 함수를 호출해 주입된 값을 꺼냄
```cpp
TEST_P(ParserTest, SplitByChunkSize){
    size_t chunk = GetParam();      // 이 인스턴스에 공급된 chunk 크기
    // chunk 크기만큼 잘라 반복 주입
}
```
- `TEST_P` 매크로란 파라미터화 픽스처에 속하는 테스트 본문을 정의하는 매크로를 가리킴
    - P는 parameterized를 가리킴
    - 첫 번째 인자는 픽스처 클래스 이름과 일치해야 함

## INSTANTIATE_TEST_SUITE_P 파라미터 공급
- `INSTANTIATE_TEST_SUITE_P`란 파라미터화 테스트에 실제 파라미터 집합을 연결해 인스턴스를 생성하는 매크로를 가리킴
    - instantiate는 본문 하나를 구체적 파라미터로 실체화한다는 뜻
- `TEST_P`로 본문만 정의한 상태에서는 아직 실행할 인스턴스가 없음
- 이 매크로가 파라미터 집합을 공급해야 비로소 각 값에 대한 인스턴스가 만들어짐
```cpp
INSTANTIATE_TEST_SUITE_P(
    ChunkSize,                      // 1. 인스턴스화 이름(접두사)
    ParserTest,                     // 2. 대상 픽스처 이름
    testing::Values(1, 2, 3, 5),    // 3. 파라미터 집합
    ChunkNameGen                    // 4. name generator (선택)
);
```
- 네 인자의 역할은 아래와 같음

| 인자 위치 | 역할 |
| --- | --- |
| 1 | 인스턴스화 접두사, 생성된 테스트 이름 앞에 붙음 |
| 2 | 파라미터를 주입할 대상 픽스처 이름 |
| 3 | 공급할 파라미터 집합 |
| 4 | 테스트 이름 생성기, 생략 가능 |

### testing::Values와 testing::ValuesIn
- `testing::Values`란 파라미터 값을 인라인으로 나열해 집합을 만드는 헬퍼를 가리킴
    - 값을 소스에 직접 적을 때 사용함
- `testing::ValuesIn`란 컨테이너나 배열에 담긴 값들을 파라미터 집합으로 공급하는 헬퍼를 가리킴
    - in은 주어진 컨테이너 안의 값들을 취한다는 뜻
- 두 헬퍼의 선택 기준은 파라미터가 정적인지 동적인지에 있음

| 구분 | testing::Values | testing::ValuesIn |
| --- | --- | --- |
| 공급 형태 | 인라인 나열 | 컨테이너/배열 |
| 값 개수 | 고정, 소수 | 가변, 런타임 구성 가능 |
| 적합한 경우 | chunk 크기 몇 개 고정 | 케이스 struct를 벡터에 모아 공급 |

```cpp
// 케이스 struct를 벡터에 모아 ValuesIn으로 공급하는 형태
std::vector<HeaderCase> cases = {
    {"GET / HTTP/1.1\r\n\r\n", "GET", "/"},
    {"POST /x HTTP/1.1\r\nHost: a:8080\r\n\r\n", "POST", "/x"},
};
INSTANTIATE_TEST_SUITE_P(Normal, ParseCaseTest, testing::ValuesIn(cases));
```

## 파라미터 타입 구조체 설계
- 파라미터로 단일 스칼라가 아니라 입력과 기대값을 함께 묶어 전달해야 하는 경우가 많음
- 이때 입력/기대값을 필드로 담는 구조체를 파라미터 타입으로 설계함
    - 하나의 케이스가 하나의 구조체 인스턴스로 표현됨
```cpp
// 하나의 파싱 케이스를 담는 파라미터 타입
struct HeaderCase{
    std::string input;              // 파서에 주입할 원본 바이트열
    std::string expected_method;    // 기대하는 method
    std::string expected_path;      // 기대하는 path
    std::string expected_version;   // 기대하는 version
    std::vector<std::pair<std::string, std::string>> expected_headers;
};
```
- 구조체를 파라미터 타입으로 쓰면 `TestWithParam<HeaderCase>`로 픽스처를 선언
- `GetParam()`이 구조체를 반환하므로 본문에서 필드 단위로 기대값을 꺼냄

## name generator
- name generator란 각 파라미터 인스턴스에 사람이 읽을 수 있는 이름을 부여하는 함수 객체를 가리킴
    - INSTANTIATE_TEST_SUITE_P의 네 번째 인자로 전달함
- 생성기를 생략하면 인스턴스 이름이 접두사에 순번을 붙인 형태로 자동 생성됨
    - `ChunkSize/ParserTest.SplitByChunkSize/0`, `.../1` 형태
    - 실패한 순번이 어떤 입력이었는지 이름만으로는 식별 불가
- 생성기를 붙이면 이름에 파라미터 정보가 드러나 실패 케이스 식별이 가능해짐
```cpp
// 파라미터를 받아 테스트 이름 조각을 문자열로 반환
struct ChunkNameGen{
    std::string operator()(
        const testing::TestParamInfo<size_t>& info) const{
            return "chunk" + std::to_string(info.param);
    }
};
```

- `testing::TestParamInfo<T>`란 name generator에 전달되는, 파라미터 값과 순번을 담은 구조체를 가리킴
    - `.param` 필드로 파라미터 값에 접근함
    - `.index` 필드로 순번에 접근함
- 이름에 허용되는 문자는 영숫자와 밑줄뿐임
    - 구조체 파라미터에서는 필드를 조합해 유효한 식별자 문자열을 직접 구성해야 함

### 생성기 부재 시 진단 곤란
- 생성기 없이 순번 이름만 있으면 실패 로그에 `SplitByChunkSize/3`처럼만 표시됨
- 순번 3이 chunk 크기 몇에 대응하는지 확인하려면 INSTANTIATE 인자 나열 순서를 역추적해야 함
- 생성기로 `chunk5` 같은 이름을 부여하면 로그만 보고 즉시 재현 조건을 특정함

## chunk 크기 파라미터화
- chunked feeding이란 하나의 입력 바이트열을 여러 조각으로 나눠 파서에 순차 주입하는 방식을 가리킴
    - chunk는 나눠진 한 조각을 가리킴
    - feeding은 파서에 반복 주입하는 동작을 가리킴
- 파서가 부분 입력을 누적하며 파싱하는 구현이라면, 입력을 어떻게 쪼개 넣어도 최종 결과가 같아야 함
- 이 성질을 검증하려면 chunk 크기를 바꿔가며 동일 입력을 반복 주입해야 함
- chunk 크기를 파라미터로 돌리면 하나의 본문이 크기별 인스턴스로 자동 확장됨
    - 크기 1, 2, 3, ... 각각에 대해 "쪼개도 동일" 검증이 자동 생성됨

```cpp
// chunk 크기만큼 잘라 반복 주입하는 헬퍼
HttpRequestParser::Result feedInChunks(HttpRequestParser& parser, const std::string& input, size_t chunk){
    HttpRequestParser::Result result{};
    for (size_t off = 0; off < input.size(); off += chunk){
        size_t len = std::min(chunk, input.size() - off);
        result = parser.parse(input.data() + off, len);
    }

    return result;
}
```
- 이 헬퍼 하나에 chunk 크기를 파라미터로 주입하면 크기별 분할 케이스가 폭증함
    - 정상 케이스 각각에 대해 크기별 커버리지가 곱으로 늘어남

### 수동 분할 작성의 문제
- chunk 크기별 분할을 케이스마다 손으로 복제하면 동일 로직이 반복 등장함
- 크기를 하나 추가하려면 모든 케이스에 그 크기의 분할 코드를 다시 붙여야 함
- 분할 로직을 `TEST_P`로 파라미터화하면 크기 추가가 `testing::Values`에 값 하나를 더하는 작업으로 축소됨

## 경계값 분석
- 경계값 분석(boundary value analysis)이란 입력 도메인의 경계 지점에 결함이 몰린다는 관찰에 근거해, 경계와 그 인접값을 집중 검증하는 기법을 가리킴
- 파서 입력에서 그 경계에 해당하는 지점은 아래와 같음
    - 빈 입력, 곧 길이 0의 바이트열
    - 요소 0개, 곧 헤더가 하나도 없는 요청
    - request line 중간에서 끊긴 부분 입력
    - CRLF 두 바이트가 청크 경계에서 갈라지는 지점
    - 크기 제한을 막 넘어서는 헤더
- 경계마다 정상 처리 또는 정의된 오류 반환 중 어느 쪽이 올바른지 케이스로 고정함

## 공개 인터페이스 검증 원칙
- 공개 인터페이스(public interface)란 클래스 외부에서 접근하도록 공개된 멤버 함수 집합을 가리킴
    - `parse()` 반환값과 `HttpRequest`의 public getter가 이에 해당함
- 검증은 공개 인터페이스만 대상으로 하고 내부 멤버 상태를 참조하지 않음
    - `buffer_`, `offset_`, `state_`같은 private 멤버에 의존하지 않음
- 내부 멤버에 의존하는 단언은 내부 구현 변경 시 함께 깨짐
    - 저장 방식을 `string_view` 기반으로 바꾸는 등 리팩터가 발생하면 내부 상태 assert가 전부 무효화됨
- 공개 반환값과 getter만 검증하면 내부 구현이 바뀌어도 테스트가 유지됨
    - 테스트가 구현이 아니라 계약(contract)을 검증하는 상태가 됨

### 헤더 비교의 순서 무관성
- 헤더 저장 컨테이너가 `unordered_map`이면 저장 순서가 보존되지 않음
- 따라서 기대 헤더와 실제 헤더를 비교할 때 순서에 의존하면 안됨
    - 키 집합과 각 키의 값이 일치하는지만 확인함
- 키가 소문자로 정규화되어 저장되는 구현이라면, 기대값도 소문자 키로 맞춰 비교함
    - 정규화(normalization)란 서로 다른 표현을 하나의 표준형으로 통일하는 처리를 가리킴
    - 기대 키를 원본 대소문자로 두면 정규화된 실제 키와 어긋나 비교가 실패함

## 동일성 검증
- 동일성 검증이란 같은 입력을 서로 다른 주입 방식으로 넣었을 때 파싱 결과가 완전히 일치하는지 확인하는 테스트
- 비교 대상은 한 번에 전부 주입한 결과와 1바이트씩 주입한 결과 두 가지임
- 두 방식의 method, path, version, headers가 모두 같아야 부분 입력 누적 로직이 올바름
```cpp
TEST_P(ParseCaseTest, ChunkingIsInvariant){
    const HeaderCase& c = GetParam();

    // 방식 1: 한 번에 전부 주입
    HttpRequestParser whole;
    whole.parse(c.input.data(), c.input.size());

    // 방식 2: 1바이트씩 주입
    HttpRequestParser byteWise;
    feedInChunks(byteWise, c.input, 1);

    // 두 결과의 public getter가 완전히 일치하는지 검증
    EXPECT_EQ(whole.request().method(), byteWise.request().method());
    EXPECT_EQ(whole.request().path(), byteWise.request().path());
    EXPECT_EQ(whole.request().version(), byteWise.request().version());
    EXPECT_EQ(whole.request().headers(), byteWise.request().headers());
}
```
- `unordered_map` 끼리의 `==` 비교는 순서를 무시하고 키-값 쌍의 집합 동일성만 판정함
    - 순서 무관 비교 요건이 컨테이너 자체 연산으로 충족됨

## CMake 테스트 타깃 등록
- 파라미터화 테스트도 일반 GoogleTest 실행 파일과 동일한 방식으로 빌드 타깃에 등록됨
- 테스트 소스를 실행 파일 타깃에 포함하고 GoogleTest를 링크함
- `gtest_discover_tests`란 빌드된 테스트 바이너리를 실행해 개별 테스트를 자동으로 CTest에 등록하는 명령을 가리킴
    - 파라미터화로 생성된 각 인스턴스도 개별 테스트로 등록됨

```cmake
# tests/CMakeLists.txt
add_executable(parser_test http/HttpRequestParserTest.cpp)
target_compile_features(parser_test PRIVATE cxx_std_20)
target_include_directories(parser_test PRIVATE ${CMAKE_SOURCE_DIR}/include)
target_link_libraries(parser_test PRIVATE http-core GTest::gtest_main)

include(GoogleTest)
gtest_discover_tests(parser_test)   # 인스턴스 단위로 CTest 등록
```
