## HTTP 요청 메시지 문법
- HTTP 메시지는 클라이언트와 서버가 주고받는 텍스트 기반 데이터 단위를 가리키는 용어
- 그중 요청 방향의 메시지를 요청 메시지라고 부름
- 요청 메시지의 문법은 RFC 7230 3장에 정의되어 있음
- 요청 메시지는 세 부분으로 구성됨
    - request line
        - 요청 메시지의 첫 줄임
    - header field
        - request line 뒤에 0개 이상 이어지는 줄
    - message body
        - 빈 줄 뒤에 선택적으로 오는 본문
- request line은 요청의 대상과 방법을 한 줄로 나타내는 첫 줄을 가리킴
- request line의 문법은 아래와 같음
```
method SP request-target SP HTTP-version CRLF
```
- 각 토큰의 정의는 아래와 같음
    - method
        - 요청 동작을 나타내는 토큰
        - GET, POST, HEAD 등이 여기에 해당함
    - SP
        - space의 약자이며 단일 공백 문자 하나를 가리킴
        - 문법상 각 경계에 정확히 한 개이며 여러 개를 허용하지 않음
    - request-target
        - 요청 대상 리소스를 지정하는 토큰
    - HTTP-version
        - 프로토콜 버전 문자열이며 `HTTP/1.1` 형태를 가짐
    - CRLF
        - carriage return과 line feed의 약자이며 `\r\n` 두 바이트를 가리킴
        - 줄의 끝을 나타내는 구분자
        - LF 하나만으로는 문법에 맞지 않음

### origin-form request-target
- request-target은 문맥에 따라 네 가지 형태 중 하나를 가짐
    - origin-form
        - 경로와 쿼리만 담는 형태이며 `/index.html?q=1` 형태를 가짐
        - 일반적인 서버 요청에서 사용하는 형태
    - absolute-form
        - `http://example.com/index.html`처럼 완전한 URI를 담는 형태
        - 주로 프록시로 보내는 요청에서 사용함
    - authority-form
        - `example.com:443`처럼 호스트와 포트만 담는 형태
        - CONNECT 메서드에서 사용함
    - asterisk-form
        - `*` 하나만 담는 형태
        - OPTIONS 메서드에서 서버 전체를 대상으로 할 때 사용함
- request-target을 그대로 path 필드에 담으면 origin-form만 가정하는 구현이 됨
- absolute-form이 들어오면 스킴과 호스트까지 path에 섞여 들어감
- 쿼리 스트링이 붙은 경우에도 path와 query가 분리되지 않음
- 이 파서는 origin-form만 지원하므로 이 제약을 헤더 파일 주석에 명시함
- 파싱 결과를 담는 구조체는 아래와 같음
```cpp
// include/http/HttpRequest.h

# include <string>

// 파싱 결과를 담는 구조체
// request-target은 origin-form만 지원
// absolute-form, authority-form, asterisk-form은 처리하지 않음
// path에는 쿼리 스트링을 분리하지 않은 request-target 원문이 그대로 들어감
struct HttpRequest{
    std::string method;     // 예: "GET"
    std::string path;       // 예: "/index.html" (origin-form 한정)
    std::string version;    // 예: "HTTP/1.1"
};
```

## 유한 상태 머신 기반 파서 설계
- 유한 상태 머신은 유한한 개수의 상태와 입력에 따른 상태 전이 규칙으로 동작을 표현하는 계산 모델
- finite state machine의 약자 FSM이라고도 부름
- 요청 파싱에 FSM이 적합한 이유는 요청 메시지가 정해진 순서로 구성되기 때문
- request line을 먼저 읽고 그 다음 header를 읽고 마지막에 body를 읽음
- 현재 어느 부분을 읽고 있는지를 상태로 표현하면 다음에 무엇을 파싱할지가 상태로 결정됨
- 파서 상태는 아래 값을 가짐
    - RequestLine
        - request line을 파싱하는 중
    - Headers
        - header field를 파싱하는 중
    - Done
        - 파싱이 완료된 상태
    - Error
        - 문법 위반으로 파싱이 실패한 상태
- 이번 단계에서는 RequestLine에서 Done으로 가는 경로만 동작
- Headers 상태는 값으로만 정의해 두고 진입하는 경로는 구현하지 않음

### enum class 상태 표현
- enum class는 C++11에서 도입된 범위 지정 열거형
- scoped enumeration이라고도 부름
- 기존 enum과 달리 열거자가 열거형 이름의 범위 안에 갇힘
- 따라서 `State::RequestLine`처럼 접근해야 하며 다른 열거형의 열거자와 이름이 충돌하지 않음
- 정수형으로 암시적 변환이 되지 않아 상태 값을 정수 연산에 섞어 쓰는 오류를 컴파일 단계에서 막음
- 상태 열거형 정의는 아래와 같음
```cpp
enum class State {
    RequestLine,    // request line 파싱 중
    Headers,        // header 파싱 중
    Done,           // 파싱 완료
    Error           // 문법 위반
};
```

### 상태별 멤버 함수 분리
- 상태별 처리 로직을 각각 별도의 멤버 함수로 분리함
- `parse()` 진입점은 현재 상태를 보고 해당 상태의 처리 함수로 분기하는 역할만 맡음
- 실제 파싱 로직은 각 상태 함수 안에 국소화됨
- 이 구조를 택하는 이유는 이후 body 파싱 단계에서 재개 로직을 각 상태 함수 안에 가두기 위함
    - 재개는 입력이 중간에 끊겼다가 다시 도착했을 때 이전에 멈춘 지점부터 파싱을 이어가는 동작을 가리킴
- 어느 함수부터 다시 실행할지가 현재 상태로 결정되므로 재개 지점 관리가 상태 하나로 단순해짐
- 파싱 로직 전체가 한 함수에 뭉쳐 있으면 재개 지점을 관리하기 어려움
- 파서 클래스 선언은 아래와 같음
```cpp
// include/http/HttpRequestParser.h

# include <cstddef>
# include "HttpRequest.h"

class HttpRequestParser{
public:
    // 파싱 진행 상태를 나타내는 3-state 반환 타입
    enum class Result{
        Ok,         // 파싱 완료
        Incomplete, // 입력이 부족해 아직 완료되지 않음
        Error       // 문법 위반
    };

    // 파싱 진입점
    // data 입력 바이트 버퍼
    // len 버퍼 길이
    Result parse(const char* data, size_t len);

    const HttpRequest& request() const { return request_; }

private:
    enum class State{
        RequestLine,
        Headers,
        Done,
        Error
    };

    // 상태별 처리 함수
    // 입력을 소비한 뒤 상태를 전이하고 진행 결과를 반환
    Result parseRequestLine(const char* data, size_t len);

    State state_ = State::RequestLine;
    HttpRequest request_;
};
```

## 3-state 반환 패턴
- 3-state 반환 패턴은 파싱 결과를 성공, 실패, 미완료 세 가지로 나누어 반환하는 방식을 가리킴
- 반환을 bool로 잡으면 두 가지 경우만 구분할 수 있음
- 성공과 실패는 나눌 수 있지만 입력이 아직 다 도착하지 않은 경우를 표현할 수 없음
- 네트워크 소켓에서 데이터는 조각으로 나뉘어 도착함
- request line의 절반만 도착한 상태에서 파싱을 시도하면 이것은 실패가 아니라 미완료임
    - 더 읽어서 이어 붙이면 완결될 수 있는 상태이기 때문
- bool 반환은 이 상태를 실패로 잘못 처리하게 만듦
- 따라서 반환 타입을 세 값을 가지는 열거형으로 정의
    - Ok
        - 파싱이 완료되었음을 나타냄
    - Incomplete
        - 입력이 부족해 더 읽어야 함을 나타냄
    - Error
        - 문법 위반으로 실패했음을 나타냄
- 이번 단계는 입력이 한 번에 전부 도착한다고 전제함
- 따라서 request line 뒤에 CRLF가 없거나 SP 개수가 맞지 않으면 Error로 처리함
- Incomplete를 실제로 반환하는 경로는 이번 단계에서 구현하지 않음
- 다만 반환 타입 자체는 세 값을 미리 열어 둠
- 이후 내부 누적 버퍼를 도입할 때 Incomplete 케이스만 채우면 되도록 시그니처를 지금 확정

### request line 파싱 구현
- request line 파싱은 두 개의 SP를 기준으로 세 토큰을 잘라냄
- 경계 조건을 먼저 검사한 뒤 토큰을 분리함
- 파싱 구현은 아래와 같음
```cpp
// src/http/HttpRequestParser.cpp

# include "http/HttpRequestParser.h"
# include <string>

HttpRequestParser::Result
HttpRequestParser::parse(const char* data, size_t len){
    // 현재 상태에 따라 처리 함수로 분기
    switch(state_){
        case State::RequestLine:
            return parseRequestLine(data, len);
        default:
            // 이번 단계에서 도달하지 않는 경로
            state_ = State::Error;
            return Result::Error;
    }
}

HttpRequestParser::Result
HttpRequestParser::parseRequestLine(const char* data, size_t len){
    std::string line(data, len);

    // CRLF 위치를 찾음. 없으면 이번 단계에서는 문법 위반으로 처리
    size_t crlf = line.find("\r\n");
    if (crlf == std::string::npos){
        state_ = State::Error;
        return Result::Error;
    }

    // CRLF 앞부분만 request line으로 취급
    std::string request_line = line.substr(0, crlf);

    // 첫 번째 SP는 method와 request-target의 경계
    size_t sp1 = request_line.find(' ');
    if (sp1 == std::string::npos){
        state_ = State::Error;
        return Result::Error;
    }

    // 두 번째 SP는 request-target과 HTTP-version의 경계
    size_t sp2 = request_line.find(' ', sp1 + 1);
    if (sp2 == std::string::npos){
        state_ = State::Error;
        return Result::Error;
    }

    // SP가 세 개 이상이면 토큰이 하나 더 있다는 뜻이므로 문법 위반
    if (request_line.find(' ', sp2 + 1) != std::string::npos){
        state_ = State::Error;
        return Result::Error;
    }

    // 세 토큰을 분리
    request_.method  = request_line.substr(0, sp1);
    request_.path    = request_line.substr(sp1+1, sp2-sp1-1);
    request_.version = request_line.substr(sp2 + 1);

    // 문법상 각 토큰은 비어 있을 수 없음
    if (request_.method.empty() || request_.path.empty() || request_.version.empty()){
        state_ = State::Error;
        return Result::Error;
    }

    // 이번 단계는 RequestLine에서 Done으로 가는 경로만 동작
    state_ = State::Done;
    return Result::Ok;
}
```
- 호출 측 사용 흐름은 아래와 같음
```cpp
// 호출 예시(테스트 진입점)

HttpRequestParser parser;
const char* input = "GET /index.html HTTP/1.1\r\n";

HttpRequestParser::Result r = parser.parse(input, std::strlen(input));

if (r == HttpRequestParser::Result::Ok){
    const HttpRequest& req = parser.request();
    // req.method  == "GET"
    // req.path    == "/index.html"
    // req.version == "HTTP/1.1"
}
```

### 경계조건과 실패 사례
- 파서가 Error로 보내야 하는 입력을 아래에 정리
    - SP가 없는 경우
        - `GET/index.html`처럼 토큰 경계가 없으면 분리에 실패함
    - SP가 두 개를 초과하는 경우
        - `GET  /index.html HTTP/1.1`처럼 공백이 연달아 오면 토큰 수가 맞지 않음
        - 문법상 SP는 각 경계에 정확히 하나이므로 공백 두 개는 빈 토큰이나 초과 토큰을 만듦
    - CRLF가 없는 경우
        - 한 번에 전부 도착한다는 전제에서 줄 끝 구분자가 없으면 완결된 request line으로 보지 않음
    - 토큰 중 하나가 비어있는 경우
        - SP는 있지만 사이 문자열이 없으면 method나 path가 빈 문자열이 됨

> 반환 타입은 처음부터 3-state로 열어둠
>
> 지금은 완결과 실패만 채우고 미완료 처리는 내부 버퍼 도입 시점에 Incomplete 케이스만 추가
