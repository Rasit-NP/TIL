## 책임 경계
- 책임 경계란 각 계층이 무엇을 알고 무엇을 몰라야 하는지를 못 박은 계약
    - 계층 사이의 지식 의존이 한 방향으로만 흐르도록 강제하는 규칙임
- 이번 연결이 다루는 두 계층은 다음과 같음
    - I/O 다중화 계층은 fd와 파서 인스턴스를 소유하고, 소켓에서 바이트를 읽어 올리는 역할을 맡음
        - 누적 버퍼는 소유하지 않음. 읽기용 스택 임시 버퍼만 콜백 안에서 잠깐 씀 (이중 버퍼링 회피 참고)
    - 프로토콜 계층은 넘겨받은 바이트를 파싱 상태로 변환하는 역할을 맡음
- 이 둘을 담는 클래스는 각각 `Connection`과 `HttpRequestParser`임
    - `Connection`은 소켓 하나에 대응하는 연결의 상태를 응집한 클래스
    - `HttpRequestParser`는 도착한 바이트열을 요청 구조로 파싱하는 상태 머신 클래스

### 의존 방향 단방향 유지
- 의존 방향이란 한 클래스가 다른 클래스의 타입이나 헤더를 알아야 컴파일되는 관계의 화살표를 가리킴
- 이 설계의 핵심 규칙은 `Connection`은 파서를 알아도 되지만 파서는 `Connection`을 몰라야 한다는 것
    - `Connection`은 파서를 멤버로 들고 호출하므로 파서 헤더를 include함
    - 파서는 fd도 epoll도 `Connection`도 알지 못한 채 바이트만 다룸
- 파서가 fd나 epoll을 모른다는 성질을 유지하면 파서를 소켓 없이 단위 테스트할 수 있음
    - 파서 단위 테스트가 플랫폼 독립적으로 성립하는 근거가 단방향 의존
```
Connection ───────────▶ HttpRequestParser
 (fd·파서 소유)     의존   (바이트 → 파싱 상태)
     ▲                          │
     └ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─┘
        Result 반환값 (타입 의존 아님)

 실선(──▶)이 의존 방향이고 한 방향뿐임
 점선(─ ─)은 값이 돌아오는 흐름일 뿐, 파서는 Connection을 역참조하지 않음
```

## 파서 인스턴스의 연결당 소유
- 파서 인스턴스를 어디에 두고 누가 소유할지 결정해야 함
- 결론은 연결 하나당 파서 하나를 두고 `Connection`이 값 멤버로 소유하는 것
    - 파싱 상태(`buffer_`, `offset_`, `state_`)가 연결마다 독립적으로 유지되어야 하기 때문
    - 파서를 전역이나 공유로 두면 서로 다른 연결의 바이트가 한 버퍼에 섞임
- `Socket`이 RAII로 fd를 단독 소유하므로 `Connection`은 복사되면 안 됨
    - 복사되면 같은 fd를 두 소멸자가 닫으려 시도해 이중 close가 발생함
    - 복사 금지를 타입 차원에서 선언해 이를 원천 차단함

```cpp
// include/Connection.h
# include "http/HttpRequestParser.h"

class Connection{
private:
    Socket            sock_;        // 연결 소켓
    HttpRequestParser parser_;      // 연결당 파서 인스턴스 1개
    // read_buf_는 두지 않음

public:
    explicit Connection(Socket sock) : sock_(std::move(sock)) {}
    Connection(const Connection&)            = delete;  // 복사 금지 (fd 이중 close 차단)
    Connection& operator=(const Connection&) = delete;
    Connection(Connection&&)                 = default; // 이동은 허용 (컨테이너 보관)
    Connection& operator=(Connection&&)      = default;
    int fd() const noexcept { return sock_.get(); }
    bool on_readable();
};
```

### 헤더 순환 의존 회피
- 순환 의존이란 A 헤더가 B 헤더를, B 헤더가 다시 A 헤더를 include해 컴파일이 서로를 가리키는 교착을 가리킴
- `Connection.h`가 `HttpRequestParser.h`를 include할 때 반대 방향 의존이 없는지 확인해야 함
    - 파서 헤더가 `Connection.h`를 include하는 순간 순환이 성립함
- 단방향 의존 규칙을 지키면 순환은 애초에 생기지 않음
    - 파서 헤더에 `Connection` 타입이 등장할 이유가 없으므로 include할 일이 없음

## read 콜백의 파싱 흐름
- read 콜백이란 소켓이 읽기 가능 상태가 되었을 때 호출되어 도착한 바이트를 처리하는 진입점을 가리킴
    - 이 코드에서는 `Connection::on_readable`이 그 역할을 맡음
- echo 서버 단계에서 이 자리는 받은 바이트를 그대로 송신 버퍼에 적재하는 코드였음
- 이 자리에 `parser_.parse(data, len)` 호출을 넣고 반환값으로 분기함

### 세 반환값의 분기 제약
- 파서의 `parse`는 `Ok`, `Incomplete`, `Error` 세 값 중 하나를 반환함
    - `Ok`는 요청 하나가 완결되어 파싱 결과가 확보된 상태
    - `Incomplete`는 데이터가 부족해 미완결이며 다음 read를 기다려야 하는 상태
    - `Error`는 파싱 불가능한 입력이거나 상한을 초과한 상태
        - 상한이란 request line 하나에 허용할 최대 바이트 수이며, 별도 카운터 없이 `buffer_.size()`로 판정함
        - 상한이 없으면 `\r\n`을 영영 보내지 않는 클라이언트 하나가 `buffer_`를 무한히 키울 수 있음
- 각 반환값에 대응하는 처리는 다음과 같음

| 반환값 | 처리 |
|-------|-----|
| `Ok` | 세 필드를 즉시 로그 출력 후 연결 정리 |
| `Incomplete` | 아무것도 하지 않고 다음 read 대기 |
| `Error` | 에러 상태를 로그로 남기고 연결 정리 |

- `Ok`와 `Error`가 표에서 똑같이 연결 정리로 끝나는 것이 현재 코드의 실제 모습임
    - 두 경로의 차이는 로그 대상(stdout / stderr)과 정상·비정상 여부뿐이고, 연결 처리는 동일함
- keep-alive가 없는 현재 단계에서는 `Ok` 직후 연결을 정리함
    - keep-alive란 하나의 연결을 여러 요청에 재사용하는 방식을 가리킴
    - keep-alive를 두지 않으므로 요청 1건을 완료하면 그 연결의 소임이 끝남
    - `Ok` 후 `continue`로 같은 연결에서 다음 요청을 계속 읽으면 사실상 keep-alive처럼 동작하므로, 일관성을 위해 `Ok` 시 연결 종료를 알림

```cpp
// src/Connection.cpp
bool Connection::on_readable(){
    char buf[4096];
    while (true){
        ssize_t n = ::read(sock_.get(), buf, sizeof(buf));
        if (n > 0){
            // 읽은 청크를 즉시 파서에 넘김
            auto r = parser_.parse(buf, static_cast<size_t>(n));

            if (r == HttpRequestParser::Result::Ok){
                const HttpRequest& req = parser_.request();
                // view가 살아 있는 이 콜백 안에 즉시 소비(출력)
                std::printf("method=%.*s path=%.*s version=%.*s\n",
                            static_cast<int>(req.method().size()),  req.method().data(),
                            static_cast<int>(req.path().size()),    req.path().data(),
                            static_cast<int>(req.version().size()), req.version().data());
                return false;       // keep-alive 없이 완결 후 연결 정리
            }
            else if (r == HttpRequestParser::Result::Error){
                std::fprintf(stderr, "parse error on fd=%d\n", fd());
                return false;
            }
            // Incomplete면 그대로 다음 read 대기
            continue;
        }
        if (n == 0) return false;
        if (errno == EAGAIN || errno == EWOULDBLOCK) break;
        if (errno == EINTR) continue;
        return false;
    }
    return true;
}
```

## reset의 초기화 대상 범위
- reset이란 요청 하나를 처리한 뒤 다음 요청을 받기 위해 파서를 초기 상태로 되돌리는 메서드를 가리킴
    - keep-alive 없는 현재 단계에서는 `Ok` 직후 연결을 닫으므로 이 경로에서 재사용을 위한 리셋을 호출하지 않음
    - 그럼에도 파서 자체는 재사용 가능한 상태로 되돌리는 `reset`을 제공하며, 그 초기화 범위를 정확히 규정해 둠
- 리셋의 함정은 일부 멤버만 되돌리고 나머지를 남겨 두어 이전 요청의 잔재가 다음 요청에 새는 것
- 되돌려야 하는 대상을 빠짐없이 열거해야 함
    - 파싱 단계 `state_`를 초기 상태로 되돌림
    - 누적 버퍼 `buffer_`를 비움
    - 파싱 커서 `offset_`을 0으로 되돌림
    - 파싱 결과 `request_`를 기본값으로 되돌림
- 오프셋 방식의 부수 효과로 `buffer_` 재할당에 대한 내성이 생김
    - 오프셋은 포인터가 아니라 정수 인덱스이므로, `append`가 재할당을 일으켜 기반 주소가 바뀌어도 인덱스가 가리키는 논리적 위치는 그대로 유효함
    - 진짜 `string_view`를 멤버로 두었다면 재할당 순간 포인터가 무효(dangling)가 되지만, 오프셋 방식은 그 부담이 없음

```cpp
// src/http/HttpRequestParser.cpp
void HttpRequestParser::reset(){
    state_ = State::RequestLine;
    buffer_.clear();
    offset_ = 0;
    request_ = HttpRequest{};
    // 헤더 맵 등 이후 추가된 상태가 있으면 여기서 함께 비움
}
```
- 상한 초과 검사는 별도 카운터 없이 `buffer_.size()`로 판정하므로 리셋 목록에 추가할 카운터가 없음
    - `buffer_.clear()`가 크기를 0으로 되돌리므로 상한 상태도 함께 초기화됨

### 리셋 시점과 error latch의 관계
- error latch란 한 번 `Error`에 도달하면 이후 어떤 입력에도 `Error`를 유지하는 흡수 상태(absorbing state) 성질을 가리킴
- 현재 단계에서는 `Ok`도 `Error`도 연결을 닫으므로 리셋을 호출할 자리가 아예 없음
    - 그래서 "`Ok`는 리셋, `Error`는 종료"라는 대비는 지금 코드에 존재하지 않음
- 그럼에도 두 상태의 성질은 분명히 다름
    - `Error`는 흡수 상태라 리셋 없이는 어떤 입력으로도 벗어날 수 없음
    - `Ok`는 흡수 상태가 아니라 리셋만 하면 다음 요청을 받을 수 있는 상태
- 이 차이는 keep-alive를 도입하는 순간 실제 분기로 드러남
    - `Ok`는 리셋 후 같은 연결을 재사용하는 경로로 감
    - `Error`는 그때도 연결 종료로 감. 잘못된 요청을 보낸 연결의 파서를 리셋해 재사용하면 신뢰할 수 없는 클라이언트를 계속 상대하게 되기 때문

## string_view 소비 창
- 소비 창(consumption window)이란 파싱 결과가 가리키는 view가 유효하게 살아 있는 시간 구간을 가리킴
- 이번 결과 소비 전략은 즉시 소비 후 연결 종료임
    - 파싱 결과인 method, path, version을 별도 문자열로 복사하지 않고 `buffer_` 내부를 가리키는 view 상태로 둠
    - view는 자신이 가리키는 원본 버퍼가 살아 있는 동안만 유효함

### view 유효 구간의 함정
- 즉시 소비 전략에서 view가 유효한 구간은 `Ok`를 감지한 read 콜백 내부로 한정됨
    - `Ok` 반환 시점에 `buffer_`가 완결된 요청 바이트를 담고 있으므로 view가 그 안을 정확히 가리킴
    - 같은 read 콜백을 벗어나기 전에 세 필드를 소비(출력)해야 함
- view를 무효화하는 것은 `reset()`이 아니라 `Connection` 소멸임
    - `return false` 이후 이벤트 루프가 `Connection`을 파괴하면 멤버인 `parser_`가 함께 소멸하고 `buffer_`가 해제됨
- 소비 창 자체는 소멸 시점까지 열려 있지만, 콜백 안에서 소비하라는 결론은 그대로임
    - `return false` 이후 소멸 시점은 이벤트 루프의 사정이라 이 함수가 통제할 수 없음
    - 통제할 수 없는 시점에 기대지 말고 통제 가능한 구간 안에서 끝내는 것이 소비 창 규칙의 일반형임
- 접근자가 반환하는 `string_view`는 널 종단(null-terminated)을 보장하지 않음
    - 널 종단이란 문자열 끝에 `\0` 바이트가 붙어 길이를 표시하는 C 문자열 관례를 가리킴
    - view는 시작 포인터와 길이 두 값으로 구간을 표현할 뿐 끝에 널을 두지 않음
- 따라서 `%s`로 view의 `.data()`를 넘기면 종단 널을 만날 때까지 버퍼 뒤쪽을 계속 읽음
    - `Ok` 직후 `buffer_`에는 세 필드 뒤에 CRLF와 후속 헤더 바이트가 이어져 있음
    - method view 뒤가 널이 아니라 공백이므로 다음 바이트로 새어 읽는 버그가 발생함
    - 길이를 명시하는 `%.*s`로 정확히 view 구간만 출력해야 함
        - `.size()`를 길이로, `.data()`를 시작 포인터로 넘김

## 이중 버퍼링 회피
- 이중 버퍼링이란 같은 바이트가 두 개의 버퍼에 중복 누적되는 상태를 가리킴
- `Connection`이 자체 read 버퍼를 들고, 파서도 `buffer_.append()`로 누적하면 데이터가 두 곳에 쌓임
    - 누적 주체가 둘로 나뉘면 어느 쪽이 진실인지 모호해지고 동기화 부담이 생김
- 누적 주체를 파서 하나로 고정
    - `Connection`은 read한 청크를 즉시 `parse()`에 넘기고 자체 버퍼링을 하지 않음
    - 점진적 누적은 파서의 `buffer_`가 전담함
- 이 결정으로 `Connection`에서 `read_buf_` 멤버가 사라짐
    - read 콜백은 스택의 `char buf[4096]`으로 `EAGAIN`이 날 때까지 반복해서 읽되, 읽을 때마다 곧바로 `parse()`에 넘긴 뒤 잊음
    - 같은 스택 버퍼를 매 반복마다 덮어쓰므로 청크가 쌓이지 않고, 누적은 오직 파서 쪽에서만 일어남

## curl 검증
- origin-form이란 request line의 request-target이 절대 경로에 선택적 쿼리가 붙는 형식을 가리킴(RFC 9112)
    - 문법은 `absolute-path [ "?" query ]`로, `/index.html`이나 `/search?q=1` 형태가 이에 해당함
    - 프록시 없이 서버에 직접 요청할 때 클라이언트가 보내는 표준 형식임
    - `curl http://localhost:8080/`은 쿼리 없는 최소 형태인 `/`를 보냄
- `curl -v http://localhost:8080/`이 실제로 보내는 request line이 origin-form 가정과 일치하는지 실측해야 함
    - `curl -v`의 출력에서 요청 라인이 `GET / HTTP/1.1` 형태로 나타나면 가정이 맞음
- 검증의 최소 목표는 세 가지
    - `Connection`이 파서를 소유하고 read한 바이트가 `parse()`로 전달됨
    - 정상 요청에서 method, path, version이 서버 stdout에 정확히 출력됨
    - 잘못된 request line 입력에서 에러 상태가 로그에 남고 연결이 정리됨

### 응답 부재로 인한 즉시 종료
- 이 단계는 파싱 결과 출력까지만 다루고 응답 생성은 범위 밖임
- `Ok` 직후 서버가 먼저 소켓을 닫으므로 `curl`은 응답 바이트를 하나도 받지 못한 채 EOF를 만남
    - `return false` → 이벤트 루프가 `Connection` 파괴 → `Socket` 소멸자가 `close(fd)` 호출
    - HTTP 응답으로 해석할 것이 없으므로 `curl`은 기다리지 않고 즉시 끝남

```
* Empty reply from server
* Closing connection 0
curl: (52) Empty reply from server
```

- 이 52는 결함이 아니라 응답 생성이 아직 없기 때문에 나타나는 정상 동작임
- 판정 기준은 `curl`의 성공 여부가 아니라 서버 쪽 출력임
    - 세 필드가 stdout에 찍혔고 `curl`이 52로 끝났다면 이 단계의 목표는 달성된 것임
    - 반대로 `curl`이 멈춰 있다면 `Ok` 경로를 타지 못하고 `Incomplete`에 머물러 있다는 뜻이므로 조사 대상임
- 정상 요청과 잘못된 요청 모두 클라이언트에서는 똑같이 52로 보임
    - 응답을 아예 만들지 않으므로 `curl`만 봐서는 두 경우를 구분할 수 없음
    - 판별은 stdout(세 필드)과 stderr(`parse error on fd=...`) 중 어느 쪽에 찍혔는지로만 가능함

### 컨테이너 필수 검증
- 이 통합의 검증은 파서 단위 테스트와 달리 서버 바이너리를 실제로 띄워야 확인 가능함
    - 파서 단위 테스트는 `sys/epoll.h`에 의존하지 않으므로 플랫폼 독립적으로 실행됨
    - 이번 통합은 epoll 기반 이벤트 루프를 포함하므로 `sys/epoll.h`가 없는 환경에서는 컴파일 자체가 실패함
- 따라서 이번 검증은 Docker(Ubuntu) 컨테이너 안에서 `curl`로 수행해야 함
    - macOS 등 epoll이 없는 로컬 환경에서는 헤더를 찾지 못해 빌드가 멈추므로 바이너리가 생성되지 않음
    - 실행해 봤더니 안 되는 런타임 실패가 아니라, 빌드 단계에서 걸리는 컴파일 실패임

## 정리
```
파서 소유와 파싱 결과 소비의 연결
    │
    ├── 책임 경계
    │     ├── Connection : fd·파서 소유 (누적 버퍼 없음)
    │     ├── HttpRequestParser : 바이트 → 파싱 상태
    │     └── 단방향 의존 (파서는 Connection 모름)
    │
    ├── 파서 소유
    │     ├── 연결당 파서 1개 (값 멤버, 복사 금지·이동 허용)
    │     ├── 결과는 request_ 멤버가 오프셋+길이로 보관
    │     └── 헤더 순환 의존 회피
    │
    ├── read 콜백 분기
    │     ├── Ok → 출력 후 연결 정리
    │     ├── Incomplete → 다음 read 대기
    │     └── Error → 로그 후 연결 정리
    │
    ├── reset 범위
    │     ├── state_ · buffer_ · offset_
    │     └── request_ 통째로 초기화 (오프셋 6종 포함, 재할당 내성)
    │
    ├── view 소비 창
    │     ├── 유효 구간 = Ok 감지 콜백 내부
    │     ├── 널 종단 부재 → %.*s 출력
    │     └── 출력 → 연결 정리 순서 고정
    │
    └── 검증
          ├── curl origin-form 실측
          ├── 응답 부재 → curl: (52) 정상
          └── epoll 의존 → 컨테이너 필수
```
