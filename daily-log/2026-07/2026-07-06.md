## 메시지 경계 부재
- TCP(Transmission Control Protocol)는 바이트 스트림 프로토콜임
    - "바이트 스트림"이란 송신 측이 넣은 바이트들이 끊김 없는 연속된 흐름으로 수신 측에 도달함을 뜻함
    - 데이터그램 단위로 경계가 보존되는 UDP와 대비됨
- 메시지 경계(message boundary)란 한 논리 단위의 요청이 어디서 시작하고 끝나는지를 구분하는 지점을 가리킴
- TCP는 이 경계를 보존하지 않음
    - 송신 측이 `write()`로 한 번에 보낸 요청이 수신 측에서 여러 `read()`로 쪼개져 도착할 수 있음
    - 반대로 여러 요청이 한 `read()`에 뭉쳐 도착할 수도 있음
- 결과적으로 한 번의 `read()` 호출이 정확히 요청 하나에 대응한다는 보장이 전혀 없음
- 이 성질이 점진적 파싱을 필요하게 만드는 근본 원인임
- 다음은 요청 하나가 여러 `read()`로 분할 도착하는 상황을 도식화한 것
```
송신 측 1회 전송:
  "GET /index.html HTTP/1.1\r\nHost: a\r\n\r\n"

수신 측 read() 3회로 분할 도착:
  read() 1회차 →  "GET /index.htm"
  read() 2회차 →  "l HTTP/1.1\r\nHo"
  read() 3회차 →  "st: a\r\n\r\n"
```
- 각 `read()` 시점에는 요청이 미완결 상태이므로, 파서는 도착한 만큼만 처리하고 나머지를 기다려야 함

## 파싱 상태의 호출 간 보존
- 점진적 파싱(incremental parsing)이란 데이터가 도착하는 대로 조각씩 처리하고, 미완결이면 멈췄다가 다음 조각이 오면 이어서 처리하는 방식을 가리킴
    - "incremental"은 "증분의, 조금씩 늘어나는"이라는 뜻으로, 입력을 한 번에 다 받지 않고 증가분마다 처리함을 나타냄
- 이 방식이 성립하려면 파서의 진행 상태가 `parse()` 호출과 호출 사이에 살아남아야 함
- 보존해야 하는 상태는 세 가지임
    - 누적 버퍼(`buffer_`) — 지금까지 도착한 모든 바이트를 이어 붙여 보관함
    - 파싱 커서(`offset_`) — 버퍼에서 어디까지 파싱했는지 가리키는 위치
    - 파싱 단계(`state_`) — 현재 요청 라인을 읽는 중인지, 헤더를 읽는 중인지 나타내는 상태 값
- 세 값을 지역 변수가 아니라 파서 객체의 멤버 변수로 승격시켜야 호출 간에 보존됨
    - 지역 변수는 함수가 반환되는 순간 소멸하므로 다음 호출에서 진행 상황을 알 수 없음
    - 멤버 변수는 객체가 살아 있는 한 유지되므로 다음 `parse()` 호출이 이전 진행 지점을 그대로 이어받음
- 상태를 멤버로 보존하는 헤더 선언은 다음과 같음

```cpp
// include/http/HttpRequestParser.h
class HttpRequestParser{
public:
    enum class Result { Ok, Incomplete, Error };
    Result parse(const char* data, size_t len);

private:
    enum class State { RequestLine, Headers, Done };

    // 아래 세 멤버가 parse() 호출 간에 보존되는 상태
    std::string buffer_;    // 도착한 모든 바이트 누적
    size_t offset_ = 0;     // 파싱 커서 (다음에 읽을 위치)
    State state_ = State::RequestLine;      // 현재 파싱 단계
};
```

## 재개 파싱 모델
- 재개(resume) 파싱이란 매 호출마다 버퍼 처음부터 다시 훑지 않고, 저장된 `state_`와 `offset_`부터 이어서 파싱하는 방식을 가리킴
- `parse()` 진입부의 구조는 "새 데이터 이어 붙이기 → 저장된 상태부터 재개"의 두 단계로 구성됨
    - 도착한 데이터를 `buffer_` 끝에 이어 붙임
    - `offset_`을 0으로 재초기화하지 않고, 보존된 값 그대로 그 위치부터 파싱을 재개함
- 상태 머신(state machine)이란 현재 상태에 따라 실행할 처리가 달라지고, 처리 결과로 다음 상태가 결정되는 구조를 가리킴
    - 여기서는 `State::RequestLine → Headers → Done`으로 전이함
    - 각 상태를 담당하는 멤버 함수(`parseRequestLine`, `parseHeaders`)가 공유 `offset_`과 `buffer_`를 보고 자기 몫만 처리함
- 재개 구조의 `parse()` 골격은 다음과 같음

```cpp
// src/http/HttpRequestParser.cpp
HttpRequestParser::Result
HttpRequestParser::parse(const char* data, size_t len){
    // 1) 도착한 데이터를 누적 버퍼 끝에 이어 붙임
    buffer_.append(data, len);

    // 상한 초과 검사 (뒤 절에서 상술)
    if (buffer_.size() > kMaxHeaderBytes){
        return Result::Error;
    }

    // 2) offset_을 0으로 재초기화하지 않음 - 보존된 값부터 재개
    //    상태 머신 루프: 저장된 state_부터 이어서 처리
    while (true){
        switch (state_){
            case State::RequestLine: {
                Result r = parseRequestLine();  // offset_·buffer_ 공유
                if (r != Result::Ok) return r;  // Incomplete/Error면 그 자리에서 멈춤
                state_ = State::Headers;        // 성공 시 다음 상태로 전이
                break;
            }
            case State::Headers: {
                Result r = parseHeaders();
                if (r != Result::Ok) return r;
                state_ = State::Done;
                break;
            }
            case State::Done:
                return Result::Ok;
        }
    }
}
```
- 세 가지 반환값의 계약은 다음과 같음
    - `Ok` - 요청 하나가 완결됨(`state_ == Done`)
    - `Incomplete` - 데이터가 부족해 미완결이며, 다음 `parse()` 호출이 이어받아야 함
    - `Error` - 파싱 불가능한 입력이나 상한 초과임
- 멤버 상태가 호출 간에 어떻게 이어지는지를 나타낸 것임

```
parse() 1회차: buffer_="GET /index.htm"
    parseRequestLine → CRLF 못 찾음 → Incomplete
    (state_=RequestLine, offset_=0 그대로 보존)

parse() 2회차: buffer_="GET /index.html HTTP/1.1\r\nHo"
    parseRequestLine → CRLF 찾음 → offset_=26으로 전진, Ok
    state_=Headers로 전이
    parseHeaders → 헤더 CRLF 못 찾음 → Incomplete
    (state_=Headers, offset_=26 보존)

parse() 3회차: buffer_="...Host: a\r\n\r\n"
    parseHeaders → offset_=26부터 재개, 빈 줄까지 파싱 → Ok
    state_=Done
```

## 멱등성 검증
- 여기서 요구되는 성질은 정확히는 분할 등가성(split-equivalence)
    - 하나의 요청을 여러 청크로 나눠 순서대로 넣은 결과가, 같은 요청을 한 번에 넣은 결과와 완전히 동일해야 함
    - HTTP 메서드의 멱등성(같은 요청을 여러 번 보내도 결과가 같음)과는 다른 개념이므로 구분해야 함
- 검증 방법은 극단적으로 잘게 쪼갠 입력을 사용하는 것
    - 요청 전체를 1바이트씩 잘라 `parse()`를 반복 호출함
    - 마지막 호출 후 `state_ == Done`이어야 함
    - 추출된 method, path, version, 헤더 맵이 한 번에 넣은 경우와 정확히 일치해야 함
- 1바이트 분할이 모든 청크 경계 조합 중 가장 가혹한 경우이므로, 이를 통과하면 임의 분할에서도 안전함이 강하게 보장됨

## CRLF 청크 경계 분할
- CRLF는 Carriage Return(`\r`, 0x0D)과 Line Feed(`\n`, 0x0A) 두 바이트로 이루어진 줄 종결 시퀀스를 가리킴
    - HTTP/1.1은 요청 라인과 각 헤더 줄의 끝을 CRLF로 표시함
    - 헤더 영역의 끝은 빈 줄, 즉 연속된 CRLF CRLF로 표시함
- 이번 절의 핵심 함정은 이 두 바이트가 서로 다른 청크로 갈라져 도착하는 경우
    - `\r`까지만 도착하고 `\n`은 다음 `read()`에 오는 상황
- 잘못된 처리는 버퍼 끝에서 `\r`을 만났을 때 이를 CRLF의 시작으로 간주해 소비해버리는 것
    - 아직 `\n`이 도착하지 않았으므로 CRLF는 미완성 상태임
    - 이때 `offset_`을 `\r` 다음으로 전진시키면, 다음 청크로 도착한 `\n`이 그 다음 줄(헤더 값 등)의 일부로 잘못 해석됨
- 올바른 처리는 버퍼 끝에 고립된 `\r`을 만나면 CRLF 미완성으로 판단하고 `Incomplete`를 반환하는 것임
    - `offset_`을 전진시키지 않고 `\r` 위치 그대로 멈춤
    - 다음 청크로 `\n`이 도착한 뒤 재개하면 완전한 CRLF를 인식함
- 다음은 `find_crlf`가 이 경계 조건을 처리하는 구현임

```cpp
// src/http/HttpRequestParser.cpp 내 익명 네임스페이스
// buffer_ 안에서 start부터 CRLF를 탐색함
// 반환: CRLF의 \r 위치. 못 찾거나 미완성이면 npos.
namespace {
    size_t find_crlf(const std::string& buf, size_t start){
        for (size_t i = start; i<buf.size(); ++i){
            if (buf[i] == '\r'){
                // \r이 버퍼 맨 끝이면 \n이 아직 안 온 것 → 미완성
                if (i + 1 >= buf.size()){
                    return std::string::npos;   // Incomplete로 이어짐
                }
                // \r 다음이 \n일 때만 완전한 CRLF
                if (buf[i+1] == '\n'){
                    return i;   // \r의 위치 반환
                }
            }
        }
        return std::string::npos;
    }
}
```
- 이 함수를 호출하는 `parseRequestLine`은 반환값에 따라 다음과 같이 분기함
```cpp
HttpRequestParser::Result
HttpRequestParser::parseRequestLine(){
    size_t crlf = find_crlf(buffer_, offset_);
    if (crlf == std::string::npos){
        return Result::Incomplete;  // \r 고립 포함, offset_ 전진 안 함
    }

    // [offset_, crlf) 구간이 요청 라인 본문
    // ... method/path/version 파싱 ...

    offset_ = crlf + 2; // \r\n 두 바이트를 건너뛰어 다음 줄로 전진
    return Result::Ok;
}
```
- 반드시 요청 라인을 `\r`에서 정확히 자르는 청크를 넣는 테스트로 이 경계를 재현해 검증해야 함
> 버퍼 끝의 고립된 `\r`은 소비하지 말고 `Incomplete`로 멈춤\
> `\r`을 소비하면 다음 청크의 `\n`이 다음 줄로 새어 들어가는 버그가 발생함

## Offset 전진 계약
- 재개 파싱 모델에서는 각 파싱 함수가 "자기가 소비한 만큼만 `offset_`을 전진시킨다"는 계약을 지켜야 함
    - `offset_`이 멤버로 살아 있으므로, 한 함수가 잘못 전진시키면 그 오류가 다음 호출·다음 함수로 그대로 전파됨
- 요청 라인 파싱이 성공하면 `offset_ = crlf + 2`로 전진해야 함
    - `crlf`는 `\r`의 위치이므로, `+2`는 `\r`과 `\n` 두 바이트를 모두 건너뛴 지점을 가리킴
    - 이 전진이 멤버 상태에 반영되어야 다음에 호출되는 `parseHeaders`가 요청 라인 바이트를 헤더로 재파싱하지 않음
- 전진이 누락되거나 `+1`만 되면 다음 파싱 단계가 남은 `\n`이나 요청 라인 잔여 바이트를 잘못 읽음
- 실패하기 쉬운 두 지점을 함께 점검해야 함
    - 재개 분기가 늘어나면서 non-void 함수의 어떤 경로에서 `return`이 누락되는 경우
        - 모든 종료 경로가 `Ok`/`Incomplete`/`Error` 중 하나를 반드시 반환하는지 확인해야 함
    - `parse()` 진입부에 `offset_`을 0으로 재초기화하거나 지역변수 `offset`을 새로 선언하는 잔재가 남는 경우
        - 이 초기화가 남으면 매 호출이 버퍼 처음부터 다시 파싱해 재개 모델 전체가 무력화됨
        - 진입부에서 멤버 `offset_`을 그대로 사용하는지, 동명의 지역 변수로 가리지 않는지 확인해야 함

## 최대 헤더 크기 상한
- slowloris는 헤더를 아주 느리게 조금씩 보내 연결을 오래 붙잡아 두는 공격 기법을 가리킴
    - 완결되지 않는 요청을 계속 흘려보내면, 재개 파싱 구조에서는 `buffer_`가 무한히 커질 수 있음
- 이를 막는 최소한의 방어가 최대 헤더 크기 상한임
    - 헤더 영역이 완결되기 전까지 누적될 수 있는 바이트 수의 상한을 상수 하나로 정의함
    - `buffer_.size()`가 이 상한을 넘으면 `Error`를 반환하고 연결을 정리함

```cpp
// 헤더 누적 바이트 상한 (예시 값)
static constexpr size_t kMaxHeaderBytes = 8 * 1024;

// parse() 진입부, append 직후 검사
if (buffer_.size() > kMaxHeaderBytes){
    return Result::Error;
}
```
- 이 상한은 정교한 방어가 아니라 무한 누적을 끊는 안전장치임을 명확히 해야 함
    - 타임아웃 기반의 정교한 slowloris 방어는 별도 계층에서 다뤄야 함
    - 지금 단계에서는 크기상한 하나로 무한 누적만 차단함

## append 후 포인터 안전성
- `std::string::append`는 문자열 뒤에 데이터를 이어 붙이는 연산임
    - 이어 붙인 결과가 현재 용량(capacity)을 초과하면 더 큰 메모리 블록을 새로 할당하고 기존 내용을 복사한 뒤 옛 블록을 해제함
    - 이 재할당(reallocation)이 일어나면, 재할당 이전에 얻어 둔 내부 버퍼 포인터(`buffer_.data()`)와 이터레이터가 모두 무효화됨
- 현재 설계가 이 무효화로부터 안전한 이유는 다음과 같음
    - 매 `parse()` 진입에서 파싱에 사용할 포인터를 새로 얻고, 오래된 포인터를 호출 간에 보관하지 않음
    - 파싱은 포인터 대신 `buffer_`와 정수 `offset_`으로 위치를 표현하므로, 재할당으로 기반 주소가 바뀌어도 `offset_`이 가리키는 논리적 위치는 그대로 유효함
- 이 안전성은 위치를 포인터가 아닌 정수 오프셋으로 다루기 때문에 성립함을 코드 주석으로 남겨 두어야 함
```cpp
buffer_.append(data, len);
// 주의: 여기서 append가 재할당을 일으키면 이전 buffer_.data()는 무효화됨.
// 지금은 파싱 위치를 포인터가 아닌 정수 offset_으로만 다루므로 안전함.
// 이후 문자열 뷰(string_view)로 버퍼 구간을 참조하게 되면,
// 이 append 재할당이 곧 뷰 무효화로 직결되므로 그때는 별도 처리가 필요함.
```
