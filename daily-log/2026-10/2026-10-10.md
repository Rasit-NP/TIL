## 인덱스 탐색 비용
- 디스크 기반 데이터베이스의 조회 시간은 키 비교 횟수보다, 디스크에서 읽어 오는 페이지 수와 그 페이지를 읽는 순서에 좌우됨
- 풀 테이블 스캔(full table scan)
    - 인덱스를 쓰지 않고 테이블의 모든 행을 처음부터 끝까지 읽는 접근 방식
    - 이 문서에서는 줄여서 풀 스캔이라고도 씀
- 인덱스가 없으면 조건에 맞는 행을 모두 찾기 위해 풀 스캔으로 테이블의 모든 페이지를 읽어야 함
- InnoDB
    - MySQL에서 테이블 데이터의 저장과 읽기를 담당하는 기본 스토리지 엔진

### 페이지(page)
- DBMS가 디스크와 메모리 사이에서 데이터를 주고받는 고정 크기의 최소 단위
- InnoDB의 기본 페이지 크기는 16KB이며, 인스턴스 초기화 시점의 `innodb_page_size` 설정으로 정해짐
- InnoDB에서 B+Tree 노드 하나는 페이지 하나에 대응함
- 행 하나만 필요해도 그 행이 들어 있는 페이지 전체를 읽음
- 버퍼 풀(buffer pool)
    - InnoDB가 디스크에서 읽은 페이지를 보관해 두는 메모리 캐시 영역
    - 필요한 페이지가 버퍼 풀에 있으면 디스크 I/O 없이 읽히고, 없을 때만 디스크 읽기가 발생함
- 따라서 인덱스 탐색 비용은 접근하는 페이지 수와, 그중 버퍼 풀에 없는 페이지를 어떤 순서로 읽는지로 정해짐

### 팬아웃(fan-out)
- 트리의 노드 하나가 가리키는 자식 노드의 수
- B+Tree의 내부 페이지 항목은 키와 자식 페이지 번호뿐이므로, BIGINT처럼 짧은 키라면 16KB 페이지 하나에 자식 포인터 수백 개가 들어감
- MySQL 8.0.46에서 BIGINT와 DATETIME 두 컬럼으로 만든 30만 항목 인덱스의 페이지를 확인한 결과는 아래와 같음

| 페이지 | 항목당 크기 | 페이지당 항목 수 |
|------|-----------|--------------|
| 리프 | 약 26바이트 | 613 |
| 루트 | 약 30바이트 | 490(리프 490장 전체를 가리킴) |

- 루트 한 장이 리프 전체를 가리키므로 이 인덱스의 높이는 2이며, 높이가 1 늘 때마다 담을 수 있는 항목 수는 수백 배씩 늘어남
- 키가 길어지면 페이지당 항목 수가 줄어 팬아웃이 작아지고, 같은 행 수를 담는 데 필요한 페이지 수와 높이가 늘어남
- 루트와 내부 페이지는 모든 탐색이 거쳐 가는 소수의 페이지이므로, 이들이 버퍼 풀에 있으면 한 인덱스에서 키 하나를 찾는 탐색의 디스크 읽기는 많아야 리프 페이지 1회로 줄어듦

### I/O 접근 패턴
- 랜덤 I/O(random I/O)
    - 디스크상 위치가 서로 떨어진 페이지를 하나씩 따로 요청해 읽는 접근
- 순차 I/O(sequential I/O)
    - 디스크상 이어진 페이지를 차례로 읽는 접근
- 하드 디스크는 랜덤 I/O마다 헤드 이동과 회전 대기가 발생하므로, 같은 양을 읽어도 순차 I/O보다 느림
- InnoDB는 순차 접근을 감지하면 다음 페이지 묶음을 미리 읽음
    - 익스텐트(extent)
        - InnoDB 데이터 파일 안에서 연속한 페이지를 묶은 단위로, 16KB 페이지 기준 64개 페이지(1MB)
    - 한 익스텐트에서 순차로 읽은 페이지 수가 `innodb_read_ahead_threshold`(기본값 56) 이상이면, 다음 익스텐트 전체를 비동기로 미리 읽음
    - 이 동작을 선형 미리 읽기(linear read-ahead)라 부르며, 흩어진 페이지 접근은 순차 패턴이 아니므로 이 미리 읽기가 시작되지 않음
- MySQL 문서는 대부분의 행을 읽어야 하는 쿼리에서는 디스크 탐색이 적은 순차 읽기가 인덱스를 거치는 것보다 빠르다고 설명함
- 인덱스 접근은 두 패턴이 섞인 형태임
    - 루트에서 리프까지 내려가는 탐색은 높이만큼의 페이지를 하나씩 따로 읽으므로 랜덤 접근이 됨
    - 시작 리프를 찾은 뒤의 범위 스캔은 키 순서로 연결된 리프를 차례로 따라가므로, 리프가 디스크에서도 이어져 있으면 순차 I/O가 됨

### 해시 인덱스(hash index)
- 키를 해시 함수에 넣은 결과로 항목의 저장 위치를 정하는 인덱스
- MySQL 문서가 정리한 해시 인덱스의 제약은 아래와 같음
    - `=` 또는 `<=>` 동등 비교에만 쓰이고, `<` 같은 범위 비교에는 쓰이지 않음
    - 다음 항목을 순서대로 찾을 수 없어 `ORDER BY` 최적화에 쓰이지 않음
    - 두 값 사이에 행이 몇 개인지 추정할 수 없어, 어느 인덱스를 쓸지 정하는 데 필요한 범위 행 수 추정이 불가능함
    - 키 전체로만 검색할 수 있어, 여러 컬럼 키의 앞부분만으로는 행을 찾을 수 없음
- 값의 순서를 보존하는 B+Tree는 동등 비교, 범위 조건, 정렬, 앞부분 일치 검색을 한 구조로 처리
- MySQL의 `CREATE INDEX`에서 InnoDB가 허용하는 인덱스 타입은 BTREE뿐이며, HASH를 고를 수 있는 엔진은 MEMORY 등으로 한정됨

> 인덱스가 빠른 이유는 비교 횟수가 아니라 읽는 페이지 수를 트리 높이 수준으로 줄이는 데 있음\
> B+Tree는 높은 팬아웃으로 높이를 낮추고, 값의 순서를 보존해 범위 조건과 정렬까지 처리함

## 클러스터드 인덱스(clustered index)
- 리프 페이지에 행 데이터 전체를 키 순서로 저장해, 인덱스 자체가 테이블의 저장 구조가 되는 인덱스
- 인덱스로 위치를 찾은 뒤 행 데이터를 얻기까지 페이지를 몇 장 더 읽는지는, 인덱스 리프에 무엇을 저장하느냐로 정해짐
- InnoDB가 클러스터드 인덱스로 쓰는 키는 아래 순서로 정해짐
    - `PRIMARY KEY`가 있으면 기본키
    - 기본키가 없으면 모든 키 컬럼이 `NOT NULL`인 첫 번째 `UNIQUE` 인덱스
    - 둘 다 없으면 삽입 순서대로 증가하는 6바이트 행 ID로 만든 숨은 인덱스 `GEN_CLUST_INDEX`
- 테이블 데이터가 곧 클러스터드 인덱스이므로, InnoDB의 풀 테이블 스캔은 클러스터드 인덱스의 리프 페이지 전체를 읽는 동작임

### 세컨더리 인덱스(secondary index)
- 리프에 인덱스 컬럼 값과 그 행의 기본키 값을 저장하는, 클러스터드 인덱스 외의 InnoDB 인덱스
- 세컨더리 인덱스가 물리적 위치 대신 기본키 값을 가지므로, 삽입으로 페이지가 나뉘어 행이 다른 페이지로 옮겨져도 세컨더리 인덱스 항목은 바뀌지 않음

### 세컨더리 인덱스 재탐색
- 세컨더리 인덱스에서 찾은 항목마다 기본키 값으로 클러스터드 인덱스를 루트부터 다시 내려가므로, 일치 행이 k개면 클러스터드 인덱스 탐색이 k번 일어남
- 기본키 타입 비교를 제외한 이 문서의 측정은 모두 아래 테이블을 기준으로 함
```sql
-- MySQL 8.0.46, 계좌 1만 개의 거래 30만 건이 시간순으로 섞여 쌓인 테이블
CREATE TABLE account_tx (
    id         BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY,  -- 클러스터드 인덱스 키
    account_id BIGINT NOT NULL,                             -- 계좌당 거래 30건
    tx_at      DATETIME NOT NULL,
    status     CHAR(1) NOT NULL,                            -- 'D' 완료 95%, 'F' 실패 5%
    amount     DECIMAL(15,2) NOT NULL,
    ref_no     VARCHAR(20) NOT NULL,                        -- '0000012345' 형태의 숫자 문자열
    memo       VARCHAR(100),
    INDEX idx_account_at (account_id, tx_at),
    INDEX idx_status (status),
    INDEX idx_ref_no (ref_no)
);
```

- 한 계좌의 거래는 다른 계좌의 거래 사이사이에 삽입되므로, account_id = 42인 30건의 id는 4839, 14839, 24839처럼 약 1만 간격으로 흩어져 있음
- 클러스터드 인덱스 리프 한 장에는 행이 약 125개 들어가므로, 30건은 서로 다른 리프 30장에 나뉘어 있음

```
idx_account_at 리프 (account_id, tx_at, id 순 정렬)
┌──────────────────────────────────────────────────────────────┐
│ (42, 01-03, 4839) (42, 01-07, 14839) ... (42, 05-07, 294839) │  ← 30개 항목이 한 장에 연속
└──────────────────────────────────────────────────────────────┘
        │ id=4839             │ id=14839                │ id=294839
        ▼                     ▼                         ▼
  클러스터드 리프 A      클러스터드 리프 B    ...     클러스터드 리프 Z
  (행 약 125개)          (행 약 125개)                (행 약 125개)

→ 세컨더리 탐색 1회 + 클러스터드 인덱스 탐색 30회, 서로 다른 리프 30장 접근
```
- 이 리프 페이지들이 버퍼 풀에 없으면 일치 행마다 랜덤 I/O가 1회씩 발생함
- 일치 행 수가 늘수록 재탐색 비용이 비례해 늘어나 풀 스캔 비용에 가까워지며, 그 교차 지점은 선택도 항목에서 다룸

### 기본키 타입
- 기본키는 클러스터드 인덱스의 정렬 기준이자 모든 세컨더리 인덱스 항목에 복사되는 값이므로, 삽입 순서와 길이가 테이블 전체의 페이지 수에 영향을 줌
- AUTO_INCREMENT
    - 새 행을 넣을 때 기존 값보다 큰 정수를 자동으로 부여하는 MySQL 컬럼 속성
- UUID(Universally Unique IDentifier)
    - 중앙 조정 없이 생성해도 서로 겹치지 않도록 설계한 128비트 식별자로, 현재 표준은 RFC 9562
- 페이지 분할(page split)
    - 가득 찬 페이지에 레코드를 넣어야 할 때 새 페이지를 할당하고 레코드 일부를 옮겨 두 페이지로 나누는 동작
- AUTO_INCREMENT 키는 자동 부여되는 새 값이 기존 키보다 크므로 오른쪽 끝 리프에 몰리고, 삽입으로 인한 분할도 오른쪽 끝에서 일어남
- 무작위 UUID 키는 새 값이 기존 키 사이의 임의 위치에 들어가므로, 가득 찬 중간 페이지가 분할되며 반쯤 빈 페이지가 생김
- 무작위 키는 삽입마다 임의의 리프 페이지를 수정하므로, 그 페이지가 버퍼 풀에 없으면 삽입마다 디스크 랜덤 읽기가 필요함
- 기본키만 다르고 나머지 구조가 같은 20만 행 테이블 세 개의 리프 페이지 수를 InnoDB 인덱스 통계로 비교한 결과는 아래와 같음

| 기본키 타입 | 삽입 순서 | 클러스터드 인덱스 리프 | 세컨더리 인덱스 리프 |
|----------|---------|------------------|------------------|
| BIGINT | 증가 | 1,787장 | 424장 |
| BINARY(16) | 증가 | 1,888장 | 576장 |
| BINARY(16) | 무작위 | 2,656장 | 579장 |

- 키 크기가 같은 BINARY(16)끼리 비교하면, 삽입 순서가 무작위인 것만으로 클러스터드 인덱스 리프가 약 41% 늘어남
- 삽입 순서와 무관하게 기본키가 8바이트에서 16바이트로 늘자 세컨더리 인덱스 리프가 약 36%~37% 늘어남
- MySQL 문서도 기본키가 길면 세컨더리 인덱스가 공간을 더 쓰므로 짧은 기본키가 유리하다고 안내함
- UUID가 필요한 경우의 선택지
    - RFC 9562는 UUIDv4처럼 시간 순서가 없는 버전이 데이터베이스 인덱스 지역성이 나쁘다고 명시함
    - 같은 RFC의 UUIDv7은 Unix Epoch 밀리초 타임스탬프에서 나온 시간 순서 필드를 앞에 두므로, 생성 순서가 키 순서와 대체로 일치함
    - UUIDv7을 BINARY(16)로 저장하면 무작위 삽입 문제는 줄지만, BIGINT보다 긴 키라는 크기 문제는 남음
    - UUID를 36자 문자열 그대로 CHAR(36)에 저장하면 키가 더 길어져 모든 세컨더리 인덱스가 더 커짐

> 세컨더리 인덱스 조회는 일치 행마다 클러스터드 인덱스를 다시 탐색하므로, 비용이 일치 행 수에 비례함\
> 기본키는 삽입 순서로 클러스터드 인덱스의 페이지 채움률을, 길이로 모든 세컨더리 인덱스의 크기를 정함

## 인덱스 사용 조건
- 인덱스가 있어도 조건의 형태 때문에 인덱스에서 읽을 범위를 정하지 못하거나, 인덱스 대신 풀 스캔이 선택되거나, 반대로 더 느린 인덱스 경로가 선택되는 경우가 있음
- 옵티마이저(optimizer)
    - 같은 결과를 내는 여러 접근 경로의 비용을 추정해 그중 하나를 고르는 DBMS 구성 요소
- 실행 계획(execution plan)
    - 옵티마이저가 고른 테이블 접근 순서와 접근 방식의 묶음

### 실행 계획 항목
- EXPLAIN
    - 쿼리를 실행하지 않고 옵티마이저가 고른 실행 계획을 표 형태로 보여 주는 MySQL 문
- 인덱스 사용 여부를 판단할 때 보는 열은 아래와 같음

| 열 | 의미 |
|---|-----|
| `type` | 테이블 접근 방식 (MySQL 문서의 용어는 join type) |
| `key` | 실제로 선택한 인덱스이며, `NULL`이면 인덱스를 쓰지 않음 |
| `key_len` | 사용한 인덱스 키의 바이트 길이로, 여러 컬럼으로 된 인덱스의 몇 번째 컬럼까지 썼는지 가늠하는 근거 |
| `rows` | 읽어야 한다고 추정한 행 수이며, InnoDB에서는 추정치 |
| `Extra` | 접근 방식 외의 부가 정보 |

- `type`의 주요 값은 MySQL 문서가 좋은 것부터 나열한 순서로 아래와 같음
| `type` | 의미 |
|--------|-----|
| `const` | 기본키나 `UNIQUE` 인덱스의 모든 컬럼을 상수와 비교해 최대 1행을 읽음 |
| `ref` | 유일하지 않은 인덱스나 인덱스의 왼쪽 일부로 등치 조회 |
| `range` | 인덱스로 주어진 구간의 행만 읽음 |
| `index` | 인덱스 트리 전체를 훑음 |
| `ALL` | 풀 테이블 스캔 |

- 인덱스 컨디션 푸시다운(index condition pushdown, ICP)
    - 인덱스 컬럼만으로 평가할 수 있는 `WHERE` 조건을 스토리지 엔진이 인덱스 항목 단계에서 먼저 검사해, 맞지 않는 항목의 행 읽기를 생략하는 MySQL 최적화
- `Extra`의 주요 값은 아래와 같음

| `Extra` | 의미 |
|---------|-----|
| `Using where` | `WHERE` 조건으로 행을 걸러 냄 |
| `Using index` | 인덱스만으로 필요한 컬럼을 모두 얻어 행 읽기를 생략함 |
| `Using index condition` | 인덱스 컨디션 푸시다운이 적용됨 |

- 실습 테이블에서 조건별 실행 계획은 아래와 같음

```
-- EXPLAIN 출력 중 일부 열 (BIGINT 8바이트, DATETIME 5바이트)
조건                                              type   key             key_len  rows    Extra
id = 100                                          const  PRIMARY         8        1       NULL
account_id = 42                                   ref    idx_account_at  8        30      NULL
account_id = 42 AND DATE(tx_at) = '2026-03-05'    ref    idx_account_at  8        30      Using index condition
account_id = 42 AND tx_at >= '2026-03-05'
                AND tx_at <  '2026-03-06'         range  idx_account_at  13       1       Using index condition
ref_no = 12345                                    ALL    NULL            NULL     297724  Using where
ref_no = '0000012345'                             ref    idx_ref_no      82       1       NULL
account_id = '42'                                 ref    idx_account_at  8        30      Using index condition
ref_no LIKE '%12345'                              ALL    NULL            NULL     297724  Using where
ref_no LIKE '00000123%'                           range  idx_ref_no      82       100     Using index condition
```
- 풀 테이블 스캔의 `rows`가 30만이 아니라 297,724로 나온 것은 InnoDB의 `rows`가 추정치이기 때문임
- `key_len` 13은 account_id(8바이트)와 tx_at(5바이트)를 모두 탐색에 썼다는 뜻이고, 8은 account_id까지만 썼다는 뜻임

### 탐색 구간
- 인덱스의 정렬 순서에서 읽기 시작할 위치와 멈출 위치로 정해지는, 연속해서 읽을 인덱스 항목의 범위
- MySQL의 범위 최적화(range optimization)는 인덱스 컬럼을 상수와 비교하는 조건(`=`, `<`, `>`, `BETWEEN`, `IN()`, 와일드카드로 시작하지 않는 `LIKE` 등)에서만 탐색 구간을 만듦
- `DATE(tx_at)`처럼 컬럼에 함수를 씌운 조건은 이 형태가 아니므로 tx_at의 탐색 구간을 만들지 못함
    - DATE()는 값의 순서를 보존하는 함수라서 일치 항목이 인덱스에서 연속해 있는데도, 실행 계획의 `key_len`은 8로 account_id까지만 탐색에 쓰였음
    - 함수가 순서를 보존하지 않으면(문자열 중간을 자르는 SUBSTRING 등) 일치 항목이 정렬 순서상 흩어져 있어 애초에 하나의 구간이 아님
    - `Using index condition`은 `DATE(tx_at)` 조건이 탐색 구간이 아니라 인덱스 항목 단계의 필터로 쓰였음을 나타냄
- 같은 조건을 컬럼 범위(`tx_at >= '2026-03-05' AND tx_at < '2026-03-06'`)로 다시 쓰면 `key_len`이 13으로 늘어 tx_at까지 탐색 구간에 쓰임
- 암묵적 형변환(implicit type conversion)
    - 비교하는 두 값의 타입이 다를 때 DBMS가 명시적 지시 없이 한쪽 또는 양쪽을 다른 타입으로 바꾸는 동작
- MySQL은 문자열과 숫자를 비교할 때 둘 다 부동소수점 수로 바꿔 비교함
- 문자열 컬럼 ref_no를 숫자 12345와 비교하면, '12345', ' 12345', '000012345'처럼 서로 다른 여러 문자열이 같은 숫자가 되므로 문자열 순서로 정렬된 인덱스로는 구간을 정할 수 없음
- 반대로 숫자 컬럼 account_id를 문자열 상수 '42'와 비교한 조건은 실행 계획에서 `ref`로 인덱스를 사용했으므로, 인덱스를 막는 경우는 문자열 컬럼 값이 숫자로 변환되는 쪽
- `LIKE`의 상수 문자열이 와일드카드로 시작하지 않으면, 고정된 앞부분으로 탐색 구간을 만들 수 있음
    - `LIKE '00000123%'`는 '00000123' 이상 '00000124' 미만 구간만 읽는 `range`로 실행됨
- `LIKE '%12345'`처럼 와일드카드로 시작하면 고정된 앞부분이 없어 정렬 순서에서 시작 위치를 정할 수 없으므로 전체를 읽음

### 선택도(selectivity)
- 조건을 만족하는 행 수를 전체 행 수로 나눈 비율
- 인덱스 선택도라는 말은 카디널리티를 전체 행 수로 나눈 값을 가리키기도 하므로, 조건의 일치 비율과는 문맥으로 구분함
- 값이 고르게 분포하면 등치 조건의 선택도는 1/카디널리티에 가까워짐
- 세컨더리 인덱스 경로의 비용은 일치 행 수만큼의 클러스터드 인덱스 재탐색이고, 풀 스캔의 비용은 모든 리프를 순서대로 읽는 비용이므로, 일치 비율이 클수록 풀 스캔이 유리해짐
- MySQL 문서에 따르면 예전에는 최적 인덱스가 테이블의 30%를 넘는지로 풀 스캔 여부를 정했지만, 현재는 고정 비율이 아니라 테이블 크기, 행 수, I/O 블록 크기 등을 반영한 비용 추정으로 정함
- 실습 테이블에서 status 조건의 실행 시간을 측정한 결과는 아래와 같음
    - 측정 중 디스크 페이지 읽기가 0회였으므로, 모든 페이지가 버퍼 풀에 있는 상태의 결과임
    - 풀 스캔 시간은 `IGNORE INDEX (idx_status)`로 인덱스를 제외해 측정함

| 조건 | 실제 일치 행 | 실행 계획 `rows` | 옵티마이저 선택 | 인덱스 경로 | 풀 스캔 |
|-----|-----------|----------------|-------------|----------|-------|
| status = 'D' | 285,000 | 148,675 | idx_status | 0.32~0.45초 | 0.05~0.07초 |
| status = 'F' | 15,000 | 27,324 | idx_status | 0.025~0.028초 | 0.046~0.067초 |

- 일치 비율 95%인 'D'는 인덱스 경로가 28만 5천 번 재탐색해 풀 스캔보다 4배 이상 느렸음
- 디스크 I/O가 없는 상태에서도 차이가 난 것은 일치 행마다 클러스터드 인덱스를 루트부터 다시 내려가는 비용 때문이며, 페이지를 디스크에서 읽어야 하면 이 재탐색이 랜덤 I/O가 됨
- 옵티마이저는 285,000행을 148,675행으로 추정한 상태로 'D'에도 인덱스 경로를 골랐으며, `rows`가 추정치인 이상 추정이 실제 분포와 어긋나면 더 느린 경로가 선택될 수 있음
- 일치 비율 5%인 'F'는 인덱스 경로가 더 빨랐으므로, 값 종류가 적은 컬럼이라도 분포가 치우쳐 있으면 드문 값 조회에는 인덱스가 유효함
- 성별처럼 값 종류가 적고 고르게 분포한 컬럼은 어느 값으로 조회해도 일치 비율이 커서, 인덱스 경로가 풀 스캔보다 이점이 작거나 오히려 느림

### 인덱스 유지 비용
- 세컨더리 인덱스는 각각의 별개의 B+Tree이므로 INSERT와 DELETE는 모든 세컨더리 인덱스를 고치고, UPDATE는 바뀐 컬럼을 포함하는 세컨더리 인덱스만 고침
    - InnoDB는 세컨더리 인덱스 컬럼이 바뀌면 기존 항목에 삭제 표시를 하고 새 항목을 삽입하며, 삭제 표시된 항목은 나중에 물리적으로 제거함
- 세컨더리 인덱스마다 페이지가 따로 필요하고 항목마다 기본키가 복사되므로, 인덱스가 늘수록 디스크 공간과 버퍼 풀을 더 차지함
- 버퍼 풀을 여러 인덱스의 페이지가 나눠 쓰면, 조회에 필요한 페이지가 버퍼 풀에서 밀려나 디스크 읽기가 늘어날 수 있음

> 인덱스는 조건이 인덱스 컬럼과 상수의 비교 형태로 남아 있을 때만 탐색 구간을 만들고, 세컨더리 인덱스 경로는 일치 비율이 낮을 때 풀 스캔보다 빠름\
> `rows`는 추정치이므로, 실행 계획에서 인덱스 사용 여부와 함께 추정 행 수가 실제와 맞는지도 확인함

## 복합 인덱스
- 여러 컬럼을 정해진 순서로 묶어 하나의 키로 정렬한 인덱스이며, MySQL 문서의 용어는 multiple-column index
- 단일 컬럼 인덱스는 다른 컬럼 조건으로 탐색 구간을 더 좁히지 못하고, 일치 행마다 생기는 재탐색도 줄이지 못함

### 왼쪽 접두사(leftmost prefix)
- 복합 인덱스의 첫 컬럼부터 빠짐없이 이어지는 앞쪽 컬럼들
- 복합 인덱스는 첫 컬럼으로 정렬하고, 첫 컬럼 값이 같은 항목 안에서만 둘째 컬럼으로 정렬함
- 따라서 둘째 컬럼만의 조건에 맞는 항목은 인덱스 전체에 흩어져 있으며, 왼쪽 접두사에 대한 조건만 탐색 구간을 만듦
- 인덱스 스킵 스캔(skip scan)
    - 앞 컬럼의 서로 다른 값마다 뒤 컬럼 조건으로 구간 스캔을 반복해, 앞 컬럼 조건 없이 복합 인덱스를 쓰는 MySQL 8.0.13 이상의 접근 방식
    - 앞 컬럼을 건너뛰며 읽는다는 뜻에서 붙은 이름
    - 단일 테이블 쿼리일 것, `GROUP BY`와 `DISTINCT`가 없을 것, 쿼리가 참조하는 컬럼이 모두 그 인덱스에 있을 것, 건너뛴 컬럼 뒤 컬럼에 범위 조건이 있을 것 등의 조건을 모두 만족할 때 적용될 수 있음
- 실습 테이블에서 tx_at 하루 범위만 조건으로 주면 결과는 조회 컬럼에 따라 갈림
    - account_id와 tx_at만 조회하면 `range`, `Using where; Using index for skip scan`으로 실행됨
    - `SELECT *`로 조회하면 `ALL`로 풀 스캔됨
- 따라서 왼쪽 접두사 규칙은 인덱스에 없는 컬럼을 읽는 쿼리에서는 그대로 성립함
- MySQL 문서에 따르면 옵티마이저는 키 컬럼 조건이 `=`, `<=>`, `IS NULL`인 동안 다음 키 컬럼까지 탐색 구간에 포함하고, `>`, `<`, `BETWEEN`, `LIKE` 같은 범위 조건을 만나면 그 컬럼까지만 구간에 씀
- 범위 조건 뒤 컬럼은 범위 안에서 정렬되어 있지 않으므로, 범위를 더 좁히는 데 쓰이지 않음
- 따라서 등치 조건 컬럼을 앞에, 범위 조건 컬럼을 뒤에 둠
- account_id = 42이고 tx_at이 3월인 거래 7건을 두 순서의 인덱스로 조회한 결과는 아래와 같음
    - 읽은 인덱스 항목 수는 인덱스 컨디션 푸시다운을 끈 상태에서 `Handler_read_next`로 세고, 실행 시간은 기본 설정에서 잼

| 인덱스 | 탐색 구간 | 읽은 인덱스 항목 | 실행 시간 |
|------|---------|--------------|---------|
| (account_id, tx_at) | account_id = 42 안의 3월 | 7 | 약 0.3~0.4ms |
| (tx_at, account_id) | 3월 전체 | 72,390 | 약 7.5~9.8ms |

- 두 경우 모두 실행 계획의 `key_len`은 13이었으므로, `key_len`만으로는 뒤 컬럼이 탐색 구간을 좁혔는지 판단할 수 없음
- 모든 컬럼이 등치 조건이면 컬럼 순서와 관계없이 같은 항목들로 구간이 좁혀지므로, 이때의 순서는 카디널리티보다 다른 쿼리가 왼쪽 접두사를 공유할 수 있는지로 정함
- (account_id, tx_at) 인덱스 하나가 account_id 단독 조회와 account_id + 기간 조회를 모두 처리하므로, account_id 단일 인덱스를 따로 만들 필요가 없고 인덱스 유지 비용도 줄어듦

### 커버링 인덱스(covering index)
- 쿼리가 필요로 하는 컬럼을 모두 포함해, 테이블 행을 읽지 않고 인덱스만으로 결과를 만들 수 있는 인덱스
- 커버링 여부는 SELECT 목록뿐 아니라 WHERE 등 쿼리가 그 테이블에서 참조하는 모든 컬럼으로 판단함
- InnoDB 세컨더리 인덱스는 항목마다 기본키를 가지므로, 인덱스 정의에 없는 기본키 컬럼을 함께 조회해도 커버링이 성립함

```sql
-- idx_account_at (account_id, tx_at), 항목에 id가 함께 저장됨
SELECT id, tx_at FROM account_tx WHERE account_id = 42;          -- ref, Extra: Using index (재탐색 0회)
SELECT id, tx_at, amount FROM account_tx WHERE account_id = 42;  -- ref, Extra: NULL (amount 때문에 재탐색 30회)
```

- 일치 비율이 큰 조건에서도 커버링이 성립하면 비용이 달라짐
    - `SELECT COUNT(*) FROM account_tx WHERE status = 'D'`는 `Using where; Using index`로 실행되어, 클러스터드 인덱스(리프 2,401장)를 거치지 않고 idx_status(리프 287장) 안에서만 읽음
- `type`의 `index`는 인덱스 트리 전체를 훑는 접근 방식이고 `Extra`의 `Using index`는 행 읽기를 생략했다는 표시이므로, 둘은 서로 다른 정보임
- 커버링 인덱스의 경계 조건은 아래와 같음
    - `SELECT *`처럼 인덱스 밖 컬럼을 하나라도 참조하면 재탐색이 다시 생김
    - InnoDB 세컨더리 인덱스 항목에는 트랜잭션 정보를 담는 숨은 시스템 컬럼이 없음
    - 그래서 세컨더리 인덱스 항목이 삭제 표시되었거나 그 페이지가 더 최근 트랜잭션에 의해 갱신된 경우, InnoDB는 커버링 기법을 쓰지 않고 클러스터드 인덱스에서 레코드 버전을 확인함
    - 커버링을 위해 컬럼을 덧붙일수록 항목이 커져 팬아웃이 줄고, 인덱스 유지 비용이 늘어남

> 복합 인덱스는 등치 조건 컬럼을 앞에, 범위 조건 컬럼을 뒤에 둠\
> 커버링 인덱스는 재탐색을 없애므로, 일치 행이 많은 조회의 비용을 인덱스를 읽는 비용으로 줄임

## 정리
```

    ├── 인덱스 탐색 비용
    │     ├── 페이지 단위 I/O (16KB, 버퍼 풀)
    │     ├── 높은 팬아웃 → 낮은 높이 → 적은 페이지 접근
    │     ├── 랜덤 I/O와 순차 I/O (선형 미리 읽기)
    │     └── 해시 인덱스 : 동등 비교만 가능, 범위·정렬 불가
    │
    ├── 클러스터드 인덱스
    │     ├── 클러스터드 리프 = 행 데이터, 세컨더리 리프 = 컬럼 값 + 기본키
    │     ├── 재탐색 : 일치 행마다 클러스터드 인덱스를 다시 탐색
    │     └── 기본키 타입 : 삽입 순서 → 페이지 채움률, 길이 → 세컨더리 인덱스 크기
    │
    ├── 인덱스 사용 조건
    │     ├── 실행 계획 : type · key · key_len · rows · Extra
    │     ├── 탐색 구간 생성 불가 : 함수를 씌운 컬럼, 문자열 컬럼의 숫자 비교, 앞쪽 와일드카드
    │     ├── 선택도 : 일치 비율이 크면 풀 스캔이 유리, rows는 추정치
    │     └── 유지 비용 : 쓰기 증가, 공간·버퍼 풀 점유
    │
    └── 복합 인덱스
          ├── 왼쪽 접두사 : 등치 조건 앞 · 범위 조건 뒤, 스킵 스캔 예외
          └── 커버링 인덱스 : 재탐색 제거, 기본키 자동 포함, 삭제 표시·최근 갱신 시 예외
```
