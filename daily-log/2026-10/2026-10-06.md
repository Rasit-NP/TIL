## 트랜잭션 프록시 내부 모니터
- 모니터
    - Java의 모든 객체에 연관되어 있으며, `synchronized`가 획득하고 해제하는 상호 배제용 락
- `@Transactional` 메서드에 `synchronized`를 붙이면 모니터가 보호하는 구간은 대상 메서드 본문뿐이며, 트랜잭션 프록시가 수행하는 트랜잭션 시작과 커밋은 그 바깥에 있음
- JPA와 InnoDB에서는 이 범위 차이 때문에 아래 두 경로로 앞 스레드의 차감이 덮임

### 모니터 해제 이후 UPDATE
- 메서드 본문에서 flush가 일어나지 않으면 변경 감지의 UPDATE는 커밋 직전 flush에서 실행되므로, UPDATE 자체가 모니터 해제 이후에 데이터베이스로 전송됨
    - 다음 스레드가 모니터를 얻어 SELECT하는 시점에, 앞 스레드의 UPDATE는 데이터베이스에 도착하지 않았을 수 있음
    - 도착하지 않은 변경은 어떤 격리 수준으로도 읽을 수 없으므로, 다음 스레드는 차감 전 잔액을 읽음
- 본문에서 `saveAndFlush()`로 UPDATE를 먼저 보내도 해결되지 않음
    - 모니터 해제 시점에 그 UPDATE는 아직 미커밋 상태이며, 다음 스레드의 일반 SELECT는 READ COMMITTED나 REPEATABLE READ에서 미커밋 변경을 읽지 않음
    - 다음 스레드의 UPDATE는 앞 트랜잭션의 행 락을 기다린 뒤 실행되지만, 쓰는 값은 차감 전 잔액으로 계산한 값이므로 앞 스레드의 차감이 덮임

### 모니터 획득 이전 읽기
- 메서드 일부만 `synchronized` 블록으로 감싸면, 모니터 획득 순서가 맞아도 블록 안의 읽기가 최신 값이 아닐 수 있음
- InnoDB 스냅샷 시점
    - MySQL 문서에 따르면 REPEATABLE READ의 스냅샷은 트랜잭션의 첫 스냅샷 읽기에서 정해지므로, 블록에 들어가기 전에 SELECT를 한 번이라도 수행했다면 블록 안의 SELECT도 그 이전 스냅샷을 읽음
    - 앞 스레드가 그 뒤에 커밋한 차감은 이 트랜잭션에 보이지 않음
- 영속성 컨텍스트의 기존 인스턴스
    - JPA `EntityManager.find()`는 엔티티가 이미 영속성 컨텍스트에 있으면 그 인스턴스를 반환함
    - Spring Data JPA의 `findById()`는 내부에서 `EntityManager.find()`를 호출하므로, 블록 이전에 같은 계좌를 조회했다면 블록 안의 `findById()`는 데이터베이스를 조회하지 않고 이전에 읽은 상태를 돌려줌

### 프록시 바깥 모니터
- `synchronized`를 트랜잭션 프록시를 호출하는 바깥 메서드로 옮기면, 트랜잭션 시작부터 커밋까지가 모니터 안에 들어가 단일 JVM에서는 위 두 경로가 닫힘
- 그러나 아래 한계가 남음
    - 모니터는 JVM 하나의 객체에 속하므로, 서버가 여러 대이면 서버마다 다른 모니터를 잠가 데이터베이스 행에 대한 상호 배제가 성립하지 않음
    - 싱글톤 빈처럼 하나의 객체를 잠그면, 계좌와 무관하게 모든 출금 요청이 그 모니터에서 순차 처리됨
    - 모니터를 쥔 채 데이터베이스 왕복과 커밋을 기다리므로, 대기 스레드가 요청 스레드 풀을 점유함
- 데이터가 데이터베이스 행에 있으면 상호 배제도 모든 서버가 공유하는 데이터베이스에서 걸어야 하며, 그 수단이 비관적 락과 낙관적 락임

## 비관적 락(pessimistic locking)
- 충돌을 전제로, 데이터를 읽는 시점에 데이터베이스 락을 먼저 획득해 다른 트랜잭션의 변경을 막는 동시성 제어 방식
- JPA 명세는 `PESSIMISTIC_READ`, `PESSIMISTIC_WRITE`, `PESSIMISTIC_FORCE_INCREMENT`를 장기 데이터베이스 락을 즉시 얻는 락 모드로 규정함
- 배타 락(exclusive lock)
    - 보유 트랜잭션 외에는 같은 행에 락을 걸거나 행을 변경할 수 없게 하는 락
- `PESSIMISTIC_WRITE`
    - 대상 행에 배타 락을 요청하는 JPA 락 모드
    - `LockModeType` API 문서는 엔티티를 갱신하려는 트랜잭션들을 직렬화하는 용도로 설명함

### 잠금 읽기
- 스냅샷 읽기
    - InnoDB의 일반 SELECT가 다중 버전 데이터로 특정 시점의 커밋 상태를 읽으며, 이는 행에 락을 걸지 않는 방식
    - MySQL 문서의 원문 용어는 consistent nonlocking read
- 잠금 읽기(locking read)
    - 최신 데이터를 읽으면서 읽은 행에 락을 거는 InnoDB의 SELECT로, `SELECT ... FOR UPDATE`와 `SELECT ... FOR SHARE`가 해당함
- Spring Data JPA에서는 repository 쿼리 메서드에 `@Lock`을 붙여 락 모드를 지정함
- Hibernate는 데이터베이스 제품별 SQL 차이를 처리하는 dialect 클래스로 락 모드를 SQL에 반영하며, MySQL에서 `PESSIMISTIC_WRITE`는 `SELECT ... FOR UPDATE`로 실행됨
- MySQL 문서에 따르면 `FOR UPDATE`는 최신 데이터를 읽고, 읽은 각 행에 UPDATE와 같은 락을 설정함

```java
public interface AccountRepository extends JpaRepository<Account, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select a from Account a where a.id = :id")
    Optional<Account> findByIdForUpdate(@Param("id") Long id);      // MySQL: SELECT ... FOR UPDATE
}

@Transactional
public void withdraw(Long accountId, long amount){
    Account account = accountRepository.findByIdForUpdate(accountId).orElseThrow(); // 행 배타 락 획득
    if (account.getBalance() < amount)
        throw new IllegalStateException("잔액 부족");
    account.setBalance(account.getBalance() - amount);
}   // 커밋 시점에 UPDATE 실행, 커밋과 함께 락 해제
```
```
T1                                        T2
──                                        ──
SELECT ... FOR UPDATE → 1000 (배타 락)
                                          SELECT ... FOR UPDATE → 대기
UPDATE balance = 900
COMMIT (락 해제)
                                          대기 종료 → 900 읽음 (최신 커밋 값)
                                          UPDATE balance = 800
                                          COMMIT

결과  잔액 800
```
- T2의 잠금 읽기는 T1이 끝날 때까지 대기하고, 대기가 끝나면 스냅샷이 아니라 T1이 커밋한 최신 값을 읽으므로 차감이 누적됨

### 락 보유 기간
- MySQL 문서에 따르면 잠금 읽기로 얻은 락은 문장이 끝날 때가 아니라 트랜잭션이 커밋되거나 롤백될 때 해제됨
- 따라서 락 보유 시간은 트랜잭션 길이와 같으며, 트랜잭션 안의 외부 API 호출 같은 느린 작업은 그 시간만큼 같은 행의 다른 요청을 대기시킴
- 잠기는 범위는 검색 조건이 쓰는 인덱스에 따라 달라짐
    - MySQL 문서에 따르면 REPEATABLE READ에서 유일 인덱스로 한 행을 찾으면 그 인덱스 레코드 하나만 잠김
    - 인덱스를 쓰지 못하는 조건이면 검색 중 훑은 레코드에 락이 걸려, 요청과 무관한 행까지 잠길 수 있음
- 락은 트랜잭션 안에서만 행을 보호함
    - Spring Data JPA 문서는 repository 인터페이스에 선언한 쿼리 메서드에 기본 트랜잭션 설정이 적용되지 않는다고 명시함
    - JPA `Query` API는 `NONE`이 아닌 락 모드를 설정한 쿼리를 트랜잭션 없이 실행하면 `TransactionRequiredException`을 던진다고 규정함
    - 락 조회와 이후의 UPDATE가 서비스 메서드의 같은 `@Transactional` 경계 안에 있어야 갱신 시점까지 행이 보호됨

### 락 대기 한도
- 락 대기 타임아웃
    - 다른 트랜잭션이 보유한 락을 기다리다 포기하기까지의 최대 시간
- JPA 표준은 `jakarta.persistence.lock.timeout` 힌트로 대기 시간을 밀리초 단위로 지정하게 함
    - 시간을 넘기면 `LockTimeoutException`이 발생하며, 이 경우 현재 트랜잭션은 롤백 표시되지 않음
    - 0을 지정하면 락을 즉시 얻지 못할 때 바로 예외가 발생해야 함
- MySQL에서 락 대기 시간의 기준은 InnoDB 시스템 변수 `innodb_lock_wait_timeout`이며, 단위는 초, 기본값은 50초임
- MySQL 8.0부터 SELECT 문에 대기 없이 실패하는 `NOWAIT`와 잠긴 행을 건너뛰는 `SKIP LOCKED`를 붙일 수 있으나, 대기 시간을 숫자로 적는 문법은 없음
- 대기 시간을 넘기면 MySQL은 오류 1205를 반환함
    - 기본 설정(`innodb_rollback_on_timeout` OFF)에서는 타임아웃이 난 문장만 롤백되고, 트랜잭션은 열린 채 앞서 얻은 락을 계속 보유함
    - 예외를 잡아 삼킨 뒤 커밋하면 타임아웃 이전의 변경만 부분 반영될 수 있음
    - Spring의 `@Transactional`은 기본 설정에서 런타임 예외가 메서드 밖으로 전파되면 트랜잭션 전체를 롤백함

### 데드락(deadlock)
- 둘 이상의 트랜잭션이 서로 상대가 보유한 락을 기다려 어느 쪽도 진행하지 못하는 상태
- 비관적 락은 락을 트랜잭션 끝까지 보유하므로, 이체처럼 한 트랜잭션이 두 행을 잠글 때 트랜잭션마다 잠그는 순서가 다르면 순환 대기가 생김
- InnoDB는 순환 대기를 스스로 해소함
    - 데드락 감지가 켜진 기본 설정(`innodb_deadlock_detect` ON)에서 순환을 감지하면, 삽입·갱신·삭제한 행 수가 적은 트랜잭션을 희생자로 골라 전체 롤백함
    - 희생자는 오류 1213을 받으며, 남은 트랜잭션은 그대로 진행함
    - 감지를 끄면 데드락도 `innodb_lock_wait_timeout`이 지나야 풀림
- 1213과 1205는 롤백 범위가 달라 애플리케이션의 처리도 달라짐
    - 1213은 트랜잭션 전체가 이미 롤백된 상태이므로, 남은 처리는 트랜잭션을 처음부터 다시 실행하는 것뿐임
    - 1205는 기본 설정에서 문장만 롤백되므로, 트랜잭션 전체를 롤백할지 애플리케이션이 결정해야 함
- 예방은 모든 트랜잭션이 행을 같은 순서로 잠그게 하는 것이며, 이체라면 두 계좌를 식별자 오름차순으로 잠금
- MySQL 문서는 애플리케이션 로직이 올바르더라도 트랜잭션 재시도가 필요한 경우를 처리해야 한다고 안내함

## 낙관적 락(optimistic locking)
- 충돌이 드물다고 보고 읽을 때 락을 걸지 않되, 쓰는 시점에 그 사이 다른 트랜잭션이 데이터를 바꿨는지 검사해 바뀌었으면 쓰기를 실패시키는 동시성 제어 방식
- 이름에 락이 들어가지만 읽는 구간에 데이터베이스 락을 잡지 않으므로, 동작은 충돌 예방이 아니라 충돌 검출임
- 버전 속성(version attribute)
    - `@Version`이 붙은 필드나 프로퍼티로, 영속성 제공자가 낙관적 락 검사에 쓰는 엔티티의 수정 번호 또는 타임스탬프
    - JPA 명세는 버전 매핑이 있는 엔티티를 자동으로 낙관적 락 대상으로 규정함
    - 엔티티당 하나만 둘 수 있으며, 애플리케이션은 값을 읽을 수 있지만 수정해서는 안 됨
    - 허용 타입은 `int`, `Integer`, `short`, `Short`, `long`, `Long`, `java.sql.Timestamp`이며, Jakarta Persistence 3.2 API 문서부터 `Instant`, `LocalDateTime`이 추가됨

### 버전 조건부 UPDATE
- Hibernate는 버전 속성이 있는 엔티티의 UPDATE와 DELETE마다 WHERE 절에 버전 검사를 넣고, UPDATE의 SET 절에서 버전 값을 새 값으로 바꿈
    - 숫자형 버전은 1 증가한 값으로 바뀜

```java
@Entity
public class Account{
    @Id
    private Long id;
    private long balance;

    @Version
    private Long version;   // 영속성 제공자가 읽고 증가시킴, 애플리케이션은 수정하지 않음
}
```
```sql
-- 조회 시 version = 3을 함께 읽었다면 Hibernate는 아래 UPDATE를 실행함
UPDATE account SET balance = 900, version = 4 WHERE id = 1 AND version = 3;
-- 갱신 행 수가 0이면 그 사이 다른 트랜잭션이 version을 바꾼 것으로 판정함
```
- 버전 검사와 갱신이 UPDATE 한 문장 안에서 수행되므로, 검사와 갱신 사이에 다른 트랜잭션의 쓰기가 끼어들 수 없음
- InnoDB의 UPDATE는 스냅샷이 아니라 최신 행으로 WHERE 조건을 평가하므로, 스냅샷 읽기로 옛 버전을 읽었더라도 검사는 최신 버전을 기준으로 이루어짐
- 잔액 1000인 계좌에 100원 출금 두 건이 동시에 들어오면 결과는 아래와 같음
```
MySQL InnoDB, REPEATABLE READ, 잔액 1000, version 3

T1                                        T2
──                                        ──
SELECT → 1000, version 3
                                          SELECT → 1000, version 3
UPDATE ... WHERE version = 3 → 1행 (version 4)
                                          UPDATE ... WHERE version = 3 → T1의 행 락 대기
COMMIT
                                          대기 종료, 최신 행은 version 4 → 0행 갱신
                                          충돌 예외 발생 → 롤백

결과  잔액 900  (T2의 출금은 덮어쓰기 대신 실패로 드러남)
```
- CAS(Compare-And-Swap)
    - 메모리 위치의 현재 값이 예상값과 같을 때만 새 값으로 바꾸며, 비교와 교체를 하나의 원자적 연산으로 수행하는 연산
- 버전 조건부 UPDATE는 읽어 둔 버전을 예상값으로 삼는다는 점에서 CAS와 같은 구조이며, 차이는 아래와 같음

| 구분 | CAS | 버전 조건부 UPDATE |
|-----|-----|-----------------|
| 예상값 | 읽어 둔 변수 값 | 읽어 둔 버전 값 |
| 비교와 교체의 원자성 | CPU의 원자적 명령어 | UPDATE 한 문장과 대상 행의 락 |
| 실패 신호 | `compareAndSet`의 `false` 반환 | 갱신 행 수 0, 이어서 예외 |
| 실패 후 처리 | 같은 스레드가 루프로 즉시 재시도 | 트랜잭션 롤백 후 새 트랜잭션으로 재시도 |
| 적용 범위 | 단일 JVM의 메모리 | 여러 서버가 공유하는 데이터베이스 행 |

- 낙관적 락의 재시도는 조회부터 커밋까지 트랜잭션 전체를 다시 실행하므로, 한 번의 실패 비용이 CAS 루프의 재시도보다 훨씬 큼

### 충돌 예외 발생 시점
- JPA 명세의 `OptimisticLockException`은 API 호출, flush, 커밋 중 어느 시점에서든 던져질 수 있으며, 활성 트랜잭션을 롤백 표시함
- Hibernate는 버전 검사 실패를 자체 예외(`StaleObjectStateException` 등)로 감지하고, JPA로 부트스트랩된 경우 JPA 표준 예외인 `OptimisticLockException`으로 변환함
- Spring은 이를 `ObjectOptimisticLockingFailureException`으로 변환하며, 이 클래스는 `OptimisticLockingFailureException`의 하위 클래스임
- 트랜잭션 프록시
    - `@Transactional`이 붙은 빈 대신 호출을 받아 트랜잭션을 시작하고, 대상 메서드를 호출한 뒤 커밋이나 롤백을 수행하는 Spring의 객체
- Spring의 `TransactionAspectSupport.invokeWithinTransaction()`은 대상 메서드가 정상 반환된 뒤에 커밋을 수행함
- 메서드 본문에서 flush가 일어나지 않으면 버전 조건부 UPDATE는 커밋 직전 flush에서 실행되고, 충돌 예외도 대상 메서드가 반환된 뒤에 발생함
    - 본문의 flush는 `flush()`나 `saveAndFlush()` 직접 호출, 기본 flush 모드(AUTO)에서 쿼리 실행 전에 일어나는 자동 flush로 발생함
    - 커밋 시점에 발생하는 경우 `@Transactional` 메서드 본문의 try-catch로는 이 예외를 잡을 수 없음

### 재시도 위치
- 낙관적 락은 충돌을 검출할 뿐 해결하지 않으므로, 재시도 여부와 실패 응답은 애플리케이션이 정해야 함
- 같은 트랜잭션 안에서는 재시도할 수 없음
    - 예외가 발생한 트랜잭션은 롤백 표시되어 커밋할 수 없음
    - Hibernate 문서는 예외를 받은 세션은 데이터베이스와 동기화가 깨진 상태이므로 즉시 폐기하라고 안내함
- 따라서 재시도 루프는 `@Transactional` 메서드 바깥에서, 호출할 때마다 새 트랜잭션과 새 영속성 컨텍스트가 만들어지도록 작성함
    - 같은 클래스 안의 메서드를 직접 호출하면 트랜잭션 프록시를 거치지 않아 새 트랜잭션이 시작되지 않으므로, 재시도 루프는 별도 빈에 둠

```java
@Service
public class WithdrawFacade{
    private final AccountService accountService;    // @Version 엔티티를 갱신하는 @Transactional withdraw를 가진 별도 빈

    public void withdraw(Long accountId, long amount){
        for (int attempt = 1; ; attempt++){
            try {
                accountService.withdraw(accountId, amount); // 새 호출마다 새 트랜잭션에서 최신 값을 다시 읽음
                return;
            } catch (ObjectOptimisticLockingFailureException e){
                if (attempt == 3) throw e;
            }
        }
    }
}
```

- 재시도는 최신 값으로 비즈니스 검사를 다시 수행하므로, 그 사이 잔액이 부족해졌다면 재시도에서 잔액 부족으로 정상 실패함
- 재시도 한도를 넘긴 요청은 처리하지 못했음을 사용자에게 알리며, HTTP API라면 409 Conflict 같은 상태 코드로 응답함
- 사용자가 화면에서 본 값을 근거로 내용을 통째로 바꾸는 요청은 자동 재시도에 부적합함
    - 새 트랜잭션에서 최신 값을 읽더라도 사용자의 입력으로 덮어쓰면, 그 사이 다른 사용자의 수정이 사라짐
    - 이런 요청은 재시도 대신 충돌 사실을 알리고 최신 내용을 다시 보여 줌

## 락 방식 선정 근거
- 두 방식의 선정은 충돌 빈도, 충돌 시 재시도 비용, 락 대기 비용의 트레이드오프로 결정됨
| 기준 | 비관적 락 | 낙관적 락 |
|-----|---------|---------|
| 충돌 처리 방식 | 읽을 때 락으로 대기시켜 방지 | 쓸 때 검출한 뒤 실패시킴 |
| 충돌이 없을 때의 비용 | 모든 요청이 락을 얻고 트랜잭션 끝까지 보유 | UPDATE에 버전 조건 하나 추가 |
| 충돌이 잦을 때의 비용 | 대기 시간 증가, 같은 행의 요청이 순차 처리됨 | 실패와 재시도 반복, 수행한 작업 폐기 |
| 대표 실패 형태 | 대기 타임아웃, 데드락 | 충돌 예외 |
| 적합한 상황 | 같은 행에 요청이 몰리고 실패 비용이 큼 | 충돌이 드물고 읽기 비중이 큼 |

- 충돌 빈도
    - 충돌이 잦으면 낙관적 락은 대부분의 시도가 실패하고, 재시도한 요청끼리 다시 충돌해 처리량이 떨어짐
    - 충돌이 드물면 비관적 락은 충돌하지 않을 요청에도 락 획득과 보유 비용을 치름
- 재시도 비용
    - 트랜잭션이 무겁거나 되돌리기 어려운 작업을 포함하면, 실패 후 다시 실행하는 낙관적 락의 비용이 커짐
- 락 대기 비용
    - 비관적 락을 기다리는 요청은 대기 동안 요청 스레드와 데이터베이스 커넥션을 계속 점유함
    - 락 보유 트랜잭션이 길어지면 대기 요청이 쌓여 커넥션 풀이 고갈될 수 있음
- 같은 계좌에 출금이 동시에 몰리는 경우는 충돌이 잦고 실패 응답의 비용이 크므로 비관적 락이 적합함
- 회원 정보 수정처럼 같은 행을 동시에 고칠 일이 드문 경우는 낙관적 락이 적합함

> 충돌이 잦고 실패가 비싸면 비관적 락으로 대기시키고,\
> 충돌이 드물면 낙관적 락으로 검출만 하고 충돌한 요청을 실패시킴

## 정리
```
JPA 엔티티 동시 갱신 제어
    │
    ├── 트랜잭션 프록시 내부 모니터
    │     ├── 모니터 해제 이후 UPDATE : 커밋 직전 flush가 모니터 밖에서 실행
    │     ├── 모니터 획득 이전 읽기 : 앞선 스냅샷 · 영속성 컨텍스트의 기존 인스턴스
    │     └── 프록시 바깥 모니터 : 단일 JVM 한정, 전체 요청 직렬화
    │
    ├── 비관적 락 : 읽을 때 배타 락으로 방지
    │     ├── 잠금 읽기 : PESSIMISTIC_WRITE → MySQL SELECT ... FOR UPDATE
    │     ├── 보유 기간 : 커밋·롤백까지, 트랜잭션 안에서만 유효
    │     ├── 대기 한도 : innodb_lock_wait_timeout(기본 50초), 1205는 문장만 롤백
    │     └── 데드락 : InnoDB가 감지 후 희생자 전체 롤백(1213), 잠금 순서 고정으로 예방
    │
    └── 낙관적 락 : 쓸 때 버전으로 검출
          ├── 버전 조건부 UPDATE : WHERE version = ?, CAS와 같은 구조
          ├── 충돌 예외 : flush 시점(대개 커밋 직전)에 발생, 트랜잭션 롤백 표시
          └── 재시도 위치 : 트랜잭션 바깥의 별도 빈, 한도와 실패 응답 
```
