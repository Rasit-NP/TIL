## 서블릿 컨테이너
- HTTP 요청이 Java 메서드 호출로 이어지려면 누군가 소켓에서 바이트를 받고, HTTP 메시지를 파싱하고, 처리할 스레드를 정해야 함
- 애플리케이션이 이 일을 직접 하면 모든 웹 애플리케이션이 같은 네트워크 처리 코드를 반복해서 가지게 됨
- Spring MVC는 이 일을 서블릿 컨테이너에게 맡기고, 컨테이너가 넘겨준 요청 객체로부터 처리를 시작함

### 서블릿(Servlet)
- Jakarta Servlet 명세가 정의한, HTTP 요청을 받아 응답을 만드는 Java 컴포넌트
- 요청 하나를 처리하는 진입점은 `service(ServletRequest, ServletResponse)` 메서드임
- HTTP용 구현은 `HttpServlet`을 상속하며, `service`가 HTTP 메서드에 따라 `doGet`, `doPost` 등으로 분기함
- 서블릿 컨테이너(Servlet Container)
    - 서블릿 명세를 구현해 서블릿의 생성, 요청 전달, 소멸을 관리하는 런타임
    - Tomcat과 Jetty가 대표 구현체이며, Spring Boot의 웹 스타터는 Tomcat을 내장 서버로 기본 사용함
- 서블릿 명세는 분산 환경이 아닌 기본 배치에서 서블릿 선언 하나당 인스턴스 하나만 쓰도록 규정함
    - 동시에 들어온 요청은 서로 다른 스레드가 같은 인스턴스의 `service` 메서드를 동시에 실행하는 방식으로 처리됨
    - 따라서 서블릿 인스턴스 필드에 요청별 상태를 두면 스레드 간 데이터 오염이 생김
    - 과거에는 `SingleThreadModel` 구현 서블릿이 예외였고 컨테이너가 인스턴스 풀을 둘 수 있었으나, 이 인터페이스는 Servlet 2.4에서 deprecated되고 Jakarta Servlet 6.0에서 제거됨

### 요청당 스레드 모델(thread-per-request)
- 요청 하나가 처리되는 동안 컨테이너 스레드 하나가 그 요청에 전담 배정되는 처리 방식
- 커넥터(Connector)
    - 특정 TCP 포트에서 연결을 받아 요청을 컨테이너 내부로 전달하는 Tomcat 구성 요소
- Tomcat 구현에서 요청을 실행하는 스레드는 커넥터의 워커 스레드 풀에서 꺼내 씀
    - Tomcat 설정 문서는 비동기가 아닌 요청 하나가 처리되는 동안 스레드 하나가 필요하다고 명시함
- 요청 스레드 하나가 필터 체인, DispatcherServlet, 컨트롤러, 서비스, 레포지토리 호출까지 차례로 실행함
    - 컨트롤러가 DB 응답이나 외부 API 응답을 기다리면 그 시간 동안 스레드도 함께 블록됨
    - 응답 작성이 끝나야 스레드가 풀로 반환됨
- 연결 수와 스레드 수는 1:1로 대응하지 않음
    - Tomcat의 기본 커넥터인 NIO 커넥터는 다음 요청을 기다리는 keep-alive 연결과 요청 헤더 읽기를 논블로킹으로 처리해 스레드를 점유하지 않음
    - 같은 커넥터에서 요청 본문 읽기와 응답 쓰기는 블로킹으로 동작하므로, 느리게 송신하거나 수신하는 클라이언트는 그 시간만큼 스레드를 점유함
- 단, 요청 처리 도중 컨테이너 스레드를 반납하는 Servlet 3.0의 비동기 처리를 쓰면, 요청 하나에 스레드 하나라는 대응이 성립하지 않음

### 스레드 풀 포화
- Tomcat HTTP 커넥터에서는 세 속성이 단계별로 동시 처리 한계를 정함

| 속성 | 의미 | Tomcat 기본값 |
|-----|-----|-------------|
| `maxThreads` | 요청 처리 스레드의 최대 수 | 200 |
| `maxConnections` | 서버가 수락해 관리하는 연결의 최대 수 | 8192 |
| `acceptCount` | `maxConnections` 도달 후 운영체제가 대기시키는 연결 큐의 최대 길이 | 100 |

- 기본값은 Tomcat 10.1 설정 문서 기준이며, Spring Boot는 `server.tomcat.threads.max` 같은 `server.tomcat.*` 속성으로 이 값을 노출함
- Tomcat 문서 기준으로, 동시 요청이 몰릴 때 거치는 단계는 아래와 같음

```
동시 요청 증가
  ├─ 사용 중 스레드 < maxThreads
  │      → 스레드를 추가 생성해 즉시 처리
  ├─ 스레드 소진, 연결 수 < maxConnections
  │      → 연결은 수락되지만 처리 스레드가 빌 때까지 대기
  ├─ 연결 수 = maxConnections
  │      → 운영체제 연결 큐에 적재 (최대 길이 acceptCount)
  └─ 운영체제 큐까지 가득 참
         → 새 연결이 거부되거나 타임아웃
```

- 흔한 오해
    - `acceptCount`를 스레드가 모두 바쁠 때 쓰는 요청 대기열로 설명하는 경우가 많으나, Tomcat 문서상 이 값은 `maxConnections` 도달 이후 커널이 accept 전 연결을 쌓아 두는 큐(listen backlog)의 길이임
- 경계 조건
    - Tomcat 내부 작업 큐의 최대 길이인 `maxQueueSize`의 기본값이 `Integer.MAX_VALUE`이므로, 연결 수가 `maxConnections` 아래인 동안에는 대기 작업이 거절되지 않고 응답 지연으로 나타남
- 실패 사례
    - 30초씩 지연되는 외부 API를 부르는 요청 200개만으로 워커 스레드 200개가 모두 블록됨
    - 이후 요청은 외부 API와 무관한 엔드포인트여도 스레드가 빌 때까지 대기함
    - 락 획득을 기다리며 블록된 스레드도 같은 방식으로 풀의 슬롯을 차지함
- `maxThreads`만 늘리는 대응의 한계
    - 블록의 원인이 DB 커넥션 풀 크기라면 스레드를 늘려도 대기 위치가 커넥션 풀로 옮겨갈 뿐임
    - 스레드마다 할당되는 스택 메모리 사용량이 늘고, CPU가 실행 스레드를 바꾸며 상태를 저장, 복원하는 컨텍스트 스위칭 비용도 늘어남
    - 근본 대응은 외부 호출의 타임아웃 설정과 요청 스레드 안의 블로킹 구간 축소임

## DispatcherServlet
- 서블릿만으로 웹 애플리케이션을 만들면 URL마다 서블릿을 하나씩 만들어 컨테이너에 매핑해야 함
    - 요청 파라미터 해석, 공통 예외 처리, 응답 본문 변환 코드가 서블릿마다 반복됨
    - 공통 정책을 바꾸려면 모든 서블릿을 수정해야 함

### 프론트 컨트롤러 패턴
- 프론트 컨트롤러(Front Controller)
    - 모든 요청을 먼저 받는 단일 진입점 객체가 공통 처리를 수행한 뒤, 요청별 처리 객체를 골라 위임하는 구조
    - 개별 컨트롤러들의 앞(front)에 서는 컨트롤러라는 위치를 따서 붙은 이름
- DispatcherServlet
    - Spring MVC가 프론트 컨트롤러로 사용하는 `HttpServlet` 하위 클래스
    - 이름의 dispatch는 받은 요청을 알맞은 처리 객체로 보내는 역할을 가리킴
- Spring Boot는 DispatcherServlet을 서블릿 컨테이너의 `/` 경로에 등록함
    - 서블릿 명세에서 `/` 매핑은 다른 서블릿 매핑에 걸리지 않는 요청을 받는 기본 서블릿 매핑이므로, 애플리케이션 요청이 사실상 모두 DispatcherServlet으로 모임
- 컨테이너 입장에서 DispatcherServlet도 서블릿 하나이므로, 모든 요청 스레드가 인스턴스 하나를 공유함
    - 컨트롤러 빈도 빈 정의당 인스턴스를 하나만 만드는 싱글톤 스코프이므로, 같은 이유로 요청별 상태를 필드에 두지 않아야 함

### 특수 빈
- DispatcherServlet은 요청 처리의 각 단계를 직접 구현하지 않고, 인터페이스로 정의된 협력 객체에 위임함
    - Spring 문서는 이 협력 객체를 특수 빈 타입(Special Bean Types)이라 부름

| 인터페이스 | 역할 |
|---------|-----|
| `HandlerMapping` | 요청을 처리할 핸들러와 적용할 인터셉터 목록을 찾음 |
| `HandlerAdapter` | 핸들러 타입에 맞는 방식으로 핸들러를 호출함 |
| `HandlerExceptionResolver` | 처리 중 발생한 예외를 응답으로 바꿈 |
| `ViewResolver` | 뷰 이름을 렌더링할 View 객체로 바꿈 |

- DispatcherServlet은 초기화 시 인터페이스별로 해당 타입의 빈을 모두 찾아 정렬해 보관하고, 하나도 없으면 `DispatcherServlet.properties`의 기본 구현을 사용함
    - 이 구조 덕분에 DispatcherServlet 코드를 고치지 않고 빈 등록만으로 처리 방식을 바꾸거나 확장할 수 있음

## 요청 디스패치
- 디스패치(dispatch)
    - DispatcherServlet이 `doDispatch` 메서드 안에서 핸들러를 찾아 실행하고 응답을 완성하기까지의 처리 단위
- 핸들러(handler)
    - 요청을 실제로 처리하는 객체를 가리키는 Spring MVC의 일반 명칭
    - `@RequestMapping` 기반 컨트롤러에서는 컨트롤러 빈과 실행할 메서드를 묶은 `HandlerMethod` 객체가 핸들러가 됨
    - 컨트롤러 메서드 외의 객체도 핸들러가 될 수 있으므로 컨트롤러 대신 핸들러라는 일반 명칭을 씀
- 요청 하나가 응답이 되기까지의 전체 단계는 아래와 같음(Spring Framework 7 소스 기준)

```
클라이언트
   ▼ HTTP 요청
[Tomcat 커넥터] ── 워커 스레드 배정
   ▼
[Filter 체인]                         ← 서블릿 컨테이너 영역
   ▼
[DispatcherServlet.doDispatch]        ← Spring MVC 영역
   │ ① HandlerMapping 조회     → HandlerExecutionChain (핸들러 + 인터셉터 목록)
   │ ② Interceptor.preHandle
   │ ③ HandlerAdapter 선택     → supports(handler)가 참인 첫 어댑터
   │ ④ HandlerAdapter.handle
   │      ├─ 인자 생성     (@RequestBody → HttpMessageConverter 읽기)
   │      ├─ 컨트롤러 메서드 호출
   │      └─ 반환값 처리   (@ResponseBody → HttpMessageConverter 쓰기)
   │ ⑤ Interceptor.postHandle
   │ ⑥ 예외 처리 또는 뷰 렌더링
   │ ⑦ Interceptor.afterCompletion
   ▼
[Filter 체인 복귀] ── 응답 전송 후 스레드 반환
```

### HandlerMapping
- 요청 정보를 보고 그 요청을 처리할 핸들러를 찾아 주는 전략 인터페이스
- `@RequestMapping` 계열 애노테이션을 처리하는 구현은 `RequestMappingHandlerMapping`임
    - 애플리케이션 시작 시 컨트롤러 빈의 매핑 애노테이션을 읽어 URL 패턴, HTTP 메서드, 헤더 조건과 `HandlerMethod`의 대응 정보를 미리 등록함
    - 요청이 오면 등록된 대응 정보에서 조건에 맞는 `HandlerMethod`를 찾음
- HandlerExecutionChain
    - 핸들러 객체와, 그 요청에 적용할 HandlerInterceptor 목록을 묶은 객체
- HandlerMapping은 핸들러만 돌려주지 않고 `HandlerExecutionChain`을 반환하므로, 핸들러를 찾는 시점에 인터셉터 적용 여부도 함께 결정됨
- 경계 조건
    - URL 패턴은 일치하지만 HTTP 메서드가 맞지 않으면 `HttpRequestMethodNotSupportedException`이 발생해 405 응답으로 변환됨
    - 어떤 HandlerMapping도 핸들러를 찾지 못하면 DispatcherServlet이 `NoHandlerFoundException`을 던짐
    - 단, Spring Boot는 정적 리소스 처리를 `/**`에 매핑하므로, 일치하는 컨트롤러가 없는 요청도 정적 리소스 핸들러가 받고, 파일이 없으면 `NoResourceFoundException`이 발생함
    - 두 예외 모두 기본 설정에서 404 응답으로 변환됨

### HandlerAdapter
- DispatcherServlet이 핸들러의 구체 타입을 몰라도 같은 방식으로 핸들러를 실행할 수 있도록, 타입별 호출 방식을 감싸는 인터페이스
- 어댑터 패턴
    - 호환되지 않는 인터페이스를 가진 객체를 기존 코드 수정 없이 기대하는 인터페이스에 맞춰 변환하는 디자인 패턴
- Spring MVC의 핸들러 타입이 하나로 고정되어 있지 않으므로 어댑터가 필요함
    - `DispatcherServlet.properties`에 등록된 기본 어댑터는 아래 네 가지임

| 핸들러 타입 | 어댑터 |
|----------|-------|
| `HandlerMethod`(`@RequestMapping` 메서드) | `RequestMappingHandlerAdapter` |
| `HttpRequestHandler` 구현 객체 | `HttpRequestHandlerAdapter` |
| `Controller` 인터페이스 구현 객체 | `SimpleControllerHandlerAdapter` |
| `HandlerFunction`(`RouterFunction` 기반 함수형 엔드포인트) | `HandlerFunctionAdapter` |

- 어댑터가 없으면 DispatcherServlet이 핸들러 타입마다 `instanceof` 분기와 호출 코드를 직접 가져야 함
    - 새 핸들러 타입을 지원할 때마다 DispatcherServlet을 수정해야 하므로 수정 없이는 확장할 수 없는 구조(개방-폐쇄 원칙 위반)가 됨
- 어댑터를 두면 DispatcherServlet은 지원 여부만 묻고 `handle()`을 호출하며, 새 타입은 어댑터 빈 추가로 지원됨
- `RequestMappingHandlerAdapter`는 단순 호출 중계에 그치지 않고 컨트롤러 메서드 실행 전후의 변환까지 맡음
    - 컨트롤러 메서드는 파라미터와 반환 타입이 자유로우므로, 호출 전에 인자를 만들고 호출 후에 반환값을 해석하는 단계가 필요함
- HandlerMethodArgumentResolver
    - 메서드 파라미터 하나의 값을 요청으로부터 만들어 내는 전략 인터페이스
    - `@PathVariable`, `@RequestParam`, `@RequestBody`는 각각을 지원하는 구현이 처리함
- HandlerMethodReturnValueHandler
    - 컨트롤러 메서드의 반환값을 응답 본문 작성이나 뷰 이름 지정으로 처리하는 전략 인터페이스

### HttpMessageConverter
- 요청 본문을 `InputStream`을 통해 Java 객체로 읽고, Java 객체를 `OutputStream`을 통해 응답 본문으로 쓰는 `spring-web` 모듈의 인터페이스
- 구현마다 다룰 수 있는 Java 타입과 미디어 타입이 정해져 있으며, `canRead`, `canWrite`로 처리 가능 여부를 먼저 판정한 뒤 `read`, `write`로 변환함
- 서버 측 기본 변환기 목록은 `RequestMappingHandlerAdapter`에 등록됨
- 변환기를 실제로 호출하는 쪽은 `RequestResponseBodyMethodProcessor`임
    - 이 클래스는 `@RequestBody` 파라미터를 읽는 HandlerMethodArgumentResolver이자 `@ResponseBody` 반환값을 쓰는 HandlerMethodReturnValueHandler임
    - 즉 JSON 변환은 DispatcherServlet이나 컨트롤러가 아닌 HandlerAdapter가 컨트롤러 호출 전후에 수행함
- `@RestController`
    - `@Controller`와 `@ResponseBody`를 합쳐, 클래스의 모든 핸들러 메서드 반환값을 뷰 이름이 아닌 응답 본문으로 쓰게 하는 애노테이션
- `@ResponseBody`가 없는 `@Controller` 메서드가 문자열을 반환하면 그 값은 뷰 이름이 되어 `ModelAndView`에 담기고, DispatcherServlet이 ViewResolver로 View를 찾아 렌더링함
- 변환기 선택 기준
    - 읽기는 요청의 `Content-Type`과 파라미터 타입을 함께 처리할 수 있는 변환기를 고름
    - 쓰기는 먼저 클라이언트 `Accept` 헤더와 매핑의 `produces` 조건으로 응답 미디어 타입을 정함
    - 그다음 반환값 타입과 그 미디어 타입을 함께 처리할 수 있는 변환기를 고름
    - JSON 변환기는 Jackson 기반이며, Spring Framework 7에서는 Jackson 3용 `JacksonJsonHttpMessageConverter`가, Spring Framework 6.x에서는 Jackson 2용 `MappingJackson2HttpMessageConverter`가 이 역할을 맡음
- 변환 실패는 아래 예외로 나타나며, 기본 설정에서 `DefaultHandlerExceptionResolver`가 상태 코드로 바꿈

| 상황 | 예외 | 상태 코드 |
|-----|-----|---------|
| 요청 `Content-Type`을 읽을 변환기가 없음 | `HttpMediaTypeNotSupportedException` | 415 |
| `Accept`가 요구하는 형식으로 쓸 변환기가 없음 | `HttpMediaTypeNotAcceptableException` | 406 |
| JSON 문법 오류 등으로 본문 읽기 실패 | `HttpMessageNotReadableException` | 400 |
| 반환 객체를 본문으로 쓰는 중 실패 | `HttpMessageNotWritableException` | 500 |

- 응답 커밋(commit)
    - 상태 코드와 헤더가 클라이언트로 전송되어 더 이상 바꿀 수 없게 된 응답 상태
- Spring 문서는 `@ResponseBody`나 `ResponseEntity`를 반환하는 메서드의 응답이 HandlerAdapter 안에서 작성되고 커밋된다고 명시함
    - 따라서 그 뒤에 호출되는 인터셉터 `postHandle`에서는 응답이 이미 커밋되어 헤더를 추가할 수 없음
    - 본문이 쓰이기 직전에 개입하려면 `ResponseBodyAdvice`를 구현함

## 요청 가로채기
- 로깅, 인코딩, 인증 같은 공통 처리를 컨트롤러마다 반복하지 않으려면 핸들러 실행 앞뒤에 끼어드는 지점이 필요함
- 이 지점은 서블릿 컨테이너 영역의 Filter와 Spring MVC 영역의 HandlerInterceptor 두 곳에 있음

### Filter
- 서블릿 명세가 정의한, 서블릿 전후에 요청과 응답을 가로채 처리하는 컴포넌트(`jakarta.servlet.Filter`)
- 필터 체인(Filter Chain)
    - 한 요청에 적용되는 필터들이 순서대로 연결되어, 각 필터가 `chain.doFilter()`로 다음 필터나 최종 서블릿을 호출하는 구조
- 컨테이너가 DispatcherServlet을 호출하기 전에 필터 체인이 실행됨
- `doFilter(ServletRequest, ServletResponse, FilterChain)`는 요청, 응답, 체인만 인자로 받으므로, 어떤 컨트롤러 메서드가 실행될지 알 수 없음
- `chain.doFilter()`를 호출하지 않으면 요청이 서블릿에 도달하지 않음
- 다음 단계로 넘기는 요청, 응답 객체를 래퍼 객체로 바꿔 전달할 수 있음
- Spring Boot 내장 컨테이너에서는 Spring 빈으로 등록된 Filter가 자동으로 컨테이너에 등록되고 기본적으로 `/*`에 매핑됨
    - 실행 순서는 Filter 클래스의 `@Order`나 `Ordered` 구현, 또는 `FilterRegistrationBean`으로 지정함
    - Spring Boot 문서는 `@Bean` 메서드에 붙인 `@Order`로는 필터 순서를 지정할 수 없다고 명시함

### HandlerInterceptor
- HandlerMapping이 찾은 핸들러의 실행 전후에 DispatcherServlet이 호출하는 Spring MVC 인터페이스

| 메서드 | 호출 시점 | 비고 |
|------|---------|-----|
| `preHandle` | 핸들러 실행 전 | `false`를 반환하면 이후 인터셉터와 핸들러 실행을 건너뜀 |
| `postHandle` | 핸들러 실행 후, 뷰 렌더링 전 | 핸들러에서 예외가 발생하면 호출되지 않음 |
| `afterCompletion` | 요청 처리 완료 후 | 예외 발생 여부와 무관하게 호출됨 |

- 실행 순서 규칙(HandlerExecutionChain 소스 기준)
    - `preHandle`은 등록 순서대로, `postHandle`과 `afterCompletion`은 역순으로 호출됨
    - `afterCompletion`은 `preHandle`이 `true`를 반환하고 끝난 인터셉터에만 호출됨
    - 세 번째 인터셉터의 `preHandle`이 `false`를 반환하면, 앞의 두 인터셉터의 `afterCompletion`만 역순으로 호출되고 핸들러는 실행되지 않음
    - 예외가 HandlerExceptionResolver로 처리되었으면 `afterCompletion`의 예외 인자로 `null`이, 처리되지 못했으면 그 예외가 전달됨
    - `afterCompletion`에서 던진 예외는 로그만 남고 전파되지 않음
- `handler` 인자를 `HandlerMethod`로 캐스팅하면 실행될 메서드와 그 애노테이션을 확인할 수 있음

```java
@Slf4j
public class TimingInterceptor implements HandlerInterceptor {

    private static final String START = "timing.start";

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        // 인터셉터 인스턴스 하나를 모든 요청 스레드가 공유하므로 요청별 값은 요청 속성에 저장함
        request.setAttribute(START, System.nanoTime());

        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler, Exception ex) {
        long elapsedMs = (System.nanoTime() - (Long) request.getAttribute(START)) / 1_000_000;
        // 컨트롤러 메서드 핸들러라면 실행된 메서드 이름을 알 수 있음
        String target = (handler instanceof HandlerMethod hm)
                ? hm.getMethod().getName() : handler.toString();
        log.info("{} {}ms", target, elapsedMs);
    }
}
```
- 인터셉터는 `WebMvcConfigurer.addInterceptors()`에서 등록하며, `addPathPatterns()`, `excludePathPatterns()`로 적용 경로를 지정함

### 두 계층의 차이
| 구분 | Filter | HandlerInterceptor |
|-----|--------|--------------------|
| 정의 주체 | 서블릿 명세 | Spring MVC |
| 호출 주체 | 서블릿 컨테이너 | DispatcherServlet |
| 실행 위치 | DispatcherServlet 진입 전후 | DispatcherServlet 내부, 핸들러 실행 전후 |
| 접근 가능한 정보 | 요청, 응답 객체 | 요청, 응답 객체, 핸들러 객체, `ModelAndView` |
| 요청, 응답 객체 교체 | 래퍼로 교체해 전달 가능 | 불가 |
| 적용 대상 | DispatcherServlet을 거치지 않는 요청 포함 | DispatcherServlet이 처리하는 요청만 |
| 던진 예외의 처리 | `@ControllerAdvice`가 기본적으로 처리하지 못함 | `preHandle`, `postHandle` 예외는 DispatcherServlet의 예외 처리 경로를 탐 |

### 인증 처리 위치
- Spring 문서는 애노테이션 기반 컨트롤러의 경로 매칭과 어긋날 가능성 때문에 인터셉터가 보안 계층으로 적합하지 않다고 보고, Spring Security나 서블릿 필터 체인에 통합된 방식을 가능한 한 앞단에 적용하도록 권장함
- Spring Security
    - 서블릿 필터 체인 위에 보안 필터 묶음을 얹어 인증과 인가를 수행하는 Spring 프로젝트
- 인증을 필터 계층에 두는 근거
    - 인증되지 않은 요청을 핸들러 탐색과 본문 변환 이전에 차단해 불필요한 처리를 줄임
    - DispatcherServlet을 거치지 않는 요청까지 같은 정책으로 보호함
    - 인터셉터의 경로 패턴이 컨트롤러 매핑과 따로 관리되면, 패턴 누락으로 보호되지 않는 엔드포인트가 생길 수 있음
- 핸들러별 실행 시간 기록처럼 실행될 핸들러 정보가 필요한 공통 처리에는 인터셉터가 맞음

## HandlerExceptionResolver
- DispatcherServlet이 디스패치 중 발생한 예외를 받아 응답이나 오류 뷰로 바꾸는 전략 인터페이스
- 같은 예외라도 디스패치의 어느 단계에서 던졌는지에 따라 `@ControllerAdvice`의 처리 대상인지가 갈림
- `@ExceptionHandler`
    - 컨트롤러나 `@ControllerAdvice` 클래스의 메서드에 붙여 특정 예외 타입의 처리 메서드로 지정하는 애노테이션
- `@ControllerAdvice`
    - 여러 컨트롤러에 공통으로 적용할 `@ExceptionHandler` 메서드 등을 모아 두는 클래스에 붙이는 애노테이션
    - `@RestControllerAdvice`는 여기에 `@ResponseBody`를 더한 애노테이션
- DispatcherServlet의 기본 resolver는 아래 세 가지이며, 등록 순서대로 시도해 처음으로 결과를 돌려준 resolver에서 멈춤

| resolver | 처리 대상 |
|----------|---------|
| `ExceptionHandlerExceptionResolver` | `@ExceptionHandler` 메서드를 찾아 실행 |
| `ResponseStatusExceptionResolver` | `@ResponseStatus`가 붙은 예외, `ResponseStatusException` |
| `DefaultHandlerExceptionResolver` | Spring MVC 표준 예외를 HTTP 상태 코드로 변환 |

- `ExceptionHandlerExceptionResolver`는 예외가 발생한 컨트롤러 클래스 내부의 `@ExceptionHandler`를 먼저 찾고, 없으면 `@ControllerAdvice` 쪽을 찾음

### DispatcherServlet 내부 예외
- `@ExceptionHandler`가 처리할 수 있는 범위는 `doDispatch`의 `try` 구조로 결정됨

```java
// DispatcherServlet.doDispatch 구조 요약 (Spring Framework 7 소스 기준)
try {
    try {
        mappedHandler = getHandler(request);                // HandlerMapping
        if (!mappedHandler.applyPreHandle(...)) return;     // preHandle
        HandlerAdapter ha = getHandlerAdapter(...);         // HandlerAdapter 선택
        mv = ha.handle(...);                                // 인자 생성, 컨트롤러, 반환값 처리
        mappedHandler.applyPostHandle(...);                 // postHandle
    } catch (Exception e) {
        dispatchException = e;                              // 이 구간의 예외를 보관
    }
    // 보관된 예외를 HandlerExceptionResolver 목록에 넘기고, 뷰가 있으면 렌더링
    processDispatchResult(request, response, mappedHandler, mv, dispatchException);
} catch (Exception e) {
    // resolver가 처리하지 못한 예외와 뷰 렌더링 중 예외
    triggerAfterCompletion(request, response, mappedHandler, e);    // afterCompletion 호출 후 다시 던짐
}
```
- 안쪽 `try` 구간의 예외는 모두 resolver를 거치므로 `@ExceptionHandler`의 처리 대상임
    - HandlerMapping 단계의 `NoHandlerFoundException`, `HttpRequestMethodNotSupportedException`
    - 인터셉터 `preHandle`, `postHandle`에서 던진 예외
    - `@RequestBody` 변환 실패, 검증 실패, 컨트롤러와 서비스에서 전파된 예외, 응답 본문 쓰기 실패
- 처리 대상이 아닌 경우
    - 뷰 렌더링 중 발생한 예외는 바깥 `catch`로 바로 가므로 resolver를 거치지 않음
    - 인터셉터 `afterCompletion`의 예외는 로그로만 남음
    - 응답이 이미 커밋된 뒤의 예외는 resolver가 호출되더라도 상태 코드와 헤더를 바꿀 수 없음
- 모든 resolver가 처리하지 못한 예외는 DispatcherServlet 밖으로 다시 던져져 서블릿 컨테이너까지 전파됨

### Filter 예외
- Filter는 DispatcherServlet 바깥에서 실행되므로, 필터가 던진 예외는 `doDispatch`의 `try` 구간을 지나지 않음
    - 따라서 `@ControllerAdvice`의 `@ExceptionHandler`는 필터 예외를 기본적으로 처리하지 못함
- Spring Boot에서 필터 예외가 처리되는 경로
    - 예외가 필터 체인 밖으로 전파되면 서블릿 컨테이너가 받음
    - Spring Boot는 `/error` 매핑을 서블릿 컨테이너의 전역 오류 페이지로 등록하므로, 컨테이너가 요청을 `/error`로 다시 전달함
    - `/error`는 Spring Boot의 `BasicErrorController`가 처리해 기본 형식의 오류 응답과 500 상태 코드를 반환함
- 실패 사례
    - 컨트롤러 예외는 `@RestControllerAdvice`가 만든 형식으로, 필터 예외는 `BasicErrorController`의 기본 형식으로 응답되어 같은 API 안에서 오류 응답 형식이 갈림
- 대응 방법
    - 필터 안에서 예외를 잡아 상태 코드와 본문을 직접 작성함
    - 또는 필터에서 잡은 예외를 `@Qualifier("handlerExceptionResolver")`로 주입받은 `HandlerExceptionResolver` 빈에 넘겨 `@ControllerAdvice` 처리를 재사용함
    - 이때 `resolver.resolveException(request, response, null, ex)`처럼 핸들러 자리에 `null`을 넘기고, 처리 후 `chain.doFilter()`를 호출하지 않음
- 위임 방식의 경계 조건
    - `handler`가 `null`이므로 컨트롤러 클래스 내부의 `@ExceptionHandler`는 탐색되지 않음
    - `basePackages` 등으로 적용 대상을 제한한 `@ControllerAdvice`는 비교할 핸들러 타입이 없어 적용되지 않으며, 제한 없는 전역 `@ControllerAdvice`만 적용됨
    - 어느 resolver도 예외를 처리하지 못하면 `resolveException`이 `null`을 반환하므로, 이 경우의 응답 작성은 필터가 별도로 맡아야 함

## 정리
```
Spring MVC 요청 처리
    │
    ├── 서블릿 컨테이너
    │     ├── 서블릿 선언당 인스턴스 1개, 요청은 스레드별 동시 실행
    │     ├── 요청당 스레드: 처리 완료까지 워커 스레드 점유
    │     └── 포화 단계: maxThreads → maxConnections → acceptCount
    ├── DispatcherServlet
    │     ├── 프론트 컨트롤러: 단일 진입점 + 위임
    │     └── 특수 빈: HandlerMapping, HandlerAdapter, HandlerExceptionResolver, ViewResolver
    ├── 요청 디스패치
    │     ├── HandlerMapping → HandlerExecutionChain
    │     ├── HandlerAdapter: 핸들러 타입별 호출 캡슐화 (어댑터 패턴)
    │     └── HttpMessageConverter: 어댑터 안에서 본문 읽기, 쓰기
    ├── 요청 가로채기
    │     ├── Filter: 컨테이너 소속, DispatcherServlet 앞
    │     ├── HandlerInterceptor: DispatcherServlet 소속, 핸들러 앞뒤
    │     └── 인증은 필터 계층 (Spring Security)
    └── HandlerExceptionResolver
          ├── doDispatch 안쪽 try 구간 예외 → @ExceptionHandler 처리
          └── Filter 예외 → 컨테이너 → /error (resolver 위임으로 @ControllerAdvice 재사용 가능)
```
