## 전송 계층 프로토콜
- 전송 계층이란 TCP/IP 모델에서 종단 호스트 사이의 데이터 전달을 담당하는 계층을 가리킴
    - 경로 결정을 담당하는 인터넷 계층(IP) 위에 위치함
- TCP와 UDP가 이 계층의 대표 프로토콜
- IP(Internet Protocol)는 패킷을 목적지로 전달하지만 순서 보장과 손실 복구를 제공하지 않음
    - 이 성질을 비신뢰성(unreliable)이라 함
    - 신뢰성이 필요하면 상위 계층인 TCP가 이를 보완

## TCP와 UDP
### TCP(Transmission Control Protocol)
- 신뢰성 있는 바이트 스트림 전달을 제공하는 연결 지향 프로토콜
    - 연결 지향(connection-oriented)이란 데이터 전송 전에 양측이 연결 상태를 먼저 수립함을 뜻함
    - 바이트 스트림(byte stream)이란 송신 측이 넣은 바이트들이 경계 없이 연속된 흐름으로 수신 측에 도달하는 전달 방식을 가리킴
- RFC 9293이 TCP의 현행 표준 명세
- 응용 프로그램이 메시지 단위로 데이터를 보내도 TCP는 그것을 바이트 흐름으로만 전달
    - 한 번의 송신이 수신 측에서 여러 번에 나뉘어 도착하거나, 여러 송신이 한 번에 뭉쳐 도착할 수 있음
    - 메시지 경계를 구분하는 책임은 응용 계층에 있음

### UDP(User Datagram Protocol)
- 연결 수립 없이 데이터그램을 전달하는 비연결 전송 프로토콜
    - 데이터그램(datagram)이란 독립적으로 처리되는 하나의 전송 단위
    - 비연결(connectionless)이란 사전 연결 설정 없이 곧바로 데이터를 보냄을 뜻함
- UDP는 순서 보장, 재전송, 흐름 제어, 혼잡 제어를 제공하지 않음
    - 대신 헤더가 작고 핸드셰이크 지연이 없어 전송이 빠름
    - 데이터그램 단위의 경계가 보존되어 한 번의 송신이 한 번의 수신에 대응함

### TCP와 UDP의 비교
| 구분 | TCP | UDP |
|------|-----|-----|
| 연결 방식 | 연결 지향 | 비연결 |
| 신뢰성 보장 | 순서 보장, 재전송 제공 | 제공하지 않음 |
| 전달 단위 | 바이트 스트림 | 데이터그램 |
| 흐름 제어, 혼잡 제어 | 있음 | 없음 |
| 헤더 크기 | 20바이트 이상(옵션 포함 시 최대 60바이트) | 8바이트 고정 |
| 주요 사용처 | HTTP/1.1 · HTTP/2, HTTPS, SSH | DNS, 실시간 스트리밍, 게임, VoIP |

- 어느 쪽이 우월한지의 문제가 아니라, 요구되는 성질이 다름
    - 은행 이체나 웹 페이지 전송처럼 한 바이트의 손실도 허용되지 않는 경우 TCP를 택함
    - 화상 통화처럼 약간의 손실을 감수하더라도 지연이 낮아야 하는 경우 UDP를 택함
- HTTP/3은 UDP 위에서 동작하는 예외에 해당함
    - HTTP/3은 QUIC 프로토콜을 전송 수단으로 사용함
    - QUIC이 신뢰성과 순서 보장을 UDP 위에서 자체적으로 구현함
    - 따라서 UDP를 쓴다고 해서 신뢰성을 포기하겠다는 결론은 성립하지 않음

## TCP 3-way handshake
- 핸드셰이크(handshake)란 통신을 시작하기 전에 양측이 정해진 메시지를 주고받아 상태를 맞추는 절차를 가리킴
- 3-way handshake란 세 개의 세그먼트를 교환하여 TCP 연결을 수립하는 절차를 가리킴
    - 세그먼트(segment)란 TCP가 다루는 전송 단위를 가리킴
- 교환하는 제어 비트의 정의는 아래와 같음
    - SYN이란 synchronize의 약자로, 초기 순서 번호를 동기화하자는 요청을 나타내는 플래그
    - ACK란 acknowledgment의 약자로, 상대의 세그먼트를 정상 수신했다는 확인을 나타내는 플래그
- ISN(Initial Sequence Number)이란 각 방향의 데이터에 붙일 첫 순서 번호를 가리킴
    - 순서 번호(sequence number)란 바이트 흐름의 각 위치를 식별하는 번호를 가리킴
    - 순서 보장과 재전송 판단의 기준이 됨

```
Client                              Server
  |                                   |
  |---- SYN (seq=x) ----------------->|   1단계: 클라이언트 ISN(x) 전달
  |                                   |
  |<--- SYN + ACK (seq=y, ack=x+1) ---|   2단계: 서버 ISN(y) 전달 + x 수신 확인
  |                                   |
  |---- ACK (ack=y+1) --------------->|   3단계: y 수신 확인
  |                                   |
  |          (연결 수립 완료)            |
```

- 각 단계의 동작은 아래와 같음
    - 1단계에서 클라이언트가 자신의 ISN인 x를 SYN에 실어 보냄
    - 2단계에서 서버가 자신의 ISN인 y를 SYN에 싣고, x를 정상 수신했다는 뜻으로 ack=x+1을 함께 보냄
    - 3단계에서 클라이언트가 y를 정상 수신했다는 뜻으로 ack=y+1을 보냄

### 세 번 교환이 필요한 이유
- 신뢰성 있는 통신은 양방향 각각의 ISN이 상대에게 전달되고 확인되어야 성립함
    - 클라이언트 → 서버 방향 ISN인 x의 전달과 확인이 필요함
    - 서버 → 클라이언트 방향 ISN인 y의 전달과 확인이 필요함
- 원리적으로는 네 번의 교환이 필요하지만, 서버의 ACK와 SYN이 하나의 세그먼트로 합쳐져 세 번으로 압축됨
- RFC 9293이 밝히는 3-way handshake의 근본 목적은 과거의 중복된 연결 요청으로 인한 혼돈을 방지하는 데 있음
    - 네트워크 지연으로 이전 연결의 낡은 SYN이 뒤늦게 도착하는 상황이 존재함
    - 두 번의 교환만으로 연결을 확정하면, 서버는 방금 받은 SYN이 유효한 새 요청인지 낡은 중복인지 구분할 수 없음
    - 세 번째 교환에서 클라이언트가 확인 응답을 보내게 함으로써, 낡은 SYN에 대해서는 클라이언트가 RST로 연결을 거부할 수 있게 됨
    - RST란 reset의 약자로, 비정상 연결을 즉시 끊으라는 제어 플래그

## TCP 4-way handshake
- 네 개의 세그먼트를 교환하여 TCP 연결을 종료하는 절차
- 연결 종료가 네 단계인 이유는 TCP 연결이 양방향이기 때문
    - 각 방향의 데이터 흐름을 독립적으로 닫아야 함
    - 한쪽이 FIN을 보내도 반대 방향은 아직 데이터를 보낼 수 있음(half-close)

```
Client                          Server
  |                               |
  |------ FIN (seq=x) ----------->|   1단계: 클라이언트 → 서버 방향 종료 요청
  |                               |
  |<----- ACK (ack=x+1) ----------|   2단계: 종료 요청 확인
  |                               |
  |        (서버 잔여 데이터 전송)     |
  |                               |
  |<----- FIN (seq=y) ------------|   3단계: 서버 → 클라이언트 방향 종료 요청
  |                               |
  |------ ACK (ack=y+1) --------->|   4단계: 종료 요청 확인
  |                               |
  |         (연결 종료 완료)         |
```

## TIME_WAIT 상태
- 능동적으로 연결을 닫은 측이 마지막 ACK를 보낸 뒤 일정 시간 대기하는 상태
- 대기 시간은 2MSL임
    - MSL(Maximum Segment Lifetime)이란 세그먼트가 네트워크에서 살아 있을 수 있는 최대 시간을 가리킴
- TIME_WAIT가 필요한 이유는 두 가지
    - 마지막 ACK가 유실되어 상대가 FIN을 재전송할 경우, 이에 다시 응답하기 위함
    - 이전 연결의 지연된 세그먼트가 같은 포트 쌍의 새 연결에 섞여 들어가는 것을 막기 위함
- 짧은 시간에 대량의 연결을 맺고 먼저 끊는 측에서는 TIME_WAIT 소켓이 누적되어 로컬 포트가 고갈될 수 있음
    - 포트 고갈은 연결을 맺는 측(클라이언트, 또는 백엔드에 접속하는 프록시·서버)에서 발생함
    - 서버 측 연결은 모두 같은 리스닝 포트를 공유하므로, 서버의 TIME_WAIT 누적은 포트가 아닌 소켓 자원을 소모함

## TCP의 신뢰성 보장 메커니즘
- TCP는 아래 세 축으로 신뢰성을 구성함

### 순서 보장
- 각 바이트에 순서 번호를 부여하여 수신 측이 도착 순서와 무관하게 올바른 순서로 재조립
- 순서 번호 덕분에 중복 도착한 세그먼트를 식별해 버릴 수 있음

### 재전송
- TCP의 ACK는 누적 확인(cumulative ACK) 방식
    - 누적 확인이란 특정 번호까지의 모든 바이트를 정상 수신했음을 하나의 ACK로 확인하는 방식을 가리킴
- 송신 측은 세그먼트를 보낸 뒤 일정 시간 안에 해당 ACK가 오지 않으면 그 세그먼트를 재전송함
    - 이 대기 시간을 RTO(Retransmission Timeout)라 부름
    - 손실은 ACK 미도착으로 감지되며, 재전송으로 복구됨

### 흐름 제어(flow control)
- 수신 측의 처리 능력을 넘어서는 전송을 막는 조절
- 수신 측이 받을 수 있는 여유 버퍼 크기를 TCP 헤더의 Window 필드로 알림
    - 이 값을 수신 윈도우(receive window)라 부름
    - 송신 측은 확인받지 않은 데이터의 양을 이 윈도우 크기 이하로 유지함
- 흐름 제어는 수신 측 한 지점의 과부하를 막는 조절이며, 네트워크 전체의 혼잡을 막는 혼잡 제어와는 대상이 다름

## HTTP
- HyperText Transfer Protocol
- 웹에서 자원을 주고받기 위한 응용 계층 프로토콜
- HTTP는 요청-응답(request-response) 모델로 동작함
    - 클라이언트가 요청을 보내면 서버가 그에 대한 응답을 하나 돌려주는 구조
- HTTP의 의미론은 RFC 9110(HTTP Semantics)이 정의함
    - RFC 9110은 2022년에 발행되어 기존 RFC 7230·7231 등을 대체함
    - RFC 9110은 메시지의 의미를 정의하며, 그것을 어떻게 전송하는지 버전별 명세(HTTP/1.1은 RFC 9112)가 다름

### HTTP 요청의 구조
- 요청은 요청 라인, 헤더, 본문으로 구성됨

```http
POST /api/users HTTP/1.1
Host: example.com
Content-Type: application/json

{"name": "hong"}
```

### HTTP 응답의 구조
- 응답은 상태 라인, 헤더, 본문으로 구성됨
    - 상태 라인(status line)이란 HTTP 버전·상태 코드·상태 메시지를 담은 첫 줄을 가리킴

```http
HTTP/1.1 201 Created
Content-Type: application/json

{"id": 123, "name": "hong"}
```

## HTTP 메서드의 안전성과 멱등성
- 메서드(method)란 요청이 자원에 대해 수행하려는 동작의 종류를 나타내는 토큰을 가리킴
- RFC 9110은 메서드를 두 가지 성질로 분류함
    - 안전성(safe)이란 그 메서드가 서버의 상태를 변경하지 않는 읽기 전용 의미를 가짐을 뜻함(RFC 9110 §9.2.1)
    - 멱등성(idempotent)이란 동일한 요청을 여러 번 보내도 서버에 대한 의도된 효과가 한 번 보낸 것과 같음을 뜻함(RFC 9110 §9.2.2)
- 두 성질의 경계는 아래와 같음
    - 모든 안전한 메서드는 멱등하나, 모든 멱등한 메서드가 안전한 것은 아님
    - PUT과 DELETE는 상태를 변경하므로 안전하지 않으나, 반복해도 서버에 대한 의도된 효과가 같으므로 멱등함
    - 응답까지 같을 필요는 없음(예: 두 번째 DELETE는 404를 돌려줄 수 있음)

| 메서드 | 주 용도 | 안전 | 멱등 |
|------|--------|-----|-----|
| GET | 자원 조회 | 예 | 예 |
| HEAD | 헤더만 조회 | 예 | 예 |
| OPTIONS | 지원 메서드 조회 | 예 | 예 |
| POST | 자원 생성, 비멱등 처리 | 아니오 | 아니오 |
| PUT | 자원 전체 교체 | 아니오 | 예 |
| PATCH | 자원 부분 수정 | 아니오 | 아니오 |
| DELETE | 자원 삭제 | 아니오 | 예 |

- 멱등성이 실무에서 중요한 이유
    - 네트워크 실패로 응답을 받지 못했을 때, 멱등한 메서드는 안전하게 재시도할 수 있음
    - POST는 멱등하지 않으므로, 무분별한 재시도는 자원을 중복 생성할 위험이 있음

## HTTP 상태 코드
- 상태 코드(status code)란 요청의 처리 결과를 나타내는 세 자리 숫자를 가리킴
- 첫 자리 숫자로 다섯 부류로 나뉨(RFC 9110 §15)

| 부류 | 의미 | 대표 예 |
|------|-----|--------|
| 1xx | 정보 응답, 처리 계속 | 100 Continue |
| 2xx | 성공 | 200 OK, 201 Created |
| 3xx | 리다이렉션, 추가 동작 필요 | 301 Moved Permanently, 304 Not Modified |
| 4xx | 클라이언트 오류 | 400 Bad Request, 401 Unauthorized, 404 Not Found |
| 5xx | 서버 오류 | 500 Internal Server Error, 503 Service Unavailable |

- 부류를 구분하는 실익은 오류의 책임 소재를 드러내는 데 있음
    - 4xx는 요청 자체에 문제가 있어 클라이언트가 고쳐야 하는 경우
    - 5xx는 요청은 유효하나 서버가 처리에 실패한 경우

## HTTP의 무상태성
- 무상태(stateless)란 각 요청이 독립적으로 해석되며, 서버가 요청 사이의 상태를 보존하지 않음을 뜻함
    - RFC 9110은 HTTP를 무상태 프로토콜로 정의함
    - 각 요청 메시지의 의미는 그 메시지만으로 이해될 수 있어야 함
- 무상태성은 서버 확장에 유리함
    - 서버가 이전 요청을 기억하지 않으므로, 같은 클라이언트의 요청을 여러 서버 인스턴스가 나누어 처리할 수 있음
- 그러나 로그인처럼 요청 사이에 사용자를 식별해야 하는 기능은 무상태성만으로는 성립하지 않음
    - 서버가 이전 요청을 기억하지 않으므로, 매 요청에 식별 정보가 함께 실려야 함

### 쿠키와 세션
- 쿠키(cookie)란 서버가 클라이언트에 저장해 두었다가 이후 요청마다 되돌려 받는 상태 정보
    - RFC 6265가 Cookie·Set-Cookie 헤더를 정의함
    - RFC 6265는 이 메커니즘의 목적을 무상태 HTTP 위에서 상태 있는 세션을 유지하는 것으로 밝힘
- 동작 순서는 아래와 같음
    - 서버가 응답에 `Set-Cookie` 헤더로 식별자를 실어 보냄
    - 클라이언트가 이후 요청마다 `Cookie` 헤더로 그 식별자를 되돌려 보냄
    - 서버는 그 식별자로 요청의 주체를 식별함
- 세션(session) 방식이란 사용자 상태를 서버 측에 저장하고, 그것을 가리키는 세션 식별자만 쿠키로 주고받는 방식을 가리킴
    - 실제 상태는 서버가 보관하므로, 클라이언트는 식별자만 지님
    - 서버가 상태를 보관한다는 점에서, 여러 서버 인스턴스가 세션 저장소를 공유해야 하는 부담이 생김

```
[로그인 요청]  Client ──────────────▶ Server
                                       세션 생성, 저장소에 상태 보관
[로그인 응답]  Client ◀────────────── Server
               Set-Cookie: SID=abc123
[이후 요청]    Client ──────────────▶ Server
               Cookie: SID=abc123      SID로 저장소 조회 → 사용자 식별
```

### 토큰
- 사용자 식별 정보 자체를 클라이언트가 지니고 매 요청에 실어 보내는 방식
    - JWT(JSON Web Token)가 대표적
    - JWT는 사용자 정보와 서버의 서명을 담으며, 서버는 서명을 검증해 위변조 여부를 판정함
- 세션 방식과의 경계는 상태를 어디에 두느냐에 있음
    - 세션 방식은 상태를 서버에 두고 식별자만 주고받음
    - 토큰 방식은 상태를 토큰 안에 담아 클라이언트가 지니므로, 서버가 세션 저장소를 유지하지 않아도 됨
- 어느 방식이든 무상태 HTTP 위에서 상태를 흉내 내는 수단이라는 점은 동일함
    - 상태 유지의 책임을 응용 계층이 매 요청에 식별 정보를 실어 보내는 방식으로 떠안음

## HTTPS와 TLS
- HTTPS란 HyperText Transfer Protocol Secure의 약자로, TLS 위에서 HTTP를 실어 나르는 프로토콜(HTTP over TLS, RFC 2818)
- TLS란 Transport Layer Security의 약자로, 전송되는 데이터에 기밀성·무결성·인증을 제공하는 보안 프로토콜
    - 기밀성(confidentiality)이란 제3자가 내용을 엿볼 수 없게 함을 뜻함
    - 무결성(integrity)이란 전송 중 내용이 변조되지 않았음을 검증할 수 있게 함을 뜻함
    - 인증(authentication)이란 통신 상대가 사칭이 아닌 진짜임을 확인함을 뜻함
- TLS는 TCP 위에서 동작함
    - 따라서 HTTP/1.1·HTTP/2 기반 HTTPS 연결은 TCP 3-way handshake를 먼저 마친 뒤 TLS 핸드셰이크를 추가로 수행함
    - 예외로 HTTP/3은 TCP를 쓰지 않으며, QUIC이 UDP 위에서 TLS 1.3 핸드셰이크를 자체 핸드셰이크에 통합함

### 대칭키와 비대칭키
- 대칭키(symmetric key) 암호화란 암호화와 복호화에 같은 하나의 키를 쓰는 방식
    - 연산이 빠르나, 그 키를 상대에게 안전하게 전달하는 문제가 남음
- 비대칭키(asymmetric key) 암호화란 공개키와 개인키의 쌍을 쓰는 방식
    - 공개키로 암호화한 것은 짝이 되는 개인키로만 복호화됨
    - 키 전달 문제를 해결하나, 대칭키에 비해 연산이 느림
- TLS는 두 방식을 결합함
    - 핸드셰이크 단계에서 비대칭키 기반 기법으로 세션 키(대칭키)를 양측이 안전하게 확보함
    - 이후 실제 데이터 전송은 빠른 대칭키 암호화로 처리

### TLS 1.2의 키 교환
- TLS 1.2는 여러 키 교환 방식을 허용했으며, 그중 하나가 RSA 키 전송(key transport)임
    - RSA 키 전송이란 클라이언트가 사전 비밀(pre-master secret)을 생성해 서버의 공개키로 암호화해 보내는 방식을 가리킴
    - 서버는 자신의 개인키로 이를 복호화하며, 양측은 이로부터 세션 키를 유도함
- 이 방식은 비대칭키 암호화로 대칭키를 직접 전달하는 구조에 해당함
- RSA 키 전송에는 순방향 비밀성이 없다는 약점이 있음
    - 순방향 비밀성(forward secrecy)이란 서버의 장기 개인키가 훗날 유출되어도, 과거에 기록된 세션은 복호화되지 않는 성질을 가리킴
    - RSA 키 전송에서는 개인키가 유출되면 그 키로 암호화된 과거 세션이 모두 복호화될 수 있음

### TLS 1.3의 키 교환
- TLS 1.3은 RFC 8446이 정의하며, 2018년에 발행됨
- TLS 1.3은 RSA 키 전송을 제거하고, 공개키 기반 키 교환으로는 임시(ephemeral) Diffie-Hellman 계열만 허용함
    - Diffie-Hellman 키 교환이란 양측이 각자의 값을 교환해, 비밀 자체는 전송하지 않고도 공통의 비밀을 계산해 내는 방식을 가리킴
    - 실무에서는 타원곡선 기반의 ECDHE(Elliptic Curve Diffie-Hellman Ephemeral)가 주로 쓰임
- 이 구조에서 세션 키는 네트워크로 전송되지 않고 양측이 각자 계산해 냄
    - 임시 키가 연결마다 새로 생성되고 폐기되므로, 장기 개인키가 유출되어도 과거 세션 키를 되살릴 수 없음
    - 이로써 (EC)DHE를 사용하는 연결에는 순방향 비밀성이 보장됨
    - 단, (EC)DHE 없이 사전 공유 키만으로 세션을 재개하는 PSK 단독 모드(psk_ke)와 0-RTT early data에는 순방향 비밀성이 없음
- 서버 인증서의 역할은 키 교환과 구분됨
    - 인증서(certificate)란 CA(Certificate Authority, 인증 기관)가 서버의 공개키에 서명해 발급한 신원 증명서를 가리킴
    - TLS 1.3에서 서버의 개인키는 키를 전달하는 데 쓰이지 않고, 핸드셰이크 전체 기록(transcript)의 해시에 서명(CertificateVerify)해 상대가 진짜 서버임을 증명하는 데 쓰임
    - 교환한 키 공유 값도 이 기록에 포함되므로 함께 보호됨
- 비대칭키가 대칭키 확보에 관여한다는 큰 그림은 두 버전에서 같으나, 그 관여 방식은 다름
    - TLS 1.2의 RSA 키 전송은 비대칭키로 대칭키를 암호화해 직접 전달
    - TLS 1.3은 비대칭키를 서명(인증)에 쓰고, 대칭키는 임시 Diffie-Hellman으로 양측이 각자 계산함

## 정리
```
TCP/IP와 HTTP 통신 기본기
    │
    ├── 전송 계층
    │     ├── TCP: 연결 지향, 바이트 스트림, 신뢰성 보장(RFC 9293)
    │     │     ├── 3-way handshake: ISN 동기화, 중복 연결 방지
    │     │     ├── 4-way handshake: 양방향 독립 종료, TIME_WAIT
    │     │     └── 신뢰성: 순서 보장 · 재전송 · 흐름 제어
    │     └── UDP: 비연결, 데이터그램, 신뢰성 미보장
    │
    ├── HTTP (RFC 9110)
    │     ├── 메서드: 안전성 · 멱등성
    │     ├── 상태 코드: 1xx~5xx
    │     └── 무상태성 → 쿠키/세션(서버 저장), 토큰(클라이언트 보유)
    │
    └── HTTPS
          └── TLS: 대칭키 + 비대칭키 결합
                ├── TLS 1.2: RSA 키 전송 허용, 순방향 비밀성 없음
                └── TLS 1.3: RSA 키 전송 제거, 공개키 기반 교환은 임시 (EC)DHE만 허용(RFC 8446)
```
