## FetchType
- 연관 엔티티를 언제 데이터베이스에서 읽어올지 규정하는 Fetch 전략 열거형
    - `jakarta.persistence.FetchType`에 정의된 EAGER와 LAZY 두 값을 가짐
    - `@OneToMany`, `@ManyToOne`, `@OneToOne`, `@ManyToMany`의 `fetch` 속성으로 지정함
- 연관 엔티티란 한 엔티티가 참조하는 다른 엔티티를 가리킴

### 즉시 로딩(EAGER)
- 부모 엔티티를 조회할 때 연관 엔티티도 함께 즉시 읽어오는 방식
- JPA 명세는 EAGER를 영속성 프로바이더 런타임에 대한 요구사항으로 규정함
    - 프로바이더는 반드시 연관 엔티티를 함께 읽어와야 함
    - 부모 엔티티를 반환하는 시점에 EAGER 필드는 이미 값이 채워져 있음이 보장됨

### 지연 로딩(LAZY)
- 지연 로딩이란 연관 엔티티를 실제로 접근하는 시점까지 조회를 미루는 방식을 가리킴
- JPA 명세는 LAZY를 영속성 프로바이더 런타임에 대한 힌트로 규정함
    - 요구사항이 아니라 힌트이므로 프로바이더가 지연 로딩을 지키지 않아도 명세 위반이 아님
    - 일부 프로바이더는 특정 필드 타입을 지연 로딩하지 못할 수 있어 힌트로만 정의됨
- Hibernate는 지연 로딩 연관 필드에 대리 객체를 넣어 두고, 접근 시점에 조회 쿼리를 실행
    - 단일 참조 연관(`@ManyToOne`, `@OneToOne`)에는 프록시 객체를 넣음
        - 프록시란 실제 엔티티를 대신하는 가짜 객체로, 실제 데이터가 필요한 순간 데이터베이스 조회를 유발하는 대리자를 가리킴
    - 컬렉션 연관(`@OneToMany`, `@ManyToMany`)에는 `PersistentBag`, `PersistentSet` 같은 Hibernate 컬렉션 래퍼를 넣음
        - 컬렉션 래퍼는 요소에 처음 접근하는 시점에 컬렉션 전체를 조회함
    - 이 대리 객체 기반 지연 로딩은 JPA 명세가 강제한 규정이 아니라 Hibernate의 구현 방식

## 연관관계별 기본 FetchType
- 연관관계 애노테이션마다 `fetch` 속성의 기본값이 다름
- JPA 명세가 규정하는 기본값은 아래와 같음

| 애노테이션 | 기본 FetchType | 대상의 다중성 |
|---------|---------------|------------|
| `@ManyToOne` | EAGER | 단일 참조 |
| `@OneToOne` | EAGER | 단일 참조 |
| `@OneToMany` | LAZY | 컬렉션 |
| `@ManyToMany` | LAZY | 컬렉션 |

- 단일 참조 연관(`@ManyToOne`, `@OneToOne`)의 기본값이 EAGER인 이유
    - 단일 엔티티 하나만 딸려오므로 즉시 로딩해도 부담이 작다는 판단에서 비롯함
- 컬렉션 연관(`@OneToMany`, `@ManyToMany`)의 기본값이 LAZY인 이유
    - 컬렉션은 다수의 행을 동반하므로 즉시 로딩하면 불필요하게 큰 결과가 딸려올 수 있음
    - 따라서 접근 시점까지 미루는 LAZY가 기본값
- `@ManyToOne`의 EAGER 기본값에 대한 실무 평가
    - 이 기본값은 N+1을 유발하기 쉬워 부적절한 기본값이라는 지적이 오래전부터 제기됨
    - 실무에서는 단일 참조 연관도 명시적으로 LAZY로 바꾸는 방식을 권장함

> 컬렉션 연관은 기본이 LAZY이나, 단일 참조 연관은 기본이 EAGER임\
> 기본값을 그대로 두면 단일 참조 연관에서 의도치 않은 즉시 로딩이 발생함

## N+1 문제
- 부모 엔티티 N건을 조회한 뒤, 각 부모의 연관 엔티티를 채우려고 추가 쿼리가 N번 더 실행되는 현상
    - 부모 목록을 얻는 쿼리 1번에 더해, 연관 데이터를 얻는 쿼리가 부모 건수만큼 나가 총 N+1번이 됨

### 지연 로딩에서의 발생
- 지연 로딩으로 설정해도 연관 엔티티에 실제로 접근하면 그 시점에 조회 쿼리가 나감

```java
// 회원 전체 조회: SELECT * FROM member → 쿼리 1번
List<Member> members = memberRepository.findAll();

for (Member member : members){
    // member.getOrders() 최초 접근 시점에 회원마다 조회 쿼리 1번씩 발생
    // SELECT * FROM orders WHERE member_id = ? → 회원 수만큼 N번
    int count = member.getOrders().size();
}
```

- 실행되는 쿼리 수의 합산
    - 회원 목록 조회 쿼리 1번
    - 회원마다 주문 조회 쿼리 N번
    - 회원이 N명이면 총 N+1번의 쿼리가 실행됨

### 즉시 로딩에서의 발생
- 즉시 로딩으로 바꾸면 N+1이 해결된다고 오해하기 쉬우나 그렇지 않음
- 문제의 핵심은 로딩 시점이 아니라 프로바이더가 연관 엔티티를 채우려고 추가 쿼리를 내보내는 점에 있음
- JPQL로 부모 목록을 조회하면 즉시 로딩이라도 N+1이 발생함
    - JPQL이란 엔티티를 대상으로 작성하는 객체지향 쿼리 언어로, SQL로 번역되어 실행되는 질의
    - Hibernate는 JPQL을 우선 해석해 부모 엔티티만 조회하는 SQL을 먼저 실행
    - 그 뒤 EAGER 연관을 채우려고 부모 건마다 추가 조회 쿼리를 내보냄
- 즉시 로딩은 발생 시점을 조회 직후로 앞당길 뿐, 추가 쿼리 자체를 없애지 못함
    - 오히려 개발자가 N+1의 발생 지점을 예측하기 어렵게 만듦

## fetch join
- fetch join이란 JPQL에서 연관 엔티티를 한 번의 조인 쿼리로 함께 읽어오도록 지시하는 구문을 가리킴
    - 일반 조인은 연관 엔티티를 영속성 컨텍스트에 채우지 않는 것과 달리, fetch join은 조인한 연관 엔티티까지 결과에 담아 영속화함
- `join fetch` 키워드로 작성함

```java
// 회원과 주문을 한 번의 조인 쿼리로 함께 조회
@Query("SELECT m FROM Member m JOIN FETCH m.orders")
List<Member> findAllWithOrders();
// 실행 SQL: SELECT ... FROM member m INNER JOIN orders o ON m.id = o.member_id
```

- Hibernate에서 JPQL의 `join fetch`는 기본적으로 SQL의 INNER JOIN으로 번역됨
    - 연관 엔티티가 없는 부모를 결과에서 제외하지 않으려면 `left join fetch`로 작성해 LEFT OUTER JOIN으로 유도함
    - 이 조인 종류 대응은 Hibernate의 구현 동작임

## 카테시안 곱과 중복 엔티티
- 카테시안 곱이란 조인 결과에서 한쪽 행이 다른 쪽 행 수만큼 반복되어 곱해지는 현상을 가리킴
    - 엄밀히는 조건 없는 교차 조인의 결과를 뜻하나, JPA에서는 1:N 조인으로 행이 불어나는 현상을 관용적으로 이렇게 부름
- 컬렉션을 fetch join하면 부모 한 건이 자식 건수만큼 결과 행에 중복됨
    - 부모 1건에 자식이 3건이면 조인 결과는 3행이 되고, 각 행마다 부모가 반복됨
    - 이 중복은 SQL 조인의 정상 동작이며 데이터 오류가 아님

```
member(1건)  ×  orders(3건)  →  조인 결과 3행

member_id | order_id
    1     |    10       ← member 1이
    1     |    11       ← 세 번
    1     |    12       ← 반복됨
```

### distinct의 두 층위
- 엔티티 조회에서 발생하는 부모 중복을 제거하려면 JPQL에 `distinct`를 붙임
- distinct는 적용 대상에 따라 의미가 갈림
    - 스칼라 값 조회에서 distinct는 SQL의 DISTINCT로 전달되어 데이터베이스가 중복 행을 제거함
    - 엔티티 조회에서 distinct는 조인으로 중복된 부모 엔티티 참조를 애플리케이션 메모리에서 제거하는 목적을 가짐
- Hibernate 5와 6의 distinct 처리 동작이 다름
    - Hibernate 5는 엔티티 조회의 distinct를 SQL의 DISTINCT로도 전달함
        - 조인된 각 행은 자식 컬럼 값이 서로 달라 SQL DISTINCT로는 제거되지 않음
        - 제거해야 할 중복은 자바 객체 참조 수준에 있으므로, SQL DISTINCT는 효과 없이 정렬 비용만 더함
        - 이 불필요한 SQL DISTINCT를 없애려면 `hibernate.query.passDistinctThrough` 힌트를 false로 설정함
    - Hibernate 6은 `join fetch` 시 중복 부모 엔티티를 항상 자동으로 걸러냄
        - distinct 없이도 부모 엔티티 참조 중복이 제거됨
        - `HINT_PASS_DISTINCT_THROUGH` 힌트는 제거되어 더 이상 존재하지 않음
    - 스칼라 값 조회의 distinct는 두 버전 모두 SQL DISTINCT로 전달함

## `@EntityGraph`
- `@EntityGraph`란 어떤 연관을 함께 조회할지 선언적으로 지정하는 애노테이션을 가리킴
    - JPQL 문자열 없이 fetch 대상 필드명을 나열해 연관 로딩을 지시함
    - Spring Data JPA 리포지토리 메서드에 붙여 사용
- `attributePaths`에 함께 조회할 연관 필드명을 지정함

```java
public interface MemberRepository extends JpaRepository<Member, Long>{
    // orders 연관을 함께 조회하도록 지정
    @EntityGraph(attributePaths = "orders")
    List<Member> findAll();
}
```

- `@EntityGraph`가 무엇을 지정하는지의 범위
    - 무엇을 함께 읽을지를 지정하며, 어떻게 조인할지를 직접 규정하지는 않음
    - Hibernate는 그래프에 지정된 연관을 모두 LEFT OUTER JOIN으로 한 쿼리에 함께 가져옴
    - 따라서 Bag 컬렉션을 둘 이상 지정하면 `@EntityGraph`에서도 `MultipleBagFetchException`이 발생함

### fetch join과 `@EntityGraph`의 조인 종류 차이
- 두 방식은 N+1 해결이라는 목적은 같으나 Hibernate가 생성하는 SQL의 조인 종류가 다름
    - JPQL의 `join fetch`는 기본적으로 INNER JOIN으로 번역됨
    - `@EntityGraph`는 LEFT OUTER JOIN으로 번역됨
- 이 조인 종류 차이가 낳는 결과
    - `@EntityGraph`는 LEFT OUTER JOIN이므로 연관이 없는 부모도 결과에 포함됨
    - `join fetch`는 INNER JOIN이므로 연관이 없는 부모가 결과에서 빠지며, 이를 막으려면 `left join fetch`를 명시해야 함

| 구분 | `join fetch` | `@EntityGraph` |
|-----|--------------|----------------|
| 작성 위치 | JPQL 문자열 | 리포지토리 메서드 애노테이션 |
| 기본 조인 종류 | INNER JOIN | LEFT OUTER JOIN |
| WHERE 조건 작성 | JPQL에 직접 작성 | 파생 쿼리 메서드나 `@Query`와 함께 사용 |
| 지정 성격 | 조회 방법까지 명시 | 함께 조회할 대상만 명시 |

## 배치 Fetch 사이즈
- 배치 Fetch란 지연 로딩할 연관 엔티티를 부모 여러 건에 대해 한 번의 IN 쿼리로 모아 읽어오는 방식을 가리킴
    - 부모마다 개별 쿼리를 내보내는 대신, 부모 식별자를 IN 절에 묶어 조회 횟수를 줄임
- `default_batch_fetch_size`란 IN 절에 묶을 부모 식별자의 최대 개수를 전역으로 지정하는 Hibernate 설정

```properties
# IN 절에 최대 100개의 식별자를 묶어 배치 조회
spring.jpa.properties.hibernate.default_batch_fetch_size=100
```

- 배치 Fetch가 쿼리 수를 줄이는 과정
    - 배치 미적용 시 부모 N건의 지연 로딩은 개별 쿼리 N번으로 실행됨
    - 배치 크기를 100으로 두면 부모 식별자 100개씩 묶어 IN 쿼리 한 번으로 조회
    - 부모가 N건이면 쿼리 수가 대략 N/100 + 1번으로 줄어듦

```
-- 배치 미적용: 부모마다 개별 쿼리
SELECT * FROM orders WHERE member_id = 1
SELECT * FROM orders WHERE member_id = 2
...

-- 배치 크기 100 적용: 식별자를 IN 절에 묶음
SELECT * FROM orders WHERE member_id IN (1, 2, 3, ..., 100)
```

- 배치 Fetch가 fetch join보다 유리한 경우
    - 컬렉션을 fetch join하면 카테시안 곱으로 결과 행이 크게 불어남
    - 배치 fetch는 부모 쿼리와 자식 IN 쿼리를 분리하므로 카테시안 곱을 만들지 않음
    - 부모와 자식을 각각 별도의 더 효율적인 쿼리로 읽어옴
- 특정 엔티티나 컬렉션에만 배치 크기를 지정하려면 `@BatchSize` 애노테이션을 사용함
    - 전역 설정 대신 대상별로 배치 크기를 조정하는 Hibernate 애노테이션
    - `@BatchSize`는 엔티티 클래스(프록시 배치 초기화)나 컬렉션 필드(컬렉션 배치 초기화)에 붙여 사용함
    - IN 절 크기 제한이 있는 데이터베이스에 유의해야 함

## 컬렉션 fetch join의 페이징 한계
- 페이징이란 결과 집합을 일정 크기 단위로 잘라 일부만 조회하는 처리를 가리킴
    - Spring Data JPA에서 `Pageable`, JPA에서 `setFirstResult`/`setMaxResults`로 지정
    - SQL에서는 LIMIT/OFFSET 같은 행 제한 절로 번역됨
- 컬렉션을 fetch join하면서 페이징하면 Hibernate가 데이터베이스에서 행을 제한하지 못함
    - 카테시안 곱으로 한 부모가 여러 행에 흩어져, 데이터베이스 행수와 부모 엔티티 수가 일치하지 않음
    - LIMIT을 SQL에 걸면 부모 단위가 아니라 조인된 행 단위로 잘려 특정 부모의 자식이 일부만 딸려오는 잘못된 결과가 됨
- Hibernate는 이 상황에서 SQL에 행 제한을 걸지 않고, 전체 결과를 읽은 뒤 애플리케이션 메모리에서 페이징을 수행
    - 조건에 맞는 전체 행을 데이터베이스에서 모두 읽어옴
    - 그 뒤 메모리에서 부모 단위로 잘라 페이지를 만듦
    - 데이터가 많으면 대량의 행을 전부 메모리에 적재하므로 성능과 메모리에 심각한 위험이 됨
- Hibernate는 이 상황을 경고 로그로 알림
    - `firstResult/maxResults specified with collection fetch; applying in memory!` 메시지가 출력됨
    - 이 메시지는 페이징이 데이터베이스가 아니라 메모리에서 처리됐음을 알리는 신호임
- 경고의 버전 차이
    - 컬렉션을 조인하면서 페이징하면 `join fetch`와 `@EntityGraph` 모두 두 버전에서 메모리 페이징을 수행함
    - Hibernate 5는 `HHH000104` 코드로 경고를 냄
    - Hibernate 6은 같은 메시지를 `HHH90003004` 코드로 냄

### 페이징 한계의 해결
- 컬렉션 fetch join과 페이징을 함께 쓰지 않고 조회를 둘로 나눔
    - 첫 쿼리로 페이징을 적용해 부모 엔티티의 식별자만 조회함
    - 둘째 쿼리로 그 식별자 목록을 IN 절에 넣어 부모와 자식을 fetch join으로 조회
    - 식별자 조회에는 컬렉션 조인이 없어 데이터베이스 행 제한이 정상 적용됨

```java
// 1단계: 페이징으로 부모 식별자만 조회 (컬렉션 조인 없음 → DB에서 행 제한 적용)
List<Long> memberIds = em.createQuery(
        "SELECT m.id FROM Member m ORDER BY m.id", Long.class)
    .setFirstResult(0)
    .setMaxResults(10)
    .getResultList();

// 2단계: 식별자 목록으로 부모와 자식을 fetch join 조회 (페이징 없음)
// LEFT JOIN FETCH: 주문이 없는 회원도 페이지에서 빠지지 않도록 함
// ORDER BY: 1단계와 같은 순서를 유지
List<Member> members = em.createQuery(
        "SELECT m FROM Member m LEFT JOIN FETCH m.orders WHERE m.id IN :ids ORDER BY m.id", Member.class)
    .setParameter("ids", memberIds)
    .getResultList();
```

- Hibernate 5에서는 2단계 쿼리에 `distinct`를 붙여야 부모 중복이 제거됨

- 배치 fetch 방식으로도 해결할 수 있음
    - 부모를 페이징으로 조회하고 컬렉션은 LAZY로 둔 뒤 `default_batch_fetch_size`로 배치 로딩함
    - 부모 조회에 컬렉션 조인이 없어 페이징이 정상 동작하며, 컬렉션은 IN 쿼리로 모아 읽어옴

## `MultipleBagFetchException`
- Bag이란 순서가 없고 중복을 허용하는 컬렉션을 가리키는 Hibernate 내부 용어
    - 연관을 자바 `List`로 매핑하면서 순서 컬럼(`@OrderColumn`)을 두지 않으면 Hibernate가 Bag으로 취급함
    - Bag은 중복을 허용하므로, 조인 결과에서 반복된 행이 실제 중복 요소인지 조인 때문에 생긴 중복인지 구분할 근거가 없음
- `MultipleBagFetchException`이란 둘 이상의 Bag을 한 쿼리에서 동시에 fetch join할 때 Hibernate가 던지는 예외를 가리킴
    - `cannot simultaneously fetch multiple bags` 메시지를 동반함
    - 두 컬렉션을 동시에 조인하면 카테시안 곱으로 각 요소가 다른 컬렉션의 크기만큼 반복되는데, Bag은 이 반복을 걸러낼 수 없어 잘못된 결과 대신 예외로 막음

```java
// authors와 reviews가 둘 다 List(Bag) → 동시 fetch join 시 예외 발생
@Query("SELECT b FROM Book b JOIN FETCH b.authors JOIN FETCH b.reviews")
List<Book> findAllWithAuthorsAndReviews();
// org.hibernate.loader.MultipleBagFetchException: cannot simultaneously fetch multiple bags
```

### 해결 방법과 각각의 성격
- 컬렉션 타입을 `Set`으로 바꾸는 방법
    - `List`(Bag) 대신 `Set`으로 매핑하면 여러 컬렉션을 한 쿼리로 fetch join해도 예외가 나지 않음
    - `Set`은 중복을 허용하지 않아 조인으로 반복된 행이 하나의 요소로 합쳐지기 때문
    - 다만 이 방법은 여전히 카테시안 곱을 만드는 우회책이며, 곱해진 대량 결과를 한 쿼리로 읽는 비효율을 낳음
    - 자식 요소 수가 적을 때만 적합
- 조회를 여러 쿼리로 나누는 방법
    - 컬렉션마다 별도의 fetch join 쿼리를 실행해 각각 채움
    - 카테시안 곱을 만들지 않아 자식 요소가 많을 때의 이상적 해법
    - 배치 fetch를 병행하면 나뉜 컬렉션 조회를 IN 쿼리로 묶어 더 효율화할 수 있음

## 정리
```
JPA N+1 문제와 Fetch 전략
    │
    ├── FetchType 기본값 (JPA 명세)
    │     ├── @ManyToOne, @OneToOne → EAGER
    │     └── @OneToMany, @ManyToMany → LAZY
    │
    ├── N+1 발생 원리
    │     ├── LAZY: 연관 접근 시점에 N번 추가 쿼리
    │     └── EAGER: 조회 직후 연관 채우려 N번 추가 쿼리
    │
    ├── 해결책
    │     ├── fetch join (JPQL, INNER JOIN)
    │     ├── @EntityGraph (선언적, LEFT OUTER JOIN)
    │     └── 배치 Fetch (IN 절로 묶음, N/size+1 쿼리)
    │
    ├── fetch join의 한계
    │     ├── 카테시안 곱 → 부모 중복 → distinct
    │     ├── 컬렉션 페이징 불가 → 메모리 페이징(5: HHH000104, 6: HHH90003004)
    │     └── 다중 Bag 동시 조인 → MultipleBagFetchException
    │
    └── distinct 버전 차이 (Hibernate 구현)
          ├── 5: SQL DISTINCT 전달, passDistinctThrough로 차단
          └── 6: 부모 중복 자동 제거, 힌트 제거됨
```
