## `@Transactional`
- `@Transactional`이란 메서드나 클래스에 붙여 그 실행 범위를 하나의 트랜잭션으로 묶도록 지시하는 Spring 애노테이션
    - 트랜잭션이란 여러 데이터 변경을 하나의 논리적 단위로 묶어, 전부 반영되거나 전부 취소되도록 보장하는 처리 단위를 가리킴
- 개발자가 커밋과 롤백 호출을 코드에 직접 쓰지 않고, 애노테이션 선언만으로 트랜잭션 경계를 지정하는 방식
    - 이런 선언 기반 방식을 선언적 트랜잭션 관리(declarative transaction management)라고 부름
    - 커밋과 롤백 호출을 코드에 직접 쓰는 방식은 프로그래밍적 트랜잭션 관리(programmatic transaction management)로 구분됨

## 프록시 기반 동작
- `@Transactional`은 대상 빈을 직접 수정하지 않고, 그 빈을 감싸는 프록시 객체를 통해 동작함
    - 프록시란 원본 객체 대신 호출을 먼저 받아 부가 로직을 실행한 뒤 원본에 위임하는 대리 객체를 가리킴
    - Spring은 컨테이너에 원본 빈이 아니라 이 프록시를 등록함
- 프록시가 트랜잭션 경계를 여닫는 순서는 아래와 같음

```
[외부 호출] → [프록시 인터셉트]
    → 트랜잭션 시작(begin)
        → 실제 메서드 실행
    → 정상 종료 시 커밋(commit)
    → 예외 발생 시 롤백(rollback)
    → [프록시가 결과 반환]
```

- 프록시 생성 방식은 대상이 인터페이스를 구현하는지에 따라 갈림
    - JDK 동적 프록시란 인터페이스를 구현해 만드는 프록시를 가리킴
    - CGLIB이란 대상 클래스를 상속(바이트코드 조작)해 서브클래스로 만드는 프록시를 가리킴
    - Spring Boot는 2.x 버전 이후 인터페이스 유무와 무관하게 CGLIB을 기본값으로 사용함

### 자기 호출 함정
- 자기 호출(self-invocation)이란 같은 클래스 내부에서 `this.method()` 형태로 자신의 다른 메서드를 호출하는 것을 가리킴
- 자기 호출은 프록시를 거치지 않으므로, 호출된 메서드의 `@Transactional`이 무시됨
    - 프록시는 외부에서 들어오는 호출만 가로챌 수 있음
    - `this`를 통한 내부 호출은 원본 객체에 직접 도달해 프록시를 우회함

```java
@Service
public class OrderService{

    public void placeOrder(Order order){
        // this. 내부 호출 → 프록시 우회 → 아래 @Transactional 무시됨
        this.saveOrder(order);
    }

    @Transactional
    public void saveOrder(Order order){
        // DB 저장 로직
    }
}
```

- 해결책은 트랜잭션 대상 메서드를 별도 빈으로 분리해 외부 호출로 만드는 구조적 분리가 우선됨
    - 자기 자신을 프록시로 주입받아 호출하는 방식도 가능하나, 가독성을 해쳐 차선책으로 둠

### 메서드 접근 제어자 제약
- 트랜잭션 어드바이스가 적용되는 메서드의 접근 제어자 범위는 프록시 방식과 Spring 버전에 따라 달라짐
    - 이는 표준 규정이 아니라 Spring AOP 프록시 구현의 제약임
- private 메서드는 어떤 프록시 방식에서도 트랜잭션이 적용되지 않음
    - JDK 동적 프록시와 CGLIB 모두 private 메서드를 가로챌 수 없음
- JDK 동적 프록시(인터페이스 기반)는 인터페이스에 선언된 public 메서드에만 적용됨
- CGLIB(클래스 기반) 프록시의 적용 범위는 Spring Framework 6.0을 기준으로 나뉨
    - 6.0 이전에는 public 메서드에만 적용되어, protected·package-private은 무시됨
    - 6.0부터는 protected·package-private 메서드에도 적용됨
- Spring Boot 3.x는 Spring Framework 6.x 기반이므로, 인터페이스가 없는 빈은 CGLIB 프록시로 protected·package-private 메서드까지 트랜잭션이 적용됨

## 트랜잭션 전파
- 전파(propagation)란 이미 트랜잭션이 진행 중인 상태에서 또 다른 `@Transactional` 메서드가 호출될 때, 기존 트랜잭션에 합류할지 새로 시작할지를 결정하는 규칙을 가리킴
- 전파 속성은 `@Transactional(propagation = ...)`으로 지정함

### REQUIRED
- `REQUIRED`란 진행 중인 트랜잭션이 있으면 그 트랜잭션에 합류하고, 없으면 새로 시작하는 전파 속성을 가리킴
    - Spring `@Transactional`의 기본값
- 바깥 메서드와 안쪽 메서드가 하나의 물리적인 트랜잭션을 공유함
    - 안쪽에서 예외가 발생해 롤백되면, 트랜잭션 전체가 함께 롤백됨

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final InnerService innerService;

    @Transactional                  // 트랜잭션 A 시작
    public void outer(){
        saveA();
        innerService.inner();       // 다른 빈 호출 → 프록시 경유 → 전파 적용
    }
}

@Service
public class InnerService {

    @Transactional(propagation = Propagation.REQUIRED)
    public void inner(){            // A에 합류 → outer와 같은 트랜잭션에서 실행
        saveB();
    }
}
```

### REQUIRES_NEW
- 진행 중인 트랜잭션이 있더라도 그것을 잠시 보류(suspend)하고 독립된 새 트랜잭션을 시작하는 전파 속성
    - 바깥 트랜잭션과 물리적으로 분리된 별개의 트랜잭션이 만들어짐
- 안쪽 트랜잭션은 바깥과 독립적으로 커밋 또는 롤백됨
    - 안쪽이 롤백되어도 바깥은 영향받지 않을 수 있음
    - 바깥이 롤백되어도 이미 커밋된 안쪽은 되돌아가지 않음
- 사용 사례는 바깥 작업의 성패와 무관하게 반드시 남겨야 하는 기록임
    - 감사 로그(audit log), 실패 이력 저장 등 본작업이 롤백되어도 별도로 보존해야 하는 데이터에 적합함

```java
@Service
@RequiredArgsConstructor
public class OrderService{

    private final LogService logService;

    @Transactional                  // 트랜잭션 A
    public void outer(){
        saveMain();
        logService.writeLog();      // 다른 빈 호출 → A 보류 → B 시작·커밋 → A 재개
        // 이후 outer가 롤백되어도, 이미 커밋된 writeLog의 결과는 남음
    }
}

@Service
public class LogService{

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void writeLog(){
        saveAuditLog();
    }
}
```
- 주의 사항은 보류된 바깥 트랜잭션과 새 트랜잭션이 동시에 각각의 DB 커넥션을 점유한다는 점
    - 커넥션 풀 크기를 초과하면 교착 상태에 빠질 수 있음

### NESTED
- 진행 중인 트랜잭션 안에 중첩된 하위 지점을 만들어, 그 지점 이후만 부분적으로 되돌릴 수 있게 하는 전파 속성
    - 되돌리는 기준점을 세이브포인트(savepoint)라 하며, 트랜잭션 도중에 설정하는 부분 롤백 지점을 가리킴
- 안쪽에서 예외가 발생하면 세이브포인트까지만 롤백되고, 바깥 트랜잭션은 계속 진행될 수 있음
    - 바깥 트랜잭션이 롤백되면 중첩된 하위 작업도 함께 롤백됨
- `NESTED`는 JDBC 세이브포인트 기능에 의존하므로, 트랜잭션 매니저가 세이브포인트를 지원해야 동작함
- JPA를 사용하는 환경에서는 NESTED가 기본적으로 막혀 있다는 점에 유의

### 세 전파 속성의 비교
- 아래 표는 바깥 트랜잭션이 진행 중인 상태에서 안쪽 메서드가 호출된 경우를 기준으로 함

| 구분 | REQUIRED | REQUIRES_NEW | NESTED |
|-----|----------|--------------|--------|
| 물리적 트랜잭션 | 바깥과 공유 | 바깥과 분리된 새것 | 바깥 안의 중첩 지점 |
| 바깥 트랜잭션 상태 | 그대로 사용 | 보류(suspend) | 그대로 유지 |
| 안쪽 롤백의 영향 | 전체 롤백 | 안쪽만 롤백 | 세이브포인트까지만 롤백 |
| 바깥 롤백 시 안쪽 | 함께 롤백 | 영향 없음(이미 커밋 시) | 함께 롤백 |
| 의존 기반 | 공통 | 커넥션 보류·재개 | JDBC 세이브포인트 |

## 롤백 규칙
- Spring `@Transactional`의 기본 롤백 규칙은 던져진 예외의 종류에 따라 달라짐
- 예외를 구분하는 기준
    - unchecked 예외란 `RuntimeException`과 그 하위 클래스를 가리킴
        - `NullPointerException`, `IllegalArgumentException` 등이 이에 해당함
        - 컴파일러가 처리를 강제하지 않는 예외
    - checked 예외란 `Exception`을 상속하되 `RuntimeException`은 상속하지 않는 예외를 가리킴
        - `IOException`, `SQLException` 등이 이에 해당함
        - 컴파일러가 `try-catch` 또는 `throws` 처리를 강제하는 예외

### 기본 롤백 대상
- Spring은 기본 설정에서 unchecked 예외(`RuntimeException`의 인스턴스 또는 하위 클래스)와 `Error`가 던져진 경우에만 트랜잭션을 롤백함
- checked 예외는 기본 설정에서 롤백을 유발하지 않고, 트랜잭션이 그대로 커밋됨
- 이 규정은 데이터베이스나 JDBC 표준이 아니라 Spring 프레임워크가 정한 기본 동작
    - 이 관례는 EJB(Enterprise JavaBeans)의 규약을 따른 것으로, 시스템 예외(unchecked)는 자동 롤백하되 애플리케이션 예외(checked)는 자동 롤백하지 않는 방식에서 유래함

```java
@Transactional
public void createOrderUnchecked(){
    orderRepository.save(new Order());
    throw new RuntimeException("실패");     // unchecked → 롤백됨
}

@Transactional
public void createOrder() throws IOException{
    orderRepository.save(new Order());
    throw new IOException("파일 없음");     // checked → 롤백되지 않고 커밋됨
}
```

### rollbackFor
- `rollbackFor`란 기본 규칙과 무관하게 롤백을 유발할 예외 타입을 명시적으로 지정하는 `@Transactional`의 속성을 가리킴
- checked 예외에도 롤백을 적용하려면 해당 예외 타입을 `rollbackFor`에 지정함

```java
@Transactional(rollbackFor = Exception.class)
public void createOrder() throws Exception{
    orderRepository.save(new Order());
    throw new Exception("checked 예외");        // rollbackFor 지정 → 롤백됨
}
```
- 반대 방향으로 `noRollbackFor` 속성을 두면, 특정 예외에 대해서는 롤백하지 않도록 예외처리할 수 있음

### 예외를 삼킨 경우
- 트랜잭션 메서드 안에서 예외를 `catch`하고 다시 던지지 않으면, 프록시는 예외를 감지하지 못해 트랜잭션이 커밋됨
    - 프록시는 메서드 밖으로 빠져나온 예외만 볼 수 있음
    - 메서드 내부에서 `catch`로 삼킨 예외는 프록시에 전달되지 않음

```java
@Transactional
public void createOrder(){
    try{
        orderRepository.save(new Order());
        throw new RuntimeException("실패");
    } catch (RuntimeException e){
        // 예외를 삼킴 → 프록시가 감지 못함 → 커밋됨
        log.error("에러", e);
    }
}
```
- 잡되 롤백은 하고 싶다면, 코드로 롤백을 직접 표시하는 방법이 있음

```java
catch (RuntimeException e){
    TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
}
```

## 정리
```
Spring 트랜잭션 관리
    │
    ├── 프록시 기반 동작
    │     ├── JDK 동적 프록시 / CGLIB
    │     ├── 자기 호출 함정 (프록시 우회)
    │     └── 메서드 접근 제어자 제약
    │
    ├── 전파 속성
    │     ├── REQUIRED (기본, 합류)
    │     ├── REQUIRES_NEW (분리, 보류·재개)
    │     └── NESTED (세이브포인트, 부분 롤백)
    │
    └── 롤백 규칙
          ├── unchecked·Error → 기본 롤백
          ├── checked → 기본 커밋
          ├── rollbackFor → 명시적 지정
          └── 예외 삼킴 → 커밋
```
