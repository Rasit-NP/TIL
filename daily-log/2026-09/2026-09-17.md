## 예외 계층 구조
- 예외란 프로그램 실행 중에 발생하는 비정상적 상황 중 프로그램 차원에서 수습이 가능한 것을 가리킴
    - 발생하더라도 대응 코드를 미리 작성해 두면 비정상 종료를 막을 수 있는 오류에 해당함
- Java는 실행 중 발생하는 이상 상황을 클래스로 표현하며, 그 계층의 최상위에 `Throwable`이 있음
    - `Throwable`이란 `throw`문으로 던질 수 있고 `catch`로 받을 수 있는 모든 객체의 최상위 클래스를 가리킴
- `Throwable`은 `Error`와 `Exception` 두 갈래로 나뉨

```
Throwable
├── Error
│   ├── OutOfMemoryError
│   └── StackOverflowError
└── Exception
    ├── IOException
    ├── SQLException
    ├── ClassNotFoundException
    └── RuntimeException
        ├── NullPointerException
        ├── IllegalArgumentException
        ├── ArithmeticException
        └── IndexOutOfBoundsException
```

- `Error`란 애플리케이션 코드가 복구를 시도하는 것이 적절하지 않은 심각한 문제를 가리킴
    - 메모리 부족(`OutOfMemoryError`)이나 스택 넘침(`StackOverflowError`)처럼 JVM 수준의 장애가 이에 해당함
    - 잡아서 처리하기보다 프로그램이 종료되는 편이 옳은 부류
- `Exception`이란 애플리케이션이 잡아서 대응하는 것이 합당한 오류를 가리킴
    - 파일 부재, 잘못된 입력, 네트워크 단절 같은 상황이 이에 해당함
- `RuntimeException`이란 `Exception`의 하위 클래스 중, 주로 프로그래밍 실수로 발생하는 예외 묶음을 가리킴
    - `Exception` 계층 안에서 별도의 취급을 받는 하위 트리를 형성함

## Checked 예외
- Checked 예외란 컴파일러가 처리 여부를 검사하여 강제하는 예외를 가리킴
    - `Exception`을 상속하되 `RuntimeException`은 상속하지 않는 예외가 이에 해당함
    - `IOException`, `SQLException`, `ClassNotFoundException`이 대표적
- 컴파일러가 `try-catch`로 처리하거나 `throws`로 선언할 것을 강제함
    - 둘 중 하나를 하지 않으면 컴파일 에러가 발생함
- 설계 의도는 호출자가 반드시 인지하고 대응해야 하는, 외부 요인에서 비롯되는 예외를 컴파일 시점에 놓치지 못하게 하는 것
    - 파일이 없거나 DB 연결이 끊기는 상황은 정상 흐름에서도 충분히 발생 가능하므로 대비를 요구함

## Unchecked 예외
- Unchecked 예외란 컴파일러가 처리를 강제하지 않는(unchecked) 예외를 가리킴
    - `RuntimeException`과 그 하위 클래스, 그리고 `Error`가 이에 해당함
    - `NullPointerException`, `IllegalArgumentException`, `ArithmeticException`이 대표적
- `try-catch`나 `throws` 없이도 컴파일이 통과됨
- 설계 의도는, 발생 자체가 코드 결함을 뜻하므로 개별적으로 잡기보다 코드를 고쳐야 하는 예외를 별도로 분류하는 것
    - `null` 참조나 배열 범위 초과는 로직을 수정해야 할 결함이지, 매번 잡아 넘길 대상이 아니라는 판단임

## Checked와 Unchecked의 선택 기준

| 구분 | Checked 예외 | Unchecked 예외 |
|-----|-------------|---------------|
| 최상위 기준 | `Exception` 상속, `RuntimeException` 미상속 | `RuntimeException` 또는 `Error` 상속 |
| 컴파일러 강제 | `try-catch` 또는 `throws` 강제 | 강제 없음 |
| 발생 원인 성격 | 외부 요인, 정상 흐름에서도 발생 가능 | 프로그래밍 결함 |
| 대표 예 | `IOException`, `SQLException` | `NullPointerException`, `IllegalArgumentException` |

- 커스텀 예외를 정의할 때 어느 쪽을 상속할지는 호출자가 복구할 수 있는 예외인가를 기준으로 판단함
    - 호출자가 의미 있는 대응을 할 수 있으면 Checked를 고려함
    - 호출자가 할 수 있는 일이 없고 결국 코드 수정이 필요하면 Unchecked를 고려
- 현대 Java 실무에서는 커스텀 예외를 `RuntimeException` 상속으로 만드는 경향이 우세함
    - Checked 예외가 `throws` 선언을 호출 체인 전체에 전파시켜 코드를 번잡하게 만든다는 비판이 널리 받아들여짐
    - 이 경향은 표준 규정이 아니라 관행에 해당하므로, 팀과 프레임워크의 방침에 따라 달라질 수 있음

## Checked 예외와 트랜잭션 롤백의 관계
- Spring `@Transactional`의 기본 롤백 규칙은 이 예외 구분을 그대로 사용함
    - Unchecked 예외와 `Error`가 던져지면 기본적으로 롤백함
    - Checked 예외가 던져지면 기본적으로 롤백하지 않고 커밋함
- 이 동작은 JDBC나 데이터베이스 표준이 아니라 Spring 프레임워크가 정한 기본값임
    - Checked 예외가 롤백되지 않는 이유는, Checked 예외를 호출자가 처리할 수 있는 비즈니스적 예외로 간주하는 관점에서 비롯됨
    - 롤백을 강제하려면 `@Transactional(rollbackFor = ...)`로 예외 타입을 명시적으로 지정함

## 예외 처리 구문
- Java의 기본 예외 처리 구문은 `try-catch-finally`임
    - `try` 블록에는 예외가 발생할 가능성이 있는 코드를 배치
    - `catch` 블록에는 특정 예외 타입이 발생했을 때 실행할 대응 코드를 배치
    - `finally` 블록에는 예외 발생 여부와 무관하게 항상 실행할 코드를 배치
- 발생한 예외 객체는 첫 번째 `catch` 블록부터 순서대로 타입이 대조됨
    - 타입이 일치하는 첫 번째 `catch` 블록 하나만 실행됨
    - 조상 타입을 먼저 배치하면 자손 타입 `catch`가 도달 불가능해져 컴파일 에러가 발생함

```java
try {
    readFile();
} catch (FileNotFoundException e ){     // 더 구체적인 자손을 먼저
    log.warn("파일 없음", e);
} catch (IOException e){                // 더 일반적인 조상을 뒤에
    log.error("입출력 오류", e);
} finally {
    releaseResource();
}
```

## finally의 흐름 개입
- `finally` 블록은 `try`나 `catch`에서 `return`이 실행되어도 그 반환 직전에 항상 실행됨
- `finally`에서 `return` 문을 쓰면 `try`나 `catch`가 결정한 반환값이나 던진 예외를 덮어씀
    - `finally`의 `return`이 최종 반환값이 됨
    - `try`에서 던지려던 예외조차 `finally`의 `return`에 의해 삼켜짐

```java
static int trap(){
    try{
        throw new RuntimeException("원래 예외");
    } finally {
        return 42;      // 예외가 사라지고 42가 반환됨
    }
}
```

- 이 동작은 예외와 반환값을 소리 없이 사라지게 하므로 `finally`에서 `return`하는 것은 금지에 가까운 안티 패턴으로 취급됨
    - `finally`의 역할은 자원 해제 등 정리 작업에 한정하는 것이 권장됨

## try-with-resources
- try-with-resources란 `try`의 괄호 안에서 자원을 선언하면 블록 종료 시 그 자원을 자동으로 닫아 주는 구문을 가리킴
    - Java 7에서 도입됨
    - 괄호 안에 선언할 수 있는 대상은 `AutoCloseable` 인터페이스를 구현한 객체로 한정됨
- `AutoCloseable`이란 `close()` 메서드 하나를 규정한 인터페이스로, 자동으로 닫을 수 있는(auto + closeable) 자원을 표시함
    - 파일 스트림, DB 커넥션, 소켓처럼 사용 후 반드시 반납해야 하는 자원이 이를 구현함
- 이 구문이 해결하는 문제는, 전통적 `try-finally` 방식에서 자원 해제 코드가 누락되거나 중첩되어 복잡해지는 것

```java
// 전통적 방식: finally에서 null 검사와 중첩 try-catch가 필요
BufferedReader br = null;
try {
    br = new BufferedReader(new FileReader("data.txt"));
    return br.readLine();
} finally {
    if (br != null){
        try {
            br.close();             // close 자체가 예외를 던질 수 있어 또 감싸야 함
        } catch (IOException e){
            // 처리 곤란
        }
    }
}
```
```java
// try-with-resources: 선언만 하면 close가 자동 보장됨
try (BufferedReader br = new BufferedReader(new FileReader("data.txt"))){
    return br.readLine();
}       // 블록을 벗어나는 순간 br.close()가 자동 호출됨
```
- 자원이 여러 개면 선언한 순서의 역순으로 닫힘
    - 나중에 만든 자원이 먼저 닫힘
    - 뒤의 자원이 앞의 자원에 의존하는 경우가 많으므로 역순 해제가 안전함

## 억제된 예외(Suppressed Exception)
- 다른 예외를 전달하기 위해 뒤로 밀려나 보관되는 예외
- try-with-resources에서 `try` 블록과 `close()`가 모두 예외를 던지면, `try` 블록의 예외가 대표로 전파되고 `close()`의 예외는 억제됨
    - 억제된 예외는 대표 예외의 `getSuppressed()` 메서드로 배열 형태로 꺼낼 수 있음
    - 이는 Java 표준(Oracle 공식 문서)이 규정한 동작

```java
try (CustomResource r = new CustomResource()){
    throw new RuntimeException("작업 중 예외");     // 이 예외가 대표로 전파됨
}   // close()가 던진 예외는 억제되어 getSuppressed()에 담김
```

- 이 지점이 전통적 `try-finally`와 정반대임에 주의함
    - 전통적 `try-finally`에서는 `try`가 예외를 던지는 도중 `finally`가 또 예외를 던지면, 나중에 발생한 `finally`의 예외가 원래 예외를 덮어써 원래 예외가 소실됨
    - try-with-resources는 원래 예외를 보존하고 `close()` 예외를 억제 목록에 붙여, 두 정보를 모두 남김

## 예외 전파(Exception Propagation)
- 예외가 처리되지 않으면 메서드 호출 스택을 따라 호출자 방향으로 되던져지는 흐름
- 어떤 메서드에서 예외가 발생했는데 그 메서드에 일치하는 `catch`가 없으면, 그 메서드를 호출한 상위 메서드로 넘어감
    - 이 과정이 반복되며 스택을 거슬러 올라감
    - 최상위까지 처리되지 못하면 `UncaughtExceptionHandler`가 받아 스택 트레이스를 출력하고 해당 스레드가 종료됨

## 예외 번역
- 하위 계층에서 발생한 예외를 상위 계층에 맞는 다른 예외로 감싸 다시 던지는 처리
    - 원래 예외를 새 예외의 원인으로 담아 던지는 방식이 일반적
- 목적은 상위 계층이 하위 계층의 구현 세부에 결합되지 않도록 추상화 수준을 맞추는 것
    - 데이터 접근 계층의 `SQLException`을 서비스 계층이 그대로 받으면 서비스가 JDBC에 종속됨
    - 이를 도메인 예외로 번역하면 계층 간 결합이 끊어짐
```java
try {
    connection.prepareStatement(sql).executeUpdate();   // SQLException을 던짐
} catch (SQLException e){
    throw new OrderSaveException("주문 저장 실패", e);      // 원래 예외를 cause로 보존
}
```
- 번역 시 원래 예외를 `cause`로 반드시 보존해야 함
    - 원인 예외를 버리면 근본 원인 추적이 불가능해짐
    - 생성자에 원인을 넘기거나 `initCause()`로 연결

## 예외 삼킴(Exception Swallowing)
- 예외를 `catch`하고도 아무 대응 없이 흐름을 계속 진행시켜 예외를 사라지게 하는 처리
- 빈 `catch` 블록이 대표적
    - 예외가 발생한 사실 자체가 어디에도 남지 않아 장애 원인 추적이 불가능해짐

```java
try {
    riskyOperation();
} catch(Exception e){
    // 아무것도 하지 않음 → 예외가 소리 없이 사라짐
}
```
- Spring 트랜잭션에서 특히 위험함
    - 트랜잭션 메서드 안에서 예외를 잡고 다시 던지지 않으면, 프록시가 예외를 감지하지 못해 롤백 대상이었던 트랜잭션이 커밋됨
- 잡아야 한다면 최소한 로그로 남기거나, 번역해 다시 던지거나, 복구가 실제로 가능한 경우에만 삼키는 것을 지향함

## Optional의 설계 목적
- `Optional<T>`란 값이 있을 수도 없을 수도 있음을 타입으로 표현하는, 하나의 값을 감싸는 컨테이너 객체를 가리킴
    - Java 8에서 도입됨
- 등장 배경은 `null` 반환이 유발하는 `NullPointerException`을 타입 수준에서 방어하는 것
    - 메서드 반환 타입이 `Optional`이면 호출자는 값이 없을 가능성을 컴파일 시점에 인지하게 됨
    - 값의 부재를 `null`이라는 암묵적 신호가 아니라 명시적 타입으로 드러냄

```java
Optional<User> findById(Long id){
    User user = repository.get(id);
    return Optional.ofNullable(user);   // user가 null이면 빈 Optional
}

// 호출 측: 부재를 명시적으로 다루도록 강제됨
String name = findById(1L)
    .map(User::getName)
    .orElse("이름 없음");
```

- 값을 꺼낼 때는 부재 상황을 함께 처리하는 메서드를 사용함
    - `orElse(기본값)`은 값이 없으면 기본값을 반환함
    - `orElseGet(공급자)`는 값이 없을 때만 공급자를 호출해 기본값을 생성함
    - `orElseThrow()`는 값이 없으면 예외를 던짐

## Optional의 오용 패턴
- `Optional`은 메서드 반환 타입으로 쓰도록 설계된 것이며, 다른 위치에서의 사용은 오용으로 지적됨
- 필드에 `Optional`을 쓰지 않는 것이 권장됨
    - `Optional`은 `Serializable`을 구현하지 않아 직렬화 대상 필드에 부적합함
    - 값 자체를 담을 목적의 필드에 컨테이너를 한 겹 덧씌우면 객체 구조가 불필요하게 복잡해짐
- 메서드 파라미터에 `Optional`을 쓰지 않는 것이 권장됨
    - 호출자가 `Optional.of(...)`로 감싸야 하는 부담이 생겨 호출부가 번잡해짐
    - 파라미터를 받지 않는 오버로딩이나 `null` 허용이 더 단순한 대안인 경우가 많음
    - 게다가 `Optional` 파라미터 자체가 `null`로 전달될 수 있어, 방어하려던 문제가 오히려 한 겹 늘어남
- `get()`을 부재 검사 없이 호출하지 않는 것이 권장됨
    - 빈 `Optional`에 `get()`을 호출하면 `NoSuchElementException`이 발생함
    - 이는 `null` 검사 없이 참조를 역참조하는 것과 위험도가 다르지 않음
- 컬렉션을 `Optional`로 감싸지 않는 것이 권장됨
    - 빈 컬렉션 자체가 이미 값의 부재를 표현하므로, `Optional<List<T>>` 대신 빈 리스트를 반환하는 편이 단순함

> Optional은 반환 타입의 부재 가능성을 드러내는 도구임\
> 필드, 파라미터, 컬렉션 래핑은 오용에 해당하며, 값 추출 시 부재 처리를 동반하는 메서드를 사용함

## 정리
```
Java 예외 처리와 Optional
    │
    ├── 예외 계층
    │     ├── Throwable
    │     ├── Error (복구 불가)
    │     └── Exception
    │           ├── Checked (컴파일러 강제)
    │           └── RuntimeException (Unchecked)
    │
    ├── 처리 구문
    │     ├── try-catch-finally
    │     ├── finally return 안티 패턴
    │     └── try-with-resources
    │           ├── AutoCloseable
    │           ├── 역순 해제
    │           └── 억제된 예외
    │
    ├── 예외 흐름
    │     ├── 전파
    │     ├── 번역 (cause 보존)
    │     └── 삼킴 (안티 패턴)
    │
    └── Optional
          ├── 반환 타입에서의 부재 표현
          └── 오용 (필드·파라미터·컬렉션·무검사 get)
```
