## 경쟁 조건
### 경쟁 조건(Race Condition)
- 둘 이상의 실행 흐름이 공유 자원에 접근할 때, 실행 순서와 타이밍에 따라 결과가 달라지는 상황
- 실행 흐름들이 공유 자원에 먼저 도달하려고 경쟁한 결과가 최종 값을 결정한다는 데서 붙은 이름
- 실행 흐름은 프로세스와 스레드 모두 가리키며, 아래 예시들은 메모리를 공유하는 스레드를 기준으로 함

### 데이터 레이스(Data Race)
- 동기화 없이 둘 이상의 스레드가 같은 메모리 위치에 동시에 접근하고, 그중 하나 이상이 쓰기인 상태를 가리키는 언어 메모리 모델 수준의 용어
- C++과 Java의 메모리 모델이 각각 이 용어를 정의함
- 데이터 레이스가 없어도 경쟁 조건은 발생할 수 있음
    - check-then-act는 조건을 확인한 뒤 그 결과에 따라 행동하는 코드 패턴
    - 잔액 조회와 출금을 각각 동기화된 연산으로 수행해도, 두 연산 사이에 다른 스레드의 출금이 끼어들면 앞서 확인한 잔액 조건이 더 이상 참이 아니게 됨
    - 이 경우 개별 메모리 접근은 모두 동기화되어 있지만, 확인과 행동을 묶은 전체 구간이 보호되지 않아 잔액이 음수가 될 수 있음

### 임계 영역(critical section)
- 공유 자원에 접근하는 코드 구간 중, 한 시점에 하나의 실행 흐름만 실행해야 하는 구간
- 보호 대상이 자원 자체가 아니라 그 자원을 읽고 쓰는 코드 구간이라는 점에서 공유 자원과 구분됨
- Windows API의 `CRITICAL_SECTION`은 같은 프로세스의 스레드끼리만 쓸 수 있는 상호 배제용 동기화 객체의 이름이며, 개념 용어인 임계 영역과는 층위가 다름
- 임계 영역 문제(critical section problem)
    - 여러 실행 흐름이 임계 영역에 안전하게 드나들도록 진입 규약과 퇴출 규약을 설계하는 문제
- 해법은 아래 세 요구 조건을 모두 만족해야 함
    - 상호 배제(mutual exclusion)
        - 한 실행 흐름이 임계 영역을 실행 중이면 다른 실행 흐름은 그 임계 영역에 들어갈 수 없다는 조건
    - 진행(progress)
        - 임계 영역이 비어 있을 때, 진입을 원하는 실행 흐름 중 다음 진입자를 고르는 결정이 무한히 미뤄지지 않아야 한다는 조건
    - 한정 대기(bounded waiting)
        - 한 실행 흐름이 진입을 요청한 뒤, 다른 실행 흐름이 먼저 진입할 수 있는 횟수에 상한이 있어야 한다는 조건
- 세 조건의 명칭과 구분은 Silberschatz 계열 운영체제 교재의 정리를 따름

### `count++` 비원자성
- 원자적 연산(atomic operation)
    - 다른 실행 흐름이 중간 상태를 관찰하거나 끼어들 수 없어, 전부 수행되었거나 전부 수행되지 않은 것으로만 보이는 연산
- `count++`는 소스 코드상 한 줄이지만 실행 시에는 세 단계의 읽기-수정-쓰기(read-modify-write)로 수행됨
    - 읽기
        - 메모리의 count 값을 레지스터로 가져옴
    - 수정
        - 레지스터 값에 1을 더함
    - 쓰기
        - 레지스터 값을 메모리의 count에 저장함
- 갱신 손실(lost update)
    - 한 스레드의 갱신이 다른 스레드의 쓰기에 덮여 최종 결과에 반영되지 않는 현상
- 두 스레드가 같은 값을 읽은 뒤 각자 1을 더해 쓰면, 먼저 쓴 쪽의 증가가 나중에 쓴 쪽의 쓰기에 덮여 갱신 손실이 발생함

```
count = 0

스레드 A                       스레드 B
────────                     ────────
읽기   (레지스터 = 0)
                             읽기   (레지스터 = 0)
수정   (레지스터 = 1)
                             수정   (레지스터 = 1)
쓰기   (count = 1)
                             쓰기   (count = 1)

결과  count = 1  (기대값 2, A의 증가가 B의 쓰기에 덮임)
```

- 세 단계 사이에 다른 스레드가 끼어드는 경로는 두 가지임
    - 선점(preemption)
        - 운영체제가 실행 중인 스레드를 중단시키고 다른 스레드에 CPU를 넘기는 것
    - 단일 코어에서는 세 단계가 별개 명령어로 실행될 때, 그 사이에서 선점이 일어나 다른 스레드가 먼저 실행되는 경로가 있음
    - 멀티코어에서는 두 스레드가 서로 다른 코어에서 세 단계를 동시에 진행하는 경로가 있음
- 아래 코드는 두 스레드가 같은 변수를 동기화 없이 증가시킴

```java
public class CounterRace {
    private static int count = 0;

    public static void main(String[] args) throws InterruptedException{
        Runnable task = () -> {
            for (int i=0; i<100_000; ++i){
                count++;    // 읽기-수정-쓰기 세 단계, 원자적이지 않음
            }
        };

        Thread a = new Thread(task);
        Thread b = new Thread(task);
        a.start();
        b.start();
        a.join();       // 두 스레드의 종료를 기다림
        b.join();
        System.out.println(count);  // 200000보다 작은 값이 나올 수 있음
    }
}
```

- 명령어 하나로 컴파일되어도 원자성이 보장되지 않음
    - x86에서 메모리 피연산자에 직접 1을 더하는 `add`, `inc` 명령어도 내부적으로는 읽기-수정-쓰기로 동작함
    - 멀티코어에서 이 명령어를 원자적으로 만들려면 `lock` 접두사를 붙여야 함
    - 따라서 한 줄의 코드인지, 명령어 하나인지는 원자성의 판단 기준이 되지 못함
- 해결은 `count++` 구간을 임계 영역으로 보고 상호 배제를 적용하는 것임

## 동기화 도구
### 동기화 도구(Synchronization primitive)
- 임계 영역의 상호 배제나 실행 흐름 사이의 순서 제어를 구현하도록 운영체제나 라이브러리가 제공하는 기본 구성 요소
- 락(lock)
    - 상호 배제를 구현하기 위해 스레드가 획득하고 해제하는 객체를 통칭하는 용어
- 블록(block)
    - 스레드가 실행 가능 상태에서 빠져, 기다리는 조건이 충족될 때까지 CPU를 할당받지 않는 상태

### 뮤텍스(mutex)
- mutual exclusion
- 한 시점에 하나의 스레드만 보유할 수 있도록 하여 임계 영역의 상호 배제를 구현하는 락
- 스레드는 임계 영역에 들어가기 전 락을 획득(lock)하고, 나올 때 해제(unlock)함
- 다른 스레드가 이미 락을 보유 중이면 요청한 스레드는 해제될 때까지 대기함
    - POSIX `pthread_mutex_lock`은 락을 얻을 때까지 호출 스레드를 블록시키도록 규정함
- 소유권(ownership)
    - 락을 획득한 스레드가 그 락의 소유자가 되며, 해제 권한이 소유자에게만 있다는 성질
    - 뮤텍스를 소유자 개념이 없는 다른 동기화 도구와 구분하는 핵심 성질
- 소유자를 알 수 있으므로 두 가지 잘못된 사용을 규정하거나 탐지할 수 있음
    - 비소유자 해제
        - 락을 보유하지 않은 스레드가 해제를 시도하는 경우
    - 재잠금
        - 락을 이미 보유한 스레드가 같은 락을 다시 획득하려는 경우
- 재귀 뮤텍스(recursive mutex)
    - 소유 스레드의 재잠금을 허용하고 잠금 횟수를 세어, 횟수가 0이 될 때 비로소 해제되는 뮤텍스
- 미정의 동작(undefined behavior)
    - 표준이 결과를 규정하지 않아 구현에 따라 어떤 결과든 나올 수 있는 동작
- POSIX 표준은 뮤텍스 유형별로 두 경우의 동작을 아래와 같이 규정함

| 유형 | 소유자의 재잠금 | 비소유자의 해제 |
|-----|-------------|-------------|
| `PTHREAD_MUTEX_NORMAL` | 데드락 | 미정의 동작 |
| `PTHREAD_MUTEX_ERRORCHECK` | 오류 반환(`EDEADLK`) | 오류 반환(`EPERM`) |
| `PTHREAD_MUTEX_RECURSIVE` | 잠금 횟수 증가 | 오류 반환(`EPERM`) |
| `PTHREAD_MUTEX_DEFAULT` | 미정의 동작 | 미정의 동작 |

- 표의 데드락은 스레드가 자기 자신이 보유한 락의 해제를 기다리며 영원히 멈추는 상태를 가리킴
    - 다른 스레드를 기다리는 일반적인 데드락 정의와 달리 스레드 하나만 관여하지만, POSIX가 이 경우도 데드락이라 부름
- 재진입(reentrancy)
    - 락을 보유한 스레드가 같은 락을 다시 획득해도 멈추지 않는 성질
- Java 구현에서는 `java.util.concurrent.locks.ReentrantLock`이 재진입을 허용하는 뮤텍스, 즉 재귀 뮤텍스에 해당함
    - 소유 스레드가 다시 `lock()`을 호출하면 보유 횟수만 1 증가함
    - 소유자가 아닌 스레드가 `unlock()`을 호출하면 `IllegalMonitorStateException`이 발생함

### 세마포어(semaphore)
- 사용 가능한 자원 수를 나타내는 정수 값과, 그 값을 원자적으로 감소시키거나 증가시키는 두 연산으로 이루어진 동기화 도구
- 1960년대 Dijkstra가 제안함
- P 연산(wait)
    - 값이 0보다 크면 1 감소시키고 진행하며, 0이면 값이 양수가 될 때까지 대기하는 연산
- V 연산(signal)
    - 값을 1 증가시키고, 대기 중인 스레드가 있으면 그중 하나를 깨우는 연산
- 구현에 따라 P 연산이 값을 먼저 감소시켜 음수를 허용하고, 그 절댓값을 대기 스레드 수로 해석하기도 함
- 연산 이름은 층위마다 다름
    - 교재(개념)의 wait, signal
    - POSIX API의 `sem_wait`, `sem_post`
    - Java `java.util.concurrent.Semaphore`의 `acquire`, `release`
- 카운팅 세마포어(counting semaphore)
    - 값을 0과 1로 제한하지 않고 자원 수만큼의 정수 값을 쓰는 세마포어
    - 동시에 쓸 수 있는 자원이 N개이면 N으로 초기화함
- 이진 세마포어(binary semaphore)
    - 값이 0과 1만 갖도록 쓰는 세마포어
    - POSIX와 Java의 세마포어에는 별도의 이진 타입이 없으며, 카운팅 세마포어를 1로 초기화해 값이 1을 넘지 않게 사용
- 세마포어에는 소유자 개념이 없음
    - 어떤 스레드든 V 연산을 호출할 수 있으며, 그 스레드가 이전에 P 연산을 했는지 확인하지 않음
    - Java `Semaphore` 명세는 `release`를 호출하는 스레드가 `acquire`로 허가를 얻었을 필요가 없다고 명시함
- 세마포어의 대표 용도는 두 가지임
    - 자원 수 제한
        - 커넥션 풀처럼 N개의 자원을 N으로 초기화한 세마포어로 보호해 동시 사용 수를 N 이하로 제한함
    - 실행 순서 신호
        - 값을 0으로 초기화하고, 기다리는 스레드가 P 연산을 호출하며, 선행 작업을 끝낸 다른 스레드가 V 연산을 호출함
        - 기다리는 쪽과 알리는 쪽이 서로 다른 스레드이므로, 소유권이 없다는 성질이 이 용도를 가능하게 함
- 두 도구의 차이는 아래와 같음

| 구분 | 뮤텍스 | 세마포어 |
|-----|------|--------|
| 상태 | 잠김 또는 풀림 | 정수 값 |
| 동시 진입 수 | 1 | 초기값만큼 |
| 소유권 | 있음 | 없음 |
| 해제 주체 | 소유 스레드만 | 어떤 스레드든 |
| 주 용도 | 임계 영역 상호 배제 | 자원 수 제한, 스레드 간 순서 신호 |

> 뮤텍스는 소유자가 있는 락이고, 세마포어는 소유자가 없는 카운터임\
> 이진 세마포어와 뮤텍스의 차이는 값의 범위가 아니라 소유권 유무에 있음

### 이진 세마포어 기반 상호 배제
- 이진 세마포어로도 상호 배제 자체는 구현됨
    - 값 1에서 시작해 진입 전 P, 퇴출 후 V를 호출하면 한 번에 하나의 스레드만 임계 영역에 들어감
    - Java `Semaphore` 명세도 1로 초기화한 세마포어를 상호 배제 락으로 쓸 수 있다고 기술함
- 다만 소유권이 없어서 뮤텍스가 주는 보장을 잃음
    - 비소유자 해제 탐지 불가
        - 임계 영역에 들어가지 않은 스레드가 실수로 V를 호출해도 오류 없이 값이 증가함
    - 값이 1을 넘는 상태 허용
        - Java `Semaphore`와 POSIX 세마포어는 V 연산 시 초기값을 기준으로 한 상한을 검사하지 않음
        - 잘못된 V 호출로 값이 2가 되면 두 스레드가 동시에 임계 영역에 들어가 상호 배제가 깨짐
    - 재진입 불가
        - 값이 0인 상태에서 같은 스레드가 다시 P를 호출하면, 정상적인 사용 흐름에서 V를 호출할 스레드가 자기 자신뿐인 상황에서 스스로 대기에 들어가 영원히 멈춤
- 상호 배제가 목적이면 잘못된 사용을 규정하거나 탐지할 수 있는 뮤텍스를, 자원 수 제한이나 스레드 간 신호가 목적이면 세마포어를 쓰는 것이 용도에 맞음

### 락 비용
- 경합(lock contention)
    - 둘 이상의 스레드가 같은 락을 동시에 요청하는 상황
- 컨텍스트 스위칭(context switching)
    - CPU가 실행하던 스레드의 상태를 저장하고 다른 스레드의 상태를 복원해 실행을 넘기는 작업
- 직렬화(serialization)
    - 여러 스레드의 실행이 한 구간에서 동시에 진행되지 못하고 차례대로 하나씩 수행되는 것
- 경합이 생기면 두 종류의 비용이 발생함
    - 락을 얻지 못한 스레드가 블록되었다가 나중에 깨어나므로 컨텍스트 스위칭 비용이 듦
    - 임계 영역은 한 번에 하나의 스레드만 실행하므로 그 구간이 직렬화되어, 코어 수를 늘려도 그 구간의 처리량은 늘지 않음
- 경합이 없을 때의 비용은 구현에 따라 다름
    - futex(fast user-space mutex)
        - 락 상태를 사용자 공간의 정수 하나로 두고, 경합 시의 대기와 깨우기만 커널이 담당하는 Linux의 락 구성 요소
    - Linux glibc의 스레드 구현(NPTL)이 제공하는 pthread 뮤텍스는 futex 위에 구현되어 있음
    - 시스템 콜(system call)
        - 사용자 프로그램이 커널의 기능을 요청하기 위해 커널 모드로 진입하는 호출
    - futex 기반 락은 경합이 없으면 사용자 공간의 원자적 연산만으로 획득과 해제가 끝나 시스템 콜이 발생하지 않음
- 따라서 락 비용은 락 사용 여부보다 경합 정도와 임계 영역 길이에 크게 좌우됨
- 공유되지 않는 데이터나 변경되지 않는 데이터에는 경쟁 조건이 생기지 않으므로, 락은 공유되면서 변경되는 데이터를 다루는 최소 구간에만 적용함

## 데드락
### 데드락(deadlock)
- 스레드 집합의 각 스레드가 그 집합의 다른 스레드만 일으킬 수 있는 사건(주로 자원 해제)을 기다려, 어느 스레드도 진행할 수 없는 상태
- 번역어는 주로 교착 상태를 사용함

### 기아(starvation)
- 시스템 전체는 진행하지만 특정 스레드만 자원을 계속 얻지 못해 무한히 기다리는 상태
- 데드락은 관련 스레드 전원이 멈추는 반면 기아는 다른 스레드가 계속 진행한다는 점이 다름

### 발생 조건
- 1971년 Coffman 등이 정리한 네 조건이 동시에 성립해야 데드락이 발생함
- 상호 배제(mutual exclusion)
    - 자원을 한 번에 하나의 스레드만 점유할 수 있다는 조건
    - 임계 영역의 요구 조건인 상호 배제와 같은 성질을 자원 관점에서 본 조건
- 점유 대기(hold and wait)
    - 스레드가 자원을 하나 이상 점유한 채로 다른 스레드가 점유한 자원을 추가로 기다린다는 조건
- 비선점(no preemption)
    - 스레드가 점유한 자원을 다른 스레드나 운영체제가 강제로 빼앗을 수 없고, 점유한 스레드가 스스로 해제해야만 한다는 조건
- 순환 대기(circular wait)
    - 스레드 T1은 T2가, T2는 T3가, ..., Tn은 T1이 점유한 자원을 기다리는 원형 사슬이 존재한다는 조건
- 네 조건은 필요조건이므로 하나라도 성립하지 않으면 데드락은 발생하지 않음
- 조건 성립이 데드락으로 확정되는지는 자원의 인스턴스 수에 따라 다름
    - 인스턴스(instance)
        - 같은 종류로 취급되어 서로 대체할 수 있는 자원 하나하나
    - 뮤텍스처럼 자원마다 인스턴스가 하나뿐이면, 순환 대기가 생기는 순간 데드락이 확정됨
    - 자원 종류마다 인스턴스가 여러 개이면, 요청과 점유 관계에 순환이 있어도 순환 밖 스레드가 같은 종류의 인스턴스를 반납해 대기가 풀릴 수 있으므로 순환만으로는 데드락이 확정되지 않음

### 데드락 예방
- 네 조건 중 하나 이상이 구조적으로 성립할 수 없도록 자원 사용 규칙을 설계하는 접근
- 요청 시점마다 할당 후 상태의 안전 여부를 계산해 할당을 결정하는 회피(avoidance)와 구분되는 접근
- 상호 배제 제거
    - 자원을 여러 스레드가 동시에 사용할 수 있는 형태로 바꿈
    - 읽기 전용 데이터나 불변 객체는 락이 필요 없으므로 이 조건이 성립하지 않음
    - 계좌 잔액처럼 갱신이 필요한 자원은 상호 배제가 정합성의 전제이므로 이 방법을 적용할 수 없음
- 점유 대기 제거
    - 필요한 락을 한 번에 모두 획득하거나, 락을 하나도 보유하지 않은 상태에서만 새 락을 요청하도록 함
    - 모든 계좌를 하나의 전역 락으로 보호하는 방식도 스레드가 락을 하나만 보유하게 되므로 여기에 속하며, 이 경우 서로 무관한 이체까지 직렬화됨
    - 필요한 자원을 미리 알아야 하고, 쓰지 않는 동안에도 자원을 붙잡아 병행성이 떨어짐
    - 여러 자원을 한꺼번에 얻어야 하는 스레드는 모든 자원이 동시에 비는 시점을 기다려야 하므로 기아가 발생할 수 있음
- 비선점 제거
    - 대기에 들어가는 스레드가 보유한 자원을 회수하는 방식
    - 락에서는 다음 락을 얻지 못한 스레드가 이미 보유한 락을 모두 스스로 해제하고 처음부터 다시 시도하는 형태로 구현함
    - Java `ReentrantLock.tryLock(timeout, unit)`은 지정 시간 안에 락을 얻지 못하면 `false`를 반환하므로 이 방식을 구현할 수 있음
    - 해제 후 재시도가 가능하려면 락을 얻기 전까지 수행한 작업이 없거나 되돌릴 수 있어야 함
    - 라이브락(livelock)
        - 스레드들이 실행은 계속하지만 서로의 재시도가 계속 충돌해 어느 쪽도 작업을 진척시키지 못하는 상태
    - 두 스레드가 같은 주기로 해제와 재시도를 반복하면 라이브락이 발생할 수 있으므로, 재시도 전 대기 시간을 무작위로 둠
- 순환 대기 제거
    - 모든 락에 순서를 정하고, 모든 스레드가 그 순서대로만 락을 획득하도록 함
    - 순서상 앞선 락을 보유한 스레드만 뒤 락을 기다리게 되어 대기 관계가 한 방향으로만 이어지므로 원형 사슬이 생기지 않음
    - 자원을 미리 모두 잡거나 작업을 되돌릴 필요가 없어, 락 사이의 순서만 정할 수 있으면 적용 비용이 작음

### 락 획득 순서 고정
- 계좌 간 이체는 출금 계좌의 락과 입금 계좌의 락을 함께 보유해야 하는 작업
- 락 획득 순서를 호출 인자 순서에 맡기면 데드락이 발생할 수 있음

```java
// 실패 사례: 락 획득 순서가 호출 인자 순서에 따라 달라짐
// Account는 계좌별 ReentrantLock을 getLock()으로 제공한다고 가정
public void transfer(Account from, Account to, long amount){
    from.getLock().lock();
    try{
        to.getLock().lock();        // from의 락을 보유한 채 to의 락을 기다림
        try {
            from.withdraw(amount);
            to.deposit(amount);
        } finally {
            to.getLock().unlock();
        }
    } finally {
        from.getLock().unlock();
    }
}
```
- 두 스레드가 같은 계좌에 대해 반대 방향으로 동시에 이체하면 아래 순서로 멈춤

```
스레드 1: transfer(A, B)          스레드 2: transfer(B, A)
────────────────────────          ────────────────────────
A 락 획득
                                  B 락 획득
B 락 대기 (스레드 2가 보유)
                                  A 락 대기 (스레드 1이 보유)

→ 두 스레드 모두 상대의 해제를 기다리며 영원히 멈춤
```

- 이 상황에서 네 조건이 모두 성립함
    - 계좌 락은 한 스레드만 보유할 수 있으므로 상호 배제가 성립함
    - 한 계좌의 락을 보유한 채 다른 계좌의 락을 기다리므로 점유 대기가 성립함
    - `lock()`으로 얻은 락은 보유 스레드가 스스로 해제할 때까지 풀리지 않으므로 비선점이 성립함
    - 두 스레드가 서로의 락을 기다리므로 순환 대기가 성립함
- 계좌 ID처럼 고유하고 변하지 않는 키로 락 순서를 정하면 순환 대기가 제거됨

```java
// 해결: 계좌 ID가 작은 쪽의 락을 항상 먼저 획득
// getId()는 계좌마다 고유하고 변하지 않는 long 값을 반환한다고 가정
public void transfer(Account from, Account to, long amount){
    if (from.getId() == to.getId()){
        throw new IllegalArgumentException("동일 계좌 간 이체 불가");
    }
    Account first  = from.getId() < to.getId() ? from : to;
    Account second = from.getId() < to.getId() ? to : from;

    first.getLock().lock();          // transfer(A, B)와 transfer(B, A)가 같은 락을 먼저 요청함
    try {
        second.getLock().lock();
        try {
            from.withdraw(amount);  // 잔액 확인과 차감이 두 락을 보유한 구간 안에서 수행됨
            to.deposit(amount);
        } finally {
            second.getLock().unlock();
        }
    } finally {
        first.getLock().unlock();
    }
}
```

- A의 ID가 B보다 작으면 두 스레드가 모두 A 락을 먼저 요청하므로, A 락을 얻은 쪽만 B 락으로 진행하고 다른 쪽은 락을 하나도 보유하지 않은 채로 대기함
- 이 방법에는 아래 경계 조건이 있음
    - 정렬 키의 고유성
        - 서로 다른 두 계좌가 같은 키를 가질 수 있으면, 두 스레드가 서로 다른 계좌를 먼저 고를 수 있어 순환 대기가 다시 가능해짐
        - 해시값처럼 같은 값이 나올 수 있는 키로 정렬해야 하면, 동률일 때만 먼저 획득하는 별도 락을 두어 순서를 강제함
    - 동일 계좌 이체
        - from과 to가 같으면 같은 락을 두 번 요청하게 됨
        - `ReentrantLock`은 재진입을 허용하므로 멈추지 않지만, `PTHREAD_MUTEX_NORMAL` 유형처럼 재진입이 불가능한 뮤텍스였다면 자기 자신을 기다리는 데드락이 발생함
        - 업무상으로도 의미 없는 요청이므로 락 획득 전에 거부함
    - 모든 코드 경로의 순서 준수
        - 이체가 ID 순서를 지키더라도, 정산 작업 같은 다른 경로가 반대 순서로 두 계좌를 잠그면 순환 대기가 다시 성립함
        - 순서 규칙은 해당 락들을 함께 획득하는 모든 코드가 지켜야 함
    - 경합 비용 잔존
        - 락 획득 순서 고정은 순환 대기 조건만 제거하며, 같은 계좌에 이체가 몰리면 경합 비용은 그대로 남음

## 정리
```
프로세스 동기화
    │
    ├── 경쟁 조건
    │     ├── count++ : 비원자적 읽기-수정-쓰기 → 갱신 손실
    │     │     └── 끼어드는 경로 : 단일 코어 선점 · 멀티코어 동시 실행
    │     ├── check-then-act : 확인과 행동 사이에 끼어듦 (데이터 레이스 없이도 발생)
    │     └── 대응 : 임계 영역에 상호 배제 적용
    │           └── 요구 조건 : 상호 배제 · 진행 · 한정 대기
    │
    ├── 동기화 도구
    │     ├── 뮤텍스 : 소유권 있음 → 비소유자 해제 · 재잠금 규정 가능
    │     ├── 세마포어 : 소유권 없음 → 자원 수 제한 · 순서 신호
    │     │     └── 이진 세마포어 상호 배제 : 해제 오류 탐지 불가 · 값 초과 · 재진입 불가
    │     └── 락 비용 : 경합 시 블록과 컨텍스트 스위칭 · 직렬화
    │
    └── 데드락
          ├── 네 필요조건 : 상호 배제 · 점유 대기 · 비선점 · 순환 대기
          ├── 조건별 예방 : 조건 하나 이상을 구조적으로 제거
          └── 락 획득 순서 고정 : 순환 대기 제거
```
