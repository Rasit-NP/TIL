## JPA와 Hibernate의 관계
- JPA란 Java Persistence API의 약자로, 자바 객체와 관계형 데이터베이스 사이의 매핑과 영속성 관리를 규정한 표준 명세를 가리킴
    - 명세이므로 인터페이스와 동작 규칙만 정의하고 구현 코드는 포함하지 않음
    - 현재 명세명은 Jakarta EE로 이관되며 Jakarta Persistence로 변경됨
- Hibernate란 JPA 명세를 구현한 구체적인 ORM 라이브러리를 가리킴
    - ORM이란 Object-Relational Mapping의 약자로, 객체와 관계형 데이터를 자동으로 대응시키는 기법을 가리킴
    - Spring Boot의 spring-boot-starter-data-jpa는 기본 구현체로 Hibernate를 채택함

## 영속성 컨텍스트(Persistence Context)
- 엔티티를 저장하고 관리하는 논리적 공간
    - 애플리케이션과 데이터베이스 사이에서 엔티티를 임시로 보관하는 중간 계층
- 엔티티란 데이터베이스 테이블의 한 행에 대응하도록 매핑된 자바 객체를 가리킴
    - `@Entity` 애노테이션이 붙은 클래스의 인스턴스가 이에 해당함
- EntityManager란 영속성 컨텍스트에 접근해 엔티티를 조작하는 인터페이스를 가리킴
    - persist, find, remove, flush 등의 메서드를 제공함
    - 영속성 컨텍스트는 EntityManager를 통해서만 접근 가능함
- EntityManager와 영속성 컨텍스트의 관계
    - EntityManager는 영속성 컨텍스트를 조작하는 창구이며, 영속성 컨텍스트는 실제 엔티티가 담기는 공간임
    - 애플리케이션이 직접 EntityManager를 생성하는 방식에서는 EntityManager 하나가 영속성 컨텍스트 하나를 관리함
    - Spring의 컨테이너 관리 방식에서는 같은 트랜잭션 안의 여러 EntityManager 호출이 하나의 영속성 컨텍스트를 공유

### 영속성 컨텍스트의 생명주기
- Spring 환경에서 영속성 컨텍스트의 생존 범위는 기본적으로 트랜잭션 단위임
    - `@Transactional`이 적용된 메서드 진입 시 영속성 컨텍스트가 생성됨
    - 해당 메서드가 종료되어 트랜잭션이 커밋 또는 롤백되면 영속성 컨텍스트가 소멸함
- 영속성 컨텍스트 소멸 시 그 안에 있던 모든 엔티티는 관리 대상에서 벗어남
    - 이후 해당 엔티티의 변경은 데이터베이스에 반영되지 않음
- OSIV 설정이 생명주기를 확장할 수 있음(Spring 옵션)
    - OSIV란 Open Session In View의 약자로, 영속성 컨텍스트의 생존 범위를 HTTP 응답이 나갈 때까지 늘리는 설정을 가리킴
    - Spring Boot에서 `spring.jpa.open-in-view`의 기본값은 true이며, 이 경우 트랜잭션 종료 후에도 컨트롤러와 뷰 계층까지 영속성 컨텍스트가 유지됨
    - 이후 서술은 OSIV를 끈 상태를 기준으로 함

## 엔티티의 4가지 상태
- 엔티티는 영속성 컨텍스트와의 관계에 따라 네 가지 상태 중 하나를 가짐
    - JPA 명세가 정의하는 네 상태는 new, managed, detached, removed임
    - Hibernate 문서와 국내 자료는 이를 transient, persistent, detached, removed로 부름
    - 국내 자료는 이를 각각 비영속, 영속, 준영속, 삭제로 옮겨 부름

### 비영속(new/transient)
- 엔티티 객체가 생성되었으나 아직 영속성 컨텍스트와 연관되지 않은 상태
    - `new` 연산자로 인스턴스를 만든 직후의 상태에 해당함
    - 데이터베이스에 대응하는 행이 없으며 식별자가 아직 부여되지 않을 수 있음
- 이 상태의 객체 변경은 데이터베이스에 반영되지 않음
```java
Member member = new Member();
member.setName("종혁");
```

### 영속(managed/persistent)
- 엔티티가 영속성 컨텍스트에 의해 관리되는 상태
    - `persist` 호출로 저장하거나 `find`로 조회한 엔티티가 이 상태에 놓임
    - 이 상태의 엔티티만 변경 감지, 1차 캐시 등 영속성 컨텍스트의 기능 대상이 됨

```java
em.persist(member);
```
- persist 호출이 곧바로 INSERT 쿼리를 실행하지는 않음(SEQUENCE, TABLE 등 채번을 미리 하는 식별자 기준)
    - 영속 상태로 전이시키는 것과 데이터베이스에 SQL을 보내는 것은 별개의 시점임
    - 실제 SQL 전송 시점은 뒤의 쓰기 지연 항목에서 다룸

### 준영속(detached)
- 한때 영속 상태였으나 영속성 컨텍스트에서 분리된 상태
    - 식별자는 보유하지만 더 이상 영속성 컨텍스트의 관리를 받지 않음
- 준영속 상태로 전이하는 경로는 세 가지임
    - `em.detach(entity)`로 특정 엔티티만 분리하는 경우
    - `em.clear()`로 영속성 컨텍스트를 초기화하는 경우
    - `em.close()`로 영속성 컨텍스트를 종료하는 경우
- 준영속 상태에서 발생하는 문제
    - 준영속 엔티티의 필드를 변경해도 변경 감지가 동작하지 않아 데이터베이스에 반영되지 않음
    - 지연 로딩으로 설정된 연관 필드에 접근하면 예외가 발생함
        - Hibernate에서는 이 상황에서 LazyInitializationException이 발생함
        - 해당 엔티티가 영속성 컨텍스트의 관리를 벗어나 추가 조회 쿼리를 실행할 수 없기 때문
        - detach와 clear는 컨텍스트가 열려 있어도 해당 엔티티가 분리되어 발생하고, close는 컨텍스트 자체가 닫혀 발생함
- 준영속 엔티티를 다시 반영하려면 병합이 필요함
    - `em.merge(entity)`는 준영속 엔티티의 상태를 같은 식별자의 영속 엔티티에 복사함
    - merge는 인자로 받은 준영속 객체를 다시 관리 대상으로 만드는 것이 아니라, 새로 관리되는 엔티티를 반환함
    - 원본 준영속 객체는 여전히 준영속 상태로 남음

### 삭제(removed)
- 엔티티가 데이터베이스에서 제거되도록 예약된 상태
    - `em.remove(entity)` 호출로 이 상태에 놓임
    - 영속성 컨텍스트에는 여전히 연관되어 있으나 삭제 대상으로 표시된 상태
- 실제 DELETE 쿼리는 remove 호출 즉시가 아니라 플러시 시점에 전송됨

### 상태 전이 흐름
```
   new Member()
        │
        ▼
   [ 비영속 ] ──persist()──▶ [ 영속 ] ──remove()──▶ [ 삭제 ]
                             │  ▲
     detach()/clear()/close()│  │
                             ▼  │ merge()
                           [ 준영속 ]
```

## 1차 캐시
- 영속성 컨텍스트 내부에서 영속 엔티티를 식별자 기준으로 보관하는 저장소
- 내부 구조는 식별자를 키로, 엔티티를 값으로 갖는 맵 형태임
    - 키는 엔티티 타입과 식별자의 조합
    - 식별자만 키로 삼으면 서로 다른 타입의 같은 식별자가 충돌하므로 타입을 함께 포함함
- 동일 식별자 재조회 시 쿼리가 한 번만 나가는 이유
    - 최초 조회 시 데이터베이스에서 읽어온 엔티티를 1차 캐시에 저장함
    - 같은 트랜잭션 안에서 같은 식별자를 다시 조회하면 데이터베이스에 가지 않고 1차 캐시의 엔티티를 반환
    - 두 번째 조회에서는 SELECT 쿼리가 실행되지 않음

```java
// 첫 조회: DB에서 SELECT 실행 후 1차 캐시에 저장
Member m1 = em.find(Member.class, 1L);
// 두 번째 조회: 1차 캐시에서 반환, SELECT 실행 안 됨
Member m2 = em.find(Member.class, 1L);
```

- 1차 캐시의 유효 범위는 영속성 컨텍스트 생존 범위와 동일함
    - 트랜잭션이 끝나면 1차 캐시도 함께 사라짐
    - 따라서 트랜잭션을 넘어서는 조회 성능 향상 효과는 없음

## 동일성 보장
- 동일성이란 두 참조가 완전히 같은 인스턴스를 가리키는 성질을 가리킴
    - Java에서 `==` 연산으로 판별하는 대상
    - 값이 같은지를 판별하는 동등성과 구분됨
- 같은 트랜잭션 안에서 같은 식별자를 조회하면 항상 같은 인스턴스가 반환됨
    - 1차 캐시가 식별자당 하나의 엔티티 인스턴스만 유지하기 때문

```java
Member m1 = em.find(Member.class, 1L);
Member m2 = em.find(Member.class, 1L);
// 같은 1차 캐시 인스턴스이므로 참조가 동일함
System.out.println(m1 == m2);   // true
```

- 동일성 보장의 범위 한정
    - 이 보장은 하나의 영속성 컨텍스트 안에서만 성립함
    - 서로 다른 트랜잭션에서 각각 조회한 두 엔티티는 값이 같아도 `==` 비교가 false가 됨

## 변경 감지
- 영속 엔티티의 필드 변경을 영속성 컨텍스트가 자동으로 탐지해 UPDATE 쿼리를 생성하는 기능
- 스냅샷이란 엔티티가 영속 상태로 편입되는 시점의 필드 값을 복제해 둔 사본을 가리킴
    - 영속성 컨텍스트는 엔티티를 1차 캐시에 넣을 때 그 시점의 스냅샷을 함께 저장함
- 변경 감지 동작 순서
    - 플러시 시점에 각 영속 엔티티의 현재 필드 값과 스냅샷을 비교
    - 값이 달라진 엔티티를 찾아 UPDATE 쿼리를 생성
    - 생성된 UPDATE 쿼리를 쓰기 지연 저장소에 등록한 뒤 데이터베이스로 전송

```java
@Transactional
public void updateName(Long id){
    Member member = em.find(Member.class, id);      // 영속 상태, 스냅샷 저장
    member.setName("변경된 이름");                     // 필드만 변경
    // 별도의 save/update 호출 없음
}   // 트랜잭션 커밋 시 플러시 → 스냅샷과 비교 → UPDATE 전송
```

### save 호출 없이 UPDATE가 나가는 이유
- 영속 상태 엔티티는 이미 영속성 컨텍스트가 관리하고 있으므로 별도 저장 호출이 필요 없음
    - 필드 값 변경만으로 스냅샷과 차이가 생기며, 플러시 때 이 차이가 UPDATE로 변환됨
    - 명시적 save 호출은 새 엔티티를 영속 상태로 만들 때 필요한 것이지, 이미 영속인 엔티티의 수정에는 불필요함
- 이 동작이 실패하는 경계 조건
    - 준영속 엔티티는 영속성 컨텍스트가 관리하지 않으므로 필드를 변경해도 변경 감지가 동작하지 않음
    - 조회 없이 필드만 채운 비영속 엔티티도 마찬가지로 변경 감지 대상이 아님

### 변경 감지의 UPDATE 컬럼 범위
- Hibernate는 기본적으로 변경 여부와 무관하게 엔티티의 모든 컬럼을 UPDATE 문에 포함함
    - 미리 생성해 둔 UPDATE 문을 재사용해 쿼리 생성 비용을 줄이려는 목적
    - 변경된 컬럼만 UPDATE에 넣으려면 `@DynamicUpdate` 애노테이션을 사용함
    - 이 동작은 JPA 표준 규정이 아니라 Hibernate의 구현 선택임

## 쓰기 지연
- INSERT, UPDATE, DELETE 쿼리를 즉시 전송하지 않고 내부 저장소에 모아 두었다가 플러시 시점에 한꺼번에 전송하는 방식(write-behind)
    - write-behind란 변경을 메모리에 먼저 반영하고 저장소 반영을 뒤로 미루는 캐시 전략을 가리킴
- 쓰기 지연 저장소란 아직 데이터베이스로 보내지 않은 SQL 쿼리를 순서대로 쌓아두는 내부 큐를 가리킴
- 동작 흐름
    - persist, remove 호출이나 변경 감지로 생성된 쿼리를 즉시 실행하지 않고 저장소에 등록함
    - 플러시 시점에 등록된 쿼리를 순서대로 데이터베이스에 전송

```java
@Transactional
public void register(){
    em.persist(memberA);    // INSERT 쿼리를 저장소에 등록, 아직 전송 안 함
    em.persist(memberB);    // INSERT 쿼리를 저장소에 등록, 아직 전송 안 함
    // 여기까지 DB에는 아무 쿼리도 도달하지 않음
}   // 커밋 시 플러시 → 쌓인 INSERT 두 건을 순서대로 전송
```
- 쓰기 지연의 이점
    - 여러 SQL을 모아 한 번에 전송하므로 데이터베이스 왕복 횟수를 줄일 수 있음
    - JDBC 배치 설정과 결합하면 다수의 INSERT를 하나의 배치로 묶어 전송할 수 있음

## 플러시(flush)
- 영속성 컨텍스트의 변경 내용을 데이터베이스에 동기화하는 처리
    - 쓰기 지연 저장소에 쌓인 쿼리를 데이터베이스로 전송하는 시점에 해당함
    - 플러시는 영속성 컨텍스트를 비우는 것이 아님
        - 데이터베이스와 동기화할 뿐, 1차 캐시의 엔티티는 그대로 유지됨
- 플러시가 발생하는 시점
    - JPA 명세는 기본 플러시 모드를 `FlushModeType.AUTO`로 규정함
    - AUTO 모드에서 명세가 규정하는 플러시 시점은 두 가지
        - 트랜잭션이 커밋되기 직전
        - 현재 영속성 컨텍스트에 반영 대기 중인 변경이 걸린 테이블을 조회하는 쿼리(JPQL/HQL)를 실행하기 직전
    - `em.flush()`를 직접 호출하는 방법도 있으며, 이는 명세가 아니라 개발자의 수동 호출임
- 쿼리 실행 직전 플러시가 필요한 이유
    - JPQL은 영속성 컨텍스트가 아니라 데이터베이스에 직접 쿼리를 실행함
    - 아직 플러시되지 않은 변경이 있으면 조회 결과가 변경 이전 상태로 나올 수 있음
    - 따라서 조회 전에 플러시해 변경을 먼저 반영함으로써 조회 일관성을 확보함
- 커밋과 플러시의 관계
    - 트랜잭션 커밋은 내부적으로 플러시를 먼저 수행한 뒤 데이터베이스 트랜잭션을 커밋함
    - 커밋 없이 플러시만 하면 SQL은 전송되나 트랜잭션은 아직 확정되지 않은 상태로 남음

## 정리
```
JPA 영속성 컨텍스트
    │
    ├── 정의
    │     ├── EntityManager로 접근
    │     └── 생존 범위: 트랜잭션 단위(OSIV로 확장 가능)
    │
    ├── 엔티티 4상태
    │     ├── 비영속 (new)
    │     ├── 영속 (managed)
    │     ├── 준영속 (detached)
    │     └── 삭제 (removed)
    │
    ├── 1차 캐시
    │     ├── 식별자 기준 맵 저장
    │     ├── 재조회 쿼리 생략
    │     └── 동일성 보장의 근거
    │
    ├── 변경 감지 (dirty checking)
    │     ├── 스냅샷과 비교
    │     └── save 없이 UPDATE 생성
    │
    ├── 쓰기 지연 (write-behind)
    │     └── SQL을 저장소에 모음
    │
    └── 플러시 (flush)
          ├── 커밋 직전
          └── 겹치는 테이블 쿼리 직전
```
