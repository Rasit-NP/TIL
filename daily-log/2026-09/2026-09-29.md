## synchronized
- 지정한 객체에 잠금을 걸어, 한 시점에 하나의 스레드만 해당 코드 구간을 실행하도록 하는 Java 언어의 동기화 키워드
- 메서드 선언의 수식어와 블록 구문, 두 가지 형태로 사용함
- `synchronized`는 임계 영역에 상호 배제를 적용하는 Java 언어 차원의 수단임
    - 임계 영역(critical section)
        - 공유 자원에 접근하는 코드 구간 중, 한 시점에 하나의 스레드만 실행해야 하는 구간
    - 상호 배제(mutual exclusion)
        - 한 스레드가 임계 영역을 실행하는 동안 다른 스레드가 같은 임계 영역에 들어갈 수 없게 하는 성질

### 모니터
- JLS(Java Language Specification)가 모든 객체에 하나씩 연관시킨, 스레드가 잠그거나(lock) 풀 수 있는(unlock) 동기화 단위
- 동시성 이론의 모니터와는 층위가 다름
    - JLS의 모니터는 개별 객체에 연관된 잠금 단위를 가리키며, 동시성 이론의 모니터 구조 전체를 뜻하지 않음
- 모니터 락
    - 스레드가 모니터에 대해 획득하고 해제하는 잠금
    - Oracle의 Java Tutorial은 같은 대상을 내재 락(intrinsic lock) 또는 모니터 락이라 부르며, JLS 본문은 모니터와 lock, unlock 동작이라는 용어로 서술함
- JLS 17.1이 규정하는 모니터의 동작은 아래와 같음
    - 한 시점에 하나의 스레드만 모니터의 락을 보유할 수 있음
    - 이미 다른 스레드가 보유한 모니터를 잠그려는 스레드는 락을 얻을 수 있을 때까지 블록됨
    - 한 스레드는 같은 모니터를 여러 번 잠글 수 있으며, unlock 한 번이 lock 한 번의 효과를 되돌림
- 객체와 모니터를 실제로 어떻게 연결할지는 JVMS가 명세 범위 밖으로 두고 구현에 맡김

### synchronized 블록
- `synchronized (식) {본문}` 형태로, 괄호 안 식이 가리키는 객체의 모니터를 락 대상으로 지정하는 구문
- JLS 14.19와 17.1이 규정하는 실행 순서는 아래와 같음
    - 괄호 안 식을 평가해 객체 참조를 구함
    - 그 객체의 모니터에 lock 동작을 수행하고, 성공할 때까지 다음으로 진행하지 않음
    - 본문을 실행함
    - 본문이 끝까지 실행되든, 예외나 `return`, `break` 등으로 중간에 빠져나가든 같은 모니터에 unlock 동작이 자동으로 수행됨
- 바이트코드에서는 `monitorenter`, `monitorexit` 명령어로 표현됨
    - JVMS 3.14는 이 두 명령어가 synchronized 문의 컴파일을 위해 제공된다고 기술함
    - 컴파일러는 본문에서 예외가 발생한 경로에도 `monitorexit`을 실행하는 예외 처리기를 생성함
- 아래는 `synchronized (obj) { ... }`의 바이트코드 흐름을 요약한 것
```
monitorenter        // obj의 모니터 획득
  (본문)
monitorexit         // 정상 종료 경로의 해제
goto 끝

예외 처리기:
monitorexit         // 예외 종료 경로의 해제
athrow              // 잡은 예외를 다시 던짐
```
- 블록 형태는 두 가지를 직접 고를 수 있음
    - 락 범위
        - 락이 필요한 구간만 블록으로 감싸 임계 영역을 좁힐 수 있음
    - 락 대상
        - `this`가 아닌 별도 객체를 락 대상으로 지정할 수 있음
- 외부에 노출되지 않는 `private final` 객체를 락 대상으로 쓰면, 클래스 밖의 코드가 같은 모니터를 잠가 상호 배제에 간섭하는 경로가 막힘
- 락 대상 필드는 `final`로 선언함
    - 락 대상 필드가 재할당되면 스레드마다 서로 다른 객체의 모니터를 잠글 수 있어 상호 배제가 깨짐

```java
public class Account {
    private final Object lock = new Object();   // 외부에 노출되지 않는 전용 락 객체
    private int balance;

    public void deposit(int amount){
        validate(amount);           // 공유 상태를 건드리지 않는 검증은 블록 밖에서 수행
        synchronized (lock){
            balance += amount;      // balance에 접근하는 구간만 임계 영역으로 지정
        }
    }

    public int getBalance() {
        synchronized (lock){        // 읽기도 같은 락으로 보호
            return balance;
        }
    }

    private void validate(int amount){
        if (amount <= 0)
            throw new IllegalArgumentException();
    }
}
```
- 같은 공유 변수에 접근하는 모든 코드는 같은 객체의 모니터를 잠가야 함
    - 한 곳은 `this`, 다른 곳은 전용 락 객체로 잠그면 두 구간은 서로 다른 모니터를 쓰므로 동시에 실행될 수 있음

### synchronized 메서드
- 메서드 선언에 `synchronized` 수식어를 붙여, 메서드 본문 전체를 임계 영역으로 지정하는 형태
- JLS 17.1은 synchronized 메서드가 호출될 때 lock 동작을 자동으로 수행하고, 락을 얻은 뒤에야 본문을 실행한다고 규정함
    - 메서드가 정상 반환되든 예외를 던지며 종료되든 같은 모니터에 unlock 동작이 자동으로 수행됨
- 락 대상은 메서드 종류에 따라 JLS가 정해 두므로 직접 고를 수 없음
- 바이트코드 수준의 구현은 블록 형태와 다름
    - JVMS 3.14는 synchronized 메서드가 보통 `monitorenter`, `monitorexit`로 구현되지 않고, `ACC_SYNCHRONIZED` 플래그로 구분된다고 기술함
    - JVMS 2.11.10에 따라 메서드 호출 명령어가 이 플래그를 확인해 모니터 진입과 해제를 암묵적으로 수행함
- 두 형태의 차이는 아래와 같음

| 구분 | synchronized 메서드 | synchronized 블록 |
|-----|-------------------|------------------|
| 락 범위 | 메서드 본문 전체 | 블록으로 감싼 구간 |
| 락 대상 | 인스턴스 메서드는 `this`, static 메서드는 `Class` 객체로 고정 | 괄호 안 식이 가리키는 객체 |
| 바이트코드 표현 | `ACC_SYNCHRONIZED` 플래그 | `monitorenter`, `monitorexit` 명령어 |
| 예외 시 해제 | 자동 | 자동 |

### 락 대상 객체
- 인스턴스 락
    - 인스턴스 메서드에 `synchronized`를 붙였을 때 잠기는, 메서드를 호출한 객체(`this`)의 모니터
    - 인스턴스마다 모니터가 따로 있으므로, 서로 다른 인스턴스에 대한 호출은 서로를 막지 않음
- 클래스 락
    - static 메서드에 `synchronized`를 붙였을 때 잠기는, 그 메서드가 정의된 클래스를 나타내는 `Class` 객체의 모니터
    - `synchronized (Account.class) { ... }` 블록도 같은 모니터를 잠금
- 클래스 락이라는 별도 종류의 락이 있는 것이 아니며, `Class` 객체도 하나의 객체이므로 그 객체의 모니터를 잠그는 것
- 인스턴스 락과 클래스 락은 서로 다른 객체의 모니터이므로, 같은 클래스의 synchronized 인스턴스 메서드와 synchronized static 메서드는 동시에 실행될 수 있음
- 락 대상을 잘못 고른 실패 사례
    ```java
    public class Visitor {
        private static int total = 0;           // 모든 인스턴스가 공유하는 static 필드

        public synchronized void visit() {      // 인스턴스 락: 인스턴스마다 다른 모니터를 잠금
            total++;                            // 서로 다른 인스턴스의 호출끼리는 상호 배제되지 않음
        }

        public static synchronized void visitSafe() {   // 클래스 락: 모든 호출이 같은 Class 객체의 모니터를 잠금
            total++;
        }
    }
    ```
- `visit()`은 인스턴스가 하나일 때는 안전해 보이지만, 인스턴스가 둘 이상이면 각자 다른 모니터를 잠그므로 `total`에 갱신 손실이 발생할 수 있음
- static 필드처럼 인스턴스 사이에 공유되는 상태는 클래스 락 또는 모든 인스턴스가 공유하는 하나의 락 객체로 보호해야 함
- 클래스 락의 범위는 엄밀히는 `Class` 객체 하나임
    - JVMS 5.3에 따라 실행 중인 클래스는 이름과 그 클래스를 정의한 클래스 로더의 쌍으로 식별됨
    - 같은 이름의 클래스를 서로 다른 클래스 로더가 각각 로드하면 `Class` 객체가 둘이 되어, 두 클래스의 static synchronized 메서드는 서로를 막지 않음

### 재진입성(reentrancy)
- 락을 이미 보유한 스레드가 같은 락을 다시 획득해도 블록되지 않는 성질
- JLS 17.1은 한 스레드가 같은 모니터를 여러 번 잠글 수 있고, unlock 한 번이 lock 한 번의 효과를 되돌린다고 규정함
    - 모니터는 보유 스레드와 잠금 횟수를 함께 추적하며, 잠금 횟수가 0이 될 때 비로소 다른 스레드가 락을 얻을 수 있음
- 재진입이 필요한 대표 경로는 같은 객체의 synchronized 메서드가 다른 synchronized 메서드를 호출하는 경우임

```java
public class Parent {
    public synchronized void work() {       // this의 모니터를 잠금
        // ...
    }
}

public class Child extends Parent {
    @Override
    public synchronized void work() {       // this의 모니터를 잠금
        super.work();                       // 같은 this의 모니터를 다시 잠금
    }                                       // 두 메서드가 반환하며 잠금 횟수가 0이 될 때 해제됨
}
```

- 재진입이 허용되지 않는다면 `super.work()`를 호출한 스레드는 자신이 보유한 락의 해제를 기다리며 영원히 멈춤
- 재진입성은 같은 스레드에만 적용되며, 다른 스레드의 획득 요청은 잠금 횟수가 0이 될 때까지 블록됨

### 단일 JVM 범위
- 모니터는 객체에 연관된 것이고 객체는 JVM 프로세스 하나의 힙 안에 존재하므로, `synchronized`의 상호 배제는 같은 JVM 안의 스레드 사이에서만 성립함
- 서버를 여러 대 띄우면 각 서버가 별도 JVM 프로세스이므로, 같은 클래스의 같은 코드라도 서로 다른 객체의 모니터를 잠금
    - 서버 A의 스레드와 서버 B의 스레드는 같은 계좌의 잔액을 동시에 차감할 수 있음
    - 한 대의 장비에서 애플리케이션 프로세스를 둘 이상 실행하는 경우도 같음
- 잔액처럼 데이터베이스에 저장된 공유 상태는 JVM 밖에 있으므로, 여러 서버가 함께 접근하는 데이터베이스나 외부 저장소 수준에서 상호 배제를 적용해야 함

### 트랜잭션 경계 불일치
- 서버가 한 대여도 Spring의 `@Transactional` 메서드에 `synchronized`를 붙이면 상호 배제가 깨지는 경로가 있음
- Spring의 선언적 트랜잭션 구현에서는 프록시가 트랜잭션을 시작한 뒤 대상 메서드를 호출하고, 대상 메서드가 반환된 뒤에 커밋함
- 대상 메서드에 붙인 `synchronized`는 대상 메서드의 본문 구간만 보호하므로, 락 해제와 커밋 사이에 틈이 생김

```
스레드 A                                   스레드 B
────────                                  ────────
프록시: 트랜잭션 시작
대상 메서드: 모니터 획득
  잔액 1000 조회 → 900으로 차감
대상 메서드: 모니터 해제
                                          프록시: 트랜잭션 시작
                                          대상 메서드: 모니터 획득
                                            잔액 조회 (A 미커밋 → 1000을 읽을 수 있음)
프록시: 커밋 (잔액 900)
                                            1000 → 900으로 차감
                                          대상 메서드: 모니터 해제
                                          프록시: 커밋 (잔액 900)

결과  잔액 900  (기대값 800, A의 차감이 B의 쓰기에 덮임)
```
- 모니터가 해제된 시점에 A의 차감은 아직 커밋되지 않았으므로, B가 읽는 잔액은 A의 차감이 반영되기 전 값일 수 있음
- 이 틈은 락의 보호 범위가 트랜잭션의 범위보다 좁아서 생기며, `synchronized` 자체의 결함이 아니라 락 범위와 트랜잭션 범위의 불일치에서 비롯됨

## volatile
- 필드 선언에 붙여, 그 필드에 대한 읽기와 쓰기를 Java 메모리 모델이 정한 동기화 동작으로 다루게 하는 Java의 필드 수식어
- 지역 변수에는 붙일 수 없으며, 인스턴스 필드와 static 필드에만 사용함
- JLS 17.4.2는 volatile 읽기, volatile 쓰기를 모니터의 lock, unlock과 같은 동기화 동작으로 분류함
- 이 수식어가 주로 다루는 문제는 가시성이며, 읽기-수정-쓰기의 원자성은 다루지 않음

### 가시성(visibility)
- 한 스레드가 공유 변수에 쓴 값을 다른 스레드가 이후의 읽기에서 관찰할 수 있는지에 관한 성질
- 동기화 없이 공유 변수를 쓰고 읽으면, 한 스레드의 쓰기가 다른 스레드에 보인다는 보장이 없음
- 재배치(reordering)
    - 메모리 접근이 소스 코드에 적힌 순서와 다른 순서로 수행되거나, 다른 스레드에 그렇게 관찰되는 것
- JLS 17장은 재배치와 가시성 문제를 만드는 주체를 아래처럼 제시함
    - JIT 컴파일러
        - 한 스레드만 놓고 볼 때 실행 결과가 달라지지 않는다면 명령어 순서를 바꾸거나, 필드 값을 레지스터에 두고 재사용할 수 있음
    - 프로세서
        - 프로세서도 명령어의 실행 순서를 바꿀 수 있음
    - 메모리 계층
        - 실행 환경의 메모리 계층 구조 때문에 코드가 재배치된 것처럼 보이는 결과가 나올 수 있음
- JLS 17.4는 위 셋을 통틀어 코드를 재배치할 수 있는 모든 주체를 컴파일러라고 부름
- JLS 17.3은 non-volatile 필드를 반복해서 읽는 루프에서, 컴파일러가 필드를 한 번만 읽고 그 값을 매 반복에 재사용할 수 있으며, 그 결과 다른 스레드가 값을 바꿔도 루프가 끝나지 않을 수 있다고 기술함

```java
public class StopFlag{
    private static boolean stop = false;        // volatile 없음

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            long n = 0;
            while (!stop) {         // 컴파일러가 stop을 한 번만 읽고 재사용하면 루프가 끝나지 않음
                n++;
            }
        });
        worker.start();
        Thread.sleep(1000);
        stop = true;                // main 스레드의 이 쓰기가 worker에 보인다는 보장이 없음
        worker.join();              // worker가 끝나지 않으면 main도 여기서 멈춤
    }
}
```

- `stop`을 `private static volatile boolean stop`으로 선언하면 해결됨
    - volatile 읽기는 동기화 동작이므로 컴파일러가 한 번 읽은 값을 반복마다 재사용하는 방식으로 바꿀 수 없음
    - worker는 반복마다 `stop`을 다시 읽으며, main 스레드의 쓰기 이후의 읽기에서 `true`를 관찰해 루프를 빠져나옴
- 이 결함은 재현 여부가 JIT 컴파일 여부, 루프 본문의 내용, 실행 환경에 따라 달라짐
    - 테스트에서 루프가 종료되었다는 사실은 코드가 올바르다는 근거가 되지 않음

### 가시성 보장 규칙
- JLS 17.4.4와 17.4.5는 volatile 변수에 대한 쓰기가, 그 뒤 같은 변수를 읽는 모든 스레드의 읽기보다 먼저 일어난 것으로 순서를 규정함
    - 여기서 그 뒤는 모든 동기화 동작을 한 줄로 세운 동기화 순서(synchronization order)상의 뒤를 가리킴
- 이 규정에 JLS 17.4.7의 규정을 더하면 두 가지 결과가 나옴
    - JLS 17.4.7에 따라 volatile 읽기는 동기화 순서상 그보다 앞선, 같은 변수에 대한 쓰기 중 가장 최근 쓰기의 값을 관찰함
    - JLS 17.4.4와 17.4.5에 따라 쓰는 스레드가 volatile 쓰기 이전에 수행한 일반 쓰기도, 그 volatile 값을 읽은 스레드가 이후에 읽을 때 관찰할 수 있음
- 두 번째 결과로 volatile 변수를 준비 신호로 삼아 다른 데이터를 넘길 수 있음

```java
int data = 0;                       // 일반 필드
volatile boolean ready = false;     // 신호용 volatile 필드

// 쓰는 스레드
data = 42;                          // 일반 쓰기
ready = true;                       // volatile 쓰기, 같은 스레드의 코드상 data = 42 뒤에 있음

// 읽는 스레드
if (ready) {
    System.out.println(data);
}
```

- `ready`가 volatile이 아니면 읽는 스레드가 `ready == true`를 보고도 `data == 0`을 볼 수 있음
- 같은 규정이 모니터에도 적용되어, JLS는 모니터의 unlock이 그 뒤 같은 모니터의 lock보다 먼저 일어난 것으로 순서를 규정함
    - 따라서 `synchronized`는 상호 배제와 함께 가시성도 보장함
    - 이 보장은 쓰는 쪽과 읽는 쪽이 모두 같은 모니터를 잠글 때만 성립함

```java
public class Holder {
    private int value;

    public synchronized void set(int v) { value = v; };     // 쓰기는 모니터를 잠금

    public int get() { return value; }                      // 읽기는 모니터를 잠그지 않음 → 최신 값 관찰 보장 없음
}
```
- `get()`에도 `synchronized`를 붙이거나 `value`를 volatile로 선언해야 읽는 스레드가 `set()`의 쓰기를 관찰할 수 있음

### 복합 연산의 비원자성
- 복합 연산(compound operation)
    - 읽기-수정-쓰기처럼 둘 이상의 메모리 접근으로 이루어진 연산
- volatile은 개별 읽기와 개별 쓰기의 가시성을 보장할 뿐, 여러 접근으로 이루어진 복합 연산을 원자적으로 만들지 않음
- `volatile int count`에 대한 `count++`도 volatile 읽기, 덧셈, volatile 쓰기의 세 단계로 실행됨
    - 두 스레드가 같은 값을 volatile 읽기로 읽은 뒤 각자 1을 더해 쓰면 갱신 손실이 그대로 발생함
```
volatile int count = 0

스레드 A                          스레드 B
────────                        ────────
volatile 읽기  (0)
                                volatile 읽기  (0)
덧셈           (1)
                                덧셈           (1)
volatile 쓰기  (count = 1)
                                volatile 쓰기  (count = 1)

결과  count = 1  (기대값 2, 두 읽기 모두 그 시점의 최신 값을 읽었지만 갱신 손실 발생)
```
- 두 스레드 모두 읽는 시점의 최신 값을 정확히 읽었으므로 가시성 문제는 없으며, 읽기와 쓰기 사이에 다른 스레드가 끼어드는 원자성 문제가 남은 것
- volatile이 원자성과 전혀 무관한 것은 아님
    - JLS 17.7에 따라 non-volatile `long`, `double`의 쓰기 한 번은 32비트 절반씩 두 번의 쓰기로 다뤄질 수 있어, 다른 스레드가 두 쓰기의 절반씩 섞인 값을 볼 수 있음
    - 같은 조항은 volatile `long`, `double`의 읽기와 쓰기는 항상 원자적이라고 규정함
    - 즉 volatile은 개별 읽기와 쓰기 하나하나의 원자성은 보장하지만, 복합 연산의 원자성은 보장하지 않음
- volatile만으로 충분한 조건은 Java Concurrency in Practice가 아래처럼 정리함
    - 쓰는 값이 변수의 현재 값에 의존하지 않거나, 값을 쓰는 스레드가 하나뿐임
    - 그 변수가 다른 상태 변수와 함께 불변 조건을 이루지 않음
    - 그 변수에 접근하는 동안 다른 이유로 락을 잡을 필요가 없음
- 종료 플래그나 준비 완료 신호는 위 조건을 만족하지만, 카운터와 잔액 차감은 현재 값에 의존하므로 만족하지 않음
- 두 키워드의 보장 범위는 아래와 같음

| 구분 | synchronized | volatile |
|-----|--------------|----------|
| 적용 대상 | 메서드, 블록 | 필드 |
| 가시성 | 같은 모니터를 잠그는 스레드 사이에서 보장 | 같은 변수를 읽는 스레드 사이에서 보장 |
| 개별 읽기, 쓰기의 원자성 | 보장 | 보장(`long`, `double` 포함) |
| 복합 연산의 원자성 | 보장 | 보장하지 않음 |
| 스레드 블록 | 락을 얻지 못하면 블록됨 | 블록되지 않음 |

> volatile은 최신 값이 보이게 하는 장치이고, 읽기와 쓰기 사이에 끼어들기를 막는 장치가 아님\
> `count++`처럼 현재 값에 의존하는 갱신은 volatile만으로 안전해지지 않음

## AtomicInteger
- `java.util.concurrent.atomic` 패키지가 제공하는, `int` 값 하나를 원자적으로 읽고 갱신하는 연산을 모은 클래스
- 이 패키지의 API 문서는 패키지를 단일 변수에 대해 락 없이 여러 스레드가 안전하게 갱신하는 프로그래밍을 지원하는 클래스 모음이라고 소개함
- `incrementAndGet()`, `addAndGet()`, `compareAndSet()` 같은 메서드가 읽기-수정-쓰기를 하나의 원자적 연산으로 수행함
- OpenJDK 소스에서 실제 값은 `private volatile int value` 필드에 저장되며, 원자적 갱신은 JDK 내부의 `Unsafe` 클래스를 거쳐 수행됨
- 락을 전혀 쓰지 않는다는 점은 명세가 모든 플랫폼에 보장하는 성질이 아님
    - Java SE 5~8의 패키지 문서는 일부 플랫폼에서는 내부적으로 락을 쓸 수 있어, 메서드가 엄밀하게 비블로킹이라고 보장되지 않는다고 명시함
    - x86처럼 원자적 명령어를 제공하는 플랫폼에서 HotSpot JVM은 아래에서 다루는 하드웨어 명령어로 이 연산들을 수행함

### CAS(Compare-And-Swap)
- 메모리 위치의 현재 값이 예상값과 같을 때만 새 값으로 바꾸며, 비교와 교체를 하나의 원자적 연산으로 수행하는 연산
- `AtomicInteger.compareAndSet(expectedValue, newValue)`의 명세는 아래와 같음
    - 현재 값이 `expectedValue`와 같으면 `newValue`로 원자적으로 설정하고 `true`를 반환함
    - `false` 반환은 실제 값이 예상값과 달랐음을 뜻함
    - 메모리 효과는 `VarHandle.compareAndSet` 명세를 따르며, 이는 현재 값을 volatile 읽기로 읽고 새 값을 volatile 쓰기로 쓰는 것과 같은 가시성 보장을 가짐
- 락 프리(lock-free)
    - 일부 스레드가 지연되거나 멈추더라도, 시스템 전체로는 유한한 단계 안에 어느 한 스레드의 연산이 반드시 완료됨을 보장하는 진행 조건
    - 특정 스레드 하나의 완료까지 보장하는 조건은 아니라는 점에서, 모든 스레드의 완료를 보장하는 더 강한 조건과 구분됨
- CAS를 쓰는 갱신이 락 없이 원자성을 얻는 원리는 아래와 같음
    - 스레드는 락을 획득하지 않고 현재 값을 읽어 새 값을 계산함
    - CAS로 쓰기를 시도하며, 읽은 뒤 다른 스레드가 값을 바꿨다면 CAS가 실패하므로 덮어쓰기가 일어나지 않음
    - 실패한 스레드는 블록되지 않고 새 값을 다시 읽어 재시도함
    - `compareAndSet`의 실패는 다른 스레드의 쓰기가 먼저 반영되었다는 뜻이므로, 누군가의 갱신은 항상 진행됨

### CAS 재시도 루프
- 현재 값 읽기, 새 값 계산, CAS 시도를 성공할 때까지 반복하는 코드 패턴
- JDK 8 이후 OpenJDK의 `AtomicInteger.incrementAndGet()`은 `Unsafe.getAndAddInt()`를 호출하며, 이 메서드의 Java 소스는 CAS 재시도 루프로 작성되어 있음
- HotSpot은 x86에서 `getAndAddInt()`를 JIT 컴파일할 때, CAS 루프 대신 `lock xadd` 명령어 하나로 대체하는 intrinsic 최적화를 적용함
    - `xadd`는 값을 더하면서 더하기 전 값을 돌려주며 비교 단계가 없으므로 실패와 재시도가 없음
- `compareAndSet`을 직접 호출하는 루프는 이 대체의 대상이 아니며, HotSpot은 x86에서 `compareAndSet`을 `lock cmpxchg`로 실행함
- 증가처럼 정해진 연산은 `incrementAndGet()`, `addAndGet()`으로 충분하지만, 조건 판단이 끼는 갱신은 직접 CAS 재시도 루프를 작성해야 함
```java
AtomicInteger balance = new AtomicInteger(1000);

// 실패 사례: 확인과 차감이 각각은 원자적이지만 둘 사이에 다른 스레드가 끼어들 수 있음
boolean withdrawBroken(int amount){
    if (balance.get() >= amount){           // 확인 시점의 잔액
        balance.addAndGet(-amount);         // 차감 시점에는 잔액이 이미 줄었을 수 있음
        return true;
    }

    return false;
}

// 해결: 읽은 값이 그대로일 때만 차감을 반영하는 CAS 재시도 루프
boolean withdraw(int amount){
    while (true){
        int current = balance.get();                        // 현재 값 읽기
        if (current < amount)                               // 잔액 부족이면 재시도 없이 실패
            return false;
        if (balance.compareAndSet(current, current - amount)){
            return true;                                    // 읽은 뒤 아무도 바꾸지 않았으면 성공
        }
        // 실패는 다른 스레드가 먼저 값을 바꿨다는 뜻이므로 새 값으로 다시 확인
    }
}
```
- 실패 사례는 개별 메서드 호출이 모두 원자적인데도, 확인과 차감을 묶은 전체가 원자적이지 않아 잔액이 음수가 될 수 있음
- 해결 코드에서는 잔액 확인에 쓴 값과 CAS의 예상값이 같은 값이므로, 확인 이후 다른 차감이 끼어들면 CAS가 실패하고 다시 확인함
- 실제 서비스의 잔액은 데이터베이스에 있으므로, 이 코드는 JVM 메모리 안의 값에 대한 원자적 갱신 원리를 보이는 예시임
- `updateAndGet()`, `accumulateAndGet()`도 내부적으로 CAS 재시도를 수행함
    - API 문서는 다른 스레드와 동시에 갱신을 시도해 실패하면 전달한 함수가 다시 적용될 수 있으므로, 함수에 부수 효과가 없어야 한다고 명시함

### 높은 경합에서의 비용
- 경합(contention)
    - 둘 이상의 스레드가 같은 락이나 같은 변수에 동시에 갱신을 시도하는 상황
- CAS 재시도 루프는 경합이 심할수록 불리해짐
    - 동시에 시도하는 스레드가 많을수록 한 번의 성공마다 나머지 스레드의 CAS가 실패함
    - 실패한 스레드는 블록되지 않고 곧바로 재시도하므로, 진행하지 못하는 동안에도 CPU를 계속 사용함
    - 실패할 때마다 앞서 읽고 계산한 작업이 버려지며, 새 값 계산이 무거울수록 낭비가 커짐
    - 시스템 전체의 진행은 보장되지만, 특정 스레드의 CAS가 계속 실패할 가능성은 배제되지 않음
- 락은 획득에 실패한 스레드를 블록시켜 CPU를 다른 작업에 넘기므로, 경합이 심하고 임계 영역이 길 때는 재시도 루프보다 CPU 낭비가 적을 수 있음
- 재시도가 없는 `lock xadd`도 경합 비용에서 자유롭지 않음
    - 여러 코어가 같은 변수에 원자적 쓰기를 반복하면, 그 변수가 담긴 캐시 라인의 쓰기 권한이 코어 사이를 계속 오가며 연산들이 차례로 처리됨
    - 따라서 하나의 `AtomicInteger`에 갱신이 몰리면 코어 수를 늘려도 그 변수의 갱신 처리량은 늘지 않음
- 두 방식의 차이는 아래와 같음

| 구분 | synchronized | AtomicInteger |
|-----|--------------|---------------|
| 원자성 확보 수단 | 모니터 락으로 임계 영역 상호 배제 | CAS 등 하드웨어 원자적 명령어 |
| 경합 시 스레드 상태 | 블록됨 | 블록되지 않고 재시도하거나 명령어 수준에서 순서대로 처리됨 |
| 보호 범위 | 블록 안의 여러 변수와 여러 연산 | 변수 하나에 대한 연산 하나 |
| 경합이 심할 때 | 블록과 깨우기 비용, 임계 영역의 순차 실행 | 재시도 낭비, 캐시 라인 경합 |
| 적용 범위 | 단일 JVM | 단일 JVM |

- `AtomicInteger`의 경계 조건은 아래와 같음
    - 변수 하나
        - CAS는 메모리 위치 하나만을 원자적으로 비교하고 바꾸므로, 두 계좌 사이의 이체처럼 두 변수를 함께 바꿔야 하는 불변 조건은 보호하지 못함
    - 단일 JVM
        - 값이 JVM 하나의 힙에 있으므로, 여러 서버가 공유하는 잔액의 동시성은 `synchronized`와 마찬가지로 해결하지 못함

## 정리
```
Java 언어 수준 동시성 제어
    │
    ├── synchronized : 모니터 락으로 상호 배제 + 가시성
    │     ├── 블록 : monitorenter · monitorexit, 락 범위와 대상 선택
    │     ├── 메서드 : ACC_SYNCHRONIZED, 본문 전체
    │     ├── 락 대상 : 인스턴스 락(this) · 클래스 락(Class 객체)
    │     ├── 재진입성 : 같은 스레드의 재획득 허용, 잠금 횟수 추적
    │     └── 한계 : 단일 JVM 범위 · 트랜잭션 커밋보다 먼저 해제
    │
    ├── volatile : 가시성 보장
    │     ├── 쓰기 → 이후 읽기에 보임 (이전 일반 쓰기 포함)
    │     └── 복합 연산은 원자적이지 않음 → volatile count++도 갱신 손실
```
