## 가비지 컬렉션
- 가비지 컬렉션(garbage collection, GC)이란 프로그램이 더 이상 사용하지 않는 객체가 점유한 메모리를 자동으로 회수하는 처리를 가리킴
    - "가비지"는 어떤 실행 경로로도 다시 접근할 수 없게 된 객체를 뜻함
    - C나 C++처럼 개발자가 `free`, `delete`로 직접 해제하는 방식과 대비됨
- GC의 존재 이유는 수동 해제에서 발생하는 오류를 제거하는 데 있음
    - 해제를 누락하면 메모리가 계속 쌓이는 누수가 발생함
    - 이미 해제한 메모리를 다시 참조하면 dangling pointer 오류가 발생함
    - GC는 해제 시점 판단을 런타임에 위임해 이 두 오류의 근원을 없앰

### 회수 대상 판정의 핵심 질문
- GC가 답해야 하는 질문은 "어떤 객체가 살아 있고 어떤 객체가 죽었는가"임
    - 살아 있음(live)이란 앞으로 프로그램이 다시 접근할 가능성이 있음을 뜻함
    - 죽음(dead)이란 어떤 경로로도 다시 접근할 수 없음을 뜻함
- 판정 기준으로 참조 계수(reference counting)와 도달 가능성(reachability) 두 방식이 존재함
    - JVM의 주류 GC는 도달 가능성 방식을 채택함

## 도달 가능성
- 도달 가능성(reachability)이란 특정 시작점에서 참조를 따라가 어떤 객체에 도달할 수 있는지 여부를 가리킴
    - 도달할 수 있으면 살아 있는 객체로 간주함
    - 어떤 경로로도 도달할 수 없으면 죽은 객체, 곧 회수 대상으로 간주함
- 판정의 출발점이 필요하며, 이 출발점을 GC Root라 부름

### GC Root
- GC Root란 도달 가능성 탐색의 시작점이 되는, 항상 살아 있다고 간주하는 참조를 가리킴
- GC Root에 해당하는 참조는 아래와 같음
    - 실행 중인 스레드의 스택에 있는 지역 변수와 매개변수
    - 클래스의 정적(static) 변수
    - JNI(Java Native Interface)를 통해 네이티브 코드가 보유한 참조
    - 활성 상태인 스레드 객체 자체
- 이들을 뿌리로 삼는 이유는 프로그램이 언제든 즉시 접근 가능한 참조이기 때문임
    - 스택의 지역 변수는 현재 실행 중인 메서드가 직접 사용 중임
    - 정적 변수는 클래스가 로드된 동안 항상 접근 가능함

### 참조 그래프 탐색
- 참조 그래프(reference graph)란 객체를 노드로, 객체 간 참조를 간선으로 보는 방향 그래프를 가리킴
- GC는 GC Root에서 출발해 참조 간선을 따라 도달 가능한 모든 객체를 탐색함
    - 이 탐색에서 방문된 객체가 살아 있는 객체임
    - 탐색이 끝난 뒤에도 방문되지 않은 객체가 죽은 객체임

```
[GC Root] ──▶ A ──▶ B ──▶ C     (모두 도달 가능 → live)
[GC Root] ──▶ D                 (도달 가능 → live)
             E ──▶ F            (어떤 Root와도 연결 없음 → dead)
```

- 위 그림에서 E와 F는 서로를 참조하지만 어떤 Root와도 연결되지 않아 회수 대상임
    - 서로 참조가 있어도 Root에서 도달할 수 없으면 죽은 것으로 판정함
    - 이 점이 참조 계수 방식과 대비되는 도달 가능성 방식의 장점임

### 참조 계수 방식과의 경계
- 참조 계수(reference counting)란 각 객체가 자신을 가리키는 참조의 개수를 세어, 그 수가 0이 되면 회수하는 방식을 가리킴
- 참조 계수는 순환 참조(circular reference)를 회수하지 못하는 한계가 있음
    - 위 그림의 E와 F처럼 서로만 참조하면 계수가 각각 1로 유지되어 0이 되지 않음
    - 도달 가능성 방식은 Root 연결 여부로 판정하므로 이 순환을 정상적으로 회수함

## Mark and Sweep
- Mark and Sweep이란 도달 가능성 판정을 표시(mark) 단계와 청소(sweep) 단계로 나눠 수행하는 GC 알고리즘을 가리킴
    - "mark"는 살아 있는 객체에 표시를 남기는 처리를 뜻함
    - "sweep"은 표시되지 않은 객체의 메모리를 회수하는 처리를 뜻함

### Mark 단계
- GC Root에서 출발해 도달 가능한 모든 객체를 순회하며 살아 있음 표시를 남기는 단계
    - 각 객체 헤더의 특정 비트를 표시 용도로 사용
- 순회가 끝나면 표시된 객체가 살아 있는 객체 전체 집합이 됨

### Sweep 단계
- 힙 전체를 훑어 Mark 단계에서 표시되지 않은 객체의 메모리를 회수하는 단계
    - 표시된 객체는 유지함
    - 표시되지 않은 객체가 점유한 공간을 가용 메모리로 되돌림

### Compact 단계
- 살아남은 객체들을 메모리 한쪽으로 모아 붙여 조각난 빈 공간을 없애는 처리
    - 회수만 반복하면 살아남은 객체 사이사이에 빈 공간이 흩어지는 단편화(fragmentation)가 발생함
- Compact는 살아남은 객체를 연속 배치해 이후 할당을 빠르게 함
    - Old 영역을 수집하는 알고리즘에서 주로 동반됨

## 힙 세대 구조
- 힙(heap)이란 `new`로 생성된 모든 객체가 저장되는, 스레드 간에 공유되는 런타임 메모리 영역을 가리킴
    - 메서드 호출과 지역 변수를 담는 스택(stack)과 구별됨
    - 스택은 스레드마다 독립적이나 힙은 모든 스레드가 공유함
- 힙은 객체의 수명(lifespan)을 기준으로 Young 영역과 Old 영역으로 나뉨
    - Young Generation은 갓 생성된 객체가 놓이는 영역
    - Old Generation은 오래 살아남은 객체가 이동해 놓이는 영역

### Young Generation의 세부 구조
- Young Generation이란 새로 할당된 객체가 처음 놓이는, 짧게 사는 객체를 위한 영역을 가리킴
- Young Generation은 다시 Eden 영역과 두 개의 Survivor 영역으로 나뉨

| 영역 | 역할 |
|-----|-----|
| Eden | 새 객체가 최초로 할당되는 공간 |
| Survivor 0 | Minor GC에서 살아남은 객체가 이동하는 공간 |
| Survivor 1 | Minor GC에서 살아남은 객체가 이동하는 공간 |

- Eden이란 `new`로 생성된 거의 모든 객체가 최초로 할당되는 공간을 가리킴
    - 명명 의도는 객체가 처음 생겨나는 장소라는 데 있음
- Survivor란 Eden에서 한 번 이상 Minor GC를 견디고 살아남은 객체가 이동해 머무는 공간을 가리킴
    - 두 개(S0, S1)를 두며, 임의의 시점에 항상 하나는 비어 있음
    - 살아남은 객체를 비어 있는 쪽으로 복사해 모으는 구조임

### Old Generation
- Young Generation에서 여러 번의 GC를 견디고 승격된, 오래 사는 객체를 위한 영역
    - Tenured Generation이라고도 부름
- Young Generation보다 크게 잡히며, 수집 빈도는 낮음
    - 오래 사는 객체는 자주 죽지 않으므로 자주 수집할 이유가 적음

```
[ Heap ]
├── Young Generation
│     ├── Eden        (새 객체 최초 할당)
│     ├── Survivor 0
│     └── Survivor 1
└── Old Generation    (승격된 장수 객체)
```

## Minor GC
- Young Generation만을 대상으로 수행하는 가비지 컬렉션을 가리킴
- 발생 조건은 Eden 영역이 가득 차서 새 객체를 할당할 공간이 없어질 때임

### 객체 이동과 age 카운터
- Minor GC 시 Eden과 현재 사용 중인 Survivor 영역에서 살아 있는 객체를 비어 있는 Survivor 영역으로 복사함
    - 복사 후 Eden과 원래 Survivor 영역은 통째로 비움
    - 죽은 객체가 대부분이라면 복사할 객체가 적어 수집이 빠름
- age란 객체가 GC를 견뎌 살아남은 횟수를 세는 카운터를 가리킴
    - 객체 헤더에 age를 기록함
    - 다른 영역으로 이동할 때마다 age를 1씩 증가시킴

### Old 영역으로의 승격
- 승격(promotion)이란 age가 특정 임계값에 도달한 객체를 Old Generation으로 이동시키는 처리를 가리킴
    - 임계값은 tenuring threshold라 부르며 `-XX:MaxTenuringThreshold`로 조정 가능함
    - HotSpot의 기본값은 15임
- 승격 흐름은 아래와 같음

```
Eden ──(Minor GC 생존)──▶ Survivor ──(age 누적)──▶ Old
```

- 오래 살아남은 객체를 Old로 옮기는 이유가 있음
    - Young 영역에 계속 두면 Minor GC마다 반복해서 복사되어 비용이 누적됨
    - Old로 옮기면 자주 수집하지 않아 반복 복사 비용을 줄임

## Full GC
- Young과 Old를 포함한 힙 전체를 대상으로 수행하는 가비지 컬렉션
    - Old 영역만을 수집하는 Major GC와 자주 혼용되나, 통상 Full GC는 힙 전역을 수집함
- 발생 조건은 주로 Old Generation이 가득 차서 승격할 공간이 부족해질 때임

### Minor GC와 Full GC의 비교
| 구분 | Minor GC | Full GC |
|-----|----------|---------|
| 수집 대상 | Young Generation | 힙 전체(Young + Old) |
| 발생 빈도 | 잦음 | 드묾 |
| 소요 시간 | 짧음 | 김 |
| 정지 영향 | 작음 | 큼 |

- Full GC가 느린 이유
    - Old 영역은 대체로 크고, 살아남은 객체가 많아 순회 대상이 많음
    - 단편화 해소를 위한 Compact가 동반되어 객체 이동 비용이 추가됨

### stop-the-world
- stop-the-world(STW)란 GC 수행을 위해 애플리케이션 스레드 전체를 일시 정지시키는 현상을 가리킴
- STW가 필요한 이유
    - 참조 그래프는 애플리케이션 실행 중 끊임없이 변함
    - 순회 도중 참조가 바뀌면 살아 있는 객체를 죽은 것으로 오판할 위험이 있음
    - 순회 시점의 그래프를 고정하기 위해 애플리케이션을 잠시 멈춤
- STW는 Minor GC에서도 발생하나, Full GC의 STW가 훨씬 길어 지연에 미치는 영향이 큼
    - 응답 지연에 민감한 서버에서 긴 Full GC의 STW는 직접적인 성능 문제로 이어짐

## 세대 분리의 전제
- 힙을 Young과 Old로 나누는 설계는 약한 세대 가설에 근거함
- 약한 세대 가설(weak generational hypothesis)이란 대부분의 객체는 생성된 뒤 금방 죽는다는 경험적 관찰을 가리킴

### 가설이 성립하는 근거
- 실제 애플리케이션에서 객체 수명 분포는 아래 두 분류로 갈림
    - 요청 처리 중에만 쓰이고 곧 버려지는 다수의 단명 객체
    - 설정값, DB 연결처럼 애플리케이션 생애 내내 유지되는 소수의 장수 객체
- 단명 객체가 압도적 다수를 차지함
    - 지역 변수, 임시 계산 결과, 반복문 내 생성 객체 등이 여기 해당함

### 세대 분리가 주는 이득
- 세대 분리가 없다면 GC는 매번 힙 전체를 순회해야 함
    - 대부분 죽는 단명 객체를 걸러내자고 오래 사는 객체까지 매번 훑는 낭비가 발생함
- 세대를 나누면 죽을 확률이 높은 Young 영역만 자주, 빠르게 수집할 수 있음
    - Minor GC는 작은 Young 영역만 대상으로 하므로 짧고 잦게 수행 가능함
    - 오래 사는 Old 영역은 드물게만 수집해 전체 GC 비용을 낮춤

## 메모리 누수
- 메모리 누수(memory leak)란 더 이상 사용하지 않을 객체가 회수되지 못하고 계속 메모리를 점유하는 상태를 가리킴
    - GC가 있으면 누수가 원천 차단된다는 통념은 정확하지 않음

### GC 환경에서 누수가 발생하는 원리
- GC의 회수 기준은 "논리적으로 더 안 쓰는가"가 아니라 "도달 가능한가"임
    - 개발자가 더 이상 쓸 의도가 없어도, 어딘가에서 참조가 남아 도달 가능하면 GC는 살아 있다고 판정함
    - 이 참조를 lingering reference, 곧 의도치 않게 남아 있는 참조라 부름
- 살아 있다고 판정된 객체는 회수되지 않으므로 메모리에 계속 쌓임

### 대표적 누수 유발 패턴
- 정적 컬렉션에 객체를 넣고 제거하지 않는 경우
    - 정적 변수는 GC Root이므로 그로부터 도달 가능한 객체는 영원히 회수되지 않음
- 캐시에 객체를 담고 만료 정책 없이 방치하는 경우
    - 캐시가 참조를 계속 붙들어 도달 가능 상태가 유지됨
- 리스너나 콜백을 등록하고 해제하지 않는 경우
    - 등록 주체가 리스너 참조를 계속 보유해 도달 가능 상태가 유지됨

### 누수 해소의 방향
- 해소의 핵심은 더 안 쓰는 객체로 향하는 참조를 끊어 도달 불가능하게 만드는 데 있음
    - 컬렉션에서 명시적으로 제거함
    - 참조 변수에 `null`을 할당해 연결을 끊음
    - 만료 정책이나 약한 참조(weak reference)로 참조 수명을 제한함
- 참조를 끊어 도달 불가능해진 순간부터 그 객체는 다음 GC의 회수 대상이 됨

## 정리
```
JVM 가비지 컬렉션
    │
    ├── 회수 대상 판정
    │     ├── 도달 가능성 (GC Root 기반)
    │     └── Mark and Sweep (+ Compact)
    │
    ├── 힙 세대 구조
    │     ├── Young (Eden + Survivor 0/1)
    │     └── Old (Tenured)
    │
    ├── 수집 동작
    │     ├── Minor GC (Young 대상, age 누적, 승격)
    │     └── Full GC (힙 전체, stop-the-world)
    │
    ├── 세대 분리의 전제
    │     └── 약한 세대 가설 (대부분 금방 죽음)
    │
    └── 메모리 누수
          └── 도달 가능한 lingering reference는 회수 안 됨
```
