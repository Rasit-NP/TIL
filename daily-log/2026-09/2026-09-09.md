## 컨테이너의 정의
- 컨테이너란 객체의 생성, 보관, 연결, 소멸을 개발자 대신 관리하는 실행 주체를 가리킴
- Bean이란 Spring 컨테이너가 생성하고 관리하는 객체를 가리킴
    - 개발자가 `new`로 직접 만들지 않고 컨테이너에 생성을 맡긴 객체
    - "Bean"이라는 이름은 자바 진영에서 재사용 가능한 컴포넌트 단위를 부르던 관례에서 유래함
- 혼동하기 쉬운 경계
    - 일반 객체는 개발자가 직접 생성하고 수명을 관리하는 객체
    - Bean은 컨테이너가 생성하고 수명을 관리하는 객체
    - 같은 클래스라도 컨테이너에 등록되어 관리되면 Bean, `new`로 만들면 일반 객체

## BeanFactory와 ApplicationContext
- Spring 컨테이너의 핵심 인터페이스는 두 가지
    - `BeanFactory`와 `ApplicationContext`임

### BeanFactory
- `BeanFactory`란 Bean의 생성과 조회를 담당하는 컨테이너의 최상위 인터페이스를 가리킴
    - Bean을 등록하고 요청 시 꺼내주는 가장 기본적인 기능만 정의함
- 기본 동작으로 지연 로딩을 사용함
    - 지연 로딩이란 실제로 Bean이 요청되는 시점에야 생성하는 방식을 가리킴
    - 컨테이너 기동 시점이 아니라 첫 조회 시점에 인스턴스가 만들어짐

### ApplicationContext
- `ApplicationContext`란 `BeanFactory`를 상속해 부가 기능을 더한 상위 인터페이스를 가리킴
    - Bean 관리라는 기본 기능 위에 실무에 필요한 기능을 얹음
- `BeanFactory`가 제공하지 않는 기능을 추가로 제공함
    - 국제화 메시지 처리
    - 이벤트 발행과 구독
    - 환경 변수와 프로파일 관리
    - 리소스 로딩 추상화
- 기본 동작으로 즉시 로딩을 사용함
    - 즉시 로딩이란 컨테이너 기동 시점에 싱글톤 Bean을 미리 생성하는 방식을 가리킴
    - 기동이 끝난 순간 대부분의 Bean이 이미 준비되어 있음

### 두 인터페이스의 관계
- `ApplicationContext`가 `BeanFactory`를 상속하는 상하 관계
    - `BeanFactory`는 컨테이너의 최소 규격임
    - `ApplicationContext`는 그 규격을 포함하고 기능을 확장한 것
- 실무에서는 `ApplicationContext`를 표준으로 사용함
    - Spring Boot가 기동 시 구성하는 컨테이너도 `ApplicationContext` 구현체임

| 구분 | BeanFactory | ApplicationContext |
|-----|-------------|--------------------|
| 위치 | 최상위 인터페이스 | BeanFactory 상속 확장 |
| Bean 로딩 | 지연 로딩 | 즉시 로딩(싱글톤) |
| 국제화 메시지 | 미지원 | 지원 |
| 이벤트 발행 | 미지원 | 지원 |

## Bean 생명주기 단계
- Bean 생명주기란 컨테이너가 Bean을 만들어 소멸시킬 때까지 거치는 단계의 전 과정을 가리킴
- 생명주기는 아래 순서로 진행됨

```
① 객체 생성 (인스턴스화)
     ↓
② 의존성 주입
     ↓
③ 초기화 콜백
     ↓
④ 사용
     ↓
⑤ 소멸 전 콜백
```
- 각 단계의 의미는 아래와 같음
    - 객체 생성은 생성자를 호출해 인스턴스를 메모리에 올리는 단계임
    - 의존성 주입은 그 인스턴스에 협력 객체를 채워 넣는 단계임
    - 초기화 콜백은 의존성이 모두 채워진 뒤 실행되는 준비 작업 단계임
    - 사용은 애플리케이션이 Bean을 실제로 호출해 쓰는 단계임
    - 소멸 전 콜백은 컨테이너 종료 직전 자원을 정리하는 단계임

### 생성과 초기화의 분리
- 생성자 호출과 초기화 콜백은 별개의 단계임
    - 생성자는 의존성이 채워지기 전에 실행됨
    - 초기화 콜백은 의존성이 모두 채워진 후에 실행됨
- 이 분리가 필요한 이유
    - 주입받은 협력 객체를 이용해야 하는 준비 작업은 생성자에서 할 수 없음
    - 생성자 시점에는 아직 의존성이 비어 있기 때문
    - 그런 작업은 의존성 주입이 끝난 뒤의 초기화 콜백에서 수행해야 함

## 초기화와 소멸 콜백
- 컨테이너가 초기화와 소멸 시점에 실행해 주는 콜백을 등록하는 방법은 세 가지임

### `@PostConstruct`와 `@PreDestroy`
- `@PostConstruct`란 의존성 주입 완료 후 실행할 초기화 메서드를 지정하는 애노테이션을 가리킴
- `@PreDestroy`란 Bean 소멸 직전 실행할 정리 메서드를 지정하는 애노테이션을 가리킴

```java
@Component
public class ConnectionManager{

    private Connection connection;

    @PostConstruct
    public void init(){
        // 의존성 주입이 끝난 뒤 호출됨
        // 커넥션 초기 연결 등 준비 작업을 수행함
        this.connection = openConnection();
    }

    @PreDestroy
    public void cleanup() {
        // 컨테이너 종료 직전 호출됨
        // 커넥션 반환 등 자원 정리를 수행함
        connection.close();
    }
}
```
- 자바 표준 애노테이션이며 특정 프레임워크에 종속되지 않음
    - 세 방법 중 실무에서 가장 권장됨

### InitializingBean과 DisposableBean
- Spring이 제공하는 인터페이스를 구현하는 방식
    - `InitializingBean`의 `afterPropertiesSet()`이 초기화 콜백
    - `DisposableBean`의 `destroy()`가 소멸 콜백
- Spring 인터페이스에 코드가 결합되는 단점이 있음
    - 해당 클래스가 Spring에 의존하게 됨

### @Bean의 initMethod와 destroyMethod
- `@Bean` 애노테이션의 속성으로 콜백 메서드를 지정하는 방식
```java
@Configuration
public class AppConfig {

    @Bean(initMethod = "init", destroyMethod = "close")
    public ExternalClient externalClient(){
        return new ExternalClient();
    }
}
```
- 외부 라이브러리 클래스처럼 코드를 수정할 수 없는 경우에 유용함
    - 애노테이션을 붙일 수 없는 클래스에도 콜백을 지정할 수 있음

## 빈 스코프
- 스코프란 Bean이 존재하고 유지되는 범위를 가리킴
    - 컨테이너가 해당 Bean의 인스턴스를 몇 개, 얼마 동안 유지하는지를 결정함

### 싱글톤 스코프
- Bean 정의 하나당 인스턴스를 하나만 생성해 공유하는 범위
    - Spring Bean의 기본 스코프
    - 기준은 클래스가 아니라 Bean 이름임
    - 같은 클래스를 다른 이름으로 두 번 등록하면 인스턴스도 두 개가 만들어짐
    - 컨테이너의 싱글톤 레지스트리가 Bean 이름을 키로 인스턴스를 보관하기 때문
- 동작 방식
    - 컨테이너가 기동 시 인스턴스를 하나 생성함
    - 이후 모든 요청이 동일한 인스턴스를 공유함

```java
// 별도 지정이 없으면 싱글톤 스코프임
@Component
public class UserService{
    // 컨테이너에 인스턴스가 딱 하나만 존재함
}
```

### 프로토타입 스코프
- Bean을 요청할 때마다 새 인스턴스를 생성하는 범위를 가리킴
```java
@Component
@Scope("prototype")
public class TaskProcessor{
    // 조회 요청마다 새 인스턴스가 만들어짐
}
```
- 프로토타입 스코프에서 컨테이너의 관리 범위는 제한적임
    - 컨테이너는 인스턴스 생성, 의존성 주입, 초기화 콜백까지 관여함
    - 반환한 뒤로는 해당 인스턴스의 참조를 보관하지 않음
    - 참조가 없으므로 소멸 시점을 알 수 없어 소멸 콜백이 호출되지 않음
    - 따라서 자원 정리는 사용하는 쪽이 직접 책임져야 함

| 구분 | 싱글톤 | 프로토타입 |
|-----|------|---------|
| 인스턴스 수 | Bean 정의당 1개 | 요청마다 생성 |
| 기본 여부 | 기본 값 | 명시 지정 필요 |
| 소멸 콜백 | 호출됨 | 호출 안 됨 |
| 초기화 콜백 | 호출됨 | 호출됨 |
| 관리 범위 | 생성부터 소멸까지 | 생성부터 초기화까지 |

## 싱글톤 빈의 상태 공유 위험
- 싱글톤 Bean에 가변 상태를 두면 동시성 문제가 발생함
    - 가변 상태란 실행 중 값이 바뀔 수 있는 인스턴스 필드를 가리킴
    - 동시성 문제란 여러 스레드가 공유 자원에 동시에 접근해 결과가 어긋나는 현상을 가리킴
- 위험이 생기는 구조는 아래와 같음
    - 싱글톤 Bean은 인스턴스가 하나뿐이라 모든 요청 스레드가 이를 공유함
    - Bean이 가변 필드를 가지면 여러 스레드가 같은 필드를 동시에 읽고 씀
    - 한 스레드의 쓰기가 다른 스레드의 값을 덮어써 데이터가 오염됨

### 위험한 코드와 실패 사례
- 아래 코드는 요청마다 달라야 할 값을 인스턴스 필드에 저장함
```java
@Service
public class OrderCalculator{

    // 가변 인스턴스 필드 - 모든 스레드가 공유함
    private int total;

    public int calculate(List<Item> items){
        total = 0;
        for (Item item : items){
            total += item.getPrice();
        }
        return total;
    }
}
```
- 실패가 드러나는 흐름은 아래와 같음
    - 스레드 A가 `total`을 0으로 초기화함
    - 계산 도중 스레드 B가 같은 `total`에 자신의 값을 더함
    - A가 반환하는 결과에 B의 계산이 섞여 잘못된 금액이 나옴

### 해결 방향
- 싱글톤 Bean은 무상태로 설계함
    - 무상태란 인스턴스 필드에 가변 상태를 두지 않는 성질을 가리킴
- 값을 지역 변수로 옮김
    - 지역 변수는 각 스레드의 스택에 독립적으로 존재해 공유되지 않음

```java
@Service
public class OrderCalculator{

    public int calculate(List<Item> items){
        int total = 0;
        for (Item item : items){
            total += item.getPrice();
        }
        return total;
    }
}
```
- 상태를 꼭 유지해야 한다면 다른 방식을 택함
    - 요청 범위로 분리해야 하는 상태는 프로토타입이나 요청 스코프 Bean으로 옮김
        - 단, 싱글톤 Bean에 프로토타입 Bean을 필드로 주입하면 주입이 1회만 일어나 프로토타입이 싱글톤처럼 동작함
    - 공유가 불가피한 상태는 동기화나 스레드 안전 자료구조로 보호함

> 싱글톤 Bean의 인스턴스가 하나뿐이라는 사실 자체는 스레드 안전을 보장하지 않음\
> 인스턴스가 하나라는 것은 오히려 모든 스레드가 그 하나를 공유한다는 뜻이므로, 가변 상태를 두면 위험함

## `@Component`와 `@Bean`
- 둘 다 Bean을 등록하는 수단이나 등록 방식과 대상이 다름

### `@Component`
- `@Component`란 클래스에 붙여 컴포넌트 스캔 대상으로 지정하는 애노테이션을 가리킴
    - 컴포넌트 스캔이란 지정된 패키지를 훑어 애노테이션이 붙은 클래스를 자동으로 Bean 등록하는 과정을 가리킴

```java
// 클래스 선언부에 붙임 - 스캔이 이 클래스를 찾아 Bean으로 등록함
@Component
public class EmailValidator{

}
```
- `@Service`, `@Repository`, `@Controller`는 `@Component`를 특수화한 애노테이션임
    - 셋 다 내부에 `@Component`를 포함하므로 컴포넌트 스캔 대상이 되는 것은 동일
    - 다만 Bean 등록 외의 부가 기능은 서로 다름

### `@Bean`
- `@Bean`이란 메서드에 붙여 그 반환 객체를 Bean으로 등록하는 애노테이션을 가리킴
    - `@Configuration` 클래스 안의 메서드에 사용함

```java
@Configuration
public class AppConfig{

    // 메서드가 반환하는 객체가 Bean으로 등록됨
    @Bean
    public ObjectMapper objectMapper(){
        return new ObjectMapper();
    }
}
```

### 두 방식의 선택 기준
- 내가 작성한 클래스는 `@Component`로 등록
    - 클래스 선언부에 애노테이션을 직접 붙일 수 있기 때문
- 외부 라이브러리 클래스는 `@Bean`으로 등록
    - 코드를 수정할 수 없어 클래스에 애노테이션을 붙일 수 없기 때문
    - 생성 로직을 메서드 안에 작성해 반환하는 방식으로 우회함

| 구분 | @Component | @Bean |
|-----|------------|-------|
| 부착 위치 | 클래스 | 메서드 |
| 등록 방식 | 컴포넌트 스캔 | 메서드 반환값 |
| 대상 | 직접 작성한 클래스 | 외부 라이브러리 포함 |
| 생성 제어 | 컨테이너 자동 | 메서드 안에서 직접 |

## 정리
```
Spring 컨테이너와 Bean 생명주기
    │
    ├── 컨테이너 인터페이스
    │     ├── BeanFactory (최상위, 지연 로딩)
    │     └── ApplicationContext (확장, 즉시 로딩)
    │
    ├── 생명주기 단계
    │     ├── 생성 → 의존성 주입 → 초기화 콜백 → 사용 → 소멸 전 콜백
    │     └── 콜백 등록: @PostConstruct/@PreDestroy 권장
    │
    ├── 스코프
    │     ├── 싱글톤 (기본, Bean 정의당 1개)
    │     └── 프로토타입 (요청마다 생성, 소멸 콜백 없음)
    │
    ├── 싱글톤 상태 공유 위험
    │     ├── 가변 필드 공유 → 동시성 문제
    │     └── 해결: 무상태 설계, 지역 변수 활용
    │
    └── 등록 수단
          ├── @Component (직접 작성 클래스, 스캔)
          └── @Bean (외부 라이브러리, 메서드 반환)
```
