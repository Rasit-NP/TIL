## IoC
- Inversion of Control의 약자, 제어의 역전
    - 통제 권한이란 객체를 언제 생성하고 어떤 객체와 연결할지를 결정하는 주도권을 가리킴
- 역전이란 그 주도권의 소재가 뒤집히는 것을 가리킴
    - 개발자가 코드 안에서 직접 결정하던 것을 외부 주체가 대신 결정하게 됨
    - 역전되는 대상은 객체 생성 시점과 의존성 연결 대상을 결정하는 권한

### 역전 이전의 제어 흐름
- 역전 이전에는 객체가 자신이 쓸 다른 객체를 스스로 생성함
- 필요한 객체를 `new`로 직접 만들어 내부에 보관함

```java
public class OrderService{
    // OrderService가 어떤 구현체를 쓸지 스스로 결정함
    private final PaymentClient paymentClient = new KakaoPayClient();
}
```
- 이 구조에서 흐름의 통제권은 개발자가 작성한 코드에 있음
    - `OrderService`가 `KakaoPayClient`라는 구체 구현을 직접 선택함

### 역전 이후의 제어 흐름
- 역전 이후에는 객체 생성과 연결을 외부 컨테이너가 담당함
    - 컨테이너란 객체의 생성, 보관, 연결, 소멸을 대신 관리하는 실행 주체를 가리킴
- 객체는 자신이 쓸 협력 객체를 외부에서 건네받음

```java
public class OrderService{
    private final PaymentClient paymentClient;

    // 어떤 구현체가 들어올지 OrderService는 알지 못함
    // 외부에서 결정해 건네줌
    public OrderService(PaymentClient paymentClient){
        this.paymentClient = paymentClient;
    }
}
```
- 통제권이 개발자 코드에서 컨테이너로 넘어감
    - 어떤 구현을 연결할지 `OrderService` 바깥에서 결정함

## DI
- Dependency Injection, 의존성 주입을 가리킴
    - "Dependency"는 한 객체가 기능 수행을 위해 필요로 하는 다른 객체를 의미함
- 의존성이란 A가 동작하기 위해 B를 필요로 할 때, A가 B에 대해 갖는 관계를 가리킴
    - `OrderService`가 `PaymentClient` 없이는 결제를 처리하지 못하면, `OrderService`는 `PaymentClient`에 의존함
- 주입이란 그 의존 대상을 객체 내부에서 만들지 않고 외부에서 전달받는 방식을 가리킴

### IoC와 DI의 관계
- IoC는 제어의 주도권이 역전된다는 원리를 가리키는 개념임
- DI는 그 원리를 실제로 구현하는 구체적 수단
    - IoC라는 추상적 방향을 코드 차원에서 실현하는 기법이 DI임
- IoC를 실현하는 수단이 DI 하나뿐인 것은 아님
    - 서비스 로케이터 등 다른 구현 방식도 존재함
    - Spring은 그중 DI를 기본 수단으로 채택함

## 강한 결합의 문제
- 결합도란 한 모듈이 다른 모듈에 얼마나 강하게 묶여 있는지를 나타내는 정도를 가리킴
    - 한쪽을 바꿀 때 다른 쪽도 함께 바꿔야 하는 정도가 높으면 강한 결합
- DI 없이 객체가 협력 객체를 직접 생성하면 구체 구현에 강하게 결합됨

```java
public class OrderService{
    // 구체 구현 KakaoPayClient에 직접 결합됨
    private final KakaoPayClient payClient = new KakaoPayClient();
}
```
- 이 구조에서 발생하는 문제는 아래와 같음
    - 구현 교체 시 `OrderService`의 코드를 직접 수정해야 함
    - `KakaoPayClient`를 `TossPayClient`로 바꾸려면 내부를 고쳐야 함
- 테스트가 어려워짐
    - `OrderService`를 테스트할 때 실제 `KakaoPayClient`가 함께 동작함
    - 결제 로직을 가짜 객체로 대체할 수 없어 단위 테스트가 곤란함

### 인터페이스 의존으로의 전환
- 구체 구현이 아니라 인터페이스에 의존하도록 바꾸면 결합도가 낮아짐
    - 인터페이스란 구현 없이 기능의 규격만 선언한 타입을 가리킴

```java
public interface PaymentClient{
    void pay(long amount);
}

public class OrderService{
    private final PaymentClient paymentClient;

    // 인터페이스 타입에만 의존함
    // 어떤 구현이 들어오는지는 외부가 결정
    public OrderService(PaymentClient paymentClient){
        this.paymentClient = paymentClient;
    }
}
```
- `OrderService`는 `PaymentClient`라는 규격만 알면 됨
    - 구현 교체 시 `OrderService`를 수정하지 않아도 됨
    - 테스트 시 가짜 구현을 주입해 결제 로직을 대체할 수 있음

## 주입 3방식
- Spring에서 의존성을 주입하는 방식은 세 가지가 있음
    - 생성자 주입, 필드 주입, 세터 주입

### 생성자 주입
- 생성자의 매개변수로 의존성을 전달받는 방식

```java
@Service
public class OrderService{
    private final PaymentClient paymentClient;

    // 생성자를 통해 주입받음
    public OrderService(PaymentClient paymentClient){
        this.paymentClient = paymentClient;
    }
}
```
- 객체 생성 시점에 모든 의존성이 함께 결정됨
    - 생성이 끝난 순간 협력 객체가 모두 채워져 있음

### 필드 주입
- 필드 주입이란 필드에 `@Autowired`를 붙여 직접 주입받는 방식을 가리킴

```java
@Service
public class OrderService{
    @Autowired
    private PaymentClient paymentClient;
}
```
- 코드가 짧아 보이나 여러 단점을 가짐

### 세터 주입
- 세터 메서드를 통해 주입받는 방식

```java
@Service
public class OrderService{
    private PaymentClient paymentClient;

    @Autowired
    public void setPaymentClient(PaymentClient paymentClient){
        this.paymentClient = paymentClient;
    }
}
```
- 객체 생성 이후 의존성이 채워짐
    - 생성과 주입 시점이 분리됨

### 세 방식의 트레이드오프
| 구분 | 생성자 주입 | 필드 주입 | 세터 주입 |
|-----|----------|---------|---------|
| final 선언 | 가능 | 불가 | 불가 |
| 불변성 | 보장됨 | 미보장 | 미보장 |
| 필수 의존성 강제 | 강제됨 | 미강제 | 미강제 |
| 테스트 용이성 | 높음 | 낮음 | 중간 |
| 주입 시점 | 객체 생성 시 | 생성 이후 | 생성 이후 |

## 생성자 주입 권장 근거
- Spring은 생성자 주입을 권장함
- 근거는 아래 네 가지임

### 불변성 보장
- 불변성이란 객체 생성 이후 상태가 바뀌지 않는 성질을 가리킴
- 생성자 주입은 필드를 `final`로 선언할 수 있음
    - `final` 필드는 생성 시점에 한 번만 값이 채워지고 이후 변경 불가함
- 필드 주입과 세터 주입은 `final` 선언이 불가능함
    - 주입 이후에도 참조가 교체될 여지가 남음

### 필수 의존성 보장
- 필수 의존성이란 그 객체가 정상 동작하기 위해 반드시 있어야 하는 협력 객체를 가리킴
- 생성자 주입은 의존성 없이는 객체 생성 자체가 불가능함
    - 생성자 인자가 채워지지 않으면 인스턴스를 만들 수 없음
    - 협력 객체가 누락된 반쪽짜리 객체가 만들어지지 않음
- 필드 주입도 `@Autowired`의 기본 값이 `required = true`라 대상 빈이 없으면 기동이 실패함
    - 다만 `final`을 붙일 수 없어 불변성이 보장되지 않음
    - `required = false`이거나 컨테이너를 거치지 않고 직접 `new`로 만들면, 필드가 빈 채로 객체가 생성되어 사용 시점에 `NullPointerException`이 발생함

### 테스트 용이성
- 생성자 주입은 순수 자바 코드만으로 객체를 만들 수 있음
    - Spring 컨테이너 없이 테스트용 객체를 생성자에 그대로 넘길 수 있음

```java
// Spring 컨테이너 없이 가짜 구현을 직접 주입해 테스트
PaymentClient fake = new FakePaymentClient();
OrderService orderService = new OrderService(fake);
```

- 필드 주입은 외부에서 값을 넣을 통로가 없음
    - `private` 필드에 직접 접근할 수 없어 리플렉션이나 컨테이너가 필요함
    - 단위 테스트 작성이 번거로워짐

### 순환 참조 조기 발견
- 생성자 주입은 순환 참조가 있으면 애플리케이션 기동 시점에 예외가 발생함
    - 컨테이너가 객체를 생성하려는 단계에서 순환을 감지함
    - 런타임에 문제가 터지기 전에 기동 실패로 드러남
- 생성자 주입은 Spring Boot 버전과 무관하게 순환 참조 시 항상 기동이 실패함
- 필드 주입과 세터 주입은 버전에 따라 동작이 갈림
    - Spring Boot 2.6 이전에는 순환을 허용해 기동은 성공하고 실행 중에 문제가 드러날 수 있음
    - Spring Boot 2.6부터는 순환 참조가 기본 금지라 기본 설정에서는 기동이 실패함
        - 허용하려면 `spring.main.allow-circular-references=true`를 명시해야 함

## 순환 참조
- 순환 참조란 둘 이상의 객체가 서로를 의존 대상으로 참조해 고리를 이루는 상태를 가리킴
    - A가 B를 필요로 하고 동시에 B가 A를 필요로 하는 구조
- 생성자 주입에서 순환 참조가 있으면 어느 쪽도 먼저 생성될 수 없음

```java
@Service
public class AService{
    private final BService bService;
    public AService(BService bService){
        this.bService = bService;
    }
}

@Service
public class BService{
    private final AService aService;
    public BService(AService aService){
        this.aService = aService;
    }
}
```
- 위 구조는 기동 시 `BeanCurrentlyInCreationException`으로 기동이 실패함

### 순환 참조의 해결 방향
- 순환 참조는 회피 기법으로 덮기 전에 설계 문제로 보는 것이 우선
    - 두 객체가 서로를 필요로 한다는 것은 책임 분리가 덜 되었다는 신호임
- 해결 방향
    - 공통 로직을 제3의 객체로 분리해 A와 B가 그 객체에 각각 의존하도록 바꿈
    - 의존 방향을 한쪽으로만 흐르도록 재설계함
- 설계 개선이 어려운 경우의 차선책이 존재함
    - `@Lazy`로 한쪽 주입을 지연시켜 실제 사용 시점까지 생성을 미룸
    - 다만 이는 근본 해결이 아니라 순환 구조를 남긴 채 회피하는 방식

> 생성자 주입이 순환 참조에서 기동 실패를 내는 것은 결함이 아니라 안전장치\
> 문제를 런타임 뒤로 미루지 않고 기동 시점에 드러내 설계를 다시 보게 만드는 장치임
