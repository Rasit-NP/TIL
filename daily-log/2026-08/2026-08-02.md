## HTTP 응답 메시지 구조
- HTTP 응답 메시지란 서버가 요청에 대한 처리 결과를 클라이언트에 돌려줄 때 전송하는 바이트열을 가리킴
- 요청 메시지와 대칭되는 구조를 가지며 세 부분으로 나뉨
    - status line은 응답의 첫 줄로 프로토콜 버전, 상태 코드, 상태 메시지를 담음
    - header 섹션은 응답 본문에 대한 메타 정보를 담는 줄들의 묶음임
    - body는 실제로 전송할 데이터이며 응답에 따라 없을 수도 있음
- 각 요소의 경계와 종료는 CRLF로 구분
- 응답 메시지의 문법을 아래와 같이 요약함
```
status-line CRLF *(header CRLF) CRLF [body]
```
- 헤더 섹션과 body 사이에는 빈 줄, 곧 아무 문자 없이 CRLF만 있는 줄이 들어감
    - 빈 줄은 헤더 섹션의 종료 신호이자 body 시작 경계
- 현재 단계에서 서버가 출력해야 하는 실제 바이트열은 아래 형식임
```
HTTP/1.1 200 OK\r\nConnection: close\r\nContent-Length: 7\r\n\r\nSuccess
```

### status line 구성
- status line은 세 토큰을 SP로 이어붙인 한 줄임
    - HTTP-version은 프로토콜 버전 표기
    - status code는 처리 결과를 나타내는 세 자리 정수
    - reason phrase는 status code를 사람이 읽을 수 있게 옮긴 짧은 설명 문구
- status code와 reason phrase는 함께 붙어 다니는 한 쌍임
    - `200`에는 `OK`, `400`에는 `Bad Request`가 대응함
- status line의 바이트열을 아래와 같이 조립함
```
HTTP/1.1 200 OK\r\n
──────── ─── ──
version code reason
```

## status code와 reason phrase 매핑
- status code와 reason phrase를 각각 별개의 값으로 보유하면 둘이 어긋날 위험이 생김
    - 두 값이 의미상 하나의 쌍인데 저장은 둘로 나뉘어 있기 때문
- 어긋남을 원천 차단하려면 code에서 reason을 결정하는 매핑 테이블을 한 곳에만 둠
    - 외부에서는 code만 저장하고 reason은 항상 매핑으로 유도
    - reason을 직접 지정하는 경로 자체를 없애 불일치 케이스를 만들 수 없게 함

```cpp
// src/http/HttpResponse.cpp

std::string reason_phrase(int code){
    switch(code){
        case 200:   return "OK";
        case 400:   return "Bad Request";
        default:    return "";      // 미등록 code: 빈 reason
    }
}
```

### 미등록 상태 코드 처리
- 현재 단계는 200과 400 두 개만 지원 대상으로 정함
    - 404 등 다른 code는 지금 등록하지 않고 이후 단계에서 추가
- 미등록 code가 들어왔을 때의 동작을 명시적으로 정함
    - 현재는 빈 reason을 반환하는 방식을 택함
    - 동작을 정해두지 않으면 미등록 code 유입 시 결과가 불명확해지므로 계약을 문서화

## 헤더 컨테이너 선택
- 헤더 컨테이너란 응답 헤더의 이름과 값 쌍들을 담아 두는 자료구조를 가리킴
- 후보는 삽입 순서를 보존하는 `std::vector<std::pair<std::string, std::string>>`와 순서를 보존하지 않는 `std::unordered_map<std::string, std::string>`임
- 두 후보를 아래 기준으로 비교함

| 구분 | `vector<pair>` | `unordered_map` |
|-----|----------------|-----------------|
| 삽입 순서 보존 | 보존함 | 보존하지 않음 |
| 직렬화 출력 순서 | 삽입 순서와 동일 | 실행마다 달라질 수 있음 |
| 키 조회 속도 | 선형 탐색 | 평균 상수 시간 |
| 바이트 불변 검증 | 가능 | 순서 고정 우회 필요 |

- 응답 헤더는 조회 속도보다 출력 바이트의 재현성이 중요함
    - 헤더 개수가 소수에 불과해 선형 탐색 비용이 문제되지 않음
    - 반면 출력 순서가 실행마다 뒤섞이면 바이트 단위 검증이 불가능해짐
- `unordered_map`을 쓰면 헤더의 출력 순서가 실행마다 달라질 수 있음
    - 순서를 고정하려면 직렬화 단계에서 별도의 정렬이나 고정 순서 배열이 필요해짐
    - 이 우회 비용을 감수할 이유가 없으므로 삽입 순서가 곧 출력 순서인 vector를 택함

> 헤더 컨테이너는 vector<pair>로 고정함\
> 삽입 순서가 직렬화 순서와 일치해야 출력 바이트를 재현할 수 있음

## 응답 직렬화
- 직렬화란 메모리 상의 객체를 전송 가능한 바이트열로 변환하는 처리를 가리킴
    - 산재한 필드를 HTTP 응답 문법 순서대로 하나의 문자열로 이어 붙이는 처리에 해당함
- HttpResponse는 status code, 헤더, body를 멤버로 보유하고 `serialize()`로 바이트열을 산출함
- 조립 순서는 응답 메시지 문법을 그대로 따름
    - status line을 먼저 붙이고 CRLF로 종료
    - 헤더를 삽입 순서대로 각각 `name: value` 형태로 붙이고 각 줄을 CRLF로 종료
    - 헤더 섹션 종료 신호인 빈 줄 CRLF를 붙임
    - 마지막에 body를 붙임

```cpp
// include/http/HttpResponse.h
class HttpResponse{
public:
    int status_code = 200;

    std::vector<std::pair<std::string, std::string>> headers;

    std::string body;

    std::string serialize() const;
};
```
```cpp
// src/http/HttpResponse.cpp

std::string HttpResponse::serialize() const{
    std::string out;

    out.reserve(body.size() + headers.size()*48 + 64);

    out += "HTTP/1.1 ";
    out += std::to_string(status_code);
    out += " ";
    out += reason_phrase(status_code);
    out += "\r\n";

    for(const auto& [name, value] : headers){
        if (name == "Content-Length")
            continue;
        out += name;
        out += ": ";
        out += value;
        out += "\r\n";
    }

    out += "Content-Length: ";
    out += std::to_string(body.size());

    out += "\r\n\r\n";

    out += body;

    return out;
}
```

### 이동 가능한 반환 설계
- `serialize()`는 지역 문자열 `out`을 값으로 반환함
- 지역 변수를 값으로 반환하면 컴파일러가 이동 또는 복사 생략을 적용해 불필요한 복사를 피함
    - 이동이란 자원의 소유권을 새 객체로 옮겨 깊은 복사를 생략하는 연산을 가리킴
    - 반환문에서 명시적 `std::move`를 쓰지 않아도 반환값 최적화가 우선 적용됨
- `const` 멤버 함수로 선언해 객체 상태를 바꾸지 않음을 계약으로 명시함
- 조립 전 `reserve`로 최종 길이를 예약하면 문자열 확장 과정의 재할당을 줄일 수 있음
    - 필수는 아니며 헤더가 소수인 단계에서는 선택 사항
