## ifstream 열림 판정
- ifstream이란 input file stream의 약자로, 파일에서 바이트를 읽어 들이는 입력 스트림 클래스를 가리킴
    - 생성자나 `open()`에 경로를 넘겨 파일을 대상 스트림에 결합함
    - 결합에 성공하면 이후 그 스트림으로 파일 내용을 순차 판독함
- 파일 서빙에서 실패는 두 층위로 갈림
    - 열기 실패는 대상 파일에 스트림을 결합하지 못한 상태를 가리킴
    - 읽기 실패는 결합에는 성공했으나 이후 판독 도중 오류가 난 상태를 가리킴
- 이 두 실패를 구분하는 두 검사 수단이 있음
    - `is_open()`은 스트림이 파일에 결합됐는지 여부만 반환함
    - `operator bool()`은 스트림의 현재 상태가 정상인지 반환하며 내부적으로 `!fail()`과 같음
- 존재하지 않는 파일, 권한 부족 파일은 열기 자체가 실패하므로 `is_open()`이 false를 반환함

### 크기 기반 판정의 오류
- 실패를 body 크기로 판정하면 빈 파일과 구분이 불가능해짐
    - 열기 실패 시 읽어 낸 body가 빈 문자열이 됨
    - 정상적으로 존재하는 0바이트 파일도 body가 빈 문자열임
    - 두 경우가 같은 결과를 내므로 크기만으로는 갈라낼 수 없음
- 판정 근거를 열림 여부에 두면 두 경우가 명확히 갈림
    - 없는 파일은 `is_open()`이 false이므로 404
    - 존재하는 0바이트 파일은 `is_open()`이 true이므로 200 빈 body

```cpp
// src/http/StaticFileHandler.cpp
// handle(const HttpRequest& req) 내부
std::ifstream file(resolved_path, std::ios::binary);
if (!file.is_open()){
    // 없는 파일·권한 실패 → 열기 자체가 실패
    return make_not_found();    // 404
}
// 여기 도달하면 열림 성공 → 0바이트여도 정상 파일
```

## 디렉터리 대상 사전 차단
- 요청 경로가 파일이 아니라 디렉터리를 가리키는 경우를 별도로 걸러야 함
- 디렉터리에 대한 ifstream 거동은 표준이 규정하지 않는 구석이 있음
    - 리눅스에서는 디렉터리를 여는 것 자체는 성공해 `is_open()`이 true를 반환하기도 함
    - 이후 읽기 단계에서 실패하는 등 플랫폼마다 거동이 갈림
- `is_open()`만으로는 디렉터리를 못 거를 수 있으므로 열기 전에 별도로 판정해야 함
- `std::filesystem::is_directory()`로 열기 이전 시점에 디렉터리 여부를 확인함
    - `std::filesystem`이란 파일과 디렉터리를 다루는 C++17 표준 라이브러리를 가리킴
    - `is_directory()`는 주어진 경로가 디렉터리인지 여부를 bool로 반환함

```cpp
// src/http/StaticFileHandler.cpp
namespace fs = std::filesystem;
if (fs::is_directory(resolved_path)){
    // 디렉터리 대상 → 열기 시도 없이 404
    return make_not_found();
}
```

### 플랫폼별 거동 차이 실측
- 로컬 개발 환경과 배포 실행 환경의 운영체제가 다르면 디렉터리 ifstream 거동이 갈릴 수 있음
    - 디렉터리를 여는 것 자체는 대개 성공하므로 `is_open()`은 양쪽 다 true가 나오기 쉬움
    - 차이는 읽기 단계에서 드러나며, 리눅스는 EISDIR로 실패해 badbit가 섬
- 표준 미규정 영역이므로 실제 실행 환경에서 직접 확인하는 절차가 필요함
    - `is_directory()` 사전 차단을 두면 플랫폼 거동 차이와 무관하게 결과가 고정됨

## 세 실패 경로 404 통일
- 정적 서빙에서 실패로 귀결되는 경로가 세 갈래로 나뉨
    - 대상 파일이 존재하지 않는 경우
    - 대상이 디렉터리인 경우
    - 경로 traversal이 차단된 경우
- 세 실패를 하나의 상태 코드로 정렬하는 이유가 있음
    - 세 경우 모두 클라이언트 관점에서는 "요청한 자원이 없음"으로 귀결됨
    - traversal만 400으로 구분하면 그 경로가 루트 경계를 벗어났다는 사실이 드러남
        - 응답 코드 차이를 반복 관찰해 루트의 위치와 디렉터리 구조를 역추적할 단서가 됨
    - 접근이 거부된 자원에 404가 아닌 코드를 주면 그 자리에 무언가 존재한다는 사실이 노출됨
    - 두 경우 모두 없는 파일과 같은 404로 응답해야 정보가 새지 않음

### 404 응답 구조
- 404 Not Found란 요청한 자원을 서버가 찾지 못했음을 알리는 상태 코드를 가리킴
- 404 응답의 body를 비우면 브라우저가 빈 페이지만 보여 원인 파악이 어려워짐
    - 최소한의 안내 HTML을 body에 담아 사람이 상황을 알 수 있게 함
- 404 응답에도 정상 응답과 같은 메타 헤더가 모두 붙어야 함
    - `Content-Type: text/html`로 body 형식을 명시함
    - `Content-Length`로 body 길이를 명시함
    - `Date`로 응답 생성 시각을 명시함

```cpp
// src/http/StaticFileHandler.cpp
// 세 실패 경로가 공유하는 404 생성 함수
HttpResponse make_not_found(){
    HttpResponse res;
    res.status_code = 404;
    res.body = "<html><body><h1>404 Not Found</h1></body></html>";
    res.headers.emplace_back("Content-Type", "text/html");
    return res;
}
```

### reason phrase 매핑 확장
- code에서 reason을 유도하는 매핑 테이블에 404 항목을 추가함
    - 404를 등록하지 않으면 미등록 code로 취급돼 빈 reason이 반환됨

```cpp
// src/http/HttpResponse.cpp
std::string reason_phrase(int code){
    switch(code){
        case 200:   return "OK";
        case 400:   return "Bad Request";
        case 404:   return "Not Found";     // 이번에 추가
        default:    return "";
    }
}
```

## 확장자 기반 Content-Type 결정
- Content-Type이란 body에 담긴 데이터의 매체 형식을 클라이언트에 알리는 헤더를 가리킴
    - 매체 형식은 MIME 타입 표기를 따름
    - MIME이란 Multipurpose Internet Mail Extensions의 약자로, 데이터 형식을 `주형식/부형식` 꼴로 나타내는 표준을 가리킴
- 브라우저는 이 헤더로 body를 어떻게 해석할지 결정함
    - `text/html`이면 HTML로 렌더링함
    - `image/png`이면 이미지로 표시함
    - 헤더가 틀리면 텍스트가 다운로드되거나 이미지가 깨져 보이는 등 오해석이 생김

### 확장자 추출과 대소문자 정규화
- `std::filesystem::path::extension()`으로 경로에서 확장자를 추출함
    - 마지막 점 이후의 문자열을 점 포함 형태로 반환함
    - `pic.png`에서 `.png`를 반환함
- 확장자는 대소문자를 구별하지 않으므로 소문자로 정규화해야 함
    - `.PNG`와 `.png`는 같은 형식을 가리킴
    - 정규화를 빠뜨리면 `.PNG` 파일이 테이블에서 조회되지 않아 fallback으로 샘

```cpp
// src/http/StaticFileHandler.cpp
std::string ext = resolved_path.extension().string();
std::transform(ext.begin(), ext.end(), ext.begin(),
               [](unsigned char c){ return static_cast<char>(std::tolower(c)); });
```

### 소수 매핑과 fallback
- 완전한 MIME 테이블을 채우는 것은 과설계이므로 필요한 소수 형식만 등록함
    - HTML, CSS, JS, PNG, JPEG, ICO 정도면 브라우저 렌더링 검증에 충분함
- 등록되지 않은 확장자는 fallback 타입으로 응답함
    - fallback이란 대응 항목이 없을 때 되돌아갈 기본값을 가리킴
    - `application/octet-stream`은 형식 미상의 일반 바이트열을 뜻하는 기본 타입임

```cpp
// src/http/StaticFileHandler.cpp
std::string mime_from_extension(const std::string& ext){
    if (ext == ".html") return "text/html";
    if (ext == ".css")  return "text/css";
    if (ext == ".js")   return "application/javascript";
    if (ext == ".png")  return "image/png";
    if (ext == ".jpg" || ext == ".jpeg") return "image/jpeg";
    if (ext == ".ico")  return "image/x-icon";
    return "application/octet-stream";      // 미등록 → 일반 바이트열
}
```

## RFC 7231 Date 헤더
- Date 헤더란 응답 메시지가 생성된 시각을 명시하는 헤더를 가리킴
    - 원 서버(origin server)가 반드시 보내야 하는 메타 헤더 (RFC 7231 §7.1.1.2)
        - 서버에 신뢰할 만한 시계가 없는 경우나 1xx/5xx 응답은 예외로 함
    - 클라이언트가 캐시 신선도 계산 등에 이 시각을 사용함
- Date 헤더의 값은 RFC 7231이 규정하는 IMF-fixdate 형식을 따라야 함
    - IMF-fixdate란 Internet Message Format의 고정 길이 날짜 표기를 가리킴
    - `Sun, 06 Nov 1994 08:49:37 GMT` 꼴의 고정 형식임

```
Sun, 06 Nov 1994 08:49:37 GMT
───  ── ─── ──── ──────── ───
요일   일  월  연도  시:분:초  GMT
```

### GMT 고정 요구
- IMF-fixdate의 시각은 반드시 GMT/UTC 기준이어야 함
    - GMT란 Greenwich Mean Time의 약자로, 경도 0도 기준 표준시를 가리킴
    - HTTP 날짜는 지역 시간대가 아니라 GMT로 고정됨
- 시각 변환 함수 선택이 이 요구를 좌우함
    - `std::gmtime`은 time_t를 GMT 기준 분해 시각 구조체로 변환함
    - `std::localtime`은 실행 환경의 지역 시간대로 변환하므로 사용하면 스펙 위반
- 표준 `std::gmtime` 대신 재진입 버전을 쓰는 이유
    - `std::gmtime`은 정적 버퍼의 포인터를 반환하므로 스레드 간에 서로 덮어씀
    - 호출자가 준 구조체에 결과를 쓰는 POSIX `gmtime_r`을 사용함
    - Windows는 `gmtime_s`이며 인자 순서가 `(tm*, time_t*)`로 반대임

### 로케일 비의존 포맷
- 요일과 월의 약어가 로케일에 따라 흔들리면 형식 위반
    - IMF-fixdate는 영문 약어 `Sun`, `Nov` 등을 고정으로 요구함
    - 프로그램은 시작 시 C 로케일 상태로 출발하므로 환경 변수만으로는 `%a`, `%b` 출력이 바뀌지 않음
    - 위험은 코드 어딘가에서 `setlocale(LC_ALL, "")`을 호출해 환경 로케일을 채택하는 순간 발생함
    - 의존하는 라이브러리가 대신 호출할 수도 있으므로, 기본 상태를 전제로 두기보다 명시적으로 고정하는 편이 안전함

```cpp
// src/http/HttpResponse.cpp
// IMF-fixdate 형식 Date 값 생성
std::string http_date(){
    std::time_t now = std::time(nullptr);
    std::tm gmt{};
    gmtime_r(&now, &gmt);       // GMT 기준 분해, localtime 금지

    char buf[64];
    // %a %b는 로케일 의존 → C 로케일 고정 전제
    std::strftime(buf, sizeof(buf),
                  "%a, %d %b %Y %H:%M:%S GMT", &gmt);
    return std::string(buf);
}
```

### serialize 단일 emit
- Date 헤더는 모든 응답에 공통으로 붙는 헤더
    - 200 응답과 404 응답 모두 Date를 가져야 함
- 이 공통 헤더를 핸들러마다 개별로 붙이면 중복과 누락이 생김
    - 핸들러가 여럿으로 늘면 각자 Date를 붙여야 해 누락 위험이 커짐
- 따라서 Date는 직렬화 지점인 `serialize()`에서 단일하게 emit함
    - `Content-Length`를 `serialize()` 단일 책임으로 둔 것과 같은 논리
    - 모든 응답이 한 경로를 거쳐 직렬화되므로 그 지점에서 붙이면 중복·누락이 원천 차단됨

## 빈 파일과 없는 파일의 경계
- 이 두 경우는 표면상 body가 빈 문자열이라는 점에서 같아 보이나 응답이 정반대로 갈려야 함
    - 없는 파일은 실패이므로 404
    - 존재하는 0바이트 파일은 정상이므로 200 빈 body
- 판정 근거를 무엇에 두느냐가 두 경우의 분기를 결정함
    - 열림 여부(`is_open()`)에 두면 두 경우가 갈림
    - body 크기에 두면 두 경우가 뭉개짐
- 두 케이스를 테스트에 반드시 함께 넣어 분기 방향을 고정해야 함

| 구분 | 열림 여부 | body 크기 | 응답 |
|-----|---------|---------|------|
| 없는 파일 | 열기 실패 | 0 | 404 |
| 0바이트 파일 | 열기 성공 | 0 | 200 빈 body |
