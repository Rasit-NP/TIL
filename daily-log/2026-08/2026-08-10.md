## Content-Length 헤더 시맨틱
- Content-Length란 HTTP 메시지 본문(body)의 길이를 바이트 단위로 명시하는 헤더를 가리킴
    - "Content"는 전송되는 내용, 즉 body를 뜻함
    - 수신 측이 body를 어디까지 읽어야 하는지를 결정하는 유일한 근거
- message body란 HTTP 메시지에서 헤더 섹션 다음에 오는 실제 페이로드 바이트열을 가리킴
    - request line과 헤더가 요청의 메타데이터라면, body는 그 요청이 실어 나르는 데이터 본체
    - POST 요청의 폼 데이터나 JSON 페이로드가 여기 해당함
- RFC 7230 §3.3.2가 정의하는 `Content-Length`의 문법은 아래와 같음
```
Content-Length = 1*DIGIT
```
- `1*DIGIT`은 한 개 이상의 10진 숫자를 뜻함
    - 값은 부호 없는 10진 정수 하나여야 함
    - 선행 부호(`+`, `-`), 소수점, 16진 표기 등은 문법 위반임
- 하나의 메시지에 Content-Length가 중복으로 오거나 서로 다른 값이 오면 안 됨
    - 단일 값만이 유효하며, 충돌하는 값은 요청을 거부할 근거가 됨

## message body 유무 결정 규칙
- 요청에 body가 존재하는지 여부는 Content-Length 헤더의 유무로 판정함
- Content-Length가 부재하면 body가 없는 것으로 간주함
    - GET 요청처럼 body 없이 오는 요청이 여기에 해당함
    - 헤더 섹션이 끝나는 빈 줄 지점에서 곧바로 파싱 완료로 전이함
- Content-Length가 존재하면 그 값만큼의 바이트를 body로 읽어야 함
- Content-Length가 0이면 값이 있으나 길이가 0인 경우임
    - 읽을 body 바이트가 없으므로 빈 줄 지점에서 즉시 파싱 완료로 전이함
    - Content-Length 부재와 값 0은 표현은 다르나 "읽을 body 바이트 없음"이라는 귀결이 동일함
- 판정 지점을 헤더 섹션이 끝나는 빈 줄 처리 자리에 두는 이유가 있음
    - 헤더 파싱이 끝나야 Content-Length 존재 여부와 값을 알 수 있음
    - 헤더 섹션 종료 순간이 곧 body 유무를 판정할 수 있는 가장 이른 시점임

### 판정 분기 위치
- 판정 로직은 헤더 파서가 빈 줄(연속된 CRLF)에 도달한 분기에 위치함
    - 빈 줄은 헤더 섹션의 종료 신호임
- 세 갈래로 분기함
```cpp
// src/http/HttpRequestParser.cpp
// parseHeaders() 내부, 빈 줄(헤더 섹션 종료)에 도달한 시점
auto it = request_.headers.find("content-length");
if (it == request_.headers.end()){
    // 1) Content-Length 부재 → body 없음 → 즉시 완료
    state_ = State::Done;
    return Result::Ok;
}

size_t len = 0;
if (!parse_content_length(it->second, len)){
    // 정수 파싱 실패 → 문법 오류
    state_ = State::Error;
    return Result::Error;
}

body_remaining_ = len;
if (body_remaining_ == 0){
    // 2) Content-Length: 0 → 읽을 body 없음 → 즉시 완료
    state_ = State::Done;
    return Result::Ok;
}

// 3) 양의 Content-Length → Body 상태로 전이
state_ = State::Body;
return parseBody();
```

## 카운터 기반 상태 전이
- body 누적은 request line·헤더 파싱과 다른 전이 원리를 사용함
    - request line과 헤더는 CRLF라는 구분자를 찾아 경계를 판정하는 offset 기반 전이
    - body는 구분자 없이 정해진 바이트 수만큼만 읽어야 하므로 잔여 카운터 기반 전이
- 잔여 카운터란 앞으로 더 읽어야 할 body 바이트 수를 담는 정수 상태를 가리킴
    - Content-Length 값으로 초기화한 뒤, 읽어 들인 만큼 차감해 나감
- body 파싱은 `parseBody()` 함수 하나에 위임함
    - `parseBody()`는 "버퍼에 있는 만큼만 body에 누적하고 잔여 카운터를 차감"하는 단일 책임만 담당
    - 이 단일 책임 분리로 이후 초과분 처리 방식을 바꿀 때 교체 지점이 이 함수 하나로 극소화됨

### `parseBody` 누적 동작
- `parseBody()`는 현재 버퍼의 offset부터 잔여 카운터만큼, 단 버퍼에 있는 만큼만 body에 누적함
    - 버퍼에 남은 바이트가 잔여 카운터보다 적으면, 남은 바이트 전부를 누적하고 그만큼만 차감함
    - 누적한 만큼 offset을 전진시켜 이미 소비한 바이트를 다시 읽지 않게 함

```cpp
// src/http/HttpRequestParser.cpp
HttpRequestParser::Result HttpRequestParser::parseBody(){
    size_t available = buffer_.size() - offset_;    // 버퍼에 남은 바이트
    size_t take = std::min(available, body_remaining_);

    request_.body.append(buffer_, offset_, take);   // 있는 만큼만 누적
    offset_ += take;
    body_remaining_ -= take;

    if (body_remaining_ > 0){
        // 아직 다 못 채움 → 다음 청크를 기다림
        return Result::Incomplete;
    }

    state_ = State::Done;
    return Result::Ok;
}
```

### 청크 경계 분할 누적 재개
- body는 TCP 청크 경계에 걸쳐 여러 parse() 호출로 나뉘어 도착하는 것이 정상임
    - TCP는 바이트 스트림이므로 송신 측이 한 번에 보낸 body가 수신 측에서 여러 조각으로 쪼개져 도착할 수 있음
- 잔여 카운터가 멤버 변수로 호출 간에 보존되므로, 다음 parse() 호출이 이전 진행 지점을 이어받음
    - 매 호출은 버퍼에 있는 만큼만 누적하고 부족하면 Incomplete로 멈춤
    - 다음 청크가 도착하면 그 자리에서 재개해 카운터를 마저 차감함
- body가 1바이트씩 나뉘어 도착하는 경우가 가장 가혹한 분할이므로 반드시 재현해 검증해야 함
    - 이 경우를 통과하면 임의 분할에서도 누적 정확성이 강하게 보장됨

## `std::from_chars` 안전 파싱
- Content-Length 값 문자열을 정수로 변환할 때는 `std::from_chars`를 사용함
    - `std::from_chars`란 문자열 구간을 정수나 부동소수점으로 변환하는 C++17 함수
- 이 함수를 택하는 이유는 실패와 범위 초과를 예외나 errno가 아니라 반환값으로 판정하기 때문임
    - 예외를 던지지 않으므로 파싱 실패가 정상 제어 흐름 안에서 처리됨
    - 변환을 멈춘 위치 포인터와 오류 코드를 구조체로 돌려줌

### `stoi`·`atoi` 대비 안정성
- 기존의 `stoi`나 `atoi`로 Content-Length를 파싱하면 방어에 취약함
    - `atoi`란 문자열을 int로 변환하는 C 함수
    - `stoi`란 문자열을 int로 변환하는 C++ 함수
- 세 함수의 실패 처리 방식을 비교함

| 구분 | atoi | stoi | from_chars |
|-----|------|------|------------|
| 비정수 입력("abc") | 0을 조용히 반환 | 예외 던짐 | errc로 실패 판정 |
| 후행 쓰레기("123abc") | 앞부분만 변환 | 앞부분만 변환 | ptr로 미소비 감지 |
| 범위 초과 | 미정의 동작 | out_of_range 예외 | result_out_of_range 반환 |
| 실패 신호 | 없음(0과 구분 불가) | 예외 | 반환값 |

- `atoi`는 `"abc"`에 0을 조용히 반환해 실패를 정상값 0과 구분할 수 없음
    - `Content-Length: 0`과 malformed 입력이 같은 결과가 되어 위험함
- `stoi`는 예외를 던지므로 예외 처리 비용과 흐름 복잡도가 늘어남
- 두 함수 모두 후행 쓰레기(`123abc`)의 앞부분만 변환하고 나머지를 조용히 버림
    - 전체 문자열이 온전한 정수인지 확인할 수단이 없음

### 세 가지 검증 조건
- `from_chars`로 다음 세 조건을 모두 확인하고, 하나라도 실패하면 `State::Error`로 전이함
    - 전체 문자열이 남김없이 소비됐는지 확인
        - 반환된 ptr이 문자열 끝과 일치해야 함
        - 일치하지 않으면 후행 쓰레기가 남은 것
    - 범위 초과가 아닌지 확인함
        - errc가 `result_out_of_range`이면 값이 size_t 표현 범위를 벗어난 것
    - 음수 부호가 없는지 확인함
        - `from_chars`는 부호 없는 타입에 `-`가 오면 실패로 처리하나, 입력 자체에 `-`가 있으면 명시적으로도 거부함

```cpp
// src/http/HttpRequestParser.cpp
// Content-Length 문자열 → size_t 안전 변환
// 성공 시 true, 실패 시 false
# include <charconv>
bool parse_content_length(const std::string& s, size_t& out){
    if (s.empty())
        return false;
    if (s.front() == '-' || s.front() == '+')
        return false;

    const char* begin = s.data();
    const char* end = s.data() + s.size();

    size_t value = 0;
    auto [ptr, ec] = std::from_chars(begin, end, value);

    if (ec != std::errc())
        return false;       // 변환 실패·범위 초과
    if (ptr != end)
        return false;       // 후행 쓰레기 잔존

    out = value;
    return true;
}
```

### 검증 누락 시 위험
- 이 검증을 생략하면 malformed Content-Length가 잠재적 공격 표면이 됨
    - 거대한 값이 통과하면 그 크기만큼 힙을 미리 예약하려다 과할당이 유발될 수 있음
    - 이는 소량의 malformed 요청으로 메모리를 고갈시키는 서비스 거부(DoS, Denial of Service) 표면이 됨
- 실패 경로를 정상값과 구분할 수 없는 파서는 이 표면을 막지 못함
    - `from_chars`의 반환값 기반 판정이 실패를 명확히 분리해 이 표면을 차단함

## body 소유 문자열 선택
- body 필드는 `string_view`가 아니라 복사 소유 `std::string`으로 둠
- body를 뷰로 두면 안 되는 이유는 재할당 무효화 때문임
    - body는 청크 경계에 걸쳐 여러 parse() 호출로 누적되는 것이 정상
    - 누적 과정에서 `buffer_.append`가 용량을 초과하면 더 큰 메모리 블록을 새로 할당하고 기존 내용을 복사한 뒤 옛 블록을 해제함
    - 이 재할당(reallocation)이 일어나면 이전 기반 주소를 가리키던 뷰가 즉시 무효화되어 dangling이 됨
- 복사 소유 `std::string`은 자신의 저장 공간에 body를 직접 담으므로 `buffer_` 재할당과 무관하게 안전함

```cpp
// include/http/HttpRequest.h
struct HttpRequest{
    // ...
    std::string body;
};
```

## Content-Length 초과분 처리
- 초과분이란 `body_remaining_`을 다 채운 뒤에도 버퍼에 남아 있는 바이트를 가리킴
    - Content-Length가 지정한 길이를 넘어 도착한 바이트
    - keep-alive 환경에서는 이 초과분이 다음 요청의 시작 바이트일 수 있음
- keep-alive란 하나의 TCP 연결로 여러 HTTP 요청·응답을 주고받는 연결 재사용 방식을 가리킴
- 초과분 처리 지점을 `parseBody()` 한 곳에 국소화하고 주석으로 이후 연결점을 명시해야 함
    - keep-alive에서는 이 초과분이 다음 요청의 시작 바이트이므로 폐기 대신 다음 파싱 사이클로 이월해야 함
    - 폐기 로직을 여러 곳에 흩뿌리면 이월 방식으로 바꿀 때 누락이 생김

### 버퍼 상한과 body의 관계
- 현재 파서는 `buffer_` 전체가 상한을 초과하면 Error로 처리함
    - 이 상한은 원래 헤더 무한 누적을 막는 안전장치로 도입됨
- body를 다루기 시작하면 이 상한이 "헤더 크기 상한"이 아니라 "요청 전체 크기 상한"으로 작동함
    - `buffer_`에 헤더와 body가 함께 누적되므로, 큰 body가 이 상한에 걸림
    - 큰 POST 요청은 헤더가 작아도 body 때문에 상한을 넘을 수 있음
- 헤더 크기 상한과 body 크기 상한의 분리는 이후 견고성 단계로 미루되, 현재 상한이 요청 전체에 작동함을 주석으로 인지해 둠

### 메서드-body 정합성 유예
- Content-Length가 있는데 method가 GET인 경우 같은 시맨틱 검증은 현재 스코프 밖임
    - Content-Length가 존재하면 method와 무관하게 body를 읽음
- RFC상 GET에 body는 비권장이나 금지는 아님
    - 엄격하게 거부하는 것은 과설계이므로 인지만 하고 넘어감
    - 메서드별 body 허용 여부 검증은 의미 검증 계층의 몫으로 분리함
