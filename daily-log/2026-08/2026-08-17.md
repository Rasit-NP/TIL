## request-target의 path와 query 분리
- origin-form이란 request-target의 네 형태 중 서버 직접 요청에 쓰이는 형태를 가리킴
    - RFC 7230이 정의하는 문법은 `absolute-path [ "?" query ]`임
    - `/index.html`이나 `/search?q=1` 형태가 이에 해당함
- absolute-path란 request-target에서 자원의 계층 경로를 나타내는 앞부분을 가리킴
    - 선행 슬래시로 시작하는 경로 문자열
- query란 `?` 뒤에 오는 부가 파라미터 문자열을 가리킴
    - `?` 문자 자체는 경로와 쿼리를 나누는 구분자이며 경로에도 쿼리에도 포함되지 않음
    - `/search?q=1`에서 `q=1` 부분

### path에 query가 섞이는 결함
- request-target을 통째로 path 필드에 담으면 query가 붙은 요청에서 path와 query가 분리되지 않음
    - `/index.html?v=1`이 통째로 path에 들어가면 path 값이 `/index.html?v=1`이 됨
- 이 상태에서는 정적 서빙 단계의 파일 매핑이 실패함
    - 루트 뒤에 이 문자열을 붙이면 `public/index.html?v=1`이라는 존재하지 않는 파일 경로가 됨
    - 결과적으로 쿼리가 붙은 정적 리소스 요청이 404로 귀결됨
- 라우팅 매칭도 실패함
    - `/echo?x=1`의 path가 `/echo?x=1`이 되면 `path == "/echo"` 비교가 거짓이 됨

### 분리 시점의 원칙
- query 분리는 라우팅 매칭보다 먼저 파서 단계에서 수행함
    - 매칭 시점에는 이미 path가 순수 경로 문자열이어야 비교가 성립함
    - 분리를 매칭 이후로 미루면 매칭 대상 문자열에 query가 섞여 있어 비교가 어긋남
- 정규화나 디코딩 같은 전처리가 매칭보다 앞서야 한다는 원칙과 동일한 순서 규칙임
    - 변형 처리가 판정보다 먼저 끝나야 판정 대상이 안정된 형태를 가짐
- 아래는 request line 파싱에서 path와 query를 나누는 부분임
    - `raw_target`은 두 SP 사이에서 잘라낸 request-target 문자열임
    - `?`의 위치를 찾아 앞은 path, 뒤는 query로 나눔

```cpp
// src/http/HttpRequestParser.cpp
std::string raw_target = request_line.substr(sp1 + 1, sp2 - sp1 - 1);

size_t q = raw_target.find('?');
if (q == std::string::npos){
    request_.path = raw_target;
}
else {
    request_.path  = raw_target.substr(0, q);
    request_.query = raw_target.substr(q + 1);
}
```

### query 보존 여부의 결정
- query를 별도 필드로 보존할지, path만 잘라내고 query는 버릴지 결정이 필요함
- 이번 범위의 echo는 본문만 사용하므로 query 값 자체는 사용하지 않음
    - path만 정확히 잘라내면 라우팅과 정적 서빙 목표가 모두 충족됨
- 다만 query 필드를 두어도 비용이 거의 없으므로 별도 필드로 보존해 둠
    - 이후 query 파라미터 처리 단계에서 재파싱 없이 바로 사용 가능

## 순수 함수 기반 최소 라우팅
- 라우팅이란 요청의 경로에 따라 어떤 처리 로직으로 보낼지 결정하는 분기를 가리킴
    - 여기서는 path 문자열을 보고 echo 처리와 정적 서빙 중 하나로 보냄
- 순수 함수란 같은 입력에 항상 같은 출력을 내며 외부 상태를 바꾸지 않는 함수를 가리킴
    - 입력은 요청 객체와 핸들러 참조이며 출력은 응답 객체임
    - 내부에 상태를 두지 않으므로 호출 간 부작용이 없음

### 라우팅 진입점 설계
- 라우팅 진입점을 자유 함수 하나로 둠
    - 자유 함수란 클래스 멤버가 아닌 독립 함수를 가리킴
    - 상태를 가질 이유가 없으므로 클래스로 감싸지 않고 자유 함수로 표현함
- 함수 시그니처는 요청과 핸들러 참조를 받아 응답을 반환하는 형태임
- 분기 구조는 최소 두 갈래임
    - path가 `/echo`이면 echo 응답을 조립함
    - 그 외 모든 path는 기존 정적 서빙 핸들러에 위임함

```cpp
// src/http/route.cpp
// path 기반 최소 라우팅 진입점
HttpResponse route(const HttpRequest& req, const StaticFileHandler& handler){
    if (req.path == "/echo"){
        // echo 응답 조립
        return make_echo_response(req);
    }
    // /echo 외 전 경로는 정적 서빙에 위임
    return handler.handle(req);
}
```

### 과설계 회피의 경계
- 라우팅을 핸들러 등록 테이블이나 method×path 디스패치로 일반화할 수 있음
    - 등록 테이블이란 경로 패턴과 핸들러를 쌍으로 등록해 두고 조회로 매칭하는 구조를 가리킴
- 이번 범위에서는 단일 조건 분기로 충분하므로 일반화를 도입하지 않음
    - 경로가 하나뿐인데 테이블을 도입하면 조회 계층이 불필요한 간접 참조만 늘림
    - 경로가 늘어나는 시점에 일반화하는 편이 각 단계의 스코프를 좁게 유지함

### 연결 계층의 호출 지점 교체
- 기존에는 연결 계층이 핸들러를 직접 호출해 응답을 조립함
    - `handler_.handle(req).serialize()` 형태로 정적 핸들러를 직접 불렀음
- 이 직접 호출을 라우팅 함수 호출로 교체함
    - 연결 계층은 이제 어떤 경로가 어디로 가는지 알 필요가 없음
    - 경로별 분기 책임이 라우팅 함수 한 곳으로 모임

```cpp
// src/connection.cpp
// 핸들러 직접 호출을 라우팅 함수 호출로 교체
const HttpRequest& req = parser_.request();

std::string out = route(req, handler_).serialize();
write_all(out);
```

## POST 본문 반사 응답 조립
- echo란 요청으로 받은 본문을 그대로 응답 본문으로 되돌려주는 동작을 가리킴
    - 클라이언트가 보낸 바이트가 서버를 거쳐 변형 없이 되돌아옴
    - 요청·응답 왕복과 본문 파싱이 올바른지 확인하는 검증 수단으로 쓰임
- POST란 서버에 데이터를 제출하는 HTTP 메서드를 가리킴
    - 본문에 페이로드를 실어 보내는 대표적인 메서드

### echo 응답의 구성 요소
- echo 응답에서 서버가 채우는 것과 자동 산출되는 것의 경계가 있음
    - 채우는 것은 상태 코드 200과 본문(요청 본문 복사)임
    - 자동 산출되는 것은 `Content-Length`이며 직렬화 단계가 본문 크기로 계산함
- 상태 코드 200은 요청이 성공적으로 처리됨을 나타내는 코드임
- 본문은 파싱된 요청 본문을 그대로 복사해 담음

```cpp
// src/http/route.cpp
// POST /echo 응답 조립
HttpResponse make_echo_response(const HttpRequest& req){
    HttpResponse res;
    res.status_code = 200;
    res.body = req.body;    // 요청 본문을 그대로 복사

    // Content-Type 반사
    // ...

    return res;
}
```

## Content-Type 반사와 fallback
- 반사란 요청에 실려 온 Content-Type 값을 응답에도 그대로 돌려주는 처리를 가리킴
    - 본문을 그대로 되돌리므로 형식 표기도 그대로 되돌리는 것이 일관됨

### 요청에 Content-Type이 없는 경우
- 요청에 Content-Type 헤더가 없을 수 있음
    - `curl --data-binary`는 기본적으로 `application/x-www-form-urlencoded`를 붙이지만, 명시하지 않으면 요청에 따라 헤더가 없을 수도 있음
- 헤더가 없으면 fallback 값을 사용함
    - fallback이란 대응 항목이 없을 때 되돌아갈 기본값을 가리킴
- fallback으로 `application/octet-stream`을 사용함
    - octet-stream이란 형식을 특정하지 않은 임의 바이트열을 뜻하는 매체 형식임
    - 형식을 알 수 없을 때 안전하게 쓰는 범용 기본값임

```cpp
// src/http/route.cpp
// Content-Type 반사, 없으면 octet-stream fallback
auto it = req.headers.find("content-type");
if (it != req.headers.end()){
    res.headers.emplace_back("Content-Type", it->second);
}
else {
    res.headers.emplace_back("Content-Type", "application/octet-stream");
}
```

## 뷰에서 소유 문자열로의 복사 경계
- string_view란 문자열의 시작 주소와 길이만 참조하고 소유하지 않는 경량 뷰 타입을 가리킴
    - 복사 없이 기존 버퍼를 들여다보므로 빠르지만, 참조 대상이 사라지면 무효화됨
- 소유 문자열이란 자신의 저장 공간에 문자를 직접 담는 `std::string`을 가리킴
    - 참조가 아니라 실제 데이터를 보유하므로 원본 버퍼와 수명이 독립적임

### dangling 위험 지점
- echo 본문을 뷰인 채로 응답에 담으면 이 위험이 발생함
    - 요청 본문이 파서의 버퍼를 참조하는 뷰라면, 응답이 그 뷰를 그대로 들고 있게 됨
    - 읽기 콜백이 끝나 버퍼가 정리되면 뷰가 가리키던 메모리가 사라짐
    - 이후 응답 직렬화가 그 뷰를 읽으면 dangling 접근이 됨

### 소유 확보로 방어
- 응답 본문 필드를 소유 `std::string`으로 두어 이 위험을 차단함
    - 요청 본문을 응답에 대입하는 순간 실제 바이트가 응답의 저장 공간으로 복사됨
    - 복사 이후 응답은 원본 버퍼와 무관하게 자기 데이터를 보유함
- 요청 본문 필드도 이미 소유 `std::string`으로 되어 있으면 대입만으로 안전함
    - 요청 본문은 청크 경계에 걸쳐 누적되므로 뷰가 아니라 소유 문자열로 두는 것이 정상

## 검증
- echo 동작은 컨테이너에서 curl로 실측
    - `curl -X POST --data-binary 'hello' http://localhost:8080/echo`가 hello를 그대로 되돌리는지 확인함
    - `--data-binary`는 입력을 변형 없이 그대로 본문에 싣는 옵션임

```
$ curl -X POST --data-binary 'hello' http://localhost:8080/echo
hello
```
- query가 붙어도 정상 동작하는지 확인
    - `/index.html?v=1`이 200으로 응답되는지 확인
    - `/echo?x=1`이 echo 응답으로 매칭되는지 확인
- 정적 서빙 회귀가 없는지 확인
    - `/echo` 외 경로에서 기존 200/404/MIME/Date 동작이 유지되는지 확인
