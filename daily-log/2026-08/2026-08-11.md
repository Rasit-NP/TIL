## 정적 파일 서빙의 정의
- 서버가 디스크에 이미 존재하는 파일을 요청받은 그대로 응답 본문에 실어 반환하는 처리
    - 요청 파라미터에 따라 내용을 계산해 만드는 동적 생성(dynamic generation)과 대비됨
    - HTML, CSS, 이미지처럼 사용자별로 달라지지 않는 자원이 정적 파일에 해당함
- 요청 경로를 디스크 상의 실제 파일 경로로 변환한 뒤, 그 파일을 읽어 응답 객체로 되돌려 주는 것이 핵심 동작임
- 이 골격이 완성하는 하나의 관통 경로
    - 요청 경로를 파일 경로로 매핑
    - 매핑된 파일을 binary로 읽어 본문에 담음
    - 본문을 실은 200 응답 객체를 조립해 반환
    - 연결 계층이 그 응답을 직렬화해 클라이언트로 내보냄

## 핸들러의 정의
- 핸들러(handler)란 파싱이 끝난 요청 객체를 입력으로 받아 그에 대응하는 응답 객체를 산출하는 구성 요소를 가리킴
    - "handle"은 요청을 처리한다는 뜻이며, 파서가 넘겨준 결과를 받아 다음 단계를 담당함
- 파서와 핸들러는 책임이 분리됨
    - 파서는 바이트열을 구조화된 요청 객체로 바꾸는 데까지만 책임짐
    - 핸들러는 그 요청 객체를 근거로 어떤 응답을 만들지 결정함
- 정적 파일 핸들러가 응답 조립을 담당하는 근거
    - 요청 경로에 해당하는 파일의 존재 여부와 확장자를 아는 주체가 핸들러임
    - 상태 코드 결정과 본문 채우기는 그 정보를 가진 쪽에서 하는 것이 자연스러움

### 클래스 인터페이스
- `StaticFileHandler`는 루트 경로를 멤버로 보유하고, 요청 하나를 받아 응답 하나를 반환하는 단일 진입점 `handle`을 제공함
- 반환 타입 `HttpResponse`는 상태 코드·헤더·본문을 담아 직렬화 가능한 응답 객체

```cpp
// include/http/StaticFileHandler.h
class StaticFileHandler {
public:
    explicit StaticFileHandler(std::string root);
    HttpResponse handle(const HttpRequest& req) const;

private:
    std::string root_;      // public/ 루트 디렉토리 경로
};
```
- 생성자에 `explicit`을 붙인 이유
    - `explicit`이란 단일 인자 생성자가 암묵적 변환에 쓰이는 것을 막는 지정자
    - 이것이 없으면 `StaticFileHandler`가 필요한 자리에 `std::string`을 넘겼을 때 핸들러가 암묵적으로 만들어지는 변환이 허용됨
    - 핸들러를 문자열로부터 실수로 만들어 내는 경로를 차단하기 위해 명시적 생성만 허용함

### const 멤버 함수로 선언하는 이유
- stateless란 객체가 호출 사이에 변하는 내부 상태를 보유하지 않음을 가리킴
    - 생성자로 주입받은 루트 경로 `root_`는 불변이며 요청마다 달라지지 않음
    - `handle`은 `req`만 입력으로 받아 응답을 산출하고 자신의 멤버를 수정하지 않음
- `handle`을 `const` 멤버 함수로 선언해 이 성질을 타입 수준에서 강제함
- stateless이므로 하나의 인스턴스를 여러 연결이 공유해도 안전함
    - 연결마다 핸들러를 새로 만들 필요가 없음
    - 하나만 소유하고 각 연결에는 참조만 넘기는 구조가 성립함

## 소유와 주입
- 소유(ownership)란 어떤 객체의 수명을 책임지고 관리하는 관계를 가리킴
- 주입(injection)이란 객체가 필요로 하는 의존 대상을 내부에서 생성하지 않고 외부에서 넘겨받는 방식을 가리킴
    - 의존 대상을 직접 만들지 않으므로 결합도가 낮아지고, 교체와 테스트가 쉬워짐
- 이 서버의 소유 계층은 아래와 같음
```
main
  │  root 경로 문자열 전달
  ▼
EventLoop   ── StaticFileHandler 하나를 멤버로 소유
  │  새 연결 수립 시 const 참조 주입
  ▼
Connection  ── const StaticFileHandler& 참조만 보유
```
- 루트 경로는 `main`에서 시작해 생성자 주입으로 아래로 전달됨
    - `main`이 `EventLoop`를 만들 때 루트 경로 문자열을 넘김
    - `EventLoop`가 그 경로로 `StaticFileHandler`를 만들어 멤버로 소유함
- `Connection`은 핸들러를 소유하지 않고 참조만 보유함
    - `EventLoop`가 새 연결을 받아들이는 `accept_new` 메서드 안에서, 소유하고 있는 핸들러의 `const` 참조를 새 `Connection`에 넘김
    - 핸들러가 stateless이므로 모든 연결이 같은 인스턴스를 참조해도 문제가 없음
- 아래는 `EventLoop::accept_new` 본문에서 새 연결을 생성하는 부분임
    - `handler_`는 `EventLoop`가 소유한 `StaticFileHandler` 멤버이며, 그 참조가 `Connection` 생성자로 전달됨

```cpp
// src/event_loop.cpp
EventLoop::accept_new(){
    // ...
    int client_fd = /* accept() 결과 */
    connections_.emplace(
        client_fd,
        std::make_unique<Connection>(Socket{client_fd}, handler_)
    );
}
```

## 요청 경로의 파일 경로 매핑
- 요청 경로(request path)란 요청 라인의 request-target에서 뽑아낸 경로 부분을 가리킴
    - `GET /index.html HTTP/1.1`에서 `/index.html`이 요청 경로임
- 매핑(mapping)이란 요청 경로를 디스크 상의 실제 파일 경로로 대응시키는 처리를 가리킴
- 기본 규칙은 루트 디렉토리 뒤에 요청 경로를 이어 붙이는 것임
    - 루트가 `public`이고 요청 경로가 `/index.html`이면 대상 파일은 `public/index.html`임

### index.html 기본 문서 매핑
- 기본 문서(index document)란 디렉토리 자체가 요청되었을 때 대신 반환할 대표 파일을 가리킴
    - 관례적으로 `index.html`이란 이름을 사용함
- 요청 경로가 `/`이면 특정 파일이 아니라 루트 디렉토리 자체를 가리킴
    - 디렉토리는 파일처럼 읽을 수 없으므로 그대로는 매핑할 수 없음
- 이 경우 `/`를 `/index.html`로 치환한 뒤 매핑을 진행함
    - 치환은 경로 결합·정규화보다 먼저 수행함
    - 치환 결과가 이후 결합과 정규화의 입력이 됨
- 아래는 `StaticFileHandler::handle` 본문의 도입부
    - 매개변수 `req`에서 요청 경로를 꺼내 지역 문자열 `target`으로 복사하고, `/`이면 기본 문서로 치환함

```cpp
// src/http/StaticFileHandler.cpp
HttpResponse StaticFileHandler::handle(const HttpRequest& req) const {
    std::string target(req.path);

    // "/" 요청은 기본 문서로 치환
    if (target == "/")
        target = "/index.html";

    // ...
}
```

## std::filesystem 경로 정규화
- `std::filesystem::path`란 파일 시스템 경로를 다루기 위한 표준 라이브러리 타입을 가리킴
    - 경로 문자열을 직접 자르고 붙이는 대신, 결합과 정규화 같은 연산을 타입 차원에서 제공함
- 경로 결합에는 `operator/`를 사용함
    - `path` 객체를 `/` 연산자로 이으면 플랫폼에 맞는 구분자로 두 경로를 연결함

### operator/의 절대 경로 대체 규칙
- `operator/`는 오른쪽 피연산자가 절대 경로이면 왼쪽 피연산자를 버리고 오른쪽으로 대체함
- 요청 경로 `/index.html`은 선행 슬래시로 시작해 절대 경로로 취급됨
    - `root / "/index.html"`은 `root`를 버리고 `/index.html`이 되어 루트 밖을 가리킴
    - 이 대체 규칙이 곧 함정이며, 선행 슬래시를 떼어 상대 경로로 만들어야 회피됨
- 아래는 `handle` 본문에서 경로를 결합하고 정규화하는 부분임

```cpp
#include <filesystem>
HttpResponse StaticFileHandler::handle(const HttpRequest& req) const {
    // ...

    namespace fs = std::filesystem;

    fs::path base = fs::path(root_).lexically_normal();
    fs::path full = (base / target.substr(1)).lexically_normal();

    // ...
}
```

### lexically_normal의 정의
- `lexically_normal`이란 경로를 실제 디스크 접근 없이 문자열 형태만으로 정규화하는 연산을 가리킴
    - 심볼릭 링크 해석이나 파일 존재 확인 없이, 경로에 담긴 `.`과 `..` 같은 요소를 규칙에 따라 접음
- 정규화가 수행하는 처리
    - 현재 디렉토리를 뜻하는 `.` 요소를 제거
    - 상위 디렉토리를 뜻하는 `..` 요소를 바로 앞 요소와 상쇄해 접음
    - 중복된 구분자를 하나로 합침
- 디스크에 접근하는 `canonical`과의 경계
    - `canonical`은 실제 파일 시스템을 조회해 심볼릭 링크까지 해석하며, 대상 경로가 실재해야 함
    - `lexically_normal`은 문자열만 다루므로 대상 파일이 없어도 동작함
    - 요청 경로가 존재하지 않는 파일을 가리킬 수도 있으므로, 존재를 전제하지 않는 `lexically_normal`이 매핑 단계에 적합함

## path traversal 방어
- path traversal이란 요청 경로에 `..`를 섞어 의도된 루트 디렉토리 밖의 파일에 접근하는 공격을 가리킴
    - directory traversal 또는 dot-dot-slash 공격이라고도 부름
- 방어가 없을 때의 유출 경로
    - 요청 경로를 루트에 그대로 이어 붙이면 `..`가 상위 디렉토리로 거슬러 올라감
    - `/../../etc/passwd` 같은 경로로 시스템 파일이 유출될 수 있음

```
루트: /srv/public
요청: /../../etc/passwd

선행 슬래시 제거 후 결합:  /srv/public/../../etc/passwd
lexically_normal 정규화:  /etc/passwd          ← 루트 밖으로 탈출
```

- 최소 방어의 원리
    - 정규화를 먼저 수행해 `..`를 모두 접음
    - 정규화된 경로가 루트 디렉토리로 시작하는지 검사함
    - 루트 밖을 가리키면 요청을 거부
- "정규화 후 판정" 순서가 핵심임
    - 정규화 전에는 `..`가 문자열에 남아 있어, 접두사 검사만으로는 탈출을 잡지 못함
    - 정규화가 `..`를 모두 접은 뒤에야 최종 경로가 루트 안인지 밖인지 확정됨

### 접두사 비교의 경계 오탐
- 정규화된 경로가 루트로 시작하는지 판정할 때, 단순 문자열 접두사 비교는 경계에서 오탐을 냄
    - 오탐이란 실제로는 루트 밖(또는 무관한 경로)인데 루트 안으로 잘못 판정하는 결함을 가리킴
- 루트가 `/srv/public`일 때 `/srv/public-secret/x`를 검사하는 경우
    - `/srv/public-secret/x`는 문자열로는 `/srv/public`으로 시작함
    - 그러나 `public-secret`은 `public`과 별개의 디렉토리이므로 루트 하위가 아님
    - 단순 접두사 비교는 이 경로를 루트 안으로 잘못 통과시킴
```
루트:       /srv/public
검사 대상:   /srv/public-secret/x

문자열 접두사 비교:  "/srv/public"으로 시작함 → 통과 (오탐)
디렉토리 경계 비교:  다음 문자가 '/'가 아니라 '-' → 거부 (정상)
```
- 경계까지 막는 판정 방법
    - 접두사가 일치하면서, 루트 바로 뒤 문자가 경로 구분자이거나 경로가 루트와 정확히 같아야 함
    - 또는 `std::filesystem`의 경로 요소 단위 비교를 사용해 문자열이 아닌 디렉토리 성분 단위로 포함 관계를 판정함
- 아래는 `handle` 본문에서 접두사 비교로 루트 이탈을 거르는 최소 구현임
    - `base`, `full`은 앞서 정규화한 경로이며, 구분자 경계까지 확인해 오탐을 막음

```cpp
HttpResponse StaticFileHandler::handle(const HttpRequest& req) const {
    // ...

    const std::string base_str = base.string();
    const std::string full_str = full.string();

    bool inside =
        full_str.size() >= base_str.size() &&
        full_str.compare(0, base_str.size(), base_str) == 0 &&
        (full_str.size() == base_str.size() || full_str[base_str.size()] == '/');

    if (!inside){
        // 루트 밖 → 접근 거부
        // 404 응답 조립
    }

    // ...
}
```

### URL 인코딩 우회의 범위 제외
- URL 인코딩(percent-encoding)이란 경로의 특수 문자를 `%` 뒤 16진수 두 자리로 표현하는 방식을 가리킴
    - `.`을 `%2e`로 표현하면 `..`가 `%2e%2e`로 위장됨
- 디코딩 계층이 없으면 이 우회를 잡지 못함
    - 현재 파서는 request-target을 디코딩하지 않고 원본 문자열 그대로를 다룸
    - 따라서 `%2e%2e`는 `..`로 복원되지 않아 정규화가 접을 대상이 되지 못함
- 디코딩 계층 부재로 이 방어는 현재 범위 밖으로 미룸
    - 디코딩을 도입하는 시점에 `%2e%2e` 우회 방어를 함께 다루는 것이 옳음

## ifstream binary 모드 파일 읽기
- `std::ifstream`이란 파일에서 데이터를 읽어 들이는 입력 파일 스트림 타입을 가리킴
    - "i"는 input, "f"는 file을 뜻함
- binary 모드란 파일 내용을 아무 변환 없이 바이트 그대로 읽는 모드를 가리킴
    - `std::ios::binary` 플래그로 지정함
- text 모드와의 경계
    - text 모드는 플랫폼에 따라 줄바꿈 문자를 변환할 수 있음
    - 예를 들어 윈도우에서는 파일의 `\r\n`을 읽을 때 `\n`으로 접음
    - 이 변환이 일어나면 파일의 원본 바이트와 읽어 들인 바이트가 달라짐
- HTML만 다루는 지금도 처음부터 binary 모드를 쓰는 이유
    - 이미지처럼 바이트 하나만 어긋나도 손상되는 자원이 곧 추가됨
    - 자원 종류에 따라 모드를 바꾸면 실수 여지가 생기므로, 모든 파일을 바이트 그대로 읽는 binary로 통일

### 파일 전체 읽기 방식과 성능 경계
- `std::istreambuf_iterator`란 스트림의 내부 버퍼에서 문자를 하나씩 순회하는 반복자를 가리킴
- 두 반복자로 범위를 지정해 파일 전체를 한 번에 문자열로 구성함
    - 시작 반복자는 파일에 연결된 스트림 버퍼를 가리킴
    - 끝 반복자는 기본 생성된 반복자로, 스트림의 끝을 나타냄
- 이 반복자 방식의 성능 경계
    - `istreambuf_iterator`는 문자를 한 글자씩 읽으므로, 파일이 커질수록 호출 오버헤드가 누적됨
    - 파일 크기를 먼저 구해 버퍼를 한 번에 확보하고 `read`로 통째로 읽는 방식이 큰 파일에서는 더 빠름
    - 지금은 파일이 작은 HTML 하나뿐이라 반복자 방식으로 충분하며, 성능이 문제되는 시점에 교체할 여지를 둠

### most vexing parse 회피
- 아래 본문에서 첫 번째 반복자 인자를 괄호로 한 번 더 감싼 이유가 있음
    - 괄호가 없으면 컴파일러가 이 줄을 변수 선언이 아니라 함수 선언으로 해석하는 모호성이 생김
    - 이 모호성은 흔히 most vexing parse라 불리며, 인자를 괄호로 감싸 표현식임을 분명히 해 회피함

## HttpResponse 조립과 반환
- 파일을 본문 문자열로 읽은 뒤, 그 본문을 실은 응답 객체를 조립해 반환하는 것이 핸들러의 마지막 단계
- 조립 시 핸들러가 채우는 것과 채우지 않는 것의 경계
    - 채우는 것은 상태 코드(200)와 본문(파일 내용)임
    - 채우지 않는 것은 `Content-Length`이며, 직렬화 단계가 본문 크기로 자동 산출함
- 아래는 `handle` 본문의 마지막 부분으로, 파일을 읽어 200 응답을 조립해 반환함
    - `full`은 앞서 정규화·검증을 통과한 경로이며, 읽은 내용을 `res.body`에 담음

```cpp
// src/http/StaticFileHandler.cpp

#include <fstream>
HttpResponse StaticFileHandler::handle(const HttpRequest& req) const {
    // ...

    std::ifstream file(full, std::ios::binary);

    std::string body(
        (std::istreambuf_iterator<char>(file)),
        std::istreambuf_iterator<char>()
    );

    HttpResponse res;
    res.status_code = 200;
    res.body = std::move(body);

    return res;
}
```
- `std::move`로 본문을 넘기는 이유
    - `body`는 이 함수에서 더 쓰이지 않고 반환 직전 소멸할 지역 변수임
    - 복사 대신 이동으로 넘기면 파일 크기만큼의 문자열 복사를 피함

## 연결 계층의 응답
- 연결 계층이 읽기 가능 이벤트를 처리하는 지점에서, 파싱이 완료된 요청을 핸들러에 넘겨 응답을 얻음
    - 핸들러가 반환한 `HttpResponse`를 직렬화해 소켓으로 내보냄
- 아래는 `Connection`이 읽기 이벤트를 처리하는 `on_readable` 본문에서 파싱 완료 분기를 다루는 부분
    - `parser_`가 요청 하나를 완성하면, 보유한 요청 객체를 `handler_.handle`에 넘겨 응답을 조립하고 직렬화함
    - `handler_`는 생성자로 주입받아 보유한 `const StaticFileHandler&` 참조임

```cpp
// src/connection.cpp

Connection::on_readable(){
    // ...

    const HttpRequest& req = parser_.request();

    std::string out = handler_.handle(req).serialize();
    write_all(out);

    // ...
}
```
